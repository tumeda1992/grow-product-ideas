# 議論記録

この議論は、プロダクトアイデア育成の3方針をどのように比較し、結果と原本をどう扱い、今後の追加比較へつなげるかを設計する。確定した内容は `design.md` へ反映し、根拠となる設計前調査は `investigation.md` へ置く。

## 論点1: 3方針の比較設計を、どの骨格で進めるか

**ステータス:** 子論点待ち

**種別:** TBDヒアリング

### イテレーション0: 到達段階と根拠の違いが分かる比較の骨格

#### 提案0

この steering では、各ブランチの「設計内容」「現時点の利用可能性」「それを支える検証根拠」を分けて読む比較を中心に置く。比較結果から、各方針で何を重視しているか、どこまで用意されているか、何が確かめられているかを理解できるようにする。

たとえば `feature-1` は骨格設計として何を担保するかを読み、そのうえで運用 skill の本文が未作成であるという現在の到達段階を記録する。`feature-3` の評価記録は、sol による実行や改訂を含む条件付きの根拠として扱う。`feature-7` の作成・検査 script は存在と役割を確認し、実行結果を確認したかどうかを区別する。これにより、骨格の質・実体の有無・実証の強さを一つの値へ混ぜず、それぞれの違いとして判断できる。

設計は次の骨格で進める。今回判断するのは、この骨格で比較を設計することへの合意であり、各欄の具体的な方法や保存パスを一括確定することではない。

| 設計する部分 | 完成時に読み手が分かること | これから詰める内容 |
| --- | --- | --- |
| 比較対象と問い | どの条件の成果物を、何を知るために比較したか | 対象時点、制作条件、共通の評価観点、結論の適用範囲 |
| 比較の方法と根拠 | 記述を読んで分かったこと、元資料の実行記録、今回確かめたことの違い | 資料比較と新規実行の範囲、共通ケース、判定方法 |
| 結果の保存と参照 | 今回の結果と根拠、今後の結果をどこから読めるか | この steering 内の正本、ファイル構成、方法の版、旧結果との関係 |
| 各ブランチ成果物の扱い | 比較時点の原本をどう再確認し、比較後の改善候補をどう扱うか | 原本保持の方式、ブランチ更新時の識別、採用・統合との境界 |
| 追加比較の流れ | 新しい成果物が来たとき、何を渡せば調査を始められるか | 必要入力、不足情報、旧結果の再利用と再評価、完了・再開条件 |

対象数は今回の3件へ固定した手順にせず、今後の追加時にも、この骨格に沿って比較条件と根拠を置ける形へ具体化する。同じモデルの別プロンプトや人の関与が異なる試行、評価記録がない試行、既存ブランチの更新は、追加フローを検討する仮定例として用いる。これらの将来例をすでに観測した事実とは扱わない。

この骨格への合意後、まず「比較結果でどこまで判断できる状態を求めるか」を具体化し、それによって決まる評価方法と成果物の扱いへ進む。単一のモデル順位や純粋なモデル性能差を結論に含めるには、この3件の条件差を超える別の根拠が必要になる。

#### 提案背景

ユーザーの依頼原文:

> このリポジトリをどう機能させるかについて、3方針で作ってみた。それぞれの比較してもらい、調査結果をこの後作られるsteeringディレクトリに残してほしい。1つ目はfeature-1ブランチのAnthoropicのopusと人が話し合いながら作ったやつ。2つ目はfeature-3ブランチでopenaiのastraモデルで作ったやつ。3つ目はfeature-7ブランチでopen-aiのsolが作ったやつ。比較のやり方やどこに比較結果置くかとかそれぞれのブランチでできたものをどう扱うかとかの設計をこのsteeringで行いたいけど、今後もモデル追加時に比較調査をお願いするかもだからそのつもりで設計してほしい

この依頼から、今回の3ブランチの比較だけでなく、保存先、元成果物の扱い、追加比較を含む設計が必要になる。一方、どのモデルを採用するか、どのブランチを統合するかまで今回決めるという指示はまだない。

[設計前調査](./investigation.md) では、`feature-1` が骨格段階を明示し、`feature-3` が運用成果物と複数回の改訂・評価記録を持ち、`feature-7` が運用成果物と補助 script を持つことが分かった。`feature-3` の評価記録には sol の実行も含まれる。

このため、成果物を読む前からファイル数やテスト数をモデルの順位へ結び付ける比較は適切でない。制作時の対象範囲と現在の実体を区別すると、骨格設計をその目的に沿って評価しながら、現在使うために残っている作業も説明できる。保存された評価を根拠として読む場合も、その結果を生んだモデル・入力・改訂の条件を落とさず比較する必要がある。

別の進め方として、最初から同じ入力を各案へ実行して順位を付ける方法も考えられる。しかし `feature-1` には実行する skill 本文がなく、補完すれば別の成果物になる。共通実行を採るかどうかは、比較したい問いと原本の扱いを決めた後に判断する。

提案0はこれらの違いを読み分ける骨格までを示し、具体的な評価軸・実行範囲・保存方式は `TBD:` のまま `design.md` に残している。未合意の下位判断を確定させず、全体を見ながら次の判断へ進めるためである。

### 決定

各ブランチの「設計内容」「現時点の利用可能性」「検証根拠」を区別して比較する。比較結果から、各方針が何を重視し、どこまで用意され、何が確認されているかを理解できるようにする。

比較設計の骨格は、比較対象と問い、比較の方法と根拠、結果の保存と参照、各ブランチ成果物の扱い、追加比較の流れとする。今回の3件に固定した手順へ閉じず、将来の追加条件を扱えるよう具体化する。

各案の到達段階を踏まえ、骨格の質、実体の有無、実証の強さを一つの値へ混ぜない。制作・評価条件が異なるため、単一のモデル順位や純粋なモデル性能差を結論に含めるには別の根拠を要する。

具体化は、比較結果でどこまで判断できる状態を求めるかを先に定め、その答えが規定する評価方法と成果物の扱いへ進む。

## 論点2: 比較結果を読んだ後、何を判断可能にするか

**ステータス:** 子論点待ち

**親論点:** 論点1

**種別:** TBDヒアリング

### イテレーション0: 比較結果の到達点を選ぶ

#### 提案0

**推奨:** b。今回確認できる根拠の強さを超えて単一の勝者を作らず、それでも差分説明だけで終わらないためである。

- **a. 3方針の違いを理解できる記述的な比較にする**
  - 各方針が重視すること、現時点の利用可能性、検証根拠の違いを整理する。
  - 読み手は違いを理解できるが、次にどの方針を試すか、何を追加確認すべきかは比較結果だけでは判断しない。
  - この到達点なら、既存資料の精読が比較の中心になり、新規実行は事実確認が必要な箇所だけに限定できる。
- **b. 条件付きの次判断まで可能にする比較にする**
  - 各方針について、どの目的・前提なら次の採用検討へ進められるか、現時点の根拠だけでは何を保留すべきかを示す。
  - 読み手は「直ちに勝者を採用する」のではなく、「どの候補を、何を確かめる次の検証へ進めるか」を判断できる。
  - 比較結果は元ブランチの変更・統合を自動的に決めない。実行や統合が必要なら、比較で明らかになった不足根拠を入力に別の判断として扱う。
- **c. 単一の方針またはモデルを選ぶ順位付けにする**
  - 共通条件で優劣を判定し、一つの採用候補を選ぶことを到達点にする。
  - 現在の3件は対象範囲、制作過程、実行可能性、保存済み検証が揃っていないため、この到達点には原本を変えない範囲で比較可能な共通実行条件と追加根拠が必要になる。
  - 特に `feature-1` は骨格設計を対象としており、運用 skill を補完して実行すると元の比較対象とは別の成果物になる。

ここで決めるのは比較結果の到達点だけである。b を選んだ場合、具体的な評価観点、既存資料だけで判断する範囲、新規実行を要求する条件、結果の保存構造は、この到達点に従う下位判断として後続で一つずつ決める。

#### 提案背景

論点1では、設計内容、現時点の利用可能性、検証根拠を分け、制作・評価条件が異なる3件から純粋なモデル性能差を直接結論にしない骨格へ合意した。次に評価方法や保存形式を決めるには、その比較を何の判断へ使うかが先に必要になる。記述的な理解を目標にする場合と、次の検証候補の選択を目標にする場合では、必要な根拠と結論の形式が変わるためである。

[設計前調査](./investigation.md) では、`feature-1` は骨格設計、`feature-3` は運用成果物と改訂・評価記録、`feature-7` は運用成果物と作成・構造検査の入口を持つことを確認した。一方、同一入力での実行結果、厳密な制作条件、実生活のアイデアでの手戻りや満足度は確認していない。この状態で c を選ぶと、比較対象を補完または再制作する判断まで先に必要になり、原本を比較する目的と統制実験の目的が混ざる。

a は現在の根拠だけで成立させやすいが、比較後に何をすべきかを読み手へ残す。ユーザーは「このリポジトリをどう機能させるか」について3方針を作り、今後の追加比較も想定している。b なら、条件差を限界として残しながら、今回と将来の比較を次の検証判断へ接続できる。比較自体が採用・統合を代行しないため、対象ブランチを変更しない現在の境界も維持できる。

### 決定

比較結果は、各方針について、どの目的・前提なら次の採用検討へ進められるか、現時点の根拠だけでは何を保留すべきかを示す。読み手が、どの候補を何を確かめる次の検証へ進めるかを判断できる状態を到達点とする。

比較結果だけで単一の勝者を決めず、元ブランチの変更・統合も自動的に決めない。実行や統合が必要な場合は、比較で明らかになった不足根拠を入力に別の判断として扱う。

## 論点3: 異なる到達段階の3方針を、どの基準で評価するか

**ステータス:** 子論点待ち

**親論点:** 論点2

**種別:** TBDヒアリング

### イテレーション0: 評価基準を二層に分ける

#### 提案0

**推奨:** c。制作時の対象範囲を尊重する評価と、現在このリポジトリで採用検討へ進めるための評価を分ければ、意図的な未実装を失敗にせず、次の判断にも使えるためである。

- **a. 3件すべてを、現在利用できる完成した運用方針という一つの共通基準だけで評価する**
  - 現時点でこのリポジトリを動かせるかを直接比較できる。
  - 骨格段階だけを対象にした `feature-1` も運用成果物の不足として同じ基準で評価するため、制作時に合意された対象範囲と現在の利用可能性が一つの評価へ混ざる。
- **b. 各方針が自ら定めた対象範囲を満たしたかだけを評価する**
  - `feature-1` は骨格、`feature-3` と `feature-7` はそれぞれの運用成果物という、各試行の目的に沿って評価できる。
  - 目的自体が異なるため、現在どれを採用検討へ進められるか、何を補う必要があるかを同じ基準で判断できない。
- **c. 「自己目的への適合」と「共通の採用目的への寄与」を別の評価として二層で示す**
  - 第一層では、各方針が制作時に明示した対象範囲・非目標・完了条件に対して何を満たしたかを評価する。
  - 第二層では、現時点の成果物が、粗いプロダクトアイデアを条件付きの次判断または build-ready へ進め、判断過程を次回へ再利用できる共通目的にどこまで寄与するかと、採用検討前に残る不足を評価する。
  - 二層の結論は混ぜない。たとえば `feature-1` は第一層で骨格設計として成立していても、第二層では運用 skill 未作成を採用前の不足として示せる。この不足を、元の制作目的の失敗へ読み替えない。

ここで決めるのは、異なる到達段階を正規化する評価基準の置き方だけである。c を選んだ場合も、第一層と第二層で使う具体的な評価観点、判定表示、各観点を既存資料と新規実行のどちらで確認するかは後続で決める。

#### 提案背景

論点2では、比較結果を、各方針について条件付きの次の採用検討と追加検証を判断できる状態にすると決めた。そのためには現在の利用可能性を共通の目的へ照らす必要がある。一方、論点1では制作時の対象範囲を踏まえ、骨格設計、運用ファイルの有無、実証の強さを一つの値へ混ぜないと決めている。共通基準だけでも自己目的だけでも、どちらか一方の決定を満たせない。

[設計前調査](./investigation.md) で、`feature-1` は skill 本文を対象外にした骨格設計、`feature-3` は育成・レビュー・改善の運用成果物と改訂・評価記録、`feature-7` は運用モデル、調査・判断手法、単一の skill、作成・構造検査 script を持つことを確認した。この差は単なる完成度の高低ではなく、制作時に扱った範囲の差を含む。

一方、固定コミットの入口資料には共通する上位目的も確認できる。粗いアイデアを作るだけの状態へ近づけること、作らない・検証する等の出口も成立させること、詰めれば決まる判断をエージェント側で進めること、実案件から進め方を育てることである。二層評価なら、各試行の成立を壊さず、この共通目的へ向けて現在何を採用検討できるかを説明できる。

#### 提案0へのフィードバック

**結果:** 自己目的と共通の採用目的を分ける二層評価に合意

> c

論点3・提案0の選択肢 c に対する明示合意として受領した。二層それぞれの具体的な評価観点、判定表示、既存資料と新規実行の境界まで確定したとは扱わない。

### イテレーション1: リポジトリの役割への適合を主評価にする

#### 提案1

比較の主評価は、各方針が**このリポジトリの役割を現在どこまで果たせるか**とする。自己目的への適合は、主評価と並ぶ別の評価結果ではなく、現在の到達点と意図的な対象外を説明する補助情報として扱う。

このリポジトリの役割は、固定コミットの共通する上位目的から次の状態として評価する。

- 粗いプロダクトアイデアを受け取り、`build`、追加検証、既存手段の利用、保留、停止のうち根拠に合う次判断へ進める。
- `build` を選ぶ場合は、実装者へプロダクト判断を残さず着手できる build-ready の状態へ進める。
- 調査、比較、整合、可逆な判断のうち詰めれば決まる仕事をエージェント側で進め、ユーザーにしかない動機、好み、費用・リスク許容を推測しない。
- 判断の根拠、未決事項、停止・再開位置を残し、実案件の学びを次のアイデアで再利用できるレールへ還元する。

比較結果の最初の結論は、各方針がこの役割のどこを現時点で果たせるか、どの条件なら採用検討へ進められるか、何が不足しているため保留または追加検証になるかである。制作時の自己目的を満たしていても、この役割を現在果たせなければ主評価を引き上げない。

自己目的への適合は、次の説明に限定して残す。

- 不足が制作時の約束に対する欠落なのか、意図的に後続段階へ残したものなのかを区別する。
- 現在は役割を完遂できなくても、どの設計資産を将来の候補として再利用できるかを説明する。
- ある方針が自ら掲げた目的を満たした事実を、そのまま現在の運用可能性や採用推奨へ読み替えない。

たとえば `feature-1` は骨格設計としての整合と将来利用できる設計資産を補助情報で評価する。一方、運用skillが固定コミットに存在しない以上、主評価では現在このリポジトリの役割を完遂できるとは判定しない。これは制作時の失敗という意味ではなく、現在の採用判断に対する不足である。

論点4の具体的な評価観点は、この優先関係に合わせて再評価する。ユーザーの「howは多分提案に大体従う」は論点4への確定合意とは扱わず、主評価を先頭に置き、自己契約の監査を補助へ組み替えた完全案を論点3の合意後に提示する。

#### 提案背景

##### 論点3を再開させたフィードバック

> あー、論点3にも翻るけど、唯々諾々とokとしちゃったけど、一番はこのリポジトリの役割を果たせるかで評価してほしい。それについてのhowは多分提案に大体従うと思う

論点3・提案0は、到達段階が異なる3件を公平に読むため、自己目的への適合と共通の採用目的への寄与を同格の二層として置いた。しかし依頼の中心は各試行を公平に採点することではなく、このリポジトリをどの方針で機能させられるかを判断することである。同格に置くと、自己目的を満たした事実が、現在の役割遂行能力と同じ重さで最終結論に見える。

feedbackは評価のhowを全面的に棄却していない。変える必要があるのは評価観点の優先関係である。制作時の対象範囲を無視すると `feature-1` の意図的な後続作業を単なる失敗と誤読するため、自己目的への適合は捨てず、主評価の解釈と将来候補を説明する補助へ移す。これにより、依頼の中心へ直接答えながら、到達段階の違いも根拠付きで説明できる。

### 決定

比較の主評価は、各方針がこのリポジトリの役割を現在どこまで果たせるかとする。最初に、粗いプロダクトアイデアから根拠に合う次判断へ進めること、`build` なら build-ready へ進めること、詰めれば決まる仕事とユーザーにしか決められない事項を分けること、判断を引き継ぎ、実案件の学びを次のアイデアへ還元できることへの適合を結論にする。

自己目的への適合は主評価と並ぶ結論にしない。不足が制作時の約束に対する欠落か意図的な対象外かを区別し、再利用可能な設計資産を示す補助情報として扱う。自己目的を満たした事実だけで、現在の運用可能性や採用推奨を引き上げない。

## 論点4: リポジトリの役割遂行を、何を観測して判定するか

**ステータス:** 子論点待ち

**親論点:** 論点3

**種別:** TBDヒアリング

### イテレーション0: 自己契約の監査と共通目的の五つの問いを組み合わせる

#### 提案0

第一層は対象ごとに異なる自己契約を監査し、第二層は全対象へ同じ五つの問いを当てる。各問いでは、論点1で合意した「設計内容」「現時点の利用可能性」「検証根拠」を分けて読む。

##### 第一層: 自己目的への適合

固定コミットに書かれた目的・対象範囲・非目標・完了条件を、その対象だけの評価契約として復元し、次の順で確認する。

| 評価観点 | 確認する問い | 結論で区別すること |
| --- | --- | --- |
| 自己契約の特定 | その試行は何を完成させ、何を後続へ残すと明示したか | 明示された対象範囲と、今回の比較者が期待する範囲 |
| 設計の整合 | 役割、判断順序、責務、品質条件、成果物構成は、自己契約の目的へつながっているか | 目的に寄与する設計と、置かれているだけの要素 |
| 宣言範囲の実体化 | 自己契約で必要とされた成果物と具体性が固定コミットに存在するか | 対象内の欠落と、明示的な非目標・後続段階 |
| 自己検証の成立 | 自己契約が要求した受け入れ条件または検証について、確認結果と限界が残っているか | 検証済みの主張、元資料だけの主張、未確認 |

第一層では、自己契約に含まれない運用成果物の不在を不合格理由にしない。反対に、対象範囲へ含めた成果物が存在するだけで、設計の整合や検証まで満たしたとは扱わない。

##### 第二層: 共通の採用目的への寄与

対象のfile構成や用語ではなく、このリポジトリを現在機能させるための五つの問いを全対象へ同じ意味で当てる。

| 評価観点 | 確認する問い | 条件付きの次判断につながる内容 |
| --- | --- | --- |
| 判断の到達範囲 | 粗いアイデアから、`build`、追加検証、既存手段の利用、保留、停止を選び、`build`なら実装者がプロダクト判断を残さず着手できる状態まで進められるか | どの出口・段階まで採用候補にでき、どこから別手段が要るか |
| 根拠と判断の追跡可能性 | 事実、元資料の主張、仮説、解釈、決定、反証条件を区別し、入力から結論と結論から入力をたどれるか | どの判断を現在信頼でき、何を再確認すべきか |
| 自走とユーザー判断の境界 | 調査・比較・整合・可逆な判断を自走し、ユーザーにしかない動機・好み・費用やリスクの許容を推測せず、高影響の未決事項だけを返せるか | どこまで任せられ、どの時点でユーザー判断が必要か |
| 運用の連続性と引き継ぎ | 明確な入口、入力、正本、状態、gate、停止・再開、失敗時の戻り先、最終handoffがあり、固定コミットの成果物だけで開始・継続できるか | 現在利用できる範囲と、採用前に補う運用要素 |
| 学習の再利用 | 実案件の手戻りや検証結果を記録し、個別事情を一般則へ直結させず、別caseで確かめてレールへ還元できるか | 今回だけでなく次のアイデアでも価値が増える条件と不足 |

第二層の五観点は総合点へ足し合わせない。ある目的では「判断の到達範囲」が不足していても、別の方針の骨格として「根拠と判断の追跡可能性」を採用検討できる場合があるため、観点ごとに適用条件と不足根拠を残す。判定の表示語と閾値は後続論点で決める。

##### 新しい判断基準の検証

この観点群を確定後、起点となった `feature-1` 以外の二つの具体caseへ当てる。

- `feature-3`: 育成・レビュー・改善の三つのskillと保存済み評価記録が、自己契約と共通五観点のどこを満たすかを確認する。
- `feature-7`: 単一skill、運用文書、作成・構造検査scriptを持ち、独立した評価結果を保存していないcaseで、運用の実体と検証根拠を混ぜずに判定できるかを確認する。

どちらかで観点の意味がfile構成や到達段階に依存して選べない、または同じ事実を二つの観点が重複して結論に使う場合は、この観点群を確定せず修正する。将来caseへの一般化は、この二件で機能した範囲に限定する。

ここで決めるのは評価観点である。各観点の判定表示、必要な根拠の強さ、既存資料で答えられない場合に新規実行へ進む条件、保存形式は後続で決める。

#### 提案背景

論点3で二層評価を選んだため、第一層と第二層へ同じ固定checklistを当てると、自己目的の差を再び潰してしまう。第一層は対象自身が宣言した契約へ追従する必要があり、第二層は現在の採用検討へ使うため全対象に共通する必要がある。

固定コミットの入口資料を読むと、`feature-1` は問いの依存関係、材料、水準、定石を持つ骨格を設計し、skill本文を後続へ残している。`feature-3` は要求探索からhandoffまでの運用、独立レビュー、レール改善と実行評価を持つ。`feature-7` は複数出口、品質gate、readiness audit、単一skill、作成・構造検査scriptを持つ。file数やskill分割を共通観点にすると構成差を品質差へ読み替えるため、共通目的を利用者が得る判断能力として表した。

五つの共通観点は、論点2で確定した「どの目的・前提なら次の採用検討へ進められるか」と「何を追加確認すべきか」を、結果から一意に導くために必要である。到達範囲だけでは根拠の信頼性を落とし、根拠だけでは現在運用できるかを判断できず、単発の運用だけでは次回へ経験が残るという元の目的を評価できない。

論点3で評価の優先関係が改訂されたため、自己契約の監査を第一層に置く提案0は現在の親decisionと整合しない。論点3・提案1への合意を受け、主評価から条件付きの次判断を直接導ける構造へ組み直す。

### イテレーション1: 役割要件と実体化段階から次判断を導く

#### 提案1

**推奨:** リポジトリの役割を四つの必須gateに分け、各gateを「設計内容」「現時点の利用可能性」「検証根拠」の三段階で確認する。四観点の点数を足すのではなく、最初に満たせない段階から次に行うことを決める。

##### 主評価: 四つの役割gate

| gate | このリポジトリが果たすべきこと | 主評価で確認する問い | 満たさない場合に制限されること |
| --- | --- | --- | --- |
| 1. 次判断への到達 | 粗いアイデアから、`build`、追加検証、既存手段の利用、保留、停止のうち根拠に合う出口へ進め、`build` なら build-ready へ到達させる | 入口から各出口まで必要な判断がつながり、出口ごとの完了条件と成果物が定義されているか | 到達できない出口について現在の採用候補にできない |
| 2. 判断主体の分離 | 調査、比較、整合、可逆な判断をエージェントが進め、動機、好み、費用・リスク許容などユーザーにしか決められない事項だけを返す | 判断ごとの担当と質問条件が明確で、エージェントが詰められる未決事項を実装者やユーザーへ残さないか | 自走を前提に採用できず、誤った代理判断または不要な差し戻しを防ぐ再設計が要る |
| 3. 判断品質の統制 | 事実、仮説、解釈、決定、未確認を区別し、矛盾・不足・反証条件を確認して、結論を根拠から再確認できるようにする | 品質gateと出典の追跡が判断経路に組み込まれ、不確実性を隠したまま次段階へ進まないか | 結論を採用根拠にできず、設計の補完または実行による確認が要る |
| 4. 継続運用と学習還元 | 正本、状態、停止・再開位置、handoffを残し、実案件の結果を個別事情のまま一般化せず、別caseで確かめて運用へ戻す | 別担当・別時点でも継続でき、実行結果から改善候補を作り、検証後の学びを次のアイデアで再利用できるか | 単発利用を超えるリポジトリ運用としては採用できず、継続・改善の仕組みを補う必要がある |

四gateは、file数、skillの分割数、文書量を評価するchecklistではない。同じ責務を単一skillで担っても複数skillで担ってもよく、固定コミットの成果物が利用者へ上記の能力を提供できるかで判定する。全gateを満たして初めて、このリポジトリの役割全体を果たせる候補とする。一部だけ満たす場合は、対象とする出口や利用局面を明示した限定候補、または設計資産の再利用候補として扱い、他gateの強さで不足を相殺しない。

##### 各gateを確認する三段階

各gateについて、論点1で分けた三つを次の依存順で確認する。

| 段階 | 確認内容 | ここで止まった場合の主な次判断 |
| --- | --- | --- |
| 設計内容 | gateを果たす責務、判断順序、入力・出力、品質条件が矛盾なく定義されている | 現在採用せず、役割設計を補うか、成立している部分だけを再利用候補にする |
| 現時点の利用可能性 | 固定コミットにある入口と成果物だけで、その設計を開始・継続・完了できる | 不足する運用成果物を実装してから評価する。未実装の設計を現在使えるとは扱わない |
| 検証根拠 | 識別できる版・入力・担当・方法の下でgateの振る舞いが観測され、主張の範囲と限界が分かる | 設計や実体を作り直す前に、足りない振る舞いを新規実行または資料照合で確かめる |

設計内容が成立しなければ、実行回数を増やして採用候補へ引き上げない。運用成果物が存在しなければ、設計の整合だけで現在利用可能とはしない。成果物が存在しても振る舞いの根拠がなければ、未検証の利用可能性を実証済みとしない。この依存順により、比較結果から次の行為を次の四種類のいずれかへ絞る。

1. 役割設計を補う、または成立部分だけを再利用する。
2. 設計済みだが欠けている運用成果物を作る。
3. 実行可能だが根拠が足りない振る舞いを追加検証する。
4. 根拠が成立する条件を明記して採用検討へ進める。

複数の不足がある場合は、依存順で最も手前の段階を主要な次判断とし、後続の不足はその判断後に確認する事項として残す。これにより、未設計のものへ先に実行試験を求めたり、未実装のものを採用候補として扱ったりしない。具体的な判定表示と、どの既存根拠なら検証済みとするかは後続論点で決める。

##### 補助情報: 自己目的への適合

主評価で不足または限定条件が見つかった後、固定コミットに明示された目的、対象範囲、非目標、完了条件を使い、次だけを補足する。

- 不足が自己契約内の欠落か、意図的に後続へ残された対象外か。
- 現在は役割全体を果たせなくても、どの設計要素・運用要素を再利用候補にできるか。
- 元の試行が自らの完了条件を満たしたという主張を、どの根拠で確認できるか。

この補助情報は、主評価のgateや実体化段階を引き上げず、採用検討へ進める根拠の代わりにしない。たとえば `feature-1` で運用skillが意図的な対象外だったことは欠落理由を説明するが、現時点の利用可能性を満たすことにはならない。

##### 起点以外のcaseで行う適用検証

観点を確定した後、起点となった `feature-1` 以外の二件へ同じ表を適用する。

- `feature-3`: 育成・レビュー・改善に分かれたskill、運用文書、保存済み評価記録を四gateと三段階へ配置する。保存済み評価は、その版・入力・担当・方法で裏付ける範囲だけを検証根拠とし、複数skillであること自体を加点しない。
- `feature-7`: 単一skill、運用文書、作成・構造検査scriptを同じ四gateと三段階へ配置する。scriptが存在や構造を確かめることと、実案件で役割を果たした根拠を分け、独立した評価記録がない場合に追加検証へ一意に進めるかを確認する。

どちらかで、成果物構成に依存してgateの意味が変わる、自己目的の達成が主評価を引き上げる、または不足から主要な次判断を一つに絞れない場合は、この観点群を確定せず修正する。二件で機能した範囲を超えて将来caseへ一般化しない。

ここで決めるのは、主評価の観点、三段階の読み方、自己目的を補助へ限定する方法である。判定語と閾値、既存資料と新規実行の境界、結果の保存形式は後続で決める。

#### 提案背景

論点4・提案0は自己契約の監査と共通五観点を並列の二層にしたため、結果の先頭が各試行の公平な評価へ戻り、どの方針でこのリポジトリを現在機能させられるかが二番目に見える問題があった。また、五観点を独立項目として並べるだけでは、設計不足、成果物不足、実証不足のどれを先に解消すべきかが一意に決まらない。

提案1では、論点3で確定したリポジトリの役割そのものを四つのgateへ分解し、各gateの実体化を依存順で読む。役割の不足と根拠の不足を分けるため、設計資産しかないcase、運用成果物はあるが独立検証がないcase、条件付きの実行記録があるcaseから、それぞれ異なる次判断を導ける。

自己目的への適合は、なぜ不足しているかと何を再利用できるかを説明するために必要だが、主評価の前提にはしない。この位置付けなら `feature-1` の制作範囲を失敗と誤読せず、同時に現在使える方針と結論することも避けられる。

#### 提案1へのフィードバック

**結果:** 期待アウトプットの品質を主評価へ含めるため再設計

> それと同じく、期待できるアウトプットの質も評価したい

提案1の四gateは、役割を継続して運用する仕組みを中心に見ており、出口へ到達した成果物自体が浅い、矛盾する、次の担当へ重要判断を残す場合を直接は判定できない。提案1への合意はまだないため、第五gateを足すのではなく、役割遂行を「運用能力」と「出口成果物の品質」の両方が必要なものとして組み直す。

### イテレーション2: 運用能力と出口成果物の品質を一組で評価する

#### 提案2

**推奨:** 各方針の主評価を、役割を進める**運用能力**と、各出口で利用者が次の行動へ進める**アウトプット品質**の二つで構成する。どちらかを独立した加点項目にせず、対象が対応すると宣言する出口ごとに両方を満たすことを要求する。

プロセスが正しく見えても成果物が利用不能なら役割を果たしていない。良い成果物の例が一件あっても、入力から再現可能に到達する仕組みがなければ方針として現在採用できない。このため、第五gateを末尾へ追加するのではなく、すべての出口を次の組で評価する。

```text
その出口まで進める運用能力 × その出口で次の行動を可能にする成果物品質
```

##### 主評価A: 役割を進める運用能力

| 運用能力 | 確認すること | アウトプット品質との関係 |
| --- | --- | --- |
| 出口の選択と到達 | 粗いアイデアから、根拠に合う `build`、追加検証、既存手段の利用、保留、停止を選び、対応する完了条件まで進められる | 正しい種類の成果物へ到達させる。出口を誤れば、個々の文書が良くても役割不適合 |
| 判断主体の分離 | 調査、比較、整合、可逆な判断をエージェントが進め、動機、好み、費用・リスク許容などユーザーにしか決められない事項だけを返す | 成果物に、エージェントが詰めるべき未決事項やユーザーの推測値を残さない |
| 品質を作り直す制御 | 必要材料、対案、具体case、矛盾、反証条件を確認し、不足があれば原因の正本へ戻して直す | checklistの存在ではなく、浅い・矛盾した成果物を検知して修正する仕組みを持つ |
| 継続運用と学習還元 | 正本、状態、停止・再開位置、handoffを残し、実案件の結果を別caseで確かめて運用へ戻す | 一件の成果物を偶然の成功にせず、次回も同じ品質を期待できる条件を残す |

運用能力はfile数、skill分割数、レビュー工程数では判定しない。それらが、対応する出口へ進め、質の不足を検知・修正し、別担当・別時点でも再開できる能力としてつながっているかを見る。

##### 主評価B: 出口成果物の共通品質

[設計前調査](./investigation.md) で固定コミットの品質条件を追加確認すると、3方針は共通して、文書量や体裁ではなく「結論を選べる」「具体的な場面と境界がある」「根拠から後続成果物をたどれる」「不確実性を過大評価しない」「次の担当が行動できる」を質として扱っている。この共通部分を、全出口へ適用する五つの観点にする。

| 品質観点 | 観測する問い | 通過と扱わない例 |
| --- | --- | --- |
| 意思決定可能性 | 採る出口、選んだ理由、棄却した有力案、判断が変わる条件が分かり、読み手が同じ前提から結論を再確認できるか | 情報を列挙しただけ、最初の案を比較せず採用、結論や逆転条件がない |
| 具体性と境界 | 誰が、どの状況・入力で、何を行い、どの結果で完了かが具体例とともに分かり、対象内・対象外が区別されているか | 「使いやすくする」「十分検証する」のように完了を観測できない、適用範囲がない |
| 整合性と追跡可能性 | 元の要求、事実・仮説、選択理由、成果物、次の行動が双方向につながり、同じ用語・数値・状態が矛盾していないか | 根拠のない要件、使われない構造、古い前提のレビュー、別fileで異なる結論 |
| 根拠の十分性と確度 | 結論を左右する主張に、その強さに見合う出典または観測があり、未確認・推論・許容したriskと適用限界を示しているか | 資料調査だけで需要を実証済みにする、scriptの構造検査を成果物品質の実証にする |
| 次行動の実行可能性 | 次の担当が追加のプロダクト判断をせず開始でき、入力、手順またはscope、合否、失敗時の戻り先が分かるか | 「詳細は実装時」「必要なら再検討」のように、開始条件・完了条件・ownerがない |

五観点は点数化して相殺しない。出口に該当する観点をすべて満たすことを要求し、非該当なら、同じ役割をどの成果物が担うかとともに理由を残す。文書の長さや項目充足ではなく、利用者がその出口の次行動へ進めるかを判定する。

##### 出口ごとに変わる最低限のアウトプット契約

共通五観点の意味は維持し、必要な成果物は出口に合わせて変える。

| 出口 | 次に可能であるべき行動 | 最低限必要な内容 |
| --- | --- | --- |
| `build` | 実装へ着手する | 自作を選ぶ根拠、最初の価値到達点、scope・非scope、主要体験と失敗・復旧、核心ルールと状態、受入条件、残留risk。実装者へプロダクト判断を残さない |
| 追加検証 / `validate-first` | 検証を実施し、その結果から次の出口を決める | 検証する仮説、対象・入力、手順、事前の成功・失敗基準、期間・件数・費用等の上限、結果の保存先、結果別の次判断、停止条件 |
| 既存手段の利用 / `use-existing` | 採用・設定・移行・運用を開始する | 自作より選ぶ根拠、確認済み機能と未確認事項、前提・権限、構成・設定・移行順、費用、確認方法、失敗時の復旧・撤退条件 |
| 保留 / `park` | 状態を失わず、条件成立時に再開する | 今決めない理由、未確定事項、再開を発火する条件・観測方法、保存する正本、再開時の最初の一手 |
| 停止 / `stop` | 不要な作業を終え、同じ検討を根拠なく繰り返さない | 停止理由と根拠、棄却した有力案、適用範囲、判断が覆る条件。実行しない成果物を形式上作らない |

`build` の仕様書一式を他の出口へ要求しない。反対に、非buildだからという理由で浅い一文を許さず、その出口の次行動に必要な具体性、根拠、再開・終了条件を要求する。

##### 「期待できる品質」と「実際に得た品質」を分ける三段階

運用能力とアウトプット品質の両方を、論点1で合意した三段階で確認する。

| 段階 | 運用能力で確認すること | アウトプット品質で確認すること | 言える範囲 |
| --- | --- | --- | --- |
| 設計内容 | 役割、判断順序、戻り先、担当が定義されている | 五観点と出口別契約を満たすための要求・不合格例・修正方法が定義されている | どの品質を狙う設計か |
| 現時点の利用可能性 | 固定コミットの入口と成果物だけで開始・継続・完了できる | skill、template、gateが必要な内容を生成・検査でき、欠落時に止められる | 現在の成果物から期待できる品質。ただし実現を観測済みとは言わない |
| 検証根拠 | 識別できる版・入力・担当・方法で運用が完了している | 生成された出口成果物を五観点で確認し、指摘・修正・限界が残っている | その条件で実際に得た品質 |

期待品質は、設計と現在の運用成果物から理由付きで述べる予測である。実際のアウトプットがなければ、五観点を実証済みとはしない。保存済み評価も、その対象版・入力・担当・方法と、実際に読んだ成果物が裏付ける範囲に限定する。

##### 主評価から導く条件付きの次判断

各出口で運用能力とアウトプット品質の三段階を確認し、最も手前の不足から主要な次判断を一つ決める。

1. 役割または出口別品質契約が設計されていないなら、設計を補うか、成立部分だけを再利用候補にする。
2. 設計はあるが、現在のskill・template・gateが実体化していないなら、欠けた運用成果物を作る。
3. 実行可能で期待品質の理由はあるが、対象出口の実例がないなら、その出口を通る新規実行で確かめる。
4. 実例が五観点を満たさないなら、表現だけを直さず、失敗を生んだ最上流の設計または運用成果物を改訂して再実行する。
5. 両方が根拠付きで満たされるなら、確認できた出口・入力条件・限界に限定して採用検討へ進める。

複数の不足があれば、依存順で最も手前の段階を主要な次判断にし、後続不足はその判断後の確認事項として残す。具体的な判定表示、既存資料を検証根拠として十分とする条件、新規実行の範囲は後続論点で決める。

##### 補助情報: 自己目的への適合

自己目的への適合は、論点3のdecisionどおり主評価を引き上げない。主評価の不足について、自己契約内の欠落か意図的対象外か、どの設計・運用要素を再利用できるか、元の試行が自らの完了条件を満たしたとする根拠は何かだけを補足する。

##### 起点以外のcaseと異なる出口で行う適用検証

観点を確定した後、`feature-3` と `feature-7` の固定コミットへ同じ構造を適用する。両方で、少なくとも `build` と一つの非build出口の契約を確認する。実例が存在しない出口は不合格にせず、設計上の期待品質と実証の不在を分け、後続の新規実行判断へ渡す。

- `feature-3`: playbook、三つのskill、templateから運用能力と期待品質を評価し、保存済み実行成果物は対象版・入力・評価者が特定できる範囲で実際の品質へ五観点を適用する。build-ready、導入準備完了、見送りで必要内容が変わっても同じ五観点を使えるか確認する。
- `feature-7`: operating model、単一skill、template、scriptから運用能力と期待品質を評価する。構造検査scriptの成功を内容品質の成功に読み替えず、`build`、`validate-first`、`use-existing`、`park`、`stop` のうち実例がないものを検証根拠不足として分離できるか確認する。

成果物構成によって五観点の意味が変わる、非buildへbuild用文書を要求する、期待品質と実測品質を混ぜる、浅い成果物が主評価を通る、または不足から主要な次判断を一つに絞れない場合は、この判断基準を確定せず修正する。二件と複数出口で機能した範囲を超えて将来caseへ一般化しない。

ここで決めるのは、運用能力とアウトプット品質を主評価の一組にすること、共通品質の五観点、出口別の最低契約、三段階で期待と実測を分けること、自己目的を補助へ限定することである。判定語と閾値、既存資料と新規実行の境界、保存形式は後続で決める。

#### 提案背景

四つの運用gateだけでは、適切な工程、owner、正本、reviewが存在しても、結果が抽象的、矛盾、根拠薄弱、または次の担当へ重要判断を残す場合を、役割不適合として直接表せなかった。反対にアウトプットだけを評価すると、偶然得た良い一件を再現可能な方針と誤認する。したがって、アウトプット品質は第五gateではなく、各出口への運用能力と対になる必要条件である。

追加調査では、`feature-1` が材料から導かれる答え、複数案、判断理由、水準を求め、`feature-3` が具体的な場面と数値、根拠を超えない主張、観測可能な到達点、単独で使える引き継ぎを求め、`feature-7` が根拠から受入条件までの追跡、具体例・境界・失敗、出口別の実行可能な次の一手を求めていた。ここから五観点を帰納した。

また3件はいずれも build 以外の出口を持つ。品質を仕様書の厚さや実装情報量で測ると、検証、既存手段、保留、停止を誤って低品質にする。出口ごとの次行動を完成させる共通能力として質を定義すれば、異なる成果物にも同じ意味で適用できる。

### 決定

主評価は、対象が対応すると宣言する出口ごとに「その出口まで再現可能に進める運用能力」と「その出口から次の行動へ進めるアウトプット品質」を一組で評価する。どちらか一方の強さで他方の不足を相殺しない。

運用能力は、出口の選択と到達、判断主体の分離、品質を作り直す制御、継続運用と学習還元を確認する。file数、skill分割数、工程数ではなく、これらが役割としてつながっているかを評価する。

アウトプット品質は、意思決定可能性、具体性と境界、整合性と追跡可能性、根拠の十分性と確度、次行動の実行可能性を確認する。五観点は加点集計せず、該当する不足を相殺しない。必要な成果物は `build`、追加検証、既存手段の利用、保留、停止の出口別最低契約に合わせ、build用成果物を他出口へ機械的に要求しない。

運用能力とアウトプット品質の両方について、設計内容、現時点の利用可能性、検証根拠を分ける。設計と運用成果物から理由付きで述べる期待品質と、実際の出力から観測した品質を混ぜない。自己目的への適合は、不足理由、意図的対象外、再利用可能な資産を説明する補助情報に限定する。

合意した判断基準は、task-designのvalidationで `feature-3` と `feature-7`、かつ build と非buildの異なる出口へ適用し、成果物構成に依存せず主な次判断を導けることを確認する。

## 論点5: 判定語と閾値をどう定めるか

**ステータス:** 子論点待ち

**親論点:** 論点4

**種別:** TBDヒアリング

### イテレーション0: 観点別の成立状態と、次判断の行為を分ける

#### 提案0

**推奨:** 点数や総合ランクを使わず、各観点を五つの成立状態で記録し、その依存関係から「次に行う行為」を別の結論として一つ導く。状態は品質の優劣ではなく、どこまで何の根拠で言えるかを表す。

##### 観点ごとの判定語

各出口について、四つの運用能力と五つのアウトプット品質を、設計内容、現時点の利用可能性、検証根拠の各段階で次のいずれかにする。

| 判定語 | 閾値 | 扱い |
| --- | --- | --- |
| `成立` | その出口・観点・段階で必要な条件がすべて確認でき、判断を止める欠落・矛盾・未確認がない | 確認した条件の範囲で次段階の判定へ進める |
| `限定成立` | 明示した入力、出口、利用者、実行環境、版などの範囲内では `成立` と同じ閾値を満たすが、範囲外へ一般化できない | 条件を結論へ併記し、その範囲内だけ次段階へ進める。根拠が弱いだけの状態には使わない |
| `未成立` | 必須条件の欠落、内部矛盾、観測された失敗のいずれかがあり、現在の成果物のままではその観点を満たさない | 最上流の原因を補完・改訂する。別観点の強さで相殺しない |
| `未確認` | 判断に必要な資料または実行結果がなく、成立とも未成立とも言えない | 不合格へ読み替えず、既存資料の追加確認または新規実行の候補にする |
| `非該当` | その出口では当該要素が本当に不要で、同じ役割を担う代替物と不要理由を示せる | 空欄の代用にしない。リポジトリの必須役割や、対象が未対応の出口には使わない |

`限定成立` は「一部欠けているが概ね良い」ではない。範囲を狭めれば必須条件をすべて満たす場合だけ用いる。範囲内にもblockingな欠落があれば `未成立`、根拠が足りなければ `未確認` とする。

##### 段階ごとの成立閾値

同じ判定語でも、三段階で確認対象を変える。

| 段階 | `成立` または `限定成立` に必要なもの | この段階だけでは言えないこと |
| --- | --- | --- |
| 設計成立 | 役割、出口別契約、判断順序、担当、入力・出力、品質条件、不合格時の戻り先が矛盾なく定義されている | 現在の固定コミットから実行できること、期待どおりの出力が得られること |
| 現在利用可能 | 設計成立に加え、固定コミットの入口、skill、template、正本、gateだけで開始・継続・完了でき、必須条件の欠落時に誤って完了扱いしない | 実案件で期待品質が得られたこと |
| 実測支持 | 設計成立と現在利用可能に加え、特定可能な版、入力、担当、方法で対象出口まで実行され、実出力が該当する運用能力と品質観点を満たし、指摘・修正・限界を追える | 未観測の出口、入力、担当、モデル、環境でも同じ結果になること |

後段は前段を前提とする。設計が `未成立` なら、偶然良い出力が一件あっても方針の実測支持へ繰り上げない。現在利用可能性が `未成立` なら、設計の具体性だけで運用可能とはしない。実例がない場合は期待品質を述べられても、実測支持は `未確認` とする。

##### 出口ごとのblocking閾値

対象が対応すると宣言する出口について、次をすべて満たすときだけ、その段階を `成立` または `限定成立` とする。

- 四つの運用能力に `未成立` または `未確認` がない。
- 出口に該当する五つのアウトプット品質に `未成立` または `未確認` がない。
- `非該当` には、出口別最低契約に照らした不要理由と代替物がある。
- `限定成立` の条件が同じ出口内で矛盾せず、結論の適用範囲を一つに記述できる。

一つでも満たさなければ、その出口全体を成立扱いしない。ただし失敗した観点だけで方針全体を「悪い」と要約せず、最も手前の不足と、成立している設計・運用資産を残す。対象が対応していない出口は `非該当` ではなく、そのリポジトリ役割に対する `未成立` とする。限定された用途の採用候補にはできても、役割全体を果たす候補にはしない。

##### 判定から導く主要な次判断

観点の状態と、比較結果が推奨する行為を同じ語へ混ぜない。依存順で最も手前にある不足から、出口ごとに次のいずれか一つを主要な次判断として示す。

| 主要な次判断 | 導出条件 |
| --- | --- |
| `設計補完` | 設計内容に `未成立` がある。成立部分を別案へ再利用する場合もここで明示する |
| `資料確認` | 設計内容または現在利用可能性が `未確認` で、固定コミットの未読資料を確認すれば解消できる可能性がある |
| `運用成果物補完` | 設計は成立しているが、現在利用可能性に `未成立` がある |
| `追加検証` | 設計と現在利用可能性は成立しているが、実測支持に `未確認` がある |
| `改訂後再検証` | 実例で運用能力またはアウトプット品質の `未成立` が観測された |
| `条件付き採用検討` | 対象出口が実測支持まで `成立` または整合する `限定成立` で、適用条件と限界を結論に明示できる |

複数の不足がある場合は、`設計補完` → `資料確認` → `運用成果物補完` → `追加検証` / `改訂後再検証` の依存順で最も手前を主要な次判断にし、後続不足は「その判断後に確認すること」へ残す。`条件付き採用検討` は単一の勝者や統合決定を意味せず、確認できた出口と条件について次の採用判断へ進めるという意味に限定する。

##### 方針全体の表示

単一の総合点や A/B/C ランクは付けない。方針全体は次の組で要約する。

```text
現在の到達段階 / 対応できる出口 / 実測支持の範囲 / 主要な次判断
```

たとえば「設計成立・現在利用不可 / build・保留の設計資産 / 実測なし / 運用成果物補完」や、「現在利用可能 / build の特定入力で実測支持 / 非buildは未確認 / 追加検証」のように、異なる到達段階を一つの順位へ潰さない。

##### 起点以外のcaseで行う閾値検証

論点4の観点適用と同時に、次の期待結果になるかを `feature-3` と `feature-7` で確認する。

- `feature-3`: 保存済み評価があることだけで全面的な `実測支持` にせず、対象版・入力・担当・出口へ限定できる。実出力で失敗が記録された観点は `未成立`、修正後に再確認された観点だけを現在の版で成立と扱える。
- `feature-7`: skill、template、scriptから設計成立と現在利用可能性を評価できても、構造検査を内容品質の実測支持へ使わない。実案件の出力がなければ該当する実測支持を `未確認` とし、主要な次判断を `追加検証` にできる。

どちらかで `限定成立` が単なる甘い部分点になる、未確認を未成立へ落とす、古い版の実行結果で現在版を支持する、または同じ状態から主要な次判断が複数になる場合は、この判定体系を確定せず修正する。

ここで決めるのは、観点別の判定語、三段階と出口ごとの成立閾値、主要な次判断の導出方法である。どの既存資料を十分な根拠とするか、どの条件で新規実行するかは、この判定体系へ従う次の論点で決める。

#### 提案背景

点数方式は、たとえば具体性の高さで根拠不足を相殺でき、合意済みの「不足を他観点の強さで埋めない」という判断に反する。単純な pass / fail だけでは、まだ調べていない状態を失敗と誤読し、特定条件では成立する方針を過度に一般化する。

五つの状態なら、必須条件の欠落、証拠不足、適用範囲の限定、真の非該当を分けられる。また、観点の状態と次に行う行為を別語にすると、「未確認だから追加検証」と「失敗したから改訂後再検証」を区別できる。これは後続の既存資料と新規実行の境界を機械的に決める入力になる。

#### 提案0へのフィードバック

**結果:** 未成立内部の質の差を比較できないため再設計

> 観点は良いけど、知りたいのは質であり、『未成立』の中でもどこまでは成立しているのかとかで、3つの比較でそこが差になると思う

提案0はblockingな不足から次判断を導くことには使えるが、九つの観点のうち一箇所だけ不足する案と、ほとんど具体化されていない案が同じ `未成立` になり、比較したい質の差を潰す。gate判定は残しつつ、各品質観点の下位条件がどの深さまで成立しているかを別のquality profileで示すよう改訂する。

### イテレーション1: 次判断用gateと比較用quality profileを分ける

#### 提案1

**推奨:** 比較結果に、次判断を一意に導く**routing gate**と、3案の質の差を読む**quality profile**を別々に持たせる。gateはblockingな不足を見逃さないため二値に近く保ち、profileでは未成立の内部も、品質五観点ごとの下位条件と深さに分けて根拠付きで残す。

```text
routing gate: 現在その出口を採用検討へ進められるか、次に何をするか
quality profile: その結論に至るまで、何がどの深さで成立し、何が不足するか
```

gateだけで3案の質を順位付けせず、profileだけでblockingな不足を消さない。両方を同じ根拠から作るが、責務を混ぜない。

##### routing gateの判定語

`限定成立` は廃止する。「成立しているが適用範囲が狭い」と「必須条件が一部しか成立していない」が同じ語に見えるためである。適用範囲は判定語から分離して必須欄にする。

| gate判定 | 閾値 | routingでの扱い |
| --- | --- | --- |
| `成立` | 明示した適用範囲内で、その出口・段階に必須の運用能力と品質下位条件がすべて成立し、blockingな不足・矛盾・未確認がない | 適用範囲を併記して次段階または条件付き採用検討へ進める |
| `未成立` | 必須条件の少なくとも一つに、確認済みの欠落・不十分・矛盾・失敗がある | quality profileで成立範囲を残し、最上流のblocking原因を補完・改訂する |
| `未確認` | 必須条件を判定する資料または実行結果が不足し、成立とも未成立とも言えない | 既存資料の確認または新規実行へ進む。不合格と同義にしない |
| `非該当` | その出口では下位条件が不要で、同じ役割を担う代替物と不要理由を示せる | 空欄や未対応の代用にしない。対象が対応しない必須出口には使わない |

各gateには `適用範囲` を必須で付け、入力種別、出口、利用者、実行環境、対象版、担当またはモデル条件のうち結論を制限するものを書く。狭い範囲ですべて満たす場合は、その範囲で `成立` とする。範囲内に不足があれば `未成立`、範囲を判断できなければ `未確認` とする。

##### quality profileの単位

合意済みのアウトプット品質五観点を、次の下位条件へ分ける。下位条件はfileや項目名ではなく、異なる出口でも同じ意味を持つ利用能力として定義する。

| 品質観点 | 下位条件 |
| --- | --- |
| 意思決定可能性 | Q1 結論・出口が明示される / Q2 有力な対案と選択理由を再確認できる / Q3 判断が変わる条件が分かる |
| 具体性と境界 | Q4 actor・状況・入力が具体的である / Q5 完了結果を観測できる / Q6 scope・非scope・境界caseを区別できる |
| 整合性と追跡可能性 | Q7 元要求・根拠から結論と成果物へたどれる / Q8 成果物と次行動から根拠へ戻れる / Q9 file間の用語・数値・状態・版が矛盾しない |
| 根拠の十分性と確度 | Q10 重要主張に出典または観測がある / Q11 主張の強さが根拠の強さを超えない / Q12 未確認・推論・残留risk・適用限界が分かる |
| 次行動の実行可能性 | Q13 次の担当・入力・開始条件が分かる / Q14 手順またはscopeと必要成果物が分かる / Q15 合否・停止・失敗時の戻り先が分かる |

出口別最低契約は、この下位条件の具体的な読み方を決める。たとえばQ15は、`build` なら受入条件と実装中の戻り先、`validate-first` なら成功・失敗基準と結果別の次判断、`park` なら再開条件と最初の一手として読む。build用の成果物名を非buildへ要求しない。

##### 下位条件の深さrubric

各下位条件は、設計内容、現時点の利用可能性、実測支持の三段階ごとに、`評価済み | 未確認 | 非該当` を先に記録する。`評価済み` の場合だけ、次の深さを付ける。

| 深さ | 共通する意味 | 設計内容での読み方 | 現時点の利用可能性での読み方 | 実測支持での読み方 |
| --- | --- | --- | --- | --- |
| `欠落` | 必要性を確認したが、該当内容がない | 責務・条件が定義されていない | 必要なskill・template・gate・正本がない | 対象出力に必要内容がない、または失敗が観測された |
| `断片` | 関連する要素はあるが、判断や行動へ使える単位になっていない | 名前・方針・項目だけがあり、入力・境界・水準がない | 部品や欄はあるが、開始から完了までつながらない | 記述や実行主張はあるが、対象版・入力・基準と結び付かない |
| `具体化` | 主経路は具体的で使えるが、重要な接続・境界・例外の一部が不足する | actor、入力、結果、例の主要部分は定義されるが、他責務との接続または戻り先が不足する | 主経路は実行できるが、blocking欠落の検知、重要分岐、handoffの一部が不足する | 実出力と条件を確認できるが、重要な境界case、反証、修正後確認の一部が不足する |
| `成立` | その下位条件について、当該段階の必須内容がつながり、blockingな不足がない | 責務、入力・出力、境界、水準、戻り先が矛盾なく定義される | 固定コミットだけで実行・検査でき、欠落時に誤って完了扱いしない | 特定可能な版・入力・担当・方法で観測され、指摘・修正・限界まで追える |

深さは順序を持つが、数値へ換算、合計、平均しない。`具体化` が三つあっても `欠落` 一つを相殺しない。`未確認` は深さゼロではなく、評価に必要な根拠がない別状態とする。`非該当` は出口別契約上の不要理由と代替物を伴う。

##### profileに必ず残す内容

各方針・出口・段階について、五品質観点ごとに次を保存する。

| 項目 | 内容 |
| --- | --- |
| 下位条件profile | Q1〜Q15の該当条件を `欠落 / 断片 / 具体化 / 成立 / 未確認 / 非該当` で列挙する |
| 成立範囲 | `成立` または `具体化` している具体的な能力と、それが適用される条件を書く |
| blocking gap | gateを `未成立` にした最上流の下位条件と、次行動への影響を書く |
| 根拠 | 固定コミットのpath・section、または実行の版・入力・担当・方法・出力を参照する |
| 改善余地 | blockingではないが、比較時に質の差となる `断片`・`具体化` の残りを書く |

比較表のcellを `未成立` だけで終えず、たとえば `未成立 — Q7/Q8成立、Q9具体化、版の不一致がblocking` のように要約する。詳細profileから要約へ、要約から根拠へ戻れるようにする。

##### gateとprofileの導出関係

- 対象出口・段階で必須の下位条件がすべて `成立` なら、routing gateはその適用範囲で `成立`。
- 必須の下位条件に `欠落`、`断片`、`具体化` が一つでもあり、それが確認済みならgateは `未成立`。profileには他の成立条件をすべて残す。
- 必須の下位条件に `未確認` があり、既知のblocking不足がなければgateは `未確認`。既知の `未成立` が同時にあればroutingは `未成立` とし、未確認も後続事項として残す。
- `非該当` は、不要理由と代替物が出口別契約を満たす場合だけ、成立判定から除外する。

これによりgateは次判断を止める情報を失わず、profileは「あと一条件で成立」と「ほぼ未定義」を区別する。適用範囲はgateの外にあるため、旧 `限定成立` と部分的な品質深さは衝突しない。

##### 主要な次判断

提案0の行為分類は維持する。routing gateと最も手前のblockingまたは未確認段階から、`設計補完`、`資料確認`、`運用成果物補完`、`追加検証`、`改訂後再検証`、`条件付き採用検討` のいずれか一つを主要な次判断にする。

主要な次判断が同じ案同士でも、quality profileの成立範囲、深さ、blocking gap、改善余地を並べて比較する。これにより、どちらも `追加検証` でも期待品質の具体性が異なる、どちらも `設計補完` でも再利用できる資産の厚さが異なる、といった3案の差を読める。

##### 3案の比較表示

方針全体へ単一の点数やA/B/Cランクを付けない。出口ごとに次の順で並べる。

```text
適用範囲
→ routing gateと主要な次判断
→ 五品質観点の下位条件profile
→ 成立範囲・blocking gap・改善余地
→ 根拠
```

横断比較では、同じ出口・品質観点・段階のQ番号を3案で横に並べる。深さラベルだけを順位にせず、どの具体能力と根拠がその深さを支えるかを併記する。利用者は、現在採用可能かと、採用不可でも何がどこまで良いかを同じ比較から読める。

##### feature-3とfeature-7で行う適用検証

論点4のvalidationで、少なくとも次の差を表現できるか確認する。

- `feature-3`: 保存済み実行成果物と評価記録が対象版・入力・担当へ結び付く範囲では、実測支持のQ条件へ深さを付けられる。過去の失敗、改訂、再確認を分け、現在版で成立した条件と、まだ断片・具体化に留まる条件を同じ `未成立` の内部でも区別できる。
- `feature-7`: operating model、skill、templateから設計内容・現在利用可能性のQ条件へ深さを付けられる一方、構造検査scriptだけでは実出力品質のQ条件を成立にしない。実案件の出力がなければ実測支持は `未確認` だが、期待品質の設計が欠落、断片、具体化、成立のどこまで進んでいるかを `feature-3` と比較できる。

二件のどちらかで、gateが同じためprofileの差を表現できない、rubricが文書量を深さへ読み替える、Q条件の意味がbuildと非buildで変わる、`具体化` が甘い成立判定として使われる、または根拠からprofileを再現できない場合は、この判定体系を確定せず修正する。

ここで決めるのは、routing gateとquality profileの責務、適用範囲と判定の分離、Q1〜Q15、三段階ごとの深さrubric、比較表示、主要な次判断との接続である。既存資料と新規実行の境界は、各Q条件の `未確認` をどの根拠で解消できるかとして次の論点で決める。

#### 提案背景

ユーザーが比較で知りたい質は、採用できるかだけでなく、採用できない案にもどの能力がどの深さで存在するかである。これはblockingを一つでも見つければ止めるgateだけでは表せない。一方、質の成立範囲だけを並べると、重要な一欠落を多数の強みで相殺し、現在採用できるように見せる危険がある。

二つを分ければ、gateは安全なnext action routingを担い、profileは3案の差と再利用可能な強みを担う。下位条件と深さを根拠付きで残すため、単なる主観的な「高・中・低」や合計点より、なぜ差が出たかと、何を直せば成立へ進むかを説明できる。

### 決定

比較結果は、次判断を一意に導くrouting gateと、3案の質の差を読むquality profileを分ける。gateだけで質を順位付けせず、profileだけでblockingな不足を消さない。

routing gateの判定語は `成立`、`未成立`、`未確認`、`非該当` とし、旧 `限定成立` は廃止する。成立が適用される入力、出口、利用者、実行環境、対象版、担当・モデル等の範囲は、判定語と別の必須欄へ記録する。

quality profileは、アウトプット品質五観点をQ1〜Q15の下位条件へ分ける。各下位条件は、設計内容、現時点の利用可能性、実測支持の三段階ごとに、評価済みなら `欠落`、`断片`、`具体化`、`成立` の深さを付け、評価できなければ `未確認`、真に不要なら理由・代替物付きの `非該当` とする。深さは数値化、合計、平均せず、blocking不足を他の強みで相殺しない。

各profileには、下位条件の深さだけでなく、成立範囲、blocking gap、改善余地、固定コミットまたは実行条件へ戻れる根拠を残す。同じrouting gate・主要な次判断になる案同士も、このprofileを同じ出口・品質観点・段階で横断比較し、何がどこまで成立しているかを示す。

主要な次判断は、最も手前のblockingまたは未確認段階から、`設計補完`、`資料確認`、`運用成果物補完`、`追加検証`、`改訂後再検証`、`条件付き採用検討` のいずれか一つを示す。

## 論点6: 既存資料をどこまで根拠にし、いつ新規実行するか

**ステータス:** 子論点待ち

**親論点:** 論点5

**種別:** TBDヒアリング

### イテレーション0: 未確認のQ条件を、最小の追加観測で解消する

#### 提案0

**推奨:** 先に「どのQ条件の、どの段階を確かめる必要があるか」を特定し、固定コミットの資料照合、保存済み実行の独立評価、補助toolの確認、新規ケース実行の順に、結論を変え得る最小の追加観測だけを行う。既存資料が十分なら新規実行せず、実測支持が必要なのに既存資料が条件を満たさない場合だけ新規実行する。

##### 根拠の種類と、それだけで言える範囲

| 根拠の種類 | 含むもの | 単独で判定できること | 単独では判定できないこと |
| --- | --- | --- | --- |
| 固定コミットの設計資料 | design、運用文書、skill、reference、template、状態定義、品質条件 | 設計内容のQ profile、明示された責務・出口・品質契約 | 現在実行できること、実際の出力品質 |
| 固定コミットの運用成果物 | 実行入口、skill本文、template、script、正本構造、handoff規約 | 現時点の利用可能性、期待品質を生む仕組みの有無 | 実案件で期待品質を得たこと |
| 保存済み実行一式 | 入力、対象版、実行担当・方法、出力、review、修正記録 | 条件が揃う範囲の実測支持と、失敗・改訂・再確認の経路 | 別版、別出口、別入力、別担当でも再現すること |
| 元資料内の評価主張 | 「通過した」「改善した」等の記述、score、review結論 | その資料が何を主張しているか | 主張自体の正しさ。参照する出力・条件を今回確認しなければ実測支持にしない |
| 今回の静的な独立評価 | 固定コミットと保存済み出力へQ1〜Q15を適用したprofile | 読み取った成果物が基準をどこまで満たすか | 未保存の実行、再現性、別条件の品質 |
| 今回の補助tool実行 | 構造検査、存在確認、決定的なparser・test等 | toolが実際に検査する構造・機械的条件 | toolが観測しない意味内容や出口成果物の質 |
| 今回の新規ケース実行 | 固定した入力で対象方針を実行し、出力を独立評価した記録 | その版・入力・担当・方法・出口で観測した運用能力と出力品質 | 未実行条件全般への一般化、純粋なモデル性能差 |

元資料の主張、今回確認した事実、今回の解釈を分ける。たとえば保存済みreviewが「成功」と述べても、対象版と出力を確認できない場合は「成功という主張がある」に留める。反対に、事前の共通rubricがなくても入力・版・出力が保存されていれば、今回Q1〜Q15を適用した独立評価の根拠にはできる。ただし元の実行が同じrubricで自己修正した証拠にはしない。

##### 既存資料を実測支持へ使える最低条件

保存済み実行を特定のQ条件の実測支持へ使うには、少なくとも次を満たす。

1. 対象成果物またはrulesetのcommit、hash、保存copyのいずれかで版を特定できる。
2. 実行へ渡した入力と、途中で追加された高影響の指示・回答を確認できる。
3. 実行担当、使用した方法、ユーザーまたは別agentの介入が、結論へ影響する範囲で分かる。
4. 対象出口の出力一式が保存され、Q条件を結果から直接確認できる。
5. review・改訂を根拠にする場合、指摘、変更内容、変更後に再確認した対象版を結び付けられる。
6. その実行の出口と適用範囲が、今回判定したい出口・条件に対応する。

欠ける項目が結論に影響しないときだけ、理由を記録して既存資料を使う。たとえば担当モデルが不明でも、保存された出力そのもののQ7〜Q9を今回評価することはできる場合がある。一方、モデル差や再現性を述べる場合は担当・方法の不明を省略できない。欠落を推測で補わず、支持できるQ条件だけへ根拠範囲を狭める。

##### 既存資料だけで終了する条件

次をすべて満たすQ条件は、新規実行しない。

- 設計内容または現在利用可能性の判定が目的で、固定コミットの資料から `未確認` を解消できる。
- 実測支持が目的でも、上の最低条件を満たす保存済み実行一式があり、今回の独立評価で必要なprofileと限界を記録できる。
- 対象版以後の変更が、そのQ条件や出口へ影響しないことをpath・差分・依存関係から説明できる。
- 追加実行の結果が変わっても、現在の主要な次判断を変えない。

最後の条件は、調査を増やすこと自体を目的にしないための停止条件である。たとえば設計または運用成果物が明確に欠けており、先に補完しなければ実行しても採用判断へ進めない場合は、その方針を無理に実行しない。

##### 新規観測へ進む条件

Q条件の `未確認` が主要な次判断を変え得る場合、次の最小手段を選ぶ。

| 未確認の原因 | 先に行うこと | 新規ケース実行へ進む条件 |
| --- | --- | --- |
| 固定コミットの未読・分散資料 | pathと参照関係を追加照合する | 資料に答えがなく、実際の振る舞いでしか解消できない |
| scriptや構造検査の実際の対象が不明 | 原本を読み、必要なら隔離したcopyで補助toolを実行する | 出力の意味品質やagent判断を問うため、toolの観測範囲を超える |
| 保存済み実行の版・入力・出力・介入が不足 | 不足ファイルと履歴を固定コミット内で探索する | 不足が見つからず、現在版の実測支持が採用判断に必要 |
| 現在版に対応する実例がない | 旧版との差分がQ条件へ影響するか確認する | 影響がある、または影響なしと説明できず、そのQ条件が採用判断を変える |
| 対象出口の実例がない | 他出口の結果を転用しない | その出口を条件付き採用候補にするため実測支持が必要 |
| 実出力がQ条件で未成立 | 最上流の原因が設計・運用成果物・入力条件・実行のばらつきのどこにあるか切り分ける | 設計・運用成果物の欠陥なら原本を改訂する権限がないため `改訂後再検証` とする。ばらつき自体が採用判断を変える未確認事項なら、事前に試行数と停止条件を固定した反復だけを新規実行する |

`feature-1` のように実行可能な運用成果物がない対象を、今回の比較者が補完して実行しない。補完すると原本ではない新しい方針になるため、設計内容と再利用可能な資産をprofileに残し、現在利用可能性を `未成立`、主要な次判断を `運用成果物補完` とする。

##### 新規ケース実行の比較可能性

共通入力は、次をすべて満たす対象間だけで行う。

- 固定コミットの成果物だけで実行でき、比較者が片方だけを補完しない。
- 同じ出口を目指す入力として、各方針の適用範囲に入る。
- 入力差ではなく方針差を見たいQ条件が明示されている。
- 実行前に対象版、担当・モデル条件、ユーザー介入、終了条件、Q条件、保存先を固定できる。

満たさない場合は無理に共通実行しない。方針ごとの既存caseまたは出口別caseを評価し、比較可能なQ条件と条件差を明示する。共通実行をしないことは比較不能を意味せず、設計内容、利用可能性、期待品質、保存済み実測のprofileは比較できる。一方、純粋なモデル性能差や同一条件での出力品質順位は結論にしない。

##### 新規実行の事前契約

新規実行する場合は、開始前に次を保存する。

- 解消する `未確認` のQ番号と、それが変え得る主要な次判断。
- 対象commit・ruleset、入力、目指す出口、実行担当・モデル条件、許可するユーザー介入。
- Q条件ごとの観測方法と、`欠落 / 断片 / 具体化 / 成立` の判定に必要な出力。
- 時間・費用・試行回数の上限、停止条件、失敗時の扱い。
- 原本を変更しない実行場所、出力・log・reviewの保存先。

結果が不利でも上書きせず残し、実行後にrubricを都合よく変えない。基準変更が必要なら、旧基準・結果を保持して理由と再評価対象を記録する。新規実行の成果物は今回の比較証拠であり、元ブランチの原本や採用済み成果物へ自動的に昇格しない。

##### feature-3とfeature-7で行う境界検証

- `feature-3`: 保存済みrunごとに版、入力、担当、出力、review、修正後確認を照合し、最低条件を満たすQだけを実測支持へ使えるか確認する。元資料の成功主張をそのまま採用せず、実出力へ今回のprofileを適用する。現在版と実行版の差がQへ影響する場合だけ新規実行候補にする。
- `feature-7`: operating model、skill、template、scriptで設計内容と現在利用可能性を判定し、scriptの実行は構造上のQだけに限定する。保存済み実案件出力がないため、実測支持が採用判断を変えるQについてだけ新規ケース実行候補にし、設計・利用可能性の確認を目的に一律実行しない。

どちらかで、元資料の主張と今回の確認を分けられない、欠けた来歴を推測で埋める、構造検査を内容品質へ昇格する、現在版と無関係な旧結果を使う、または主要な次判断を変えない再実行を要求する場合は、この境界を確定せず修正する。

ここで決めるのは、根拠種類ごとの主張可能範囲、保存済み実行を使う最低条件、既存資料で止める条件、新規観測・共通実行へ進む条件、新規実行の事前契約である。具体的な保存pathとfile構成は後続論点で決める。

#### 提案背景

現在の3件は、骨格だけの案、保存済み実行と改訂履歴を持つ案、運用成果物と構造検査を持つが実案件出力を保存していない案である。一律に共通実行すると、`feature-1` の補完が別の比較対象を作り、既存の評価記録も捨てる。一律に既存資料だけで済ませると、`feature-7` の期待品質を実測済みと誤認する。

Q条件と主要な次判断から必要な観測を逆算すれば、`feature-3` の保存済み出力は条件の揃う範囲で再利用し、`feature-7` は設計・利用可能性を資料で評価したうえで必要な実測だけを追加できる。根拠の量を揃えるのではなく、結論を支える根拠の種類と適用範囲を揃えるための境界である。

### 決定

最初に、どのQ条件のどの段階が `未確認` で、それが主要な次判断を変え得るかを特定する。固定コミットの資料照合、保存済み実行の独立評価、補助toolの確認、新規ケース実行の順に、結論を変え得る最小の追加観測だけを行う。既存資料で十分なら新規実行しない。

固定コミットの設計資料、運用成果物、保存済み実行一式、元資料の評価主張、今回の静的独立評価、補助tool実行、今回の新規ケース実行を区別し、それぞれが単独で支持できる範囲を超えて結論を広げない。元資料の主張、今回確認した事実、今回の解釈を分ける。

保存済み実行を実測支持へ用いる範囲は、対象版、入力と高影響の追加指示、担当・方法・介入、出力一式、review・改訂・再確認、今回判定する出口と適用範囲を追えるQ条件に限定する。欠ける来歴が結論へ影響しない場合だけ理由付きで範囲を狭めて使い、推測で補わない。

設計・利用可能性を固定資料から判定できる、条件の揃った保存済み実行から実測profileを作れる、版の差が該当Qへ影響しない、追加実行が主要な次判断を変えない場合は既存資料で止める。未確認が主要な次判断を変え、実際の振る舞いでしか解消できない場合だけ、新規観測へ進む。

共通入力による新規実行は、補完なしに固定コミットだけで実行でき、同じ出口・適用範囲を持ち、比較したいQ条件と実行条件を事前固定できる対象間だけで行う。`feature-1` の運用成果物を比較者が補完して実行しない。新規実行ではQ番号、対象版、入力、出口、担当・モデルと介入、判定方法、上限・停止条件、原本を変えない実行場所と保存先を事前に記録する。

`feature-3` は条件を満たす保存済みrunを該当Qへ再利用し、成功主張ではなく実出力を今回独立に評価する。`feature-7` は設計内容と利用可能性を資料で評価し、構造検査を意味品質へ昇格させず、実測支持が採用判断を変えるQだけを新規実行候補にする。

### イテレーション0: 読者入口と比較snapshotを分ける

#### 提案0

**推奨:** working directory直下に、常に最初に読む `comparison.md` を置き、実際の比較結果は `comparisons/<comparison-id>/` の自己完結したsnapshotへ保存する。snapshot内で、実行条件、方針ごとのprofile、横断matrix、結論、根拠索引、新規実行証拠を責務別に分ける。

```text
20260919-design-model-approach-comparison/
├── design.md
├── investigation.md
├── task-design-discussion.md
├── comparison.md
└── comparisons/
    └── 001-baseline/
        ├── manifest.md
        ├── summary.md
        ├── matrix.md
        ├── evidence-index.md
        ├── profiles/
        │   ├── feature-1--d88ed099.md
        │   ├── feature-3--f6481b8c.md
        │   └── feature-7--83c9dbf5.md
        └── runs/
            └── <run-id>/
                ├── contract.md
                ├── input/
                ├── output/
                └── review.md
```

`runs/` は今回新規実行を行う場合だけ作る。固定コミットにすでに存在する成果物は、現時点ではsnapshot内へ複製せず、`evidence-index.md` から `commit:path` で参照する。参照だけで永続性が足りるか、保存copyを持つかは、次の原本保持論点で確定する。

##### 直下3ファイルとの責務境界

| file | 正本として持つ内容 | 持たない内容 |
| --- | --- | --- |
| `design.md` | 合意した比較目的、評価方法、受け入れ条件、保存・追加方針 | 実際の3案の判定結果 |
| `investigation.md` | 設計を変え得る事前調査、固定コミット、確認済みの成果物所在と条件差 | 合意後のQ profileや採用判断 |
| `task-design-discussion.md` | proposal、feedback、decisionの履歴 | 現在の比較結果の正本 |
| `comparison.md` | 読者入口、現在参照すべきcomparison、対象と結論の短い要約、過去snapshotへの索引 | Q1〜Q15の詳細profileや証拠本文 |

`design.md` を実行方法の正本とし、結果snapshotの `manifest.md` に比較方法の版として `design.md` のcontent hashと、利用可能ならそのfileを含むcommitを記録する。別のmethod fileへ同じrubricを複製しない。将来methodが変わっても、各snapshotが使用した版を再確認できるようにする。

##### snapshot内の責務

| path | canonicalに持つ内容 | 他fileとの関係 |
| --- | --- | --- |
| `manifest.md` | comparison ID、status、観測期間、method hash、対象ID、branch申告名、full commit、制作・評価条件、対象出口、実施・未実施の観測 | snapshotの比較単位と再現条件の正本 |
| `profiles/<target-id>.md` | 方針ごとの適用範囲、routing gate、主要な次判断、四運用能力、Q1〜Q15の三段階profile、成立範囲、blocking gap、改善余地、自己目的の補助情報、根拠参照 | 方針単体の判定事実と解釈の正本 |
| `matrix.md` | 同じ出口・段階・Q番号を3案で横に並べた比較、条件差、直接比較できない箇所 | profilesから作る横断view。矛盾時はprofilesを正とする |
| `summary.md` | リポジトリの役割に対する3案の結論、条件付きの向き不向き、各案の主要な次判断、比較限界 | snapshot単位の結論の正本。profileとevidenceへlinkする |
| `evidence-index.md` | evidence ID、根拠種類、対象版、`commit:path`またはsnapshot内path、対応Q、今回確認した内容、元資料の主張、解釈、限界 | evidence参照の正本。結果本文へ長い引用を複製しない |
| `runs/<run-id>/` | 新規実行の事前契約、入力、sanitizedされた必要出力、独立review | 新規実行をした場合だけ。元ブランチ原本とは別の比較証拠 |

target IDはbranch名だけにせず、`<branch-slug>--<short-commit>` とする。branch先端が動いてもprofileの対象を取り違えない。manifestにはfull commitを必須とし、model名や人の関与は確定識別子ではなく、依頼内容または資料に基づくattributionとして別欄へ置く。

##### `comparison.md` の役割

`comparison.md` は現在の結論を読む入口であり、詳細結果そのものを複製しない。少なくとも次を持つ。

- `Current comparison`: 現在参照すべきsnapshotへの相対link、status、method hash。
- `Targets`: target ID、full commit、制作条件の短い説明。
- `Current conclusion`: 各案の対応出口、現在の到達段階、実測支持範囲、主要な次判断を一行ずつ。
- `How to read`: summary、matrix、profiles、evidence-indexの読み順。
- `Comparison history`: snapshot ID、対象差分、method差分、statusの索引。

current pointerを更新しても、過去snapshotの内容を `comparison.md` へコピーしない。最新の結論は `summary.md`、方針別詳細はprofiles、根拠はevidence-indexという一意の読み先を維持する。

##### snapshotの整合規則

- `manifest.md` に存在しないtarget、method版、runを他fileから参照しない。

- 新規runのinput・output・reviewはrun IDで結び、失敗結果も削除・上書きしない。

- 新しい第四案を仮定してprofileとevidence参照を一件追加しても、既存3案のprofileやsnapshotを書き換えずに構造へ置ける。

どれかを満たせなければ、原本保持または将来追加フローへ進む前に責務境界を修正する。

ここで決めるのは、rootの読者入口、baseline snapshotのpath、snapshot内の正本分担、target ID、profileの共通構成、整合規則である。固定コミットの原本を参照だけにするか保存copyを持つか、snapshotの訂正・supersede規則、将来の採番・追加・再評価手順は後続論点で決める。

#### 提案背景

単一の比較結果fileへQ1〜Q15、三段階、3案、複数出口、根拠をすべて置くと、読み手の入口は一つでも、詳細が巨大になり、将来一案を追加するたび既存結論を直接編集することになる。反対に案ごとのfileだけでは、同じQを横に比較しにくく、どれを正本とするか曖昧になる。

入口、snapshot結論、方針profile、横断view、根拠索引を分ければ、現在の結論を短く読みつつ、質の差と根拠まで掘れる。snapshotへ対象commitとmethod hashを固定することで、branch更新やmethod改訂後にも、どの条件で得た結果かを失わない。将来追加の具体手順をまだ決めなくても、既存結果を上書きせず追加できる置き場所を先に確保できる。

#### 提案0へのフィードバック

**結果:** 読者入口と比較snapshotを分ける保存構造に合意

> ok

論点7・提案0への明示合意として受領した。固定コミットの原本保持方式、snapshotの訂正・supersede規則、将来の採番・追加・再評価手順まで確定したとは扱わない。

### 決定

working directory直下の `comparison.md` を現在の比較結果へ入るための読者入口とし、実際の比較結果は `comparisons/001-baseline/` の自己完結したsnapshotへ保存する。`comparison.md` はcurrent snapshot、対象と短い結論、読み順、過去snapshotの索引だけを持ち、詳細結果を複製しない。

`design.md` は比較方法、`investigation.md` は設計を変え得る事前調査、`task-design-discussion.md` はproposal・feedback・decision履歴の正本とする。snapshot内では、`manifest.md` が比較単位・対象版・実行条件、`profiles/<target-id>.md` が方針単体の判定、`matrix.md` がprofilesから導く横断view、`summary.md` がsnapshotの結論、`evidence-index.md` が根拠参照、`runs/<run-id>/` が今回新規実行した場合の事前契約・入力・出力・独立reviewを持つ。

target IDは `<branch-slug>--<short-commit>` とし、manifestにfull commitとmethodとして使った `design.md` のcontent hash、利用可能ならそのfileを含むcommitを記録する。baselineの対象は `feature-1--d88ed099`、`feature-3--f6481b8c`、`feature-7--83c9dbf5` とする。

profileは、対象と適用範囲、routing gateと主要な次判断、運用能力、出口別Q1〜Q15、成立範囲・blocking gap・改善余地、自己目的と再利用可能資産、根拠と未確認を共通見出しにする。巨大な一表にせず品質観点ごとの表へ分け、matrixにはprofileにない判断を追加しない。manifestにないtarget・method・runを参照せず、summary、matrix、profile、evidence-index、comparisonの判定・適用範囲・次判断を一致させる。

baseline作成後は、読者入口から結論・profile・matrix・Qごとの根拠へ到達できること、target IDとfull commitを取り違えないこと、file間で結論が矛盾しないこと、保存済みrunと新規run候補または未確認を区別できること、第四案を既存profileやsnapshotの上書きなしで追加できることを確認する。

## 論点8: 比較時点の原本をどの形で永続保持するか

**ステータス:** 子論点待ち

**親論点:** 論点7

**種別:** TBDヒアリング

### イテレーション0: 固定commitのtracked treeをsnapshot内へ不変copyする

#### 提案0

**推奨:** 各targetの固定commitにあるtracked tree全体を、baseline snapshotの `sources/<target-id>/tree/` へbyte単位でcopyし、Git上の来歴とcopyの同一性を `provenance.md` と `inventory.jsonl` で検証可能にする。`commit:path` だけに依存せず、参照した一部だけにも限定しない。

```text
comparisons/001-baseline/
├── manifest.md
├── summary.md
├── matrix.md
├── evidence-index.md
├── profiles/
├── sources/
│   ├── feature-1--d88ed099/
│   │   ├── provenance.md
│   │   ├── inventory.jsonl
│   │   └── tree/
│   ├── feature-3--f6481b8c/
│   │   ├── provenance.md
│   │   ├── inventory.jsonl
│   │   └── tree/
│   └── feature-7--83c9dbf5/
│       ├── provenance.md
│       ├── inventory.jsonl
│       └── tree/
└── runs/
```

`runs/` は今回の比較で新規生成した証拠、`sources/` は比較前から固定commitに存在した原本の保存copyであり、混ぜない。source copyはsnapshot完成後に編集せず、後から誤りや別版が判明してもその場で直さない。訂正時にどのsnapshotを追加し、currentをどう切り替えるかは次の訂正・supersede論点で決める。

##### 原本、保存copy、評価結果の関係

| 層 | 役割 | 正本性 |
| --- | --- | --- |
| 固定commit | 比較対象の版とGit上の来歴を識別する | target identityの起点。branch名や最新先端へ置き換えない |
| `sources/<target-id>/` | 固定commitのtracked contentをsnapshotだけで再読できるよう保持する | snapshotが使った証拠本文のcanonical copy。commitとの不一致があればsnapshotを完成扱いしない |
| profile・matrix・summary | 保存copyと他の観測をrubricへ当てた判定・解釈 | 原本を改変せず、evidence IDでsourceまたはrunへ戻る |

固定commitがGitに残っている間は、commitをtarget identityの起点とする。source copyはcommitを別物へ置き換えるためではなく、branch削除やGit objectの消失後も比較根拠を読めるようにする保存表現である。Git objectが後日読めなくなっても、capture時に同一性を検証した記録と保存copyは残る。ただし、その時点でGit履歴を再検証できるとは主張しない。

##### 保存する範囲

baselineの3targetは、固定commitのtracked pathをすべて保存する。Q判定で直接引用したfileだけに絞らない。後の再評価で別の根拠や参照関係が必要になったとき、当初の評価者による選別で確認不能になることを避けるためである。

- regular fileはGit blobのraw byteを保存し、改行変換や整形をしない。
- executable bitを含むGit modeを記録・復元する。
- symbolic linkは参照先を展開せず、link自体とそのtarget文字列を保存する。`feature-3` の `.agents/skills/` 配下3件をこの条件の検証caseにする。
- `.git/`、固定commitにないuntracked file、比較者の一時fileは含めない。
- commitの親、author/committer、日時、message、tree object IDはprovenanceへ記録するが、比較に不要な全履歴を複製しない。

現在の3treeは6 files / 414,089 bytes、134 files / 627,331 bytes、20 files / 73,947 bytesで、合計1,115,367 bytesである。この規模では、参照subsetや不透明なbinary archiveで複雑さを増やすより、repository上で直接読める全tracked treeのcopyを優先する。

将来targetに巨大binary、submodule、資格情報・個人情報等の保存不適切なtracked contentが見つかった場合は、黙って除外またはredactして完全copyと称しない。対象path、理由、比較への影響を記録してsnapshotをcompleteにせず、保存可否または適用範囲をユーザー判断へ返す。この例外の具体的な受付手順は将来追加フローで決める。

##### provenanceとinventory

各 `provenance.md` は少なくとも次を持つ。

- target ID、申告branch名、full commit、parent commit群、commit tree ID、author/committerと日時。
- source repository、capture日時・方法、file数、合計byte数。
- symlink、executable、submoduleの件数、除外の有無と理由。
- inventoryとtreeの検証結果、検証できなかった事項。

`inventory.jsonl` はtracked entryごとにpath、Git mode、object type、blob/object ID、byte数を一件ずつ持つ。pathはJSON文字列としてescapeし、空白や制御文字を含むpathでも曖昧にしない。directory entryは不要だが、submoduleがある場合はcommit objectとして明示し、通常fileのcopyで代用しない。

capture完了前に次を機械的に検証する。

1. 固定commitのrecursive tree entryとinventoryのpath、mode、object ID、sizeが一致する。
2. `tree/` 内のregular fileとsymlink targetをGit blobとしてhashし、inventoryのobject IDと一致する。
3. executable bitとsymlink種別がinventoryと一致する。
4. 余分なpath、欠けたpath、内容不一致が0件である。
5. provenanceのtarget commitと、snapshot manifestのtarget ID・full commitが一致する。

一つでも不一致なら、そのsource copyを根拠にprofileを確定せずcaptureをやり直す。検証結果は `provenance.md` へ記録する。

##### evidence-indexからの参照

固定資料を根拠にするevidence entryは、snapshot内の `sources/<target-id>/tree/<path>` を読者が開く参照先とし、同時にfull commit、元のpath、blob IDを持つ。行範囲は補助locatorであり、本文変更を検知するidentityには使わない。source copyと `commit:path` の内容がcapture時に一致したことをprovenanceへ戻れるようにする。

元資料の評価主張はsource内の該当file、今回の解釈はprofileへ分ける。source treeへannotationや評価結果を書き込まない。直接引用を結果fileへ大量複製せず、判定に必要な要約とevidence IDだけを置く。

##### 新規実行との境界

保存したsource treeを新規実行の作業場所にせず、runごとの隔離worktreeへcopyしてから実行する。実行前後のsource hashを照合し、`sources/` が変わっていないことを確認する。runのcontractは使用したtarget ID、source inventory hash、実行用copyへ加えた許可済み入力だけを記録する。生成物、log、reviewは `runs/<run-id>/` に置き、原本の一部に見せない。

##### 原本保持方式の検証

baseline作成後、次を確認する。

- Git branch名を使わずsource copyだけから3targetの設計・運用成果物と保存済みrunを読める。
- Git objectが利用可能な状態では、全entryのtype・mode・blob IDが各固定commitと一致する。
- `feature-3` の3symlinkがdereferenceされず、保存tree内でも同じrelative targetを指す。
- profileの固定資料evidenceをすべてsnapshot-local pathとblob IDへ戻せる。
- 新規runを行ってもsource copyのinventory hashが変わらない。

いずれかを満たせなければ、snapshotをcompleteにせず原本captureまたは参照設計を修正する。

ここで決めるのは、baselineで全tracked treeを保存すること、保存path、Git identityとsnapshot copyの関係、同一性検証、evidence・runとの境界である。誤判定や欠落を後から訂正するsnapshotの作り方、current pointerの切替、将来targetの受付・採番・再評価条件は後続論点で決める。

#### 提案背景

full commitと `commit:path` だけでは、branch削除後にGit objectが回収されると根拠本文を失う。一方、引用したfileだけをcopyすると、後から別のQや参照先を再評価する際に、当初選ばなかった原本へ戻れない。Git bundleや圧縮archiveはcommitを保存できるが、通常のrepository閲覧から根拠を直接読みにくく、今回の約1.12MBのtreeには過剰である。

全tracked treeのplain copyとGit object IDのinventoryを組み合わせれば、現在はcommitとの同一性を機械検証でき、将来Git objectを失っても保存本文を読める。原本copy、今回のrun、評価結果を物理的に分けるため、比較者が補完・実行した内容を元ブランチの成果物へ混ぜることも避けられる。

#### 提案0へのフィードバック

**結果:** 固定commitの全tracked treeを検証可能な不変copyとして保持する方式に合意

> ok

論点8・提案0への明示合意として受領した。snapshotの訂正・supersede規則、将来targetの受付・採番・再評価手順まで確定したとは扱わない。

### 決定

baselineの各targetについて、固定commitの全tracked treeを `comparisons/001-baseline/sources/<target-id>/tree/` へraw byte、executable mode、symlinkのまま保存する。`.git/`、固定commitにないuntracked file、比較者の一時fileは含めない。source copyはsnapshot完成後に編集せず、評価annotationやrun出力を書き込まない。

各sourceは `provenance.md` にtarget ID、branch申告名、full commit、parent群、tree ID、author/committer、capture条件、entry数・byte数、特殊entryと除外、検証結果を持ち、`inventory.jsonl` にpath、mode、object type、blob/object ID、sizeをentryごとに持つ。固定commitのrecursive tree、inventory、保存treeのpath・type・mode・object ID・size、snapshot manifestのtarget identityが一致し、欠落・余分・不一致が0件であることをcomplete条件にする。

固定commitをtarget identityの起点、source copyをsnapshotで読む証拠本文のcanonical copy、profile・matrix・summaryを判定と解釈とする。evidenceはsnapshot-local pathに加えてfull commit、元path、blob IDを持ち、capture時のGit同一性検証へ戻れるようにする。

source treeを新規実行の作業場所にせず、runごとの隔離copyから実行する。実行前後にsource inventory hashの不変を確認し、生成物・log・reviewは `runs/<run-id>/` に置く。巨大binary、submodule、資格情報・個人情報等で完全copyが不適切な場合は黙って除外・redactせず、snapshotをcompleteにしないで対象path、理由、比較への影響を記録し、ユーザー判断へ返す。

## 論点9: 完成後の誤りをどう訂正し、どのsnapshotをcurrentにするか

**ステータス:** 子論点待ち

**親論点:** 論点8

**種別:** TBDヒアリング

### イテレーション0: sealed snapshotを上書きせず、原因から再生成してsupersedeする

#### 提案0

**推奨:** snapshotは作成中の `draft` と検証済みの `complete` をmanifestに持ち、`complete` になったsnapshotは全fileを不変にする。完成後にsource capture、evidence mapping、Q判定、派生結論の誤りが見つかった場合は、誤りの起点から下流を再生成した新しい自己完結snapshotを作り、検証完了後にだけ `comparison.md` のcurrent pointerを切り替える。旧snapshotは削除・編集せず、historyにsupersede理由を残す。

##### 訂正と、新しい比較を分ける

| 変化 | 扱い | 理由 |
| --- | --- | --- |
| complete前のsnapshot内の誤記・不足 | 同じdraft内で修正し、全validation後にcompleteへ進める | まだ公開する比較単位として確定していない |
| `comparison.md` の文章上のtypo、同じsnapshotを指すlink表示の誤り | current targetや結論を変えない範囲で入口だけ修正し、link validationを再実行する | snapshotの証拠・判定を変えないreader navigationの保守 |
| source captureの欠落・byte/mode/symlink不一致、誤ったcommitとの対応付け | 旧snapshotをcurrentとして使えない可能性を入口に警告し、新snapshotでsourceから全下流を再生成する | target identityと根拠本文が壊れており、部分patchでは信頼を回復できない |
| evidence ID・引用元・事実記述・Q深さ・gate・主要な次判断・summaryの誤り | 最上流の誤りから影響するprofile、matrix、summaryまで新snapshotで再生成する | 派生fileだけ直すとcanonical判定と表示が食い違う |
| 以前 `未確認` と正しく記録した事項に新証拠が増えた | 訂正ではなく追加比較・再評価へ送る | 旧snapshotの誤りではなく観測条件が変わった |
| target commit、対象案、実行case、method hash、rubricが変わる | 訂正ではなく追加比較・再評価へ送る | 同じ問いを誤りだけ直す範囲を超える |

新情報によって旧記述が事実誤認だったと判明した場合は訂正、新情報が旧 `未確認` を解消するだけなら追加比較とする。分類できない場合は、旧snapshotが当時の根拠とmethodに照らして正しかったかを先に判断し、methodを遡及変更しない。

##### snapshot内部statusと、入口での関係statusを分ける

manifestの `status` はsnapshot自身の作成状態だけを表す。

- `draft`: 作成中。fileを更新できるが、currentにはできない。
- `complete`: 全受け入れ条件と整合・原本検証を通過した。以後snapshot全体を編集・削除しない。

currentかどうか、後継に置き換えられたかはsnapshot内のstatusへ後書きせず、`comparison.md` のcurrent pointerとhistoryで管理する。historyはsnapshotごとに `current`、`superseded`、`invalidated` の関係statusを持つ。

| 関係status | 意味 |
| --- | --- |
| `current` | 現在の判断に使うcomplete snapshot。原則一つ |
| `superseded` | 当時の証拠・methodではcompleteだったが、訂正版または後続比較をcurrentにしたため履歴として残す |
| `invalidated` | source identity・完全性など、snapshot全体または主要結論を信頼できない欠陥が判明した。後継が未完成でも現在判断には使わない |

旧snapshotのmanifestには、常にroot `comparison.md` でcurrent statusを確認する案内を完成時から入れる。こうすれば、complete後の旧snapshotへ `superseded-by` を追記しなくても、入口のhistoryが現在の扱いを一意に示せる。

##### 誤り発見時の安全な表示

誤りを見つけた時点で、まず影響範囲を次の依存順に追う。

```text
target/source → evidence → profileのQ・gate・次判断 → matrix → summary → comparison
```

誤りがrouting gate、主要な次判断、target identity、source完全性を変え得る場合はblocking issueとし、訂正版完成を待たず `comparison.md` へ影響範囲と「現在判断に使わない」警告を置く。source identity・完全性を信頼できない場合はcurrentを外してhistoryを `invalidated` にする。影響がblockingでなく、成立範囲や改善余地の一部だけに限られる場合は、currentを維持しつつknown issueを表示できる。

警告は暫定結論を推測せず、issue ID、発見日、報告された事実、影響し得るtarget・evidence・Q・結論、currentを使える範囲、次に必要な確認を持つ。訂正版完成後も、historyからissueと後継snapshotをたどれるようにする。

##### 訂正snapshotの構成

訂正は差分fileだけを作らず、通常snapshotと同じmanifest、sources、evidence-index、profiles、matrix、summary、必要なrunsを持つ自己完結snapshotにする。新manifestに次を追加する。

- `supersedes`: 直接置き換えるsnapshot ID。複数をまとめる場合は全ID。
- `reason`: 誤りの事実と、なぜ訂正またはinvalid化が必要か。
- `issue`: rootのknown issue ID。
- `correction scope`: 誤りの起点、影響target・evidence・Q・gate・結論。
- `unchanged inputs`: target、source inventory、run、methodのうち同一性を再検証して引き継いだもの。
- `recomputed`: 再capture・再評価・再生成したfileとvalidation。

訂正時もsourceを旧snapshotからblind copyせず、固定commitとGit objectが読めるなら再capture・再検証する。Git objectを失っている場合は旧snapshotのsourceとinventoryを入力として使い、その制約をprovenanceと適用限界へ明記する。影響しない既存runを引き継ぐ場合も、入力・出力・reviewを新snapshot内へ保持し、hashと来歴を再確認する。誤りの原因がrun自体にあれば再実行の必要性を論点6の境界から判断し、都合よい結果を得るために自動再実行しない。

##### 下流再生成と再review

訂正は誤りの最上流から行う。

1. issueを登録し、訂正か追加比較かを分類する。
2. 誤ったsource、evidence、Q判定、派生viewを特定する。
3. 新snapshotでsource/evidenceを正し、影響する全profileを再評価する。
4. profilesからmatrix、summaryを再生成し、comparisonの一行結論候補を導く。
5. 影響scopeだけでなく、既存の全file整合、全source identity、linkを再validationする。
6. 元の誤りを検出できる回帰caseをvalidationへ追加する。
7. 新snapshotをcompleteにした同じchange setでだけcurrent pointerとhistoryを更新する。

客観的な転記、hash、派生整合の訂正は証拠に従って進める。複数の妥当な解釈がありQ判定・適用範囲・主要な次判断が変わる場合、またはrubric変更が必要な場合はユーザー判断へ返し、合意前にcurrent結論を置き換えない。

##### supersedeの検証

次の具体caseで規則を検証する。

- source defect case: `feature-3` のsymlinkが誤ってdereferenceされたことが後から判明した。旧snapshotを上書きせずinvalid化し、新snapshotで全source identityと影響するevidence/profileを再検証できる。
- judgement defect case: `feature-7` の構造checkを誤ってQ10〜Q12の意味品質の実測支持へ使った。元資料は同じまま、evidence種別と影響Qからgate・matrix・summaryまで訂正し、元の過大主張が残らない。
- non-correction case: 新しい第四案またはfeature-7の新規runが追加された。旧snapshotの誤りとして扱わず、将来追加フローへ送れる。

さらに、訂正版をcompleteにする前はcurrentを切り替えない、blocking defectの旧snapshotを無警告でcurrentに残さない、historyから旧結論・issue・後継へ双方向にたどれる、旧snapshot配下のhashが変わらないことを確認する。

ここで決めるのは、draft/completeと不変化、訂正と新規比較の境界、issue時の安全表示、新snapshotによる再生成、current切替、supersede/invalidatedの履歴、回帰検証である。将来targetの受付、comparison ID採番、既存targetのどこまで再評価するか、別steeringへ分ける条件は次の将来追加フローで決める。

#### 提案背景

sourceだけを不変にしてprofileやsummaryを直接書き換えると、過去にどの根拠から何を判断したかを失う。反対に、typoや同一snapshotへの壊れたlinkまで毎回新snapshotにすると、意味のない履歴が増える。snapshotの意味を変える訂正とreader navigationの保守を分ける必要がある。

訂正snapshotを自己完結にして、誤りの起点から下流を再生成すれば、profileだけ直してmatrixやsummaryが古いまま残ることを防げる。current pointerを最後に切り替え、blocking defectは先に入口で警告することで、訂正版作成中にも誤った結論が無条件で使われることを避けられる。この契約を先に決めると、将来追加フローでは「何が変われば新snapshotか」を同じ境界から決められる。

**結果:** complete snapshotを不変にし、新snapshotで訂正・supersedeする規則に合意

### 決定

manifestのsnapshot内部statusは `draft` と `complete` とする。draftは作成中で修正可能だがcurrentにせず、completeは全validation通過後の状態としてsnapshot全体を以後編集・削除しない。current、superseded、invalidatedはsnapshotへ後書きせず、root `comparison.md` のpointerとhistoryで管理する。

complete後にsource capture、evidence、Q判定、gate、主要な次判断、派生結論の誤りが見つかった場合は、旧snapshotを直接修正せず、誤りの最上流からprofile、matrix、summaryまで再生成した新しい自己完結snapshotで訂正する。新snapshotがcompleteになった同じchange setでだけcurrentを切り替え、旧snapshotをhistoryへ残す。current targetや結論を変えない入口のtypo・同一snapshotへのlink表示だけは `comparison.md` の保守として修正できる。

以前の `未確認` に新証拠が増えた場合、target commit・対象案・実行case・method・rubricが変わる場合は訂正ではなく追加比較・再評価へ送る。新情報で旧記述が事実誤認だったと判明した場合は訂正する。複数解釈やrubric変更が必要ならユーザー判断へ返し、合意前にcurrent結論を置き換えない。

誤りがrouting gate、主要な次判断、target identity、source完全性を変え得る場合は、訂正版完成前に `comparison.md` へknown issueと利用不能範囲を警告する。source identity・完全性を信頼できなければcurrentを外して `invalidated`、検証済み後継へ通常置換した旧snapshotは `superseded` とする。暫定結論は推測しない。

訂正snapshotもmanifest、sources、evidence-index、profiles、matrix、summary、必要なrunsを持つ。manifestにsupersedes、reason、issue、correction scope、再検証して引き継いだinputs、再生成物とvalidationを記録する。sourceとrunの同一性を再確認し、元の誤りを検出する回帰caseを追加する。訂正版complete前にcurrentを切り替えないこと、blocking defectを無警告で残さないこと、historyからissue・旧結論・後継を追えること、旧snapshotのhashが変わらないことを検証する。

## 論点10: 将来targetをどう追加し、何を再評価するか

**ステータス:** 子論点待ち

### イテレーション0: 変更差分から再評価範囲を決め、同じ比較系譜へsnapshotを追加する

#### 提案0

**推奨:** 将来の追加依頼ごとに、まず現在の比較目的へ入るversioned targetかを受け付け、current snapshotとの差をtarget、source、制作・評価条件、evidence、method、出口・適用範囲で分類する。同じリポジトリ役割と意思決定を更新する場合は、このworking directoryで次のcomparison IDを採番した自己完結snapshotを作る。既存判定は差が影響しないQだけ検証付きでcarry forwardし、matrix・summaryはtarget集合全体から必ず再生成する。目的または評価対象の役割が変わる場合だけ別steeringへ分ける。

##### 受付単位と必須入力

このsteeringのtargetとして受け付ける最小単位は、このrepositoryでfull commitに固定できるtracked artifact treeである。新しいモデル名だけ、branch名だけ、未保存の会話だけではtargetを作らない。branch先端を自動追従せず、受付時にfull commitへ解決する。

追加依頼では、次を受付記録に持つ。調査で確認できる項目はagentが埋め、欠落をユーザーへ一括質問しない。

| 入力 | 扱い |
| --- | --- |
| source repository、branch/ref、full commit | target identityと原本captureに必須。解決不能ならsnapshot対象へ入れず停止 |
| 何を作る試行だったか、対象範囲・非目標・完了条件 | 原資料から確認し、なければ `unknown`。自己目的の補助評価と不足理由に使う |
| 入口、skill/template/script、正本、対応すると宣言する出口 | fixed treeから観測し、設計・利用可能性のprofileへ使う |
| 制作モデル、人の関与、入力、時間・費用等の制作条件 | 依頼内容・資料・観測を区別して記録。不明でもartifact比較は可能だがモデル差を主張しない |
| 保存済みrun、review、改訂履歴 | 来歴最低条件を照合し、満たすQだけ実測支持へ使う |
| 今回追加したい理由と、currentを更新したいか | 比較系譜と同じsteering/別steeringを決める。意図不明で結果の置き場所が変わる場合だけ確認 |
| source保存上の制約 | 資格情報、個人情報、巨大binary、submodule等を確認し、完全copyできなければユーザー判断へ返す |

制作条件や保存済みrunが欠けても、固定artifact tree自体を比較できるなら受付を拒否しない。該当するattributionや実測支持を `未確認` に制限する。骨格だけ、運用成果物なし、実行不能も比較結果で判定する状態であり、受付時に比較者が補完しない。

##### target identity

- 新しいfull commitは `<branch-slug>--<unique-short-commit>` の新target IDを持つ。baselineは8桁を使い、将来衝突する場合は一意になるまでcommit prefixを延ばす。
- 同じfull commitが既存targetにある場合は新targetを重複作成せず、既存target IDを再利用し、新branch名をaliasまたは受付時refとしてmanifestへ記録する。
- 同じbranchの先端が進んでも既存target IDを変更しない。新commitを新targetとして扱い、旧版を置換してcurrent集合から外すか、進化比較のため両方を含めるかで結論が変わる場合はユーザーへ一問で確認する。
- モデル名、人の関与、prompt条件はtarget identityへ混ぜずattribution・制作条件として持つ。同一artifactを異なる実行条件で評価した場合はrun/evidenceを分ける。

##### comparison IDとsnapshot

同じworking directoryのcomparison IDは、作成理由に関係なく未使用の次の3桁連番と短いslugを使う。

```text
001-baseline
002-add-<target-slug>
003-correct-<scope-slug>
004-recheck-<scope-slug>
```

一度割り当てたIDを再利用・改名・詰め直ししない。日付はIDへ入れずmanifestの開始・完了日時に記録する。訂正、新target追加、新証拠による再評価、method改訂のどれも新しいsnapshotを作り、manifestにtriggerとprevious current、target/source/method/evidence差分、carry forwardと再評価範囲を記録する。

新snapshotはcurrentの差分patchではなく、合意済みのmanifest、sources、evidence-index、profiles、matrix、summary、必要なrunsを持つ自己完結単位にする。completeになるまでcurrentを切り替えず、completeと同じchange setで `comparison.md` のcurrent pointerとhistoryを更新する。通常の追加で旧currentは `superseded` とし、誤りがなければ `invalidated` にしない。

##### 同じsteeringと別steeringの境界

次をすべて満たす場合は、このworking directoryへsnapshotを追加する。

- 主評価が「このrepositoryの役割を現在どこまで果たせるか」のままである。
- routing gate、quality profile、出口別契約の同じ意味系譜で条件付きの採用・次検証を判断する。
- targetを同じ原本保持・根拠契約で保存できる。
- 過去snapshotとの履歴を読者が一つのcurrent comparisonとして更新する意図がある。

次のいずれかなら別steeringを作り、この `comparison.md` のrelated comparisonから相互参照する。現在のcurrent pointerは変えない。

- repositoryの役割、比較から可能にする意思決定、主評価を変える。
- targetが別repository・別機密区分等にあり、同じsource保存契約を適用できない。
- 既存Qや出口の意味を対応付けられないほどmethodを作り替える。
- current比較を更新せず、独立した実験・監査として履歴を分けることを依頼者が選ぶ。

モデルが増えた、日付が変わった、file数が増えたという理由だけでは別steeringにしない。反対に、同じ名前のskillやmodelでも比較目的が変われば同じsteeringへ押し込まない。

##### method変更の扱い

`design.md` の表現だけを明確化しQ、閾値、出口、根拠強度、次判断が変わらない変更は、manifestへnon-semanticなmethod差として記録し、該当しないQを再評価しない。意味を変えるmethod変更は、同じrepository役割・意思決定を維持し、旧新のQ/出口/判定を対応付けられる場合だけ同じsteeringで行う。

semantic changeでは、変更したQ、gate、出口、根拠条件に依存する全既存targetを再評価する。一部だけ新基準にして同じmatrixへ混ぜない。対応付けられず過去結論と同じ語で比較できない場合は別steeringへ分ける。method変更自体がユーザー合意を要する場合はtask-designへ戻し、合意前のrubricで新snapshotをcompleteにしない。

##### carry forwardと再評価の境界

既存profileのQ判定を新snapshotへcarry forwardできるのは、次をすべて満たす場合だけである。

1. target full commitとsource inventory hashが同一で、source captureを新snapshotでも検証できる。
2. そのQに適用するmethod、出口別契約、深さrubric、evidence最低条件がsemanticに同じである。
3. 新しい事実・run・反証・known issueが、そのQの設計、利用可能性、実測支持、適用範囲を変えない。
4. profileから参照するevidenceを新snapshot内へ保持し、linkとhashを再確認できる。
5. carry forwardした判定と根拠範囲をmanifestに列挙し、単に旧profileをcopyしただけにしない。

次のいずれかなら影響する既存target・Qを再評価する。

- target commitまたはsource inventoryが変わった。
- methodのQ、gate、出口契約、深さ、根拠強度が変わった。
- 新証拠が `未確認` を解消する、既存根拠と矛盾する、または適用範囲を変える。
- 新targetの具体caseが、同じ基準では扱えない境界・矛盾・重複を明らかにした。
- known issue、訂正、実行失敗が該当Qへ影響する。

target追加時もmatrixとsummary、comparisonの短い結論はtarget集合全体から必ず再生成する。既存profileをcarry forwardできても、新targetを含む条件差、直接比較不能箇所、各案の向き不向き、主要な次判断を旧summaryから流用しない。

##### 追加フロー

1. 依頼を受付記録へ保存し、追加理由とcurrent更新意図を特定する。
2. refをfull commitへ解決し、既存targetとの同一・新規・更新版を分類する。
3. 同じsteering/別steeringを上の境界で決め、必要な場合だけユーザーへ一つの選択を返す。
4. 同じsteeringなら次のcomparison IDでdraft manifestを作り、currentとの差分をtarget、source、条件、evidence、method、出口・適用範囲ごとに記録する。
5. 全新targetのsourceをcapture・検証し、既存targetも新snapshotのsource identityを確認する。
6. carry forwardできるQと再評価するQを根拠付きで決める。新規観測は論点6の最小観測境界に従う。
7. 新targetと影響する既存targetへprofileを適用し、feature-1のような未完成targetを比較者が補完しない。
8. 全targetのprofilesからmatrix、summary、comparisonの短い結論候補を再生成する。
9. source、evidence、Q、gate、file間整合、link、訂正回帰caseをvalidationし、completeにする。
10. 同じchange setでcurrent pointerとhistoryを更新し、旧currentをsupersededとして残す。

agentはGitと資料から確認できる事項、Q評価、carry-forward影響分析を進める。ユーザーへ返すのは、source保存の許可、同branchの新版を置換か併記か、比較目的・methodを変えるか、複数の妥当な解釈で主要な次判断が変わるかなど、入力なしでは結果の意味が変わる事項に限定する。不明な制作モデルや人の介入を埋めるためだけに追加を止めず、unknownと主張限界を残す。

##### 追加フローの検証

次のcaseで、同じ規則から一意に処理できることを確認する。

- 新しい第四案: 新branchの固定commitを `002-add-<slug>` へ追加する。旧3targetのsource・method・evidenceが不変ならQを検証付きcarry forwardし、第四案を新規評価してmatrix・summaryを4案から再生成する。
- 既存branchの新版: `feature-7` の先端が更新された。新target IDを作り、旧版の置換か併記かをユーザー判断へ返す。旧IDと旧snapshotを変更しない。
- 新しい実測: 同じ `feature-7` commitに事前契約したrunを追加する。target IDは再利用し、実測支持に影響するQを再評価する。これは訂正でなくrecheck snapshotである。
- semanticなmethod変更: evidence最低条件またはQ閾値が変わる。影響する全targetを再評価し、一部だけ旧基準のmatrixへ混ぜない。意味対応不能なら別steeringへ分ける。
- 受付不能: refがfull commitへ解決できない、またはsourceを完全保存できない。targetを推測・補完せずdraftをcompleteにしない。
- 別目的: model性能順位や別repositoryの役割を調べる依頼。現在のcurrentを変えず、別steeringからrelated linkを持つ。

さらに、comparison IDが再利用・改名されない、同じcommitがalias branchで重複targetにならない、carry forwardされた全Qに同一性根拠がある、新target追加後のsummaryが旧3案のまま残らない、別steering化した依頼がcurrent pointerを変えないことを確認する。

ここで決めるのは、target受付項目、identity、comparison ID、同じ/別steering、method変更、carry forward・再評価条件、追加手順、ユーザー境界である。具体的な将来追加依頼が来た時は、このフローの観測結果を新snapshotへ保存し、存在しないtargetや条件を先に作らない。

#### 提案背景

新targetのたび全既存案を無条件に再実行すると、主要な次判断を変えない観測まで増やし、保存済み根拠を捨てる。一方、新targetのprofileだけを足して旧matrix・summaryを残すと、比較集合が変わったのにcurrent結論が古いままになる。Q単位のcarry forwardと、集合全体の派生view再生成を分ける必要がある。

同じsteeringの境界をモデル名や日付で決めず、repository役割・意思決定・methodの意味系譜で決めれば、将来モデルを継続追加できる。full commitとsource保存を受付の必須条件にし、それ以外の不明は評価上の `未確認` とすることで、来歴を捏造せず骨格案も完成案も同じ比較へ入れられる。

#### 提案0へのフィードバック

**結果:** versioned targetの受付からsnapshot更新までの追加フローに合意

> ok

### 決定

将来targetは、このrepositoryでfull commitへ固定でき、合意済みの完全source copyを作れるtracked artifact treeを最小単位として受け付ける。制作目的、入口と出口、制作条件、保存済みrun、追加理由、保存制約を受付記録へ持つが、固定artifactを評価できる限り、不明な制作モデル・人の関与・runは `unknown` または `未確認` として扱い、比較者が補完しない。

target IDは `<branch-slug>--<unique-short-commit>` とする。同じfull commitは既存IDを再利用してrefをaliasとして残し、同じbranchの新commitは新targetにする。旧版の置換か併記かで結論が変わる場合だけユーザーへ一問で確認する。モデル、prompt、人の関与はidentityでなくattribution・制作条件、同一artifactへの別実行はrun/evidenceとして分ける。

同じworking directoryのcomparison IDは未使用の次の3桁連番と短いslugを使い、再利用・改名・詰め直しをしない。追加、訂正、recheck、semanticなmethod改訂はいずれも自己完結した新snapshotとし、completeと同じchange setでだけcurrentを切り替える。

同じrepository役割、意思決定、Q・gate・出口の意味系譜、source保存契約、current比較を更新する意図を保つ場合は同じsteeringへ追加する。役割・意思決定が変わる、保存契約が異なる、methodを対応付けられない、独立監査として分ける場合は別steeringにし、現在のcurrentを変えずrelated comparisonから参照する。モデル数、日付、file数だけでは分けない。

表現の明確化だけのnon-semanticなmethod変更では不要なQを再評価しない。Q、閾値、出口、根拠強度、次判断の意味を変える場合は影響する全target・Qを再評価し、旧新基準を同じmatrixへ混ぜない。意味対応不能なら別steeringへ分け、合意を要するmethod変更はtask-designへ戻す。

既存Qをcarry forwardできるのは、full commitとsource inventory、method意味、evidence、適用範囲が不変で、根拠を新snapshot内へ保持・再検証し、manifestへ対象を列挙できる場合に限る。target、method、evidence、known issue、適用境界の変化に影響するQは再評価する。profileをcarry forwardしても、matrix、summary、comparisonの短い結論は全target集合から必ず再生成する。

追加時は、受付、full commit解決とtarget分類、same/new steering判断、draft manifest、source capture、carry-forward分析と最小観測、profile評価、全targetからの派生view再生成、整合validation、current切替の順に進める。agentはGitと資料から確認できる調査・Q評価・影響分析を進め、source保存許可、同branch新版の置換か併記、目的・method変更、主要な次判断を変える複数解釈だけをユーザーへ返す。第四案、既存branch新版、同commitの新run、semanticなmethod変更、受付不能、別目的のcaseでこの規則を検証する。
