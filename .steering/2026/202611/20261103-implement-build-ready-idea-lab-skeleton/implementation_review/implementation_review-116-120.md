# 実装後レビュー（論点116〜120）

## 論点116: 必要な時点でskillを適用し、終端で読んだことに置き換えない進行をどう作るか

**ステータス:** 調査中

**親論点:** 論点110

**種別:** レビュー指摘への改善検討

### イテレーション0（論点116）: 適用漏れを埋める仕事を、薄い進行へ戻す

#### 検討記録（論点116・イテレーション0）

##### 起きたことと現在

別実行者は各decision直後のdoc-enricher origin-reviewをその場で全件通しておらず、一部を最後に行った。文書標準の一部も最終auditで追加読取りした。fileと最後の検査が揃っても、必要だった時点で問い/観点を当てた証拠にはならない。通常のplugin自動読込みを試した結果でもない。

**現在:** 手順の適用漏れは記録済み。後からのreviewを当時の実施済みとはしていない。

根拠: [適用漏れの実行者報告](../integration-check/require-build-rerun/executor-findings.md#今回の適用上の限界と残した摩擦) / [親側が留保した手順適合](../integration-check/require-build-rerun/README.md#発見した訂正と未解消の所)

##### この論点で決める問い

現在の層/専門/decisionの区切りに必要なskillとその返りを、その時に実施して次の仕事へ渡せる進行をどう作るか。終端の形式検査や読取hashを、検討/適用済みの代わりにしない。適用漏れの発見時は影響する判断へ戻し、無関係な仕事を全部やり直す扱いにはしない。

##### 戻す仕事と、まだ決めていないこと

実行の進め方とsharedのfacilitate-discussion/document-review等の接続を確認する。呼出しの時点は既存指示にあるため、新しい必須手続きを足すことを結論にしない。実行者がその場で実施できなかった理由と、小さいblockの引渡しに必要な受領/確認を診断する。sharedへの改稿が必要なら正本側への具体の改善候補として扱い、install cacheは編集しない。

##### 原事例で確かめる差

decision直後のreviewと文書をemitする前のreviewがそれぞれ何を判断へ返すか、C1の一blockで辿れるようにする。読んだ一覧だけで終わる案と、必要な判断/出力へ適用する案を分ける。薄い進行を保ち、専門全部を監督する新しい巨大な台帳/管理役や、毎回全skillの再読を所与にしない。

この回は改善の受付であり、具体の改稿案とその採否はまだ無い。元の方法/ケースは変更せず、後の提案で変更先・変更前後・理由と、ここで示した原事例への返しを揃える。
