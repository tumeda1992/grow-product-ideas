## 論点106: 原文の話者と出典を保ち、設定と見立てを本人の発言へ変えない

**ステータス:** 反映済み

**種別:** レビュー指摘への改善提案

### イテレーション0（論点106）: 受け入れから採否まで、誰のどんな記述かを保つ

#### 提案0（論点106）

**原文を残す時に、語だけでなく話者と出典も保つ。本人の原文、依頼/設定の説明、assistantの整理を読み分けられる形で保存し、別の記録へ写しても帰属を変えない。** 記録規約へその書き方を置き、growの受入れ/発言の受渡しと正本の雛形から繋ぐ。

##### C3で、実際にどう書き分けるか

| 内容 | 保存する姿 |
| --- | --- |
| 「仕事帰りに、いつも使うペンの替芯を買いに行った。」で始まるアイデア | 検査用の当人C3の原文として引用する。実際の利用者への調査結果とはしない |
| 黒0.5mmの替芯、来週までに1組という動機の補足 | 「設定の地の文から整理した動機」とし、元の記載へ結ぶ。本人がそう話したquoteにはしない |
| 原入力からこちらが読み取った望みや原因 | assistantの解釈/仮説と根拠を示す。元にない経験や動機を本人の言葉として追加しない |

原の文面は案件内に保持し、抜粋・整理からその箇所へ辿れるようにする。本人の原文は原文のまま使え、説明の要約も整理と分かれば使える。通常の短い発言へ全行の分類や再質問を要求せず、混ざるblockの境界が分かる見出し等で足りる。新しい入力台帳や固定の分類schemaは作らない。

話者や由来が分からない文は未確認と残し、判断がそこへ依存する時だけ認識合わせへ返す。本人の動機・体験・採否を補作しない。依頼文に含まれる他人の引用も、今回その人へ直接聞いた返答には替えない。

**記述者が分かることと、内容を事実として確かめたことも分ける。** 例えば、提案への「ok」はその判断への採用として原文を記録するが、提示外の解釈や未取得の事実を確認したことにはしない。試運転の設定や役の採否は、実際の利用者の経験/採用の証拠にしない。

##### 元の一件へ戻すと、何が違ったか

N（現状）には、既に二人が読める献立メモと、D2の変更希望を伝えるメッセージがあった。Pはそこへ日付/本人/希望/不明の追記と同じ記述の引用を足す。「共有出来る」「変更を伝えられる」だけは、現状に無かった改善として数えられない。卵/玉ねぎが分からず、残りを食べたことが繋がらない点も残る。
