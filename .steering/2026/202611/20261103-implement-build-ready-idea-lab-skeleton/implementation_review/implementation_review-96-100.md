### イテレーション0（論点96）: 根拠・着想・不足の違いを、受け取る判断まで保つ

#### 提案0（論点96）

**採用したgather-target-user-voicesを、各層からの依頼・受領と、候補へ使う根拠に接続する八fileの変更集合を採用する。**

現在はBの実行方法の詳細化である。78で採用した本文はそのまま使い、今回決めるのは、その本文へ何を頼み、返った根拠・着想・不足を次の判断へどう使うかと案内・登録の同期である。
共通の一覧に名前があることや、材料が出来たことだけでは、その層の成立にはしない。

##### 各層が、返った違いを何の判断へ使うか

```text
層：対象・問題意識、止まる判断、既知の記録と粒度を渡す
  |
  v
体験探索：確認した経験と文脈／候補への着想／不足と限界を返す
  |
  +--> why       ：価値の仮説と、本人へ戻す問いを育てる
  +--> what      ：条件群へ当てる場面と、確認すべき事実へ使う
  +--> how-to-solve：候補と成立の前提の比較へ使う
  +--> how-to-build：同じ版の体験・規則・情報の設計へ照合する
  |
  v
各層：自分の方法で吟味・採否し、不足又は別の判断へ返す
```

whyは仮説が完成する前にも頼める。別の人の良い体験から価値を広げても、それを本人の望みとして確定しない。
whatは、条件が全部真でも言い分が崩れる場面を作り、経験から得たことと反例のための追加仮定を分ける。経験の未取得は論理的な反例の吟味を妨げないが、作った場面を観測済みの事実にはしない。
how-to-solveは、実際のしのぎ方と勧めの着想を分けてpropose-alternativesへ渡す。経験の根拠が無い時も候補を全部落とさず、続くことの判断に必要な不足と、候補を広げる材料として使える所を分ける。
how-to-buildは、想定する理解・引受け・完了の前提を照合する。選定の決め手・条件・価値を変える差は、その判断を持つ層へ返す。

例えば「署名する予定」は署名完了の根拠ではない。「共有calendarがよい」という解説の勧めは候補に残せるが、別の家族が自ら取り込み・引き受け続けた経験にはならない。
本人の事情は本人へ、現在の機能・規則・費用は該当する根拠へ戻す。本人との対話や提供記録で足りる用途に、外部調査を一律に足さない。

## 論点100: Cの一式試運転を、どの題材と区切りで進めるか

### イテレーション0（論点100）: 新しい入力から実物の成果と出口を作り、小さく検査する

#### 提案0（論点100）

**新しい三つの題材を、growの受け入れから出口まで一件ずつ通す。各層と専門の返りがまとまるたびに検査し、最後は実物の成果からCの成立と未確認を判じる。**

今回の採否は、以下の題材・実行方法・検査の区切り・保存先と実行前の準備を、一式試運転の具体案として採るかである。Bの役割や方法の再合意には戻らず、99で残した「新しい一件で実際に使えるか」を確かめる。

##### Cで使う新しい三つの入口

最初の三件は次とする。全てassistantが用意する検査用の題材であり、この利用者本人の体験や望みとして扱わない。出口は実際の検討で決める。

| 題材と受け入れる着想 | 入口に置く具体の事情と、この件で確かめる違い |
| --- | --- |
| C1：自作のカードゲームで、ルールを変えた時の遊び方を試したい | 小さな自作の一人用ゲームを、カードを手で並べて試している。ルールの違いで途中の選択がどう変わるかを見ることと、自分の道具を作ることにも楽しみがある。既存のゲーム規則・手で行った一回・試したい違いを入力へ残し、価値を先に選び、その後で紙・表計算・小さな道具等を比較する。作る楽しみだけで選ぶ部分があれば、その理由を独立して残す |
| C2：二人で夕食を選ぶ楽しみを保ち、平日の確認と買い足しを減らしたい | 週末の相談は好きだが、平日は食材と予定を相手へ確認し直している。二人が使える共有メモが既にあり、新しいものを作ること自体には強い動機が無い。一回の相談から買物・調理・変更までの出来事と本人役の認識を入力へ置き、人の決め方や既存道具で届く道と作る道を同じ条件で比べる |
| C3：欲しい物を探して複数の店舗を回る空振りを減らしたい | 最新の在庫が分かれば行先を選べそうという着想があるが、対象店舗の情報取得方法と利用条件は未確認。毎回調べ直す時間や費用にも限りがある。直接確認・既存のサービス・対象を絞る部分案も比較し、取得していない在庫やAPIをあるものとして進めず、保留なら何が分かると再開できるかまで残す |

三件は初期の検査集合である。各件へ「作る・作らない・保留」をあらかじめ割り当てない。全件が同じ出口へ向かえば、その結果を保持し、まだ通していない経路をどう追加で確かめるかを結果付きで提案する。特に、作る版を設計・引継ぎまで通せなければ、その受け入れ条件は未達のままとする。

##### 入力と利用者役を、結果より先に置く

各件の受け入れ前に、元のアイデア・動機・着想、一回の体験、当時の認識と今の評価、既存道具と使い方、時間・費用・環境の制約、既知の事実と未確認を入力用fileへ残す。C1の規則の全文もここで固定し、logicを作る段で都合よく補わない。選ぶ価値や手段・出口の正解は先に書かない。
利用者への問いと採否はassistantが当人役を演じ、各件のdiscussionで「検査用の利用者役の応答」と明示する。採否の理由は固定した望み・制約へ結び、実在の利用者の合意へ替えない。追加の入力が必要なら、旧入力で止まった所・不足・追加理由を残し、追加前にも通ったようには記録しない。
C1の実行対象の候補は、今回使えるローカルの検査環境である。別PCへの導入は対象にせず、実行時のOS・runtime等を確認してから設計の条件へする。これは77の未特定の家のPCが検証済みになった意味ではない。C2・C3も実在のサービスの機能や技術を使う判断なら、検査用の語りだけでその性質を保証しない。

##### 実際に作る成果と、区切りごとの検査

`grow-product-idea`の受け入れから一件ずつ進める。入力用fileから既成の条件や材料・結論を写す方法にはしない。各層と専門の本文を実際に使い、依頼・返り・根拠と判断の更新を残す。

```text
入力と環境を固定 → growの受け入れ
  → whyを探索・選択して閉じる
  → whatを導出・判定して閉じる
  → how-to-solveで比較し、版と得失を選ぶ
       ├─ 作る部分あり → how-to-buildで設計・裏づけ・引継ぎ
       ├─ 作らない     → 実際の行いと担い手を伴う出口
       └─ 保留         → 不足・理由・再開条件を伴う出口
  → 案件内の読み切れと、残る検証を判定

専門の返りごと・層の閉じごとに、次が使えるか検査する
  適用漏れ → その出力を直し、影響する接続を再検査
  方法の欠け → 実際の入力と返りを残し、影響するA／Bへ戻す
```

| 区切り | 次へ渡す具体の成果と、その場で確かめること |
| --- | --- |
| whyの閉じ | 体験から問いが育ち、価値の候補と範囲を広げて比べ、選んだ姿・大きさ・測りと理由が残る。最初の着想を目標に直結させず、畳んだ時に失った良さを元の一回へ戻して確かめる |
| whatの閉じ | 各言い分から条件を導き、全部真でも崩れる場面へ当てる。違う手段を同じ入力で、何の根拠から通し又は落としたかを残す。条件・案の説明・事実・価値の不足を分ける |
| 専門材料の返りと選定 | 候補の幅と強い非開発案、独立した改善のある部分案、意味のある別の作り方を比較する。事実と出典、同じ期間の費用・負担、未達と未確認を受け、何の判断・値を更新したかまで残す |
| 作る版の設計 | 必要な全場面と境界を並べ、表示・操作のラフ、中核の入力と規則、情報の具体の読取りと変更、機能と実装構成、必要な技術の根拠を繋ぐ。比較用の粗い材料だけで詳細を済ませない。画面を持つ版は必要な全画面と状態、CLI等ならその入力・表示・失敗後の操作を同じ粒度で具体化する |
| 設計の一巡と引継ぎ | 同じ一件の値で操作→規則→保存→次の処理と人の行いを通す。入力の変更・中断・失敗で、残る情報から続けられるかを確かめる。導入・訂正・復旧、取得済みの裏づけ、実装後の受入れ、委ねる裁量と再判断の線を渡す |
| 案件の出口 | 正本・層の記録・材料と決定過程から、価値・条件・選定と設計・根拠と限界を読める。必要な本質的判断を実装者へ残さない。必要な根拠が無い版は閉じず、未実施を合格にしない |

例えばラフが選択と残時間を使うのに保存から読めなければ、その材料の返りで情報へ戻す。構成で照合する部品や人の行いが増えれば、費用を更新して選定の境目へ戻す。各材料の単体の自己評価だけで次へ進めず、依頼側が具体の値を使って読み戻す。最後に初めて問題を見つける進め方にはしない。
新しい専門が必要なら、その件で何が決められないかを根拠に返し、archiveを順に復元しない。必要な方法の改稿は既存のimplementation_reviewで採否を扱い、元の案件の不足も直して影響する区切りを再検査する。既に安定している無関係なブロックまでは作り直さない。

##### 保存する場所と、作る二fileの構成

全体の観測の入口と検査用の入力を二fileへ分ける。各件は既存の配置・雛形と議論の方法を使い、このsteering直下の`product-plans/`へ残す。slugは受け入れ時の既存の命名手順で確定する。

```text
│   └── inputs.md       検査用の初期入力・当人役と制約

    └── <各件のslug>/   正本・層の記録・議論・専門材料
```

`integration-check/README.md`の構成は次とする。

```text

├── 検査する範囲      採用した計画と、何を主張する検査か
├── 起動と環境の観測  読んだ入口・skillと版、実際の環境・未確認
├── 各件の入口と結果  案件内の成果への導線、実際の出口と到達点
├── 継ぎ目の摩擦      入力・使った方法・返りの差、原因と修正・再検査
```

`integration-check/inputs.md`は「検査用設定と利用者役の範囲」「C1」「C2」「C3」「入力の追加・変更」の構成にする。各件には受け入れ前の具体の体験と望み、規則・道具・環境と制約、既知と未知を置き、最後に追加の理由と旧入力の到達点を残す。期待する出口や、選ばせるための完成済みの案は置かない。
案件の判断に必要な入力の要点は、各件の内側にも残す。外の検査用入力又はレールのfileを見ないと判断を読めない製品の正本にはしない。原資料の出典URLは使った要点・対象と時点・限界を案件内へ残した上で辿れるようにする。
