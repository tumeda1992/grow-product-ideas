# 議論記録（論点16〜20）

## 論点16: 材料の中身が薄く、専門の仕事として機能していない

**ステータス:** 決定

**種別:** レビュー指摘

### イテレーション0（論点16）: 原因の切り分けと、材料に水準を持たせる方向

#### 提案0（論点16）

利用者の指摘: 材料の`README.md`は大したことが書かれていない。skillがやっつけ仕事をしたのか、期待もこの程度だったのか。材料は問いにおいて専門分野を扱う存在だから、問いではなく材料として置かれたのではなかったか。directoryに`README.md`しか無いなら、directoryは要らない。

##### 原因

二つが重なっている。

| 原因 | 中身 |
| --- | --- |
| 作った時の手抜き | 材料は前回の自演でassistantが手順を通さずに書いた。例えば`cost-comparison`の「約16時間」は、画面や操作ごとの内訳も、比べた過去の実績も無く、「確かめた方法と限界」は「概算した」の一文である |
| レールの設計の欠け | 材料には水準（満たさない例）が無い。問いには水準があり、`settle-question`が書いた後に確かめるが、材料の質は誰も確かめない。さらに`what-defines-a-product/README.md`の「問いを閉じるのに足りる最小の粒度で作る」は、薄く作ることを許す方向に読める。材料skillの本文も約2KBで、専門の仕事の深さ（例: テーブル構成なら、画面が出す情報を全てクエリで引けるかの確かめ）を持っていない |

手抜きだけなら作り直せば済むが、設計の欠けがあるため、手順どおりに動かしても同じ薄さになりうる。

##### 期待されていたもの

材料を問いと分けたのは、問いが「詰めれば決まる判断」を持ち、材料が判断の根拠になる専門の仕事（調査、見積り、体験の設計、ロジック・テーブル・モジュールの設計、技術検証）を持つためである（`what-defines-a-product/README.md`の「材料skillは、材料を作るだけで、問いへ答えない」）。各問いの定石の「個人版への翻訳」は、専門の手法を個人でどう代替するかを書いており、その実際の仕事を行うのが材料skillである。期待は、利用者の指摘のとおり、専門分野の仕事が材料に積もることだった。今の材料はそれに届いていない。

##### 方向

1. 材料ごとに水準を持たせる。材料skillの本文に、その材料の「満たさない例」と、専門の仕事として行う確かめ（例: `cost-comparison`は画面・操作ごとの内訳と比べた実績、`tables`は画面の情報を引くクエリと例の行、`core-logic`は境界の例を入れた入出力表）を足す。品質は作る時に担保し、`settle-question`の手順2で、材料を使う前に水準に照らして漏れを確かめる。
2. 「最小の粒度」の書き方を、「問いを閉じるのに要る粒度で止め、その粒度の中では専門の仕事として省かない」へ改める。粒度は範囲の広さであり、深さを薄くしてよい意味ではないことを明示する。
3. 置き方は、中身が決まってから決める。既定を`materials/<識別子>.md`の一つのfileにし、付随file（技術検証のcode、ラフ画の画像、案ごとの詳細）ができた時にdirectory（`materials/<識別子>/README.md`）へ育てる案を推す。ただし1と2で中身が厚くなれば、案ごとにfileが分かれ、directoryが自然に要る可能性もある。

1と2を先に決め、振替の模型の材料を一つ（`cost-comparison`）作り直して、厚さと置き方を確かめてから3を決める。

#### 検討記録（論点16・イテレーション0）

模型の材料8種は、前回の自演の材料をidentifierだけ直して写したもので、模型を作る時に中身を見直していなかった。模型が「できてほしい形」を示すものである以上、材料も期待する厚さで当てるべきだった。

#### 提案0へのフィードバック（論点16）

**結果:** 修正要求（材料の案の質への追加の指摘）

> 選択肢が他人事でしか書いてないし選択肢もうっすいしその後の深堀りもない

利用者は提案0への応答の前に、材料（`cost-comparison`）の中身へ追加で指摘した。提案0の原因の表は「内訳が無い」等の欠けを挙げたが、案そのものの質（誰の生活の中の案か、案の幅、選んだ後の深掘り）を見ていなかった。

### イテレーション1（論点16）: 材料の案が持つべき三つの質

#### 提案1（論点16）

##### 指摘を`cost-comparison`に当てる

| 指摘 | `cost-comparison`で起きていること |
| --- | --- |
| 他人事 | 「狭く取る」「主要な場面を一通り」「周辺まで含める」は、どのアイデアにも当てはまる一般の区切りを並べただけである。この家族の生活（妻が欠席連絡の直後に登録する、夫は平日夜しか見ない、規則の変更は年度初め）のどこを切るかで案が立っていない |
| 案が薄い | 案は作る時間の大小で並んだ一つの軸の上の三点であり、違う考え方の案（例: 登録をやめて教室のLINEの転送から拾う、規則の計算をやめて期限だけ手で入れる、妻ではなく夫が登録する前提で作る）が無い |
| 深掘りが無い | 案ごとに一行で終わり、選ばれそうな案について、内訳、効く前提、崩れる条件、その案で残る痛みを掘っていない |

模型の問いの決着の記録の「答えに至った筋」も、採らなかった見方を一文で片付けており、同じ欠けを持つ。

##### 材料の水準に入れるもの

提案0の1（材料に水準を持たせる）に、案の質として次の三つを、材料skillの共通の水準として入れる。材料ごとの専門の確かめ（内訳、クエリ、境界の例）はその上に足す。

| 質 | 満たさない例 | 満たす形 |
| --- | --- | --- |
| このアイデアの中で立つ | 「狭く・中くらい・広く」のような、どのアイデアにも当てはまる区切り | 案ごとに、このアイデアの誰が、どの場面で、何をするかが書かれ、受け入れ時の入力・閉じた問いの答え・前提にする条件のどれに基づくかが分かる |
| 考え方の違う案がある | 一つの軸（時間、範囲の大小）の上に並んだ案だけ | 少なくとも一つ、前提を変えた案（やめる、別の人がやる、別の場所に置く等）がある。前提を変えた案を退ける時は理由を書く |
| 有力な案を掘る | 案ごとに一行 | 有力な案（最終的に選ばれうる案、二つ以上）ごとに、中身の内訳、効く前提、崩れる条件、その案で残る痛みが書かれている |

この三つは問いの決着の記録の「答えに至った筋」にも当てる。採らなかった案を一文で片付けず、なぜ退けたかを、効く前提と崩れる条件で書く。

##### 進め方

提案0の進め方を保つ。共通の水準と`compare-build-and-alternative-costs`の水準を書き、振替の模型の`cost-comparison`を作り直して見せる。厚さと置き方（提案0の3）はそれを見て決める。

#### 検討記録（論点16・イテレーション1）

指摘の三つは、材料skillが「専門の仕事」をする時の中身そのものである。専門家の見積りや設計は、相手の状況から案を立て、前提の違う案を比べ、有力な案を掘る。今の材料は、案の形（表）だけがあり、この仕事をしていない。

### イテレーション3（論点16）: 前回designが材料skillに見込んだことと、今のskillの差

#### 提案3（論点16）

##### 見込んだことと、今のskill

前回design（`.steering/2026/202609/20260912-design-build-ready-idea-lab-skeleton/design.md`）は、材料skillに次を見込んでいた。

| 見込んだこと | 前回designの記述 | 今のskill |
| --- | --- | --- |
| 世間の一般通説を、個人開発の制約下で実行できる形で取り込む | 「プロセスが我流で、外部の知見が入っていない」を解く問題に挙げ、定石に「一般通説の手法、個人版の代替、落ちる精度」を持たせた | 一般通説の手法は、問いの定石に一行の名前（「機能の規模から工数を見積もる手法」等）で置かれただけで、その手法を個人版でどう行うかの手順はどのskillにも無い。材料skillは手法を持たない |
| 生成系の材料skillは厚い | 体験とラフ画、心臓部ロジックを「厚い」、テーブル・モジュールを「中」とし、厚さは失敗が起きやすいかで決めるとした | 厚いはずの`sketch-experience`（約2.7KB）、`design-core-logic`（約2.2KB）が、薄いはずの調査系（約2KB）と同じ厚さである |
| 定石の構成パターンの参照先を持つ | 体験とラフ画、テーブル構成に「定石の構成パターンの参照先」を挙げた | 参照先は問いの定石（選択肢の一覧）であり、構成パターンそのもの（例: 体験の流れの描き方、画面遷移の型、テーブルの正規化と出来事の記録の型）は無い |
| 品質は作る時に担保する | 論点2以降で原則として決めた | 材料には水準が無かった（論点16で共通の水準と`cost-comparison`だけ足した） |

前回designは「判断基準を内蔵するかどうかは立てる条件ではない。厚さの問題であり、中身は問いのセット側が持てばよい」とした。問いの定石は「答えの選択肢と判断軸」であり、材料を作る専門の仕事のやり方ではない。材料の中身を問いのセット側が持つという前提が、材料skillでは成り立っていなかった。そのため、skillの本文は置き場所と手順の骨組みだけになった。

今のskillのままでは、前回designが見込んだこと（一般通説の取り込み、生成系の厚さ、作る時の品質）は実現できない。

##### 直し方

材料skillを、専門の仕事のやり方を持つskillとして書き直す。各skillに次を持たせる。

| 持つもの | 中身 |
| --- | --- |
| 支える判断 | どの問いのどの判断の根拠になるか。判断に効かない作業をしない |
| 専門の手法と個人版 | 一般通説の手法（例: 見積りなら部品分解と実績比較、体験なら利用場面の時系列とつまずきの洗い出し、テーブルなら画面の情報からの実体の抜き出しと例の行での確かめ）を、個人開発で行う具体的な手順にしたもの。落ちる精度 |
| 水準 | 共通の水準に加えて、その材料の満たさない例 |
| 利用者の事実 | 利用者しか持たない事実が要る時に、`settle-question`へ返して問う（イテレーション2の見つかったこと1） |
| 書き方 | 材料の入口の形に加えて、その材料の中身の見出し |

厚さは前回designの見込み（生成系の体験・心臓部は厚く、テーブル・モジュールは中、調査系は薄い）を目安にするが、薄い調査系でも手法と水準は省かない。

##### 進め方

1. この構成で`sketch-experience`を一つ書き直す（生成系で最も厚く、最も多くの問いが使うため）。`tumeda-dev`の`skill-update-review`で工程の切り出しを確かめる。
2. 利用者がその一つを確かめた後、残りの7つを同じ構成で書き直す。`compare-build-and-alternative-costs`もイテレーション2で足した水準に手法を足す。
3. skillを書き直した後はsessionを再開し、振替の模型の材料を、skillを起動して作り直す。材料が変われば、それを使う問いを答え直す。

#### 検討記録（論点16・イテレーション3）

前回designのskill一覧の表を読み直すと、「持つもの」の欄は手順の名前（全画面を一度に並べる、複数案を作る）を挙げており、今のskillはその名前を本文に写した。手順の名前を写すことと、その手順を専門の仕事として行えることは別である。今回のskillは前者で止まっていた。

### イテレーション4（論点16）: `cost-comparison`一つを、振替の件の中で吟味しきる

#### 提案4（論点16）

##### 一つ目に選ぶもの

`compare-build-and-alternative-costs`（材料`cost-comparison`）にする。既に作り直しを始めており、振替の件の中で三つの問い（スコープ、最初に作る分、費用）が実際に使う。使う側と下流の判断がそろっているため、環境に合うかを確かめられる。

##### 吟味しきった状態

次が全てそろった時を、一つ目が終わった状態とする。

- 振替の件の三つの問いを、作り直した`cost-comparison`で答え直し、材料の薄さを答えの側で補っていない（答え直しで、材料に足りないものが出なくなる）
- 材料skillの本文が、その材料を作るのに要ったこと（この家族の場面の読み方、前提を変えた案の立て方、内訳と比べる先、利用者の実績が無い時の扱い）を持ち、skillを起動し直すと同じ厚さの材料ができる
- 利用者が、材料と答え直した問いを確かめた

##### その後

一つ目で要ったもののうち、他の材料skillにも要るかを、他の材料ごとに振替の件で確かめてから足す。共通にできるものだけを共通にし（例: 論点16で先に書いた「材料の水準」の共通の四つの質も、ここで本当に共通かを確かめ直す）、他は材料ごとに考える。共通の構成を先に決めて当てない。

#### 検討記録（論点16・イテレーション4）

前回skill群を作った時も、designの表の項目名を全skillへ同じ形で写して薄いskill群を作った。提案3は同じ型を繰り返していた。先に足した共通の水準（イテレーション2）も、一つの材料で確かめる前に共通として置いたものであり、一つ目を吟味した結果で見直す対象に含める。

### 決定（論点16）

#### 提案0（論点17）

前回steering（[design.md](../../../202609/20260912-design-build-ready-idea-lab-skeleton/design.md)、[task-design-discussion.md](../../../202609/20260912-design-build-ready-idea-lab-skeleton/task-design-discussion.md)）の記録から、四つを整理した。直し方はまだ出さない。この整理が利用者の認識と合っているかを確かめたい。

##### 1. 実現したいこと

利用者が「自分の中では弱い」と挙げた領域の一つである（task-design-discussion.md 586行付近の原文）。

> 代案を考えて、競合調査やあり物の組み合わせを考えて、それをプロダクトとして作るのと比べて構築コストと、代案のランニングコストどちらが高いとか

背景の診断は、紆余曲折が「払わなくてよい思考コスト」として現れていることで、その一つが「対案を比べていない」（思いつきをそのまま適用する。対案が無いのは知識不足ではなく、対案を出す工程がプロセスに無いため）だった。作る費用と代案の費用の比較は、情報を集めて比べれば答えが出る「詰将棋」の側にあり、寝かせる頭（苗床）を使わずにレールが詰めるものとされた。

まとめると、実現したいことは「作るか代案で済ませるかを、思いつきや気分ではなく、作る費用と代案を使い続ける費用を比べた根拠で決められること。しかも利用者の頭を使わずに」と読んだ。

##### 2. 実現の考え方

| 考え方 | 記録 |

##### 整理していて気づいたこと（認識を揃えたい点）

直し方ではなく、この整理が今の状況とどうずれているかである。

- 前回steeringが挙げたアンチパターンは、比べる「枠」（比べるか、尺度、ラフの有無、精度、作り込み）に関するものだけで、比べる「中身」の質（論点16で利用者が指摘した、他人事の案、一つの軸の上の薄い案、深掘りの無さ）は挙がっていなかった。

- 「粒度は最小」は、論点16で「範囲は最小、その中の専門の仕事は省かない」と読み替えたが、前回steeringの「作りすぎると苗床を空ける目的に逆行する」の苗床は利用者の頭のことであり、レールが材料を厚く作ることは苗床を使わない。前回steeringの最小は、レール側の手間を減らす意味ではなかったと読める。

## 論点18: 材料`cost-comparison`は、振替の件の三つの判断それぞれに何を渡せば、判断が思いつきでなくなるか

**ステータス:** 決定

**親論点:** 論点16

**種別:** 認識合わせ

### イテレーション0（論点18）: 使う側の判断から、材料が渡すべきものを決める

#### 提案0（論点18）

skillの書き方の前に、この材料を使う側（振替の件で`cost-comparison`を要求する三つの問い）が、何を判断し、そのために材料から何を受け取る必要があるかを揃える。材料skillが持つべき中身は、ここから決まる。

##### 三つの判断と、材料が渡すべきもの

| 問い | 判断 | 思いつきで決まる時の形 | 材料が渡すべきもの |
| --- | --- | --- | --- |
| スコープの内と外 | この家族の場面のどこまでを仕組みに任せ、どこを人や代案に残すか | 「予約の代行は大変そうだから外」。どれだけ大変か、外にした時に誰が何を払うかが無い | 場面の任せ方ごとの作る時間と、任せなかった場面を誰がどれだけの手間で払い続けるか。前提を変えた任せ方（登録をやめる、計算をやめる） |
| 最初に作る分 | 痛みの核心の場面（夫が代われる）が一度通る、最も小さい切り方はどれか | 「MVPは通知だけ」。核心の場面が通るかと、切り方ごとの時間の差が無い | 切り方ごとの作る時間と、その切り方で核心の場面が通るか、通らない時に何が欠けるか |
| 費用は見合うか | 最初に作る分を作るか、代案を使い続けるか。負けた時に、得たいものと照らして続けるか | 「週末で作れるし、楽しいから作る」。作る費用と代案の費用が同じ尺度に無く、楽しみが費用に混ざる | 同じ尺度に揃えた、作る費用（作る時間と保守）と代案の費用（誰の手間か）。逆転するかと、その前提が崩れる条件。見積りの確からしさ |

##### 見積りの確からしさをどう出すか

三つの判断とも、見積りの数字がどれだけ確かかで判断の重みが変わる（論点17の「精度が落ちたことを自覚しない」）。一般通説の見積りの手法には、次がある。

| 手法 | 中身 | 個人開発での形の候補 |
| --- | --- | --- |
| 部品に分けて積む | 作るものを部品に分け、部品ごとに見積もって足す | ラフ画と心臓部ロジックから、画面・操作・ロジック・外部連携の部品に分ける |
| 似たものと比べる | 過去に作った似たものの実績と比べる | 利用者が過去に作ったものの実績。利用者しか持たない事実であり、材料skillは問えない（論点16の見つかったこと1） |
| 幅で出す | 楽観・最も確か・悲観の三点で出す | 部品ごとに三点で出し、合計の幅を判断へ渡す。「±50%」の一言で済ませない |
| 使い続ける費用まで含める | 作った後の保守、運用、依存先の変化まで含めた総額で比べる | 保守を部品（依存先の追従、不具合、データの手当て）に分ける |

この表は、どの手法を採るかを決めるものではなく、「確からしさ」を渡すために一般通説に何があるかを揃えるためのものである。

##### 揃えたいこと

- 三つの判断と、材料が渡すべきものの整理が、利用者の考えと合っているか
- 見積りの確からしさを判断へ渡すことが要るか。要るなら、上の手法の中に、この家族の件で効きそうなものがあるか（特に「似たものと比べる」に使える、利用者が過去に作ったものがあるか）

#### 検討記録（論点18・イテレーション0）

論点17の整理では、前回steeringは比べる枠（比べるか、尺度、ラフの有無）を決め、比べる中身を決めていなかった。中身を決めるには、材料を使う側の判断から逆に辿るのが早い。振替の件では、`cost-comparison`は三つの問いから要求されており、判断の形がそれぞれ違う。

#### 提案0へのフィードバック（論点18）

**結果:** 修正要求（目的の取り違えと、表層の問い）

> ん？目的って判断が思いつきじゃなくなることなの？ あと、表層しか見ていない感じが問いからうかがえるんだけど

提案0は、目的を「判断が思いつきでなくなること」と置き、三つの問いの題を判断として言い直しただけだった。「思いつきだとこうなる」の例も、問いの題から作った藁人形であり、利用者の実際の紆余曲折から来ていない。

### イテレーション1（論点18）: 痛みの本体に戻って、この材料の目的を置き直す

#### 提案1（論点18）

##### 前回steeringが痛みの本体として閉じたこと

前回steeringの論点（[task-design-discussion.md](../../../202609/20260912-design-build-ready-idea-lab-skeleton/task-design-discussion.md) 845行付近）は、痛みを次のように閉じていた。

- 痛みの本体は「全部で2ヶ月くらい土日が溶ける」であり、作る量の問題である。どう作るかをいくら精緻にしても、作る量そのものは減らない
- 痛みの所在は、作るか／どれだけ作るかという判断にある
- 作ると決める時点が早いため、苗床の使い先が「作ると決めた後」へ寄っている
- 利用者が弱いと挙げた領域の多くは、「作らない・作る量を減らす」方向の選択肢を持つ判断である

##### この材料の目的の置き直し

「判断が思いつきでなくなる」は手段の言い方であり、目的ではない。この材料の目的は、作ると決める前に、何をどれだけ作るとどれだけの土日が溶けるかと、作らずに済ませると誰が何を払い続けるかを見えるようにし、作る量を決められる（減らす・作らないを含めて）ようにすることだと読んだ。

そうすると、この材料が見るべきものが変わる。

| 提案0の見方 | 置き直した見方 |
| --- | --- |
| 三つの問いがそれぞれ何を判断するか | 作る量をどこに置くと、溶ける土日と、残る痛みがどう変わるか。三つの問いは、作る量を決める同じ判断の、範囲（スコープ）・順番（最初に作る分）・総額（費用）の三つの切り口 |
| 見積りの数字の確からしさ | 見積りが、実際に溶ける時間と同じものを数えているか。2ヶ月という結果は、見積りに入っていない時間（パッチワークの継ぎ足し、後から見直したテーブルや体験の作り直し）から来ている可能性がある |
| 作る費用と代案の費用を並べる | 作る量を減らした時に、減らした分を誰が何で払うか（代案、運用、我慢）まで並べ、減らす方向の選択肢を材料の側から出す |

##### 確かめたいこと

この置き直しが合っているかに加えて、利用者の過去の紆余曲折について一つ確かめたい。表層ではなく、見積りが実際とずれる仕組みを知るためである。

- 過去に作った時、作り始める前に「どれくらいで作れる」と思っていたか。それが2ヶ月の土日になった時、どこで時間が増えたか（作り直し、継ぎ足し、想定外の部品、保守、それ以外）

#### 検討記録（論点18・イテレーション1）

論点17で、前回steeringの記録から実現したいことを整理したが、提案0ではその整理のうち「対案を比べていない」だけを拾い、痛みの本体（作る量、作ると決める時点の早さ）を落とした。問いの題から判断を言い直したため、利用者の実際の紆余曲折から材料の中身を決める筋が無かった。

#### 提案1へのフィードバック（論点18）

**結果:** 修正要求（目的は対案を挙げること）

> 目的の置き直しもピントずれてる。浮いたから何か、という結果で挙げているけどその結果は私の生活だからこのシステムの外。シンプルに対案を挙げることが目的。作りたいものをmust,betterとかで分解して、mustだけ満たすならこの方法でできると提案するとか、betterも合わせてあり物の組み合わせで実現するとか。あと、このスキル終わった後、他のスキル行く前にwhyとかhowの整理もやっつけなんじゃないかと疑いを持ったから、そっちに移行するよう論点作るとか、進め方のところに書くとか忘れないようにしておいて

提案1は、目的を「溶ける土日が見え、作る量を決められること」と置いたが、それは利用者の生活の結果であり、このレールの外にある。利用者は、この材料の目的を、対案を挙げることだと示した。

後半の指示（このskillの後、他の材料skillへ進む前に、why・howの層の整理を見直す）は、論点19として保留の論点に立てた。

### イテレーション2（論点18）: 作りたいものを分解し、満たす範囲ごとに対案を挙げる

#### 提案2（論点18）

##### 目的

この材料の目的は、対案を挙げることである。作りたいものを要求の重み（must、better）で分解し、満たす範囲ごとに、それを実現する道を対案として挙げる。

振替の件に当てると、次の形になる。

| 満たす範囲 | 対案の例 | その道で満たすもの・満たさないもの | 費用 |
| --- | --- | --- | --- |
| mustだけ | 共有表計算に規則の計算式を書き、期限が近い行を共有カレンダーの予定にする | 期限の計算と二人での共有は満たす。期限前の知らせは予定の通知で満たす。入力は手で残る | 作る時間と、使い続ける手間 |
| mustとbetter | あり物の組み合わせ（共有表計算＋自動化サービスでLINEへ知らせる、等）で実現する | … | … |
| mustとbetter | mustはあり物で済ませ、あり物で満たせない一部だけを作る | … | … |
| mustとbetter | 全部を作る | … | … |

費用（作る時間、使い続ける手間）は、対案を比べるための一つの軸であり、目的ではない。

##### 確かめたいこと

- 目的をこう置くことで合っているか
- must・betterの分解は、何を作るか層の要求の問い（`what-to-build/requirements`）の答え（必須とあれば嬉しい）を使うことでよいか。今は費用の問いが`how-far-to-build`にあり、要求の後に来るため、分解は手元にある
- 既にある材料`existing-alternatives`（代案の候補ごとに痛みのどこが残るか）との違いは、`existing-alternatives`が候補を一つずつ見るのに対し、この材料は候補を組み合わせ、満たす範囲ごとの道にする点だと読んだ。この線引きでよいか

#### 検討記録（論点18・イテレーション2）

提案0は判断の質、提案1は利用者の生活の結果へ目的を置き、どちらもこのレールが作るものから離れていた。レールが作るのは材料であり、材料の目的は材料が何を差し出すかで言う。この材料が差し出すのは対案である。

#### 提案2へのフィードバック（論点18）

**結果:** 修正要求（目的は合意。周りの前提を吟味していない）

> 目的は合ってる。must,betterのことについても唯々諾々と受け流しているけどこのスキルとして吟味対象。howとwhyも同様。whatもhow-farも。あなたopusだから期待しているのに考えずに脊髄反射で発言しているよね

目的（対案を挙げること）は合意された。提案2は、must・betterの分解を「要求の問いの答えが手元にある」という置き場所の都合で受け入れ、このskillが対案を挙げるのに、その分解と、各層（why、what、how-far、how）の答えが合っているかを吟味していなかった。

### イテレーション3（論点18）: 対案を挙げるために、周りの層の答えと並びが合っているか

#### 提案3（論点18）

目的から逆に辿り、このskillが対案を挙げるのに要るものと、今の層の答えと並びを照らした。直し方ではなく、吟味で見つかったことである。

##### 1. must・betterの分解（what: 要求）

| 見つかったこと | 中身 |
| --- | --- |
| 要求は代案を見た後に作られ、代案で解ける所を先に下げている | 要求の水準は「代案で既に解けている場面の要求は、優先度を下げている」とする。要求の前に代案の問いがあり、代案は要求ではなく痛みと比べられる。対案をmust・betterで挙げるには、代案を見る前の、解き方に中立な分解が要る。今の並びでは、mustが既に「代案で解けない所」に寄っており、「mustだけならあり物で足りる」という対案が出にくい |
| 分解が、満たし方を含んだ形で書かれやすい | 水準は「解決策を書かない」とするが、模型のR3「どの端末からも振替の一覧…を見られる」は一覧という形を含む。対案（共有カレンダーで足りる等）を公平に比べるには、満たされる状態（「夫が、予約を代われるだけの情報を自分で見られる」）で書く必要がある |
| mustの線を何で引くかが無い | 定石はMoSCoWの名前だけで、必須と嬉しいの線をどこで引くかの基準が無い。対案の道は線の位置で変わる。線は、痛みの核心（この件では分担）が解けるかで引くことになると考えるが、なぜ作るか層の答えと結び付ける規則が無い |
| 満たすのに払い続ける手間が分解に無い | あり物の対案は、満たし続けるのに誰かが手間を払う（カレンダーに予定を作り続ける）。must・betterごとに「満たした状態を保つのに誰が何を払うか」が見えないと、対案の比較が作る時間と代金だけになる |

##### 2. 対案を挙げる時点（what、how-far）

対案が効くのは、解き方とスコープを決める前である。今の並びでは、このskillが要求される問いのうち、対案が一番効く費用の問いは`how-far-to-build`にあり、解き方（ウェブの一覧とLINE）とスコープが決まった後に来る。その時点で「mustだけなら共有表計算で足りる」という対案を挙げても、解き方は既に選ばれている。

論点12で費用の問いを`how-far-to-build`へ移したのは「作る費用は最初に作る分の画面と操作から見積もる」ためであり、作る費用の見積りの精度を優先した。目的が対案を挙げることなら、対案ごとの粗い費用を解き方の前に出し、最初に作る分が決まった後の費用は精度を上げる確認に回す、という二段になる可能性がある。

##### 3. 対案の重み（why）

対案の比べ方は、なぜ作るか層の二つの答えで変わる。

- 痛み: mustの線は痛みの核心で引く。痛みが道具の形（「通知が欲しい」）で書かれると、mustも道具の形になる。痛みの答えが、満たされる状態で書かれているかが、このskillの入力の質を決める
- 作ることで得たいもの: 作ること自体を得たい時、あり物だけの対案は「作る楽しみを得られない」道になる。対案ごとに、得たいもののどれを満たすかの列が要る

##### 4. 作る部分の費用（how）

対案のうち「一部だけ作る」「全部作る」の費用には、作る部分の粗い形（`experience-sketch`、`core-logic`）が要る。解き方の前に対案を挙げるなら、作る部分の見積りは、解き方の案ごとの粗いラフ画（今の`experience-sketch`の解き方の粒度）で足りるかを確かめる必要がある。「一部だけ作る」の境目（あり物で満たせない所はどこか）は、心臓部（この件では規則の計算）がどこにあるかで決まる。

##### 5. `existing-alternatives`との関係

対案を挙げることが目的なら、`existing-alternatives`（候補を一つずつ、痛みのどこが残るかで見る）と、このskill（候補を組み合わせ、満たす範囲ごとの道にし、費用を付ける）は、同じ目的の前段と後段である。二つのskillに分けておくか、対案を挙げる一つの仕事にまとめるかも吟味の対象になる。

##### 次に揃えたいこと

上の五つのうち、どこから吟味するかを決めたい。私は、1（must・betterの分解）を先にするのがよいと考える。2〜5は、分解が解き方に中立な形で、どの時点にあるかで変わるためである。

### イテレーション4（論点18）: 対案を挙げるための分解を、振替の件で吟味する

#### 提案4（論点18）

##### 分解の単位: 機能ではなく、満たされた状態

対案は、同じものを別の道で満たす提案である。分解が機能（「一覧」「LINEの通知」）で書かれていると、あり物ややり方を変える道が、その機能を持つかでしか比べられない。分解は、満たされた状態で書く。

振替の件を、受け入れ時の入力（期限と残り回数を管理したい、期限前にLINEで通知）と痛み（核心は妻だけが担うこと）から、状態に分解した。

| 状態 | must / better | 線を引いた理由 |
| --- | --- | --- |
| S1 期限が過ぎる前に、二人のどちらかが気づく | must | 満たさないと失効が残る（昨年度5回） |
| S2 夫が、妻に聞かずに、どの子のどの教室の振替がいつまで何回残るかを知れる | must | 痛みの核心（分担）そのもの |
| S3 欠席した時に、期限を規則から出すことが、妻の記憶に頼らない | must | 規則を知るのが妻だけなら、入力も妻に残り、分担が解けない |
| S4 予約済み・使用済みが二人の間でずれない | must | 夫が予約を代わると、二重予約や取り忘れが起きる |
| S5 欠席の連絡の直後に、数十秒で記録できる | better | 無くても核心は解けるが、手間が大きいと続かない（S1〜S4を保つ手間に効く） |
| S6 期限の計算そのものが自動で行われる | better | S3は、規則を二人が見られれば手で計算しても満たせる |
| S7 予約まで任せられる | better | 核心は代われることで、予約の手作業は残ってよい |
| S8 失効を振り返れる | better | 核心に関わらない |

must・betterの線は、痛みの核心が解けるかで引く。そのため、分解には、なぜ作るか層の痛みの答えが要る。

##### 分解から出てくる対案

状態で分解すると、模型に無かった対案が出る。

| 対案 | 満たす範囲 | 作るもの | 満たし続ける手間 |
| --- | --- | --- | --- |
| A やり方を変える: 教室ごとの規則を一枚の共有メモにまとめ、欠席したら連絡した方が共有カレンダーに「振替期限」の予定を作り、予約したら予定の名前を変える | S1・S3・S4。S2は予定を見れば期限は分かるが、残り回数は数えないと分からない | なし | 欠席ごとに約2〜3分。二人のどちらでも |
| B あり物の組み合わせ: 共有のフォームから記録すると共有表計算に行が入り、計算式で期限と残り回数が出る。期限の通知はカレンダーへの反映か、表計算の通知で行う | must全てとS5・S6 | 計算式とフォームの設定 | 欠席ごとに数十秒。規則が変わる時に計算式を直す |
| C 一部だけ作る: Bの記録と一覧はあり物のまま、期限前にLINEへ知らせる小さなscriptだけを書く | must全てとS5・S6、LINEでの知らせ | 定期実行のscript一つ | Bと同じ。scriptの保守 |
| D 全部作る（模型の解き方） | must全てとS5・S6・S8 | ウェブの一覧、規則の計算、通知 | 保守 |

AとBは、模型の代案の表（共有カレンダー、共有表計算）を、痛みのどこが残るかで一つずつ見た時には出なかった。満たす状態ごとに見ると、「規則を共有メモにすれば、S3は作らずに満たせる」ことが見える。

また、この分解で対案を挙げようとすると、専門の知識が要る所が出る。例えば、Cの「LINEへ知らせる」を個人で行う手段として以前よく使われたLINE Notifyは、2025年3月末で提供を終えている（材料として扱う時は出典で確かめる）。対案の実現手段が今も使えるかを確かめることは、このskillの専門の仕事に入る。

##### 吟味で揃えたいこと

- 分解の単位を満たされた状態にし、must・betterの線を痛みの核心で引く、で合っているか
- 「満たし続ける手間」を対案ごとに持つ、で合っているか。あり物ややり方を変える対案は、作らない代わりに人が手間を払い続けて成り立つため
- この分解を、このskillが自分で行うか、要求の問い（`what-to-build/requirements`）の答えを使うか。要求の問いは今、代案を見た後に機能に近い形で書かれており（模型のR1〜R5）、そのままでは上の対案A・Bが出ない

分解を振替の件で実際に行い、そこから対案が出るかを確かめた。模型の要求R1〜R5は、受け入れ時の着想（LINEで通知）と選んだ解き方に引かれた形であり、対案を挙げる入力にはならなかった。模型の要求の問いの記録（`what-to-build/questions/requirements.md`）は「判断は生じず、材料から導いた」と一行で閉じており、論点19の疑いの具体例でもある。

### イテレーション5（論点18）: 分解を誰が持つか

#### 提案5（論点18）

| 問い | 対案として見ると |
| --- | --- |
| 代案 | 作らずに（やり方を変える、あり物で）mustを覆う道があるか |

| リスク | 選んだ道が依存するあり物が、使えなくなった時に何が起きるか |
| スコープ | どの状態を作るものの内で覆い、どれを外（あり物、運用、我慢）に置くか |

どの問いも、「状態ごとに、どの手段で、いつ覆い、誰が何を払い続けるか」という同じ材料の違う切り口を判断している。

##### 推す案

二つを一つの材料skillにまとめ、対案を挙げる仕事を一箇所に置く。材料の中身は次になる。

- 候補の事実: あり物ごとの、できること、制約、費用、今も使えるか（例: LINE Notifyの提供終了）。リスクの問いが依存先の事実として使う
- 覆い方の対案: 要求の状態（must・better）ごとに、やり方を変える・あり物・組み合わせ・一部作る・全部作るのどれで覆うかの組み合わせ。満たす範囲ごとに挙げる
- 対案ごとの費用: 作る部分の見積り（部品ごとの内訳）、満たし続ける手間（誰が、何分を、年に何回）、得たいもののどれを満たすか、残るもの

比べて一つを選ぶことは、今のとおり問い（`settle-question`）が行う。材料は比べるための対案を差し出す。

##### 比べた分け方

| 分け方 | 評価 |
| --- | --- |
| 一つにまとめる（推す案） | 候補を探すことと組み合わせることが一つの仕事になり、組み合わせを考える中で調べるべき事実（例: 知らせる手段が今も使えるか）がその場で分かる。skillは厚くなる |
| 今のまま二つ。`existing-alternatives`は候補の事実、このskillは組み合わせと費用 | 組み合わせを考えるskillが事実を持たず、事実を調べるskillが組み合わせを知らない。振替の件でA・Bが出なかった形が残りやすい |
| 対案（候補と組み合わせ）と、作る部分の見積りの二つに分ける | 見積りの専門の仕事（部品分解、似たものとの比較、幅）を独立させられる。ただし、見積りを要るのは対案の中の作る部分であり、対案と切り離すと、どの覆い方の作る部分かの文脈が見積り側から見えない |

##### このまとめ方が求めるもの

まとめると、代案の問い、スコープ、最初に作る分、費用の問いが同じ材料の切り口になる。問いのセットの側（どの問いを残すか、並びをどうするか）が変わる可能性があるが、それはこの分け方が決まってから吟味する。

| 問い | 今の水準が求めるもの | 対案の材料から見ると |
| --- | --- | --- |
| 代案（`existing-alternatives-fall-short`） | 候補ごとに痛みのどこが残るか。核心が残らなければ作らないへ | 作らない覆い方（やり方を変える、あり物）でmustが覆えるか。覆い方を選ぶ判断の一部 |
| 解き方（`solution-shape`） | 解き方の案が二つ以上、各案が必須の要求を全て満たすか、選んだ理由 | 作る部分を含む覆い方の中から選ぶ。定石の「既にある道具への追加」は、対案の「一部作る」と同じもの |
| スコープ（`scope-in-and-out`） | 全ての要求が内か外に分けられ、外に置いたものを誰がどう扱うか（代案に任せる、手作業で残す、やらない） | 覆い方を選べば、状態ごとの手段（作る／あり物／運用／我慢）が決まり、内と外はそれと同じもの |
| 費用（`build-cost-pays-off`） | 最初に作る分の費用が、代案を使い続ける費用に見合うか | 覆い方を選ぶ時に、対案ごとの費用で既に比べている。最初に作る分が決まった後に要るのは、見積りを細かくして選んだ時の見立てが崩れないかの確かめ |

覆い方を選ぶ一つの判断を、代案、解き方、スコープの三つの問いに分けて問い、費用はその後で問い直している。分けて問うと、振替の件のように、代案は候補ごとに痛みと比べられ、解き方は作る形だけで比べられ、スコープは選んだ解き方の内側で切られ、組み合わせて覆う対案がどの問いにも現れない。

##### 推す案

| 層 | 問い（並び順） | 中身 |
| --- | --- | --- |
| 何を作るか | 1. 要求（`requirements`） | 満たされた状態とmust・better（イテレーション5の決定） |
| 何を作るか | 2. どう覆うか（新設。代案・解き方・スコープをまとめる） | 対案の材料の覆い方の中から、作らない道を含めて一つを選ぶ。選んだ覆い方で、状態ごとの手段（作る／あり物／運用／我慢）が決まり、それがスコープの内と外になる。作らない道を選べば作らないへ向かう（得たいものと照らす）。作る部分の形（記録・閲覧、通知、自動化等）もここで決まる |
| 何を作るか | 3. リスク（`risks-of-building`） | 選んだ覆い方が依存するあり物と、作る部分のリスク。避ける手当てで覆い方を変える時は2へ戻る |
| どこまで作るか | 1. 最初に作る分（`first-build-cut`） | 作るもので覆う状態のうち、どれを先に覆うか。水準に、最初に作る分を細かく見積もった時に、2で比べた費用の見立てが崩れないかを足す。崩れたら2へ戻る |
| どこまで作るか | 2. 運用で済ませること、3. AIに任せる範囲 | そのまま。運用で済ませることは、作ったものを動かす中の手当て（データの修正、設定の変更、例外）であり、状態を覆う手段の運用とは粒度が違う |

廃止する問い: 代案（`existing-alternatives-fall-short`）、解き方（`solution-shape`）、スコープ（`scope-in-and-out`）、費用（`build-cost-pays-off`）。それぞれの中身（三つの範囲で探すこと、解き方の形の定石、外に置いたものの扱い、尺度と逆転点、機会損失）は、新設の問いと対案の材料へ移す。問いの数は16から13になる。

##### もう一つの懸念: 表を埋めることが目的になる

2. 要求の状態のうち、条件が曖昧なものを要求の問いへ返す

5. 候補×状態の表にまとめる

| 8 | 着想の反証から | 受け入れ時の着想（LINEで通知）が要らないとする最も強い主張を作る | 「通知が無くても、二人が毎朝見る場所に期限が書いてあれば足りる」 |
| 9 | 他の人のしのぎ方から | `target-user-voices`の、同じ痛みを持つ人が実際にやっていることを候補にする | 親同士のやり方（今の材料には無い。声を集め直す必要） |
| 10 | 道具の側から | 家族が既に毎日開いている道具（利用者の事実）の機能を一つずつ当てる | 使っているカレンダーやLINEの、まだ使っていない機能 |

##### 推す作り方: 切り口を候補として多く持ち、件ごとに選ぶ

一つの型を毎回当てない。上の切り口を、材料skillが候補として持ち、件ごとに選んで使う。

- 毎回使うのは三つに限る。2（今のしのぎ方から）と10（道具の側から）は、一番強い対案が出る所であり、5の「何もしない」は比べる基準になるためである
- その他は、件の手がかりで選ぶ。例えば、受け入れ時の着想が道具の形で強く書かれていれば8（反証）、痛みの原因が一人に寄ることなら3（原因から）と7（前提を外す、担う人を変える）、期限や残数のような構造が他の領域にもあれば4（別の領域から）
- どの切り口を使い、どれを使わなかったかを、理由とともに材料に一行ずつ残す。読む人が、探していない方向を知れる
- 止める基準は表を埋めたかではなく、新しい切り口を使っても、mustを覆う新しい候補が出なくなった時（飽和）にする

提案9の七つの漏れのうち、1（候補×状態の表）、3（状態を保つ操作）、4（規約・安全）、5（条件は要求へ返す）、6（利用者の事実を先に）は、候補を探した後の確かめ方とまとめ方として残す。2（手段の種類の偏り）と7（他の人のしのぎ方）は、切り口の候補に吸収される。

##### 比べた作り方の選び方

| 選び方 | 評価 |
| --- | --- |
| 推す案（切り口を候補として持ち、件ごとに選ぶ。毎回は三つだけ） | 件に合う方向へ広がり、型を埋める作業にならない。選ばなかった切り口を記録するため、探していない方向が見える |
| 全ての切り口を毎回使う | 漏れは最も少ないが、提案9と同じ「埋める」作業になり、切り口が増えるほど重くなる |
| 切り口を選ばず、材料skillの思いつきに任せる | 軽いが、前回の`existing-alternatives`と同じく、思いついた範囲（製品名の検索）に閉じる |

#### 検討記録（論点18・イテレーション10）

対案を挙げる材料skillの作り方を決める時に、作り方の対案を一つしか出していなかった。対案を挙げることが目的のskillの作り方は、それ自体が対案の考え方（両端、前提を外す、別の領域から）の対象になる。

### イテレーション12（論点18）: まとめた材料skillの中身（三）対案ごとの費用をどう出すか

#### 提案12（論点18）

##### 何を数えるかの対案

前回designは「二つを同じ尺度へ揃える」をこのskillの存在理由とした（尺度を毎回決めるとブレるため）。ただ、振替の件の痛みの核心（妻の頭にだけ残ること）は、時間に換算すると消える。数え方を比べた。

| # | 数え方 | 評価 |
| --- | --- | --- |
| 1 | 全てを時間に換算する（前回design） | 比べやすい。頭に残る負担、忘れた時の損失、作る楽しみが消えるか、根拠の無い換算になる |
| 2 | 時間を共通の軸にし、時間にできないものを決まった数の列で並べる | 尺度のブレは時間の軸で防ぎ、痛みの核心を列として残せる。比べて選ぶのは問いの側（材料は判断しない） |
| 3 | 項目を件ごとに決める | 件に合うが、前回designが防ごうとした尺度のブレが戻る |

推す数え方は2。列は次に絞る。

| 列 | 中身 | 出し方 |
| --- | --- | --- |
| 作る時間 | 作る部分の時間（幅つき） | 下の「作る時間の見積り方」 |
| 続ける時間 | 状態を保つ操作の時間、保守の時間（年あたり） | 候補の事実の「状態を保つ操作」×年の回数。保守は依存先の変化、不具合、データの手当て |
| きっかけの無い操作 | 覚えていないとできない操作と、それを誰が担うか | 候補の事実の操作を、きっかけがある（欠席の連絡、通知）か、覚えていないとできない（毎週末に見る、見る習慣）かで分ける。頭に残る負担を、時間に換算せずに観察できる形にする |
| 忘れた時の損失 | 操作を忘れた時に起きること（この件では失効）と、起きやすさの見立て | きっかけの無い操作がある道ほど起きやすい、を根拠として書く。数字にする時は前提を書く |
| お金 | 代金、外部サービスの費用 | 候補の事実の費用 |
| 得たいもの | 作る楽しみ等の、どれを満たすか | なぜ作るか層の答え |

##### 作る時間の見積り方の対案

| # | 見積り方 | 評価 |
| --- | --- | --- |
| 1 | 部品に分けて積む | 何に時間がかかるかが見え、覆い方の境目（何を作るか）と対応する。部品の抜け（認証、配置、例外）で過小になりやすい |
| 2 | 利用者が過去に作ったものと比べる | 実績に基づくが、利用者しか持たない事実であり、材料skillは問えない |
| 3 | 三点（楽観・最も確か・悲観）で出す | 不確かさを判断へ渡せる |
| 4 | 似た計画が実際にどれだけ延びたかで補正する（計画は楽観に寄るため、過去の計画と実績の差で直す） | 個人開発は見積りより延びやすい。補正の根拠には利用者の過去の計画と実績が要る |
| 5 | 決めた時間の中で何が作れるかで考える（時間を先に固定する） | 作る量を時間に合わせて削れる。費用の比較ではなく、最初に作る分の決め方に近い |

推す見積り方: 1で部品に分け（部品の抜けを防ぐため、認証・配置・通知の失敗時の扱い等の、ラフ画に描かれない部品の一覧を持つ）、3で幅を出し、2と4の利用者の実績は`settle-question`へ問いとして返して得られた時に補正する。得られない時は、補正していないことと、その分だけ楽観に寄っていることを書く。5は最初に作る分の問いの定石に近く、この材料には持たせない。

| 道 | 作る時間（楽観／確か／悲観） | 続ける時間（年） | きっかけの無い操作 | 忘れた時の損失 | お金 | 作る楽しみ |
| --- | --- | --- | --- | --- | --- | --- |
| P0 何もしない | 0 | 0 | 期限を覚えておく（妻） | 年約5回失効（約12,500円） | 0 | 無い |

この表から見えること: P3の続ける時間は、知らせが無いために毎週末の確認が要り、P2より多い。P3のままでは弱く、P4（知らせだけ作る）かP2（置き場所をカレンダーにする）へ寄る。この見方は、時間だけで並べた時（P3は記録が速いので安く見える）には出ない。

##### 自己レビューで直したこと

- 最初は前回designのとおり全てを時間に換算していた。痛みの核心が消えることに気づき、数え方を対案として比べた
- 頭に残る負担を「負担が大きい・小さい」で書いていた。観察できないため、「きっかけの無い操作」として、候補の事実の操作から出せる形にした
- 作る時間の見積りに、ラフ画に描かれない部品（認証、配置、失敗時の扱い）が抜けていた。前回の「約16時間」も、合言葉と配置は入れていたが、通知が失敗した時の扱いは入れていなかった

#### 検討記録（論点18・イテレーション12）

前回designの「同じ尺度へ揃える」は、尺度のブレという失敗への対策として正しいが、揃える対象を全てにすると、この件の痛みの核心を比べられなくなる。時間の軸は残し、時間にできないものを、観察できる形の列として決めて持つことで、ブレを防ぎつつ核心を残す。

## 論点20: 閉じた問いを答え直す時の扱い

**ステータス:** 決定

**親論点:** 論点14

**種別:** レビュー指摘

### イテレーション0（論点20）: 誰が答え直しを決め、記録をどう残し、下流をどう確かめるか

#### 提案0（論点20）

##### 試運転で起きたこと

振替の件で、材料`propose-alternatives`が、閉じていた要求の問いの答え（R1〜R7）を入力として足りないと返した。`settle-question`がそのまま要求の問いを答え直した。その中で三つが決まっていなかった（[試運転の摩擦](../self-play-frictions.md)の3〜5）。

| 摩擦 | 中身 |
| --- | --- |
| 3 | 既にある問いの決着の記録を書き換えるのか、前の答えを残すのかが無い |
| 4 | 閉じた層の問いを答え直すと層は閉じていない状態に戻るはずだが、誰が戻すかが無い |
| 5 | 答えが変わると、それを使っていた下流の問い（R1〜R7を参照するスコープ、最初に作る分、AIに任せる範囲等）が古くなるが、どれを答え直すかを誰が決めるかが無い |

もう一つ、試運転の流れ自体にも穴があった。材料skillは要求の問いの答えが足りないと`settle-question`（代案の問い）へ返し、その`settle-question`が別の問い（要求）を直接答え直した。進行を持つ`grow-product-idea`を通っておらず、層の状態も問いの一覧も、進行の側からは見えなかった。

##### 答え直しが起きる場面

| 場面 | 例 |
| --- | --- |
| 下流の問いや材料が、上流の答えを入力として足りないと返す | 今回（材料が要求の形を返した） |
| 層の閉じで、利用者が修正を求める | `grow-product-idea`の手順5に既にある（起点の問いへ戻す） |
| 前提にする条件が足され、閉じた答えが反する | `grow-product-idea`の手順5に既にある（閉じた問いを戻す） |
| 材料が作り直され、その材料で答えた問いの根拠が変わる | 今回、`alternatives`を作ったことで、代案・解き方・スコープ等の根拠が変わる |
| レールが変わる（問いや水準が変わる） | このsteeringの論点12・18 |

##### 推す扱い

1. 答え直しを決めるのは`grow-product-idea`にする。`settle-question`と材料skillは、別の問いの答えが足りないと分かった時、自分で答え直さず、どの問いの答えの何が足りないかを付けて`grow-product-idea`へ返す。`settle-question`の手順2が既に持つ「他の問いの答えが閉じていなければ`grow-product-idea`へ返す」と同じ形にする。進行（どの問いを開け直し、どの順で答えるか）と層の状態は、進行を持つskillが一か所で持つ。
2. `grow-product-idea`は、答え直す問いを開け直す。層の問いの一覧で、その問いの状態を「答え直し」にし、理由を書く。その問いの層が閉じていれば、層の状態を「未閉じ」に戻し、理由を書く。層の閉じは、答え直しで立った論点への利用者の応答を得て、もう一度行う。
3. 問いの決着の記録は、今の決着を書く場所として書き換える。そのうえで「答え直しの経緯」の節を足し、回ごとに、きっかけ（誰が何を返したか）、前の答えの要点、何が足りなかったか、何が変わったか、立った論点を書く。前の答えの全文は残さない。判断の変遷は決定過程の論点に残っており、正本は今のプロダクトの説明だからである。
4. 答えが変わった時、`grow-product-idea`は下流を洗い出す。下流は、層fileの「必要な材料」でその問いの答えを挙げている問いと、その問いが作り直させた材料を要求した問い（材料の「要求した問いと粒度」の表にある）であり、そこから先も同じように辿る。下流の閉じた問いは、すぐに答え直さず、状態を「確かめ直し待ち」にする。
5. 「確かめ直し待ち」の問いは、`settle-question`が手順5（立て直した基準で確かめる）だけを、変わった入力で行う。答えが変わった入力でも基準を満たすなら、問いの決着の記録の「答え直しの経緯」に「確かめ直した。変わらない」と書いて閉じ直す。満たさないなら、答え直しに回す。全ての下流を一律に答え直さないのは、紆余曲折を減らすという目的に反するためである。

##### 比べた扱い

| 扱い | 評価 |
| --- | --- |
| 推す案（進行が開け直しと下流の洗い出しを持つ） | 層の状態と問いの一覧が一か所で正しく保たれる。下流は確かめ直しから入るため、変わらない問いを答え直さない |
| 気づいた`settle-question`が直接答え直す（今回の流れ） | 速いが、層の状態と問いの一覧が進行から見えず、下流を誰も洗い出さない（摩擦4・5がそのまま残る） |

| 前の答えを別のfile（`questions/<slug>.v1.md`等）に残す | 前の答えを読めるが、問いの記録が増え、どれが今の決着かが分かりにくくなる。前の答えの要点は「答え直しの経緯」で足りる |

##### 変わるもの

| 対象 | 変更 |
| --- | --- |
| `grow-product-idea/SKILL.md` | 答え直しを決める手順（開け直し、層の状態を戻す、下流を洗い出して確かめ直し待ちにする）を足す。流れの図に、返された答え直しと確かめ直しを足す |
