# 構成の材料を、隣の専門の方法へ渡した結果

同じassistantが、依頼側として[構成の材料](implementation-structure.md)を受け、既存のdesign-data-model、verify-technical-feasibility、propose-alternativesの該当する方法を順に適用した。独立した別agentの評価ではない。材料から本質的な意味を補完した所が無いかと、足りずに返す所を見るBの局所確認である。

## 情報設計が返した意味と更新の条件

必要な読取りは、J1の実行対象、同じ依頼の取得可否、結果が未確認か、R1の結果が現行R2にも対応するか、である。ここから次の関係を組んだ。

| 情報 | 意味・鍵と守る関係 |
| --- | --- |
| 原情報の現行 | S1を鍵に現行の版を読む。内容の差を保持する必要がある所では版ごとの内容へ結ぶ |
| 依頼 | J1を鍵にS1・依頼時のR1・送信先と内容を保持する。再実行を新しい業務上の依頼へ替えない |
| 実施・観測 | 試行をJ1へ結び、送信を試みたことと外部の結果を観測したことを分ける。外部IDの空欄だけで未作成とはしない |
| 現在の反映成功の読取り | 依頼の対象版と現行の版が一致し、外部結果の確認根拠があるものだけを現在の成功として読む。旧版の結果は履歴として残る |

取得はJ1が未取得で、依頼の対象と現行が一致することを条件に更新する。二つの接続が同じ未取得を読んでも、条件を満たして取得を確定した実行者だけが開始する。
R1の結果保存は履歴の観測として行えても、R2の現在の成功へ結ぶ更新とは分ける。単にversionというcolumnを置くことでなく、読取りと更新の条件へ対象版を使う必要がある。
この読取りと取得の条件の一部を[probe.py](probe.py)に写した。SQLiteでの結果は[probe-results.json](probe-results.json)である。実APIと本番の保存先は対象外。

情報側から追加で返した問いは、取得権の期限切れで再実行してよい条件である。手元で取得者を書き換えても、前の実行者が外部で作用しない根拠にはならない。構成と技術の問いへ戻した。

## 技術検証が返した問い・方法と未確認

| 主張 | 回復側に渡してよい入力・方法 | 反例と、結果による構成への返り |
| --- | --- | --- |
| 外部IDを失っても結果を照合できる | J1、送信前に保存したR1の内容、送信先だけを回復側へ渡す。外部に作成された正解は検査側で別に観測する | 似た題名の別予定を拾う、回復側へ本来失われる外部IDを渡す。照合できないなら自動復旧の構成は成立したとしない |
| 同じJ1の再送が別の効果を作らない | 同じ識別・同じ内容の再送と、識別は同じで内容を変える対照を実対象へ当て、副作用と返却結果を読む | 応答が同じでも対象が二つできる。識別の有効期限・対象範囲が依頼の再開条件を覆わない |
| 古い実行者と新しい実行者が同時に外部作用しても保証を保てる | 期限切れの前後で古い実行者の送信を遅らせ、新しい実行者の送信と順序を変える | 手元の取得権が変わっても古い送信が実施される。必要なら外部の重複抑制・更新の条件を別に確かめる |
| 条件付き取得と現行の読取りが意図した意味で使える | 二つのSQLite接続に同じ前提を読ませ、片方の取得確定後にもう片方を実施。R1の結果保存後、現行をR2へして読取りを比較 | 取得前の再読だけなら両方が開始する。旧版の結果を現在の成功へ読む。今回の順序での観測を全transactionの結果へ広げない |

最初の三つはAPI未指定のため未実施であり、技術的に不可能と判定したのでもない。構成の材料から検査の条件を作れたが、性質を確認できたこととは区別する。第四の限定した模型だけを局所で実行した。

## 見積もり側が受け取れた部品と、返す不足

propose-alternativesの「作る部分を部品ごとに見積もる」と、部品・配置・連携・定期実行・失敗・訂正、継続の行いを積む方法を適用した。

| 部品・行い | Aに必要 | Bの差・追加 |
| --- | --- | --- |
| J1と対象版を残し、開始と結果を読む | 必要 | 共通で再利用する。二重に計上しない |
| 外部へ送信し、結果と原情報の対応を保存 | 必要 | 共通。応答の戻り先と実行者が変わる |
| 未確認の表示・照合・訂正の入口 | 必要。同期でも結果不明はある | 受付と待ちを表示し、別実行の未確認も同じ根拠で扱う |
| 配置・設定・接続先と権限 | 操作側と保存先に必要 | 別実行者の起動・配置・設定・接続が追加 |
| 取得・停止・再開・監視 | 再開時の同じ仕事の取得と確認が必要 | 複数の実行者、停止の発見、再取得の条件と監視の対象が増える |
| 人の継続作業 | 未確認を何を契機に誰が確認するか | 操作側の停止と別実行者の停止で、確認する根拠と頻度が変わる |

「復旧対応」という一項だけでは落ちていたA側の照合入口と、B側の稼働・取得権の部品を切り出せた。技術の性質が分かると部品や人の照合が変わるため、その差を再見積もりへ戻せる。
実装する方式・配置先・利用量、利用者の作業実績、未確認の発生頻度が未指定である。今回は金額や部品ごとの三点を根拠なく補わず、その条件で変わる部品と必要な事実を依頼側へ返した。見積もりの完成・費用の採否は未完である。
現行のpropose-alternativesの「作る部分の形」の出所の案内には新しい材料の名前が無い。本文が受け取る形と粒度へ渡せても、実際の呼出しと案内の同期は別に残る。使用可能な専門の登録の変更時に、この出所の接続も同じ変更集合で示す必要がある。

## 本文と構成へ戻した点

取得権の期限切れと古い実行者の外部作用を分ける必要、手元の現行の読取りと外部の古い作用を分ける必要を、本文の同時実行・変更の扱いへ戻す。条件付き更新を置けば外部も解決済みとする薄い材料を防ぐためである。
今回使えたのは、構成案の差と、情報設計・技術の具体の問い・見積もりの部品の入力である。実APIの成立と実費用、呼出しの同期、案件の全体の成立は確認していない。
