# 実装構成設計の局所確認

論点90で作成した専門の本文を実行し、返した材料を既存の情報・技術検証・見積もりの方法へ渡すBの確認である。新しい製品案件の一式適用や、実APIの成立を検証するCではない。同じassistantが順に方法を適用し、独立した別agentの評価とはしない。

## 入力として置く模型

これは確認用に与える前提であり、利用者の実製品の要件ではない。

対象S1の原情報R1を、依頼J1として外部の予定へ反映する。人は受付と外部の結果の確認を区別でき、同じ依頼の再開で別の予定を重複作成せず、古い原情報の結果を現在の反映成功と取り違えないことを求める。
原情報はR2へ変わり得る。利用者が画面を閉じても処理が続くことは未選定で、同期処理と別実行の違いとして比較する。外部への送信後、成功応答を手元に保存する前の停止を含む。処理が外部で成功したかと、手元の観測を分ける。
API・host・本番の保存先は未指定。外部へ依頼の識別を渡せるか、再送と照合をどう扱うか、前の実行者が止まる保証は未確認である。題名だけで同じ予定と判定してよいとはしない。

別の模型は、確定した入力版L1から手元の一覧を再生成する処理。外部への作用はなく、一人が手元で使い、入力L1と生成時の設定を保存している。共有の常駐実行は必要とされていない。これに同じworkerや耐久的依頼を強制しないかを確かめる。

## 入力からの実行と記録

1. 新しい実装構成設計の方法で[構成の材料](implementation-structure.md)を作る。
2. 依頼側がその材料の問いと根拠を既存の専門へ渡し、[隣の方法で作った返り](consumer-results.md)を得る。構成の専門が別skillを直接呼んだ扱いにしない。
3. 別の模型で[再生成の比較](local-regeneration.md)を作り、外部作用の仕組みを一律に課していないかを見る。
4. 情報設計が返す条件付き更新と読取りの一部だけを[SQLiteの模型](probe.py)で動かし、観測を[probe-results.json](probe-results.json)に残す。外部APIは実行しない。

本番の費用や人の実際の負担、実APIの再送・照合、実hostでの動作は未確認である。この模型を理由に製品や全体をbuild-readyにしない。
