# CR-010の適用と検証 — 試運転の妥当な出口と検査範囲を分ける

## 現物の問題と修正

ドライランだけに適用する振返りをrootの保守入口へ置き、進行skillから繋いだ。原依頼→実際に通った判断→未検査→次の入力を既存の保守記録へ返す。通常案件の新台帳は作らない。

## 具体例の机上追跡

C3の根拠のない適合・在庫を創作せず保留した判断は妥当である。その結果だけでwhyの優先・部分再開・設計・初回構築まで合格にしない。
型番と適合根拠だけを追加入力にした次の試運転は、商品同定と公開調査の部分再開を確認でき、店舗の未確認は残す。
既存フィードバックは保持し「何も還元されなかった」と書かない。通っていない枝の記録は保守側に置き、通常製品の正本へ外部の試験台帳を混ぜない。

## 検証の意味と限界

本文と雛形を入口・判定・記録・後続への順に読み戻し、上の判断が手順から導けるかを照合した。
文書reviewでは初見の実行可能性、誤用の境界、旧版から削った要素、根拠と仮説、参照・現在表示を確認した。
この原因の恒久的な知識は修正本文へ収めたため、doc-enricherの独立した重複提案は行わない。
机上追跡を自律agentの実利用・外部仕様の実測とは扱わない。機械検査は隣のJSONへ記録する。
