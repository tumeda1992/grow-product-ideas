# どう作るか層の接続試運転

## 検査する問いと、固定した入力

今回の結果は、専門の材料を同じ用件へ繋いで設計の欠けを見つけ、必要な根拠を得て戻せた一方、二つの版とも必須の不足が残り、どう作るか層を閉じなかった、である。
ローカル版をbuild-readyまで通した検証は、まだ完了していない。

| 検査用の版 | 固定した入力と、実際の結果 |
| --- | --- |
| [学校ローカル版](product-plans/20261114-school-local/README.md) | 家のPC一台・一process・loopback。原本・家族の選択・署名・提出・calendarの転記照合は人。設計候補と保存の指定条件の根拠を得たが、対象PCの実行条件と導入の成立が未特定で閉じない |
| [学校外部反映版](product-plans/20261114-school-external/README.md) | 次の行いを自動反映し、全件の手動転記・照合を不要にする。ただしAPI未選定。照合・再送・変更の根拠が無く、閉じずにhowの選定と技術の確認へ返した |

いずれも学校限定の三週の実験版で、三教室の振替の負担と失効の痛みは残す。
管理・手続の全作業の物差しは夫週60分・妻週30分、原則19:30–20:00、20:00–20:30の親子の時間は使わず、通常一件・繁忙二件の学校と担当二日の不在を扱う。
学校の署名準備は15分、原本の回収を提出完了とし、署名・予定の作成と分ける。

この価値・条件・時間の設定は既存の架空の模型から維持した。
日付・原本の変更規則・使えるPCとcalendarの操作・初回構築24/56/112時間と上限112時間・月額追加0円等は検査専用の追加仮定であり、実在の家族の事実や今回の版の費用の見積りではない。
それぞれの正本に出所と条件を固定してから設計し、不足が出た後で入力をLinuxのPCだったことにしていない。

既存の模型の「学校限定の三週の非開発試行」という選定は変えていない。
上流を固定入力として受け取った試験であり、why・what・howを今回最初から実演したものではない。
当人役の採否はassistantが演じた検査であり、実際の利用者の応答や選定とは別である。

## 材料を依頼し、設計へ繋いだ方法

最初に導入・受領・選択・引受け・予定への受渡し・実際の提出・変更・不在・中断競合・観測・終了のS0–S10を並べた。
[ローカルの層記録](product-plans/20261114-school-local/how-to-build/README.md)と[外部反映の層記録](product-plans/20261114-school-external/how-to-build/README.md)に、条件との対応と全場面を置いた。

ローカルでは以下の実物のskillを読み、方法を同じ版へ適用した。
順を全製品へ固定せず、この版で何が次を規定するかから依頼した。

| 依頼 | 実際に行った専門の方法と、次が使った返り |
| --- | --- |
| E1 sketch-experience | 価値と条件から場面を起こし、人・PC・学校・calendarの一巡をラフへ落とした。原情報の版だけで保存を比較できない不足をD1へ返した |
| L1 design-core-logic | 必要な結果から入力と規則を導き、決定表・時間の境界・二件の共有枠を机上で通した。D1へ現行の選択・残時間と根拠、F1へ確定時の共有枠の検査を返した |
| D1 design-data-model | 読取りと変更から現行・根拠・更新比較・反映内容を分け、保存方式の差とSQLiteの鍵・型・制約・queryを返した。予定の現行性は原情報の版だけでは足りないとE1/F1へ戻した |
| F1 functional-structure-design | 一巡から現行と根拠、引受けと枠、予定への手渡しと照合の責任を構成した。対象・前提・結果を繋ぎ、必要な保存の原子性と再開の意味をT1へ返した |
| T1 verify-technical-feasibility | 問いを期待と反例へ写し、SQLiteの独立connectionの順序・transaction・backupを局所実行した。条件付きの事実と未確認をD1/F1/E1へ戻した |

共通の調整部分に専門の規則を集めず、層は依頼と返りを繋ぎ、設計候補を選び、同じ用件の具体の値と出来事で照合した。
材料は各版のdirectory内で読め、reportを読まなくても設計候補・根拠・不足へ辿れるようにした。

外部反映版は、APIの性質が情報と機能を規定するためT1を先に依頼した。
F1へその不足の影響を問い、未確認の性質が残るまま全専門の詳細を形式のために作らなかった。

## ローカル版で得た設計と、閉じの判定

保存はSQLite案を選び、現行と根拠、引受けと枠、予定への手渡しと照合の責任を分ける候補を得た。
[検査用の判断](product-plans/20261114-school-local/how-to-build/discussion.md)にはJSON案等との差と、採った条件を残した。
class・serviceの数を三つに決めたものではない。

設計の要点は、原情報の版・全変更を比較するtoken・calendarへ反映したpayloadを別に扱い、本人の選択と必要時間を根拠付きで保持することである。
R1金曜からR2木曜へ変われば現行を読み直し、古い予約を外し、選択・残り・引受けと予定を再確認する。
同じ本文B1の署名の事実は残すが、署名・持出し・予定反映の成功から提出完了を導かない。

| 観測する境界 | 方法と結果 |
| --- | --- |
| 同じR2の古い保存 | SQLite実行で先の引受けを保持し、後の古いtokenの保存は0件で拒否した |
| 別用件が同じ人の15分を使う | SQLite実行で二件目はoverlap。隣接なら双方を保存した。用件単位の比較だけでは足りない |
| 保存途中の制約違反 | token・根拠・commandを全てrollbackした |
| commit後に応答を失う | 同じcommand/payloadの再送は二重適用しなかった。別payloadで同じIDは拒否した |
| writerのlock | SQLITE_BUSY/code5と古い前提の0件を区別した。lock終了後の明示の再実行は保存した |
| backup中の書込み | 別connectionのbackupはcommit済みの整合した時点を保存した。commit後は全変更を含み、再openの外部鍵検査にも違反なし |
| 現行の選択と未予約の残時間 | 最初のschemaの欠けを直した後、SQLでR1の参加・15分を読めた。R2で現行の再確認が無ければNULL/NULL、要確認と不明を入れるとneeds_check/NULLを返し、R1も保持した |
| 19:45/19:46、不明、二件 | 規則とラフの机上照合で、15分なら20:00/20:01、5分なら19:51、不明なら要確認。二件とも最後の15分に収まるとはしない |
| 不在と人の転記の結果不明 | 机上で、次の人が原本・過去の根拠・現行の残りから再引受けし、markerと反映payloadでcalendarを照合する手順を辿った。実際の人・calendarの操作は未実施 |

[実行code・観測と条件](product-plans/20261114-school-local/materials/technical-feasibility/README.md)を保存した。
修正後のschemaで17項目を実行し期待と一致した。選択・必要時間の追加の読取りも実行した。
対象はPython3.12.14・SQLite3.53.1・Linux、WAL・外部鍵ON・busy_timeout0・BEGIN IMMEDIATEで、独立connectionの順序を制御した検査である。
アプリ本体・UI・実calendar・多host・高負荷・実PCの耐久性を確認した証拠へは広げない。

導入・誤記・原情報変更・中断・backupと復元・紙への退避・終了の担い手と手順、実装後の受入れと実利用後の観測を層記録へ渡した。
しかし固定入力の「家の既存PC」はOS・architecture・runtimeの導入と運用の条件が特定されていなかった。
今回のLinuxの観測を、そのPCで起動・保存・復元できる根拠にはできない。

そのため、対象PCの条件を取得し、何をどう導入するかと必要な技術の裏づけを揃える不足を残して、層を閉じなかった。
これは実アプリの全てを先行実装する要求ではなく、どこで動かす設計なのかが未特定という不足である。
設備・費用・担い手が変わるならhowへ返す。学校以外の痛みや実利用の効果の未観測は、これと別の未達・未知として維持する。

## 外部反映版で残った不足と、返す判断

[技術T1](product-plans/20261114-school-external/materials/technical-feasibility.md)で、照合と再送の性質を分けた。
作成の成功応答とIDの保存前に止まる時、手元の実施中・ID無しという同じ状態から、W1は外で作成済み、W2は未作成であり得る。
これを見分ける観測が無いのに、成功扱いにも無条件の再送にもできない。

実APIは未選定で、照合の識別を相手へ書けるか、検索・取得・見つからない時の意味、再送と重複、R2変更・取消しの性質は未確認である。
正常に作成して返ったIDで取得する検査や、便利なfieldを持つ模擬ではこの根拠を代用できない。

[F1の返り](product-plans/20261114-school-external/materials/functional-structure.md)で、反映結果の確認と照合訂正の責任を定められないことを示した。
ローカルの状態を増やすだけでは外部の事実は得られない。
人の全件照合へ差し替えると、選定の決め手と負担が変わるので、自動版の合格にはしなかった。

howへ対象API・用途と開示・利用条件の選定を確かめ直す判断を返し、その対象のT1へ必要な性質を問う形で止めた。
APIの操作、候補の採用、実対象への実行は行っていない。技術が不可能という結論や、恒久的な中止の判断ではない。

## 試運転で現れた摩擦と、その原因

| 実際に見つかった差 | 検知と修正・残る不足 | 原因の扱い |
| --- | --- | --- |
| 体験・logicが使う家族の選択と残時間を、初稿の保存構造では読めない | S2/S3/S7を戻って照合し、対象原情報と根拠付きで保持する構造へ直した。旧い値を現行へ使わない追加の実測を得た | 専門の返しを存在だけで受け取らず、具体の読取りまで照合する必要があった。方法には既に指示があり、今回は適用の漏れとして扱う |
| 原情報の版が同じでも予定の内容は変わる | 担当と枠を含むpayloadを保持し、現在の内容と比較する表示・機能へ戻した | 別の役割の識別を一つのversionへまとめると継ぎ目が壊れる。共通skillの要素を機械的に追加したものではない |
| 用件ごとに古い保存を拒めても、別用件の同じ枠を守れない | 確定時に同じtransactionで全用件の枠を見直し、SQLの非重複で検査した | 局所の正しさから全体の資源の成立は導けない。具体の仕事の共有を見て必要な条件を返した |
| ローカルの実行対象の入力が足りない | Linuxの実測を家のPCへ広げず、実行条件と導入の成立の不足へ返して閉じない | 試運転の入力と設計の未特定が残った。合格に合わせてPCの条件を後付けしなかった |

初稿のschemaをSQLで17項目検査できたことだけでは、体験とlogicの全入力を保持する欠けを検知できなかった。
専門の単体の検査と、全場面へ戻した接続の照合は、得られる証拠が違う。
今回の修正は検査用の設計と材料の中で行い、共通skillや層fileの本文は変更していない。

## 言える結論と、残る検証

必要な専門の実物を使い、返りを同じ版の次の判断へ渡し、欠けを具体の読取りから発見・修正する往復を実行できた。
SQLiteの限定した条件で必要な保存の性質を実測し、実測・机上照合・未実施を分けて返せた。
外部反映の未確認を、人手への差替えや模擬の成功で隠さず止められた。

一方、ローカル版を実装・導入へ渡せる設計として閉じ、build-readyへ通す検証は未完である。
続けるには対象PCの条件とruntime・導入の成立を特定し、固定した範囲と費用の中で必要な根拠を得て、導入手順と閉じの確認へ戻す必要がある。
条件を変える検査を行うなら、元の入力で閉じたことにせず、変更と選定への影響を明記する。

外部反映版には対象APIと利用条件の選定と、その対象での性質の検証が残る。
どちらも実製品の実装・導入・実利用、費用や負担と価値の実測、新しいsessionで新しいアイデアを最初から通す再現は行っていない。
同じ担当が当人役も演じる試運転の結果であり、実際の利用者の採否や他の担当の読解を確認したことにはしない。

利用者の進行指示により、上記の追加検証は宿題として残し、共通の方法・専門の整備を先へ進める。
ローカル版は作る版をbuild-readyまで通す適用検証を再開する時、自動反映版はその版を再検証する時に、それぞれの不足へ戻る。
個別版の設計が閉じたことや、未確認の技術が確認できたことにはしない。
