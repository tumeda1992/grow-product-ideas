- 状態: 決めている（必須の不足が残るため閉じない。検査用）

## 受け取った物差し

[正本の固定入力](../README.md#前提にする条件)の価値、A–H、学校限定の範囲、残る三教室の痛み・Gの未観測、費用と担い手を使う。
対象は既存PCのローカル版、人が予定へ転記・照合する版。今回の検査後も実際の模型の非開発試行は変更しない。

## 決め方

### 1. 選んだ版の一巡から、設計すべき判断を取り出す

| 場面 | 始まり・受領するもの | 人・仕組みの仕事と、終わりの根拠 | 条件と設計の問い |
| --- | --- | --- | --- |
| S0 導入 | 既に届いた原本・引受け・署名や提出の根拠 | 二人が原本と実際の根拠を見て既存分を入れる。新しい予定を無条件に作らない | A/D/E。過去分と新規をどう区別するか |
| S1 受領 | 紙の受け口に原本、又は変更の知らせ | その日の確認担当が原本を確認し用件を識別する。妻が全部仕分ける前提にしない | A/E。題名が同じ別の用件を統合しないか |
| S2 選択 | 現行の原情報・本人の望み・使える時間 | 家族が参加又は見送りと理由を選ぶ。不明なら要確認、無応答を見送りにしない | B/F。選択に必要な情報と、誰が得るか |
| S3 引受け | 必要な行い・期限・時間枠 | 実施できる本人が引き受け、次の行いへ進む。割当名だけでは引受けにしない | C/G。候補枠と重複・未知をどう扱うか |
| S4 予定へ渡す | 引受けた行い・その時点の原情報 | calendarへ予定を反映し、何が確認できたかを残す。反映を提出にしない | C/E。反映の対象と結果不明をどう保つか |
| S5 実施と提出 | 現行の原本・署名等の根拠 | 署名準備→持ち出し→学校による回収。実施した人と確認した根拠を分けて記録する | D/E。原本が家に残る入力で完了しないか |
| S6 原情報の変更 | R1金曜からR2木曜、又は本文の変更 | 現行と残り・引受け・予定を再確認。旧い根拠を消さず対象を残す | B/C/E。何を再計算し、何を有効と読むか |
| S7 不在・交替 | 元担当へ二日連絡できない | 次の本人が原本・根拠・残りを見て引き受ける。聞き直しを前提にしない | C/H/G。間に合わない引受けをどう見つけるか |
| S8 中断・競合・誤記 | 保存の途中、古い画面、外の結果だけ済んだ | 現行を失わず、保存済み・未記録・結果不明を読み分け、照合・訂正へ続く | D/E/H。自動再実行で何を壊すか |
| S9 日常・繁忙・価値観測 | 通常一件、繁忙二件、三教室の残る作業 | 人別の受領・入力・実施・照合・復旧時間と役割・望む関わりを記録する | F/G。学校の部分だけで全体を合格にしないか |
| S10 終了・中止 | 三週終了、上限超過、引受け不成立 | 新規投入を止め、未完と根拠を取り出して紙へ戻す。継続・変更・中止を選び直す | E/G/H。完了していない用件を取り残さないか |

### 2. 必要な専門材料を、依存と粒度を持って揃える

E1/L1を先に得て、D1へ必要な読取りと変更、F1へ機能の受渡し、T1へ保存の性質を頼んだ。
専門の材料は、[体験](../materials/experience-sketch.md)、[logic](../materials/core-logic.md)、[情報](../materials/data-model/README.md)、[機能構成](../materials/functional-structure.md)、[技術の観測](../materials/technical-feasibility/README.md)にある。
D1からsource_rev・token・予定payloadの区別をE1へ戻し、T1から更新0件・枠の競合・BUSYと再実行の意味をF1/E1へ戻した。

全場面へ戻したところ、D1初稿に家族の選択・理由と、未予約の必要時間の保存先が無かった。
選択をresponse_decision、必要分数と根拠をaction_needへ保持する構造へ直し、E1/L1/F1へ現行の入力の不足を要確認とする条件を返した。
修正前後を材料に残し、SQLの追加の読取りと最終schemaで元の17項目を実行した。
専門のfileの存在だけで満たしたとはせず、各入力が何のqueryで読めるかを照合した。

T1が返したLinuxの条件の根拠はあるが、家のPCの実行条件は未特定である。その材料を育て中として残す。

### 3. 設計の案を同じ一件へ当て、継ぎ目を照合して選ぶ

保存はSQLite、機能は現行と根拠・引受けと枠・予定への手渡しを分ける案を検査用当人役が選んだ。
[保存方式の判断](discussion.md#論点1-ローカルの保存をどの方式で具体化するか)と[機能構成の判断](discussion.md#論点2-機能の責任と受渡しをどの構成で示すか)に代替案・決め手・限界を残す。
この設計候補は、一台のPC、一processの書込み、loopbackからのブラウザ操作を前提とし、遠隔公開・自動calendar連携・自動の家族の選択を作らない。

| 入力・出来事 | 操作→情報→規則・機能→外の結果と残り | 確かめた方法と結果 |
| --- | --- | --- |
| 導入時に既に提出済み | 原本と回収の根拠を確認して既存分を入力。新規転記をしない | 机上。導入と新規を分ける操作がE1にある。実際の初期投入は未実施 |
| 同じ題名の別の原本 | 別idで取り込み、識別を疑う時は原本で人が確認。題名で自動統合しない | schemaのid・queryとE1を机上照合 |
| 家族の選択と未予約の必要時間 | F-Aの選択、F-Bの必要時間を原情報ごと保持し、U2とlogicへ渡す | 初稿の欠けを検知して修正。追加のSQL実行でR1の参加/15分を読み、R2では再確認無しに旧値を使わない |
| R1金曜→R2木曜・同じ本文B1 | U3で新原情報、現行参照を更新し古い枠を外す。過去の署名R1/B1を保つ。選択・残り・引受け・転記は現行条件で再確認 | SQLで現行はR2木曜、署名はR1、submittedは0。本文B2なら旧署名を現行に使わない読取りを確認 |
| 同じR2の古い画面 | 読んだtokenで保存。先に別の変更があれば0件で拒み、入力を残し現行を再読込み | 二connectionの順序を制御して実行し、先の担当とtokenを保持 |
| S1/S2が同じ人の19:45–20:00へ確定 | F-Bがtransaction内で全用件の枠を再検査し、二件目を拒む | SQLでoverlap、S2はtoken0・予約無し。隣接なら二件とも保存 |
| 19:45/19:46の残り15分、19:46の5分、不明 | 本人の引受けと原本の利用を確かめ、空きと必要分数で候補を返す | 机上計算で20:00/20:01/19:51。不明は要確認で0としない。実際の所要時間の測定ではない |
| 夫が二日連絡できない | 妻がU2で原本・過去の判断と根拠・現行の残りを読み、使える条件を確認し再引受けする | 表示・query・規則・機能を机上で接続。必要な本人の望み等が不足すれば要確認で止まる |
| 人が転記後に成功保存前で停止 | F-Cが残すmarker・payload・実施中から結果不明と読み、人が旧新の予定日で照合・訂正。読めなければ不明を保つ | 机上。成功のIDや便利なAPIで代用しない。外の操作は未実施 |
| R2のまま担当又は枠が変わる | 現在のpayloadと最後に確認したpayloadが違うので予定は要照合。無関係な根拠でtokenが増えただけなら再転記しない | 情報・F-C・U2の机上照合。原情報の版だけでは足りない境界を検知 |
| 署名・持出しだけ済む | evidenceの対象と種別を読み、学校の回収の根拠が無ければ提出は未完 | SQLでsignedとsubmittedを分離、ラフと機能でも提出未完を維持 |
| 途中の保存失敗／応答を失った保存 | 共通保存で全体をrollback、又は同じcommandの結果を照合。実際の出来事は対象を保って再入力へ | SQLで原子性と重複適用の拒否を確認。UIが入力を保持できるかは実装後の受入れへ |
| 日常・繁忙・終了 | 未完と根拠を紙へ戻し、人別の時間と役割・余白を観測し、三週又は停止条件で選び直す | 手順の机上照合。実際の運用・時間と価値は未観測 |

APIの不確かな性質へ依存しないローカル案でも、人の照合が残る。その負担を隠さず、元から選んだ人の転記・照合を具体化した。
ただし家のPCに何をどう導入できるかは未特定で、設計の成立を左右する不足が残る。

### 4. 導入・修正・復旧と、受入れの確かめ方を設計する

| 場面 | 担い手・きっかけ・根拠・手順の終わり | 受入れと負担の扱い |
| --- | --- | --- |
| 導入 | 夫が既存の原本・根拠から初期入力。妻も自分の引受けを確認。既存分は新しい予定を勝手に作らず、未確認は未確認で残す | 準備週の夫60分へ分割し、超過はhowへ返す。対象PCのruntime・導入方法と権限は未特定で、ここはまだ実施できる手順に閉じていない |
| 起動と終了 | 二人が同じPCで起動・一覧の現行確認、終了前に未完と転記の不明を読む。常駐通知や遠隔アクセスは前提にしない | 実装後にloopbackのみ待受け・同じPCから利用・再起動で保存済み状態を読めることを試す |
| 誤記・原情報変更 | 確認した本人が根拠付きで追加訂正。元の出来事は残し、訂正先が同じ用件かを検査。本文変更・期限変更で選択・残りを再確認 | R2・同じ本文／違う本文、古いtoken、実際の出来事を記録し損ねた入力を受入れへ渡す |
| calendarの不明 | その行いの引受け人がmarkerとpayloadで旧新の予定日を照合し、訂正の後もう一度読んで記録。読めない時は不明で止まる | 毎日の全件照合を妻に押し戻さず、変わった行い又は不明の行いを担当本人が扱う。照合・復旧の時間も計上 |
| 保存先の失敗とbackup | 成功を表示せず未保存の内容を紙に残す。運用する夫又は不在時の妻が、DBが読める時はbackup APIで別fileへ取り、別名へ復元して現行・未完・根拠とcommandを読む | SQLiteで整合したbackupの性質は確認。実装後に同じPCで停止・復元・再起動の手順を試す。WALのDB本体だけをcopyしない |
| 破損・紛失 | DBが読めない時は上書きせず、読めるbackupを別名へ復元。どこまでの状態かを原本・calendarと照合し、その後の出来事を紙から再入力。両方失えば紙から再構成 | 完全な無損失を保証しないという固定入力を維持。新規投入を止め、期限に間に合う残りを先に人が扱う |
| 三週の観測と中止 | 各人が受領・入力・実施・転記・照合・復旧の時間と、妻の全件管理へ戻る行い・親子の時間を記録。超過や引受け不成立で新規投入を止め、未完一覧を紙へ渡す | 通常一件・繁忙二件・二日の不在を通す。三教室の作業も別に計上し、学校だけの減少を全体のGの合格にしない |

未完の書出しは用件id・現行原情報と原本の場所・選択と理由・残る行いと期限・担当と引受け・根拠・転記の対象と結果を含む。
backupと書出しは準備・日常・復旧の管理時間へ含め、頻度は開始前と一日の変更終了時、復元は受入れ時と障害時に確認する。
一日の変更分を失う可能性があるため、復旧では原本・紙・calendarとの照合が要る。全く使えないPCから自動的に別PCへ移せるとは仮定しない。

取得済みはT1のSQLiteの指定条件と、材料の机上照合である。
実装後はUIの入力保持・同じcommandの扱い・起動・待受け・backup復元を、上の入力と期待で確かめる。実利用後は人別の時間・役割・余白と望む関わりを三週で観測する。
まだ実施していないものを合格にしない。実行条件が決まれば導入手順を完成させる。

### 5. 決めた設計を渡し、裁量と選び直す差を残す

実装へ渡す候補の要点・詳細はこのdirectoryの材料から読める。層はまだ閉じず、正本へ完成した「どう作るか」は書かない。
[閉じない判断](discussion.md#論点3-現在の入力と根拠でローカル版の設計を閉じられるか)に残る不足を特定した。

| 区分 | 渡すものと、選び直す境界 |
| --- | --- |
| 委ねる裁量 | class・fileの分割、配布の具体、見た目。入力・結果・根拠の意味、固定した利用範囲・費用を保つ。対象PCが決まる前に配布を選定済みとしない |
| 保つ設計 | 原情報の版・token・反映payloadの区別、選択・必要時間の根拠、署名と回収の違い、共有資源の確定時検査、commandと原子的な保存、結果不明の照合 |
| 実行条件の必須の不足 | 家のPCのOS・architecture、導入と運用の権限、runtimeの供給と版、起動・保存・復元が成立する根拠。材料と導入の設計を育ててから閉じを再判定する |
| howへ返す差 | 別のPCや費用、遠隔運用、新しい外部開示、別の担い手が必要な場合。入力の設備・費用・分担が変わるので選定を確かめ直す |
| 実利用で観測する未知 | 所要時間と価値・使いやすさ。今回止まる理由とは別で、受入れの手順と三週の観測へ残す |

実装の細かいtasklistは作っていない。保存契約や導入先の未決を「実装担当の自由」として渡さない。
