## 中身

### 一巡から取り出した仕事と、まとまりの差

[体験](experience-sketch.md)は、原本から始め、本人が行いを引き受け、実際に提出し、変更と不在から続ける。
[logic](core-logic.md)と[情報](data-model/README.md)を使って機能を構成する。
予定への転記と学校での提出は別の結果であり、一つの「完了」へ集めない。

全てを「用件管理」の一つへまとめる案でも作れるが、根拠の現行性と、時間枠の成立と、外の結果不明の扱いが箱の内へ隠れやすい。
三つの機能に分ける案なら、次の入力と結果で継ぎ目を検査できる。class・serviceやdirectoryを三つへ分ける指定ではない。
細かい表示の取得・入力確認・保存ごとに別機能を増やす意味は無く、共有する保存の契約として扱う。
案の採用は層へ返す。

| 機能 | 前提・受け取るもの | 成立させる結果・次へ返すもの | 不足・失敗と続き |
| --- | --- | --- | --- |
| F-A 用件の現行と根拠を保つ | 本人が確認した原本・変更点、参加等の選択、実際の署名・回収の根拠、読んだtoken | 同じ用件の現行原情報と過去の根拠を読み分ける。source変更では古い枠を外し、F-Bに再引受けと候補の再判断、F-Cに対象の差を渡す | 原本・本文の変化が不明なら要確認。古い保存なら現行と未保存の入力を返し、人が対象を照合する。古い画面から実際の出来事が届いてもその事実を黙って捨てない |
| F-B 行いの引受けと枠を確かめる | 現行・残り、本人の明示の引受け、原本を使える条件、必要時間、他用件を含む枠 | 候補と不足を返し、本人が選んだ非重複の枠を保存する。F-Cに用件・行い・原情報・担当・枠を渡す | 確定時のtransaction内で他の用件を再検査。競合・枠なしなら別枠等の判断を返し、20:00以降を勝手に使わない |
| F-C 予定へ渡し、反映した対象を照合する | F-Bの現行payload、用件/行いのmarker、以前の反映payloadと結果 | 人が行う転記・修正の内容を示す。開始前に対象と実施中を保存し、実際に読んだ内容を根拠に確認済み又は結果不明を返す | 現行payloadと違う反映を現行の成功にしない。結果不明ならmarkerと以前の内容から人が照合・訂正し、未作成と決めて二重転記しない |

### 一つの保存の契約と、薄い接続

```mermaid
flowchart LR
  H[家族・原本と学校] --> A[F-A 現行と根拠]
  A -->|現行・残り| B[F-B 引受けと枠]
  B -->|対象payload| C[F-C 予定へ手渡す]
  C --> K[人が既存calendarを照合・操作]
  K -->|確認した結果| C
  H -->|実際の回収の根拠| A
```

各機能が、対象、使った前提、次が使える結果、残る不足を返す。
UIは結果を表示し、保存の共通部分はcommand・token・transactionを扱う。調整役が、現行や提出・枠の規則を別に発明し直す形にはしない。
同じDBのtableを複数機能が使ってもよく、DBやclassの所有境界とこの機能の責任を混同しない。
書込みは一process内で直列化し、BEGIN IMMEDIATEから比較・業務の再検査・変更・command記録をまとめる。
source変更時に現行参照だけを変え予約が残るような半端な保存は認めない。

| 共通の返り | 読み手・人がどう続けるか |
| --- | --- |
| 保存済み | 保存したcommandと対象・結果のtokenを返し、一覧は改めて最新を読む |
| 同じ要求を確認済み | 同じpayloadなら前回の結果を示す。古い結果を最新表示へ上書きしない |
| 古い前提 | 保存せず、最新と未保存の入力を見せて再照合する。無条件にretryしない |
| 枠の競合 | 他用件を含む現在の枠と、候補又は不足を返す |
| BUSY | 更新0件の古い前提とは区別する。結果が不明な要求はcommandを調べ、未実行なら明示の再実行へ |
| 保存先に届かない | 成功を示さず、未保存の内容を紙へ残す。再起動・backupの照合後に取り込む |

### 人の転記が結果不明になる場合の具体の続き

S1/prepareのR1・夫・金曜向けの予定を人が作った後、確認の保存前にブラウザを閉じたとする。
F-Cには開始前に保存したmarkerとtarget_payload・実施中が残る。再開ではこれを結果不明と読み、現行の作業を実施済みにしない。
本人がcalendarの旧予定日と新予定日を開き、markerが同じ予定と内容を照合する。
一つが一致すれば根拠を記録し、不一致なら現行の内容へ訂正して再読取りする。重複なら正しい一つを残す確認をしてから余分を取り消し、再読取りの結果を記録する。
一つも見つからず、対象範囲を確認できた場合だけ新規転記する。読めない・対象範囲が分からない・結果を確かめられない時は結果不明を保つ。
自動で予定を追加しない。残る行いは原本と用件一覧から進め、照合の時間を記録する。
期限に間に合わない又は上限を超えるなら、固定入力の中止条件へ渡し、新規投入を止め紙で残りを扱う。
これらは検査用の人の手順であり、実calendarの操作を行った記録ではない。

### 具体の変更・失敗での機能の照合

R2木曜・本文B1を受けたF-AはR1の署名を消さず、古い予約を外す。
F-Bは連絡できない夫のR1の引受けを現行へ自動転用せず、妻が原本と残りを見て再引受けし、19:45+15分の枠を確定する。
F-CはR1の反映payloadのままなら照合が必要と返す。本文B2へ変わった場合はF-Aの根拠を保ったまま、logicの要確認をF-Bへ渡す。
R2のまま枠だけ変わった場合もpayloadが変わるため、F-Cは古い「確認済み」を現行の成功にしない。
署名とcalendarの反映が済んでも、学校の回収の根拠をF-Aが受けるまでは提出未完とする。

### 他の材料へ返すもの

E1へ、古い前提の保存と未保存の実際の事実の再照合、marker・対象payload・結果不明の表示を返す。
D1へ、source変更と古い予約の除去、枠の確定とcommandの保存を同じtransactionにする条件を返す。
T1へ、古い前提・共有資源・保存途中の失敗・応答を失った再実行・backup後の読取りを確かめる問いを渡す。
導入・停止・backupは層が人の手順へ繋ぎ、この材料へ初回構築のtasklistを取り込まない。

## 確かめた方法と限界

同じS1の原情報・根拠・引受け・予定payloadを各機能へ机上で渡し、R1→R2、R2内の枠変更、署名と提出、保存前後の停止を辿った。
保存の保証はT1の実測を待つ。機能図から実APIや人の操作の成功を保証していない。

### T1からの返り

[指定の保存条件の観測](technical-feasibility/README.md#実行した条件と17項目の結果)で、要求の重複・古い前提・枠の競合・BUSYを別の結果で返す根拠を得た。
機能の入出力にはこの意味を保ち、BUSYなら古い入力を自動適用せず、同じcommandの確認と最新の再読取りへ繋ぐ。
対象PCの実行条件は未特定で、機能図と今回のDB実行だけで導入できる版としない。

### 選択と必要時間の欠けを受けた責任の明確化

F-Aは現行の参加等の判断と根拠を受けて保存し、F-Bは現行の行いの必要時間とその根拠を受けて保存する。
両者は原情報を対象にし、古い判断・時間を自動的に現行の入力にしない。
原情報の変更から返る再確認が揃うまでは、本人の引受けと枠を確定しない。
