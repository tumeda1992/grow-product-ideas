## 検査する範囲

[論点100の採用済み計画](../implementation_review/implementation_review-96-100.md#決定論点100)に従い、新しい検査用の案件をgrow-product-ideaの受け入れから出口へ通す。各層と専門の本文を使って実際の依頼・返り・採否・差し戻しと正本を作り、次が具体の根拠と値を使えるかを区切りごとに検査する。[実行仕様](../design.md#cの一式試運転論点100)が、題材・進め方・各区切りの検査と受入れの正本である。

2026-11-17、**現在のCodex CloudでC1〜C3を受け入れから実際の出口まで通した**。C1は設計のbuild-ready、C2は非開発の部分案を選び「作らない」、C3は具体入力不足で正式な保留。入力と出口を先に対応付けず、各層・専門の依頼と返り、利用者役の採否、差し戻しと読み戻しを案件内に残した。全て検査用の自演で、実際の利用者の合意・実装・実利用の効果は未確認。新規文脈とClaude Codeの実起動も未確認で、論点100の全受け入れの合格とはしない。
作る版が実際に選ばれた場合、必要なラフ・規則・情報・機能と実装構成・技術の根拠、導入・訂正・復旧・受入れと裁量までを繋ぐ。非開発・保留も実際の検討から選び、出口を三種類へ揃えるための入力変更はしない。作る経路を通さなければ、その受入れ項目は未検査とする。
このCで確かめるのは判断と設計のレールである。製品本体の実装・導入・実利用の効果、77の家のPC／実APIの宿題、80と91の保留の解除、shared pluginの改稿は今回の結果へ混ぜない。

### 次の作る前提の再ドライラン

1. 現在の未コミットの方法を含む作業treeから、AGENTS、root README、what-defines-a-product、product-plansの規約、.agents/skillsと.claude/skillsの入口を一時領域の独立した写しへ固定し、対象fileとhashを記録する。実際に使うshared pluginの版/実体も確認する。HEADだけを写して103〜107を落とさず、過去のCの成果やdiscussion、会話履歴は写さない。写しは新規実行の検査入力であり、元の正本を置換しない。
2. [版1の固定入力](inputs.md)の三件を、過去の出力/採否を伴わず写す。別の実行条件の記録に、利用者の「そのあと作る前提でもう1回ドライラン回そう」を出典としてbuild_policy: require-buildを明示する。元のinput/hashは変更しない。作る部分の規模/手段は探索し、成立しなければ保留出来る。三件の出口を先に割り当てず、C2の時間枠やC3の不足を便利な事実で埋めない。
3. 別processのCodexを、resume/forkを使わず新規execで起動する。起動の形は`codex exec --ephemeral --sandbox workspace-write --cd <写しの絶対path> --json -`とし、stdinへ固定入力とこの試行の依頼/操作範囲を渡す。認証やsandboxを回避するoptionは使わない。元の会話や前の答えは渡さず、通常のgrow-product-ideaの入口から、実物のskillを使って依頼/返り/採否/差し戻しを局所で検査しながら出口へ進めさせる。この別実行者は検査用の写しだけを編集し、元のdiscussion/製品/共有cacheを編集しない。
4. 現在の担当が、起動の実際のevent、読んだfileと版、案件の具体の成果と根拠を確認する。別processの自己申告だけで通過にせず、103〜107の意味、部分案が出た時の元の一件との差/必要な依存/追加負担、未確認の扱い、設計の一巡と案件内の読み切れを読む。実利用の効果は試運転の役から補わない。新規文脈の適用とclientの自動発見/実読込みも、証拠がある範囲を別々に報告する。
5. 認証/実行環境等で新規起動が出来なければ、止まった箇所と原因/未確認を残し、同じ入力とrequire-buildで現在の担当がこの会話から再ドライランを続ける。途中で止まった場合も、その新規文脈で実際に出来た所までと、引継ぎ後の結果を区別する。起動不能を成功にも全レールの不成立にもせず、同じ失敗を無条件に再試行し続けない。利用者へローカルのCLI操作を開始条件として求めない。

結果は今回の実行単位の入力/環境/使用版と、各件の成果・具体の摩擦/修正/再検査・残る条件としてこのintegration-check配下へ追加し、案件は元の三件を上書きせず別のslugで残す。生の認証情報は記録しない。新しいprocessが起動しただけで一式の再現を完了とせず、途中の手動補完や根拠不足を隠さない。同じproviderの別processであり、人による独立reviewとは呼ばない。
