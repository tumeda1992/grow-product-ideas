# 習い事の振替を、家族で期限内に使い切るための一覧と通知

子ども二人が通う三つの習い事の振替について、教室ごとに違う規則で決まる期限と残り回数を一つの一覧にまとめ、期限が近づくと家族の二人へLINEで知らせる。妻だけが頭の中で担っていた振替の管理を、二人で分けられるようにする。

- 状態: build-ready

## 受け入れ時の入力

利用者から受け取ったものを、言い換えずに残す。

### アイデア

子どもの習い事の振替の期限と残り回数を管理したい。

### 作りたい動機

失効をなくしたい。こういうのを作るのは好き。

### 既にある着想

期限の前にLINEで通知が来ればいい。

## 解く痛み

<!-- この節を決める問い: why-to-build/pain-to-solve -->

子ども二人が、スイミング、ピアノ、英会話の三つの教室に通っている。欠席した分の振替は、教室ごとに規則が違う。

| 教室 | 振替の規則 |
| --- | --- |
| スイミング | 月2回まで。欠席した月の翌月末まで |
| ピアノ | 年度に4回まで。年度末（3月31日）まで |
| 英会話 | 欠席ごとに発行。発行日から60日 |

| 痛み | 場面 | 頻度 |
| --- | --- | --- |
| 期限と残り回数が散らばる | 三つの教室のアプリ・LINE・紙を見比べる | 欠席のたび（月2〜3回） |
| 期限に気づけず失効する | 期限が過ぎてから気づく | 昨年度5回（約12,500円） |
| 管理を妻だけが担う | 夫は残り回数も期限も分からず、予約を代われない | 常時 |

核心は三つ目の分担である。一つ目と二つ目は、妻が一人で抱える負担の中身である。今は、妻の記憶と、各教室のアプリをときどき開くことでしのいでいる。

根拠: [なぜ作るか 論点1](why-to-build/discussion.md#論点1-振替の規則と昨年度の失効の実態)、[なぜ作るか 論点2](why-to-build/discussion.md#論点2-痛みの核心を一覧や通知ではなく分担に置く)。材料 [target-user-voices](materials/target-user-voices/README.md)

## 何を作るか

### 要求

<!-- この節を決める問い: what-to-build/requirements -->

| 状態 | 条件 | must / better | 線を引いた理由 |
| --- | --- | --- | --- |
| S1 期限が過ぎる前に、二人のどちらかが気づく | 期限の7日前までに、二人が毎日見る場所で | must | 満たさないと失効が残る。7日前は、教室の振替が数日前までの予約を条件にしているため、予約が間に合う余裕 |
| S2 夫が、妻に聞かずに、どの子のどの教室の振替がいつまで何回残るかを知れる | 平日の夜に、家で、予約する時に | must | 痛みの核心（分担）そのもの |
| S3 欠席した時に、期限を規則から出すことが、妻の記憶に頼らない | 欠席の連絡をした当日中に | must | 規則を知るのが妻だけなら、記録も妻に残り、分担が解けない |
| S4 予約済み・使用済みが、二人の間でずれない | 予約した当日中に、もう一方に分かる | must | 夫が予約を代わると、二重予約や取り忘れが起きる |
| S5 欠席の連絡の直後に、1分以内に記録できる | 連絡した人のスマートフォンで | better | 無くても核心は解ける。記録の手間は、状態を保つ手間として対案ごとに比べる |
| S6 期限の計算が人の手を介さない | — | better | S3は、規則を二人が見られれば手で計算しても満たせる |
| S7 予約まで任せられる | — | better | 核心は代われること。予約の手作業は残ってよい |
| S8 失効を年度ごとに振り返れる | 年度末に | better | 核心に関わらない |

二人が毎日見るのは、LINE、家族で共有しているGoogleカレンダー、冷蔵庫の横のボード。夫が予約するのは平日の夜に家から。

根拠: [何を作るか 論点5](what-to-build/discussion.md#論点5-夫はいつどこで振替を確かめて予約するか)、[何を作るか 論点6](what-to-build/discussion.md#論点6-要求を満たされた状態で書き直しmustの線を分担が解けるかで引く)。材料 [target-user-voices](materials/target-user-voices/README.md)

### 代案で残るもの

<!-- この節を決める問い: what-to-build/existing-alternatives-fall-short -->

作らない道（やり方を変える、あり物、組み合わせ）で、mustの状態はほとんど覆える。

| must | 作らない道で最もよく覆う道 | 弱い所（人の手に頼って崩れうる所） |
| --- | --- | --- |
| S1 7日前に二人のどちらかが気づく | 家族の共有カレンダー。二人が既定の通知を7日前にする | 期限の予定の作り忘れ |
| S2 夫が、期限と残り回数を知れる | フォームと表計算（計算式で残り回数まで出る） | カレンダーだけでは残り回数を手で数え、数え間違える。表計算を使うと、期限をカレンダーへ手で写す |
| S3 規則が妻の記憶に頼らない | 規則の共有メモ、または表計算の計算式 | 規則が変わった時の書き直し |
| S4 予約がずれない | 共有カレンダーの予定の名前に「予約済み」 | 書き換え忘れ |

弱い所は、残り回数を数えることと、期限を写すことに集まる。前者は痛みの核心（分担）にある。

作らない道でmustのほとんどを覆えるため、作らないを示しうるが、得たいもの（作る楽しみ）は作らない道では得られない。作らないへは進まず、作らない道を、弱い所を作って消す道と並べて比べる（[解き方](#解き方)）。

根拠: [何を作るか 論点8](what-to-build/discussion.md#論点8-共有カレンダーで相手が作った予定に自分の既定の通知が付くか)、[何を作るか 論点9](what-to-build/discussion.md#論点9-作らずにmustのほとんどを覆えるが作る楽しみと照らして作る道とも比べる)。材料 [alternatives](materials/alternatives.md#覆い方の対案)

### 解き方

<!-- この節を決める問い: what-to-build/solution-shape -->

今日から、家族の共有カレンダーで覆い（作らない道）、作るものとして、フォームと表計算と知らせるscriptを作り、できたら移る。

| 時期 | 覆い方 |
| --- | --- |
| 今日から | 欠席を連絡した人が、規則のメモを見て、家族のカレンダーに期限の日の終日の予定（子・教室・残り回数）を作る。二人が家族のカレンダーの既定の通知を7日前にする。予約したら予定の名前に「予約済み」を足す |
| 作るものができたら | 欠席・予約・受講を、スマートフォンのフォームから送る。表計算が規則の計算式で期限と残り回数を出す。毎朝scriptが表を読み、7日前の振替について家族のカレンダーに予定を作る（二人に通知が届く）。夫は表計算を読むだけで、書き換えない |

作るものは、表計算の計算式と、毎朝カレンダーへ写すscriptである。フォームと家族のカレンダーは既にある道具を使う。

比べた道: 共有カレンダーだけ（作る楽しみが無く、残り回数を手で数える）、着想どおり全部作る（補正後の作る時間が約76時間で、知らせを既にある家族のカレンダーに任せられることを使っていない）、表計算とカレンダーを手で写す（写し忘れでS1が欠ける）。

根拠: [何を作るか 論点10](what-to-build/discussion.md#論点10-今日から共有カレンダーで覆い残り回数と期限の写しを作るものに置き換える)。材料 [alternatives](materials/alternatives.md#覆い方の対案)、[experience-sketch](materials/experience-sketch/README.md#覆い方の対案ごとの流れ)

### リスクと手当て

<!-- この節を決める問い: what-to-build/risks-of-building -->

| 観点 | 内容 | 手当て |
| --- | --- | --- |
| 法務・規約 | 子どもの呼び名・教室・期限は、二人が使っているGoogleのアカウント（フォーム、表計算、家族のカレンダー）の中にだけ置く。外部のサービスへ送らない | なし |
| 依存の継続性 | Googleのフォーム、表計算、カレンダー、Apps Scriptに依存する。Apps Scriptの割り当ては予告なく変わることがある | 受け入れる。止まっても、家族のカレンダーに手で予定を作る道で覆い直せる |
| 実現性 | 毎朝表を読んでカレンダーに予定を作るscriptは、広く使われている仕組みの組み合わせで、実現できない見込みは小さい。家族のカレンダーへ書き込む権限、上限の数値、止まった時の知らせ方は確かめていない | 作り始める時に最初に確かめる |
| 運用 | 規則が変わった時（年1〜2回）に計算式を直す（夫）。scriptが止まったことに気づけないと、期限に気づけない。今日からの道から移る時に、その時点の振替をフォームで入れ直す | 減らす: scriptが毎朝の結果か失敗を知らせ、止まったら気づけるようにする |

根拠: [何を作るか 論点11](what-to-build/discussion.md#論点11-lineを使わず子どもの情報の送り先を増やさない残るのはscriptが止まることと確かめていない権限)。材料 [technical-feasibility](materials/technical-feasibility/README.md#フォームと表計算とカレンダーへ写すscript)、[alternatives](materials/alternatives.md#候補)

## 最初に作る分

<!-- この節を決める問い: how-far-to-build/first-build-cut -->

欠席の登録、期限と残り回数の計算、二人への通知、一覧（期限順、教室ごとの残り回数）、予約済み・使用済みの印を、最初に作る（約16時間）。

規則の編集画面は最初に作らず、規則は設定fileで持つ。規則の変更が年3回を超えたら、編集画面を作る。

通知だけを先に作る区切りは、夫が一覧を見られず予約を代われないため、分担の痛みが解けない。

根拠: [どこまで作るか 論点1](how-far-to-build/discussion.md#論点1-一覧を最初に作る分に含める)。材料 [experience-sketch](materials/experience-sketch/README.md#最初に作る分の区切りの案)、[cost-comparison](materials/cost-comparison/README.md#区切りの案)

## 作る費用と代案の費用

<!-- この節を決める問い: how-far-to-build/build-cost-pays-off -->

| | 作る時間 | 保守の時間 | 代金 | 残る手間 |
| --- | --- | --- | --- | --- |
| 最初に作る分 | 約16時間 | 年約12時間 | — | なし |
| 共有表計算 | — | — | 0円 | 年約2.7時間（入力と確認） |

時間だけで比べると、作る方が1年目は約28時間、2年目以降も毎年約10時間多くかかり、逆転しない。機会損失として、約16時間で他に作れたものがある。後で作る分（規則の編集画面）は約6時間。

費用の比較では作る側が負けるが、得たいもの（作る楽しみ）と照らして続ける。

根拠: [どこまで作るか 論点2](how-far-to-build/discussion.md#論点2-費用は代案に負けるが作る楽しみで続ける)。材料 [cost-comparison](materials/cost-comparison/README.md#作る案と代案)

## 体験

<!-- この節を決める問い: how-to-build/experience -->

1. 教室へ欠席を連絡した直後に、連絡した方が一覧を開き、子ども・教室・欠席日を選んで登録する
2. 期限と残り回数が表示される
3. 期限の7日前に、二人へLINEで知らせが届く
4. 知らせから一覧を開き、教室のアプリで振替を予約し、一覧で「予約済み」にする
5. 受講した日に「使用済み」にする

- 予約しなかったら、前日にもう一度知らせる
- 期限を過ぎたら「失効」として一覧の下へ移り、失効の回数が残る
- 登録の途中で閉じたら、何も保存しない

根拠: [どう作るか 論点1](how-to-build/discussion.md#論点1-予約しなかった時と失効した時の流れを決める)。材料 [experience-sketch](materials/experience-sketch/README.md#体験の流れの案)

## データ

<!-- この節を決める問い: how-to-build/tables -->

| テーブル | 一行が表すもの | 項目 |
| --- | --- | --- |
| `children` | 子ども一人 | 名前、色 |

## モジュール

<!-- この節を決める問い: how-to-build/modules -->

| モジュール | 役割 | 持たないもの |
| --- | --- | --- |
| `rules` | 規則から、振替が発生するか・期限・残り回数を計算する純粋な計算 | 保存、画面、通知 |
| `makeup_lessons` | 欠席の登録、状態の変更、一覧の取得。`rules`を呼んで期限を決め、保存する | 通知 |
| `notifications` | 毎朝、期限の7日前・前日の振替を選び、送っていなければLINEへ送り、送った記録を残す | 期限の計算 |
| `web` | 一覧の画面 | 判断 |

依存の向き: `web` → `makeup_lessons` → `rules`、`notifications` → `makeup_lessons` → `rules`。新しい型の規則は`rules`だけを触る。

根拠: [どう作るか 論点4](how-to-build/discussion.md#論点4-規則の計算を純粋な計算のモジュールに切り出す)。材料 [core-logic](materials/core-logic/README.md)、[modules](materials/modules/README.md)

## 後から返済する負債

<!-- この節を決める問い: how-to-build/debt-to-repay-later -->

| 負債 | 返済のきっかけ | 変える場所 |
| --- | --- | --- |
| 規則を設定fileで持ち、編集画面が無い | 規則の変更が年3回を超えた時、または妻が自分で変えたくなった時 | `rules`と`schools`の設定の読み込み |
| 家族の二人だけの合言葉で守る簡易な認証 | 家族の二人以外が使う時（前提にする条件を見直す時） | `web`の入口 |
| 通知の失敗を見張っていない | 届かなかったことが一度でも分かった時 | `notifications`（失敗を記録し翌朝に再送） |
| 期限の基準が三つの型だけ | 三つに当てはまらない教室が加わった時 | `rules` |
| 講師都合の振替の期限をデータベースで直接空にする | 年に5回を超えた時 | `web`と`makeup_lessons` |
