# modules: 振替を家族で把握する仕組みのモジュール構成

## 要求した問いと粒度

| 問いのidentifier | 問いの文面 | 求めた粒度 | この材料で満たしたか |
| --- | --- | --- | --- |
| `how-to-build/modules` | コードをどのモジュールに分けるか | 全てのモジュールを一度に並べたモジュール構成の案が二つ以上ある程度 | 満たした |

## 中身

### 案A: 層で分ける

| モジュール | 役割 | 持たないもの |
| --- | --- | --- |
| `web` | 一覧の画面、登録と状態の変更の受付 | 期限の計算 |
| `services` | 登録・状態変更・通知の対象の選択・期限の計算 | 画面、保存の詳細 |
| `store` | 四つのテーブルの読み書き | 判断 |
| `jobs` | 毎朝の定期実行で`services`を呼び、LINEへ送る | 判断 |

依存の向き: `web` → `services` → `store`、`jobs` → `services` → `store`。

### 案B: 心臓部を切り出し、扱う対象で分ける

| モジュール | 役割 | 持たないもの |
| --- | --- | --- |
| `rules` | 規則から、振替が発生するか・期限・残り回数を計算する。保存も画面も持たない純粋な計算 | 保存、画面、通知 |
| `makeup_lessons` | 欠席の登録、状態の変更、一覧の取得。`rules`を呼んで期限を決め、テーブルへ保存する | 通知 |
| `notifications` | 毎朝、期限の7日前・前日の振替を選び、送っていなければLINEへ送り、送った記録を残す | 期限の計算 |
| `web` | 一覧の画面 | 判断 |

依存の向き: `web` → `makeup_lessons` → `rules`、`notifications` → `makeup_lessons` → `rules`。循環は無い。

### スコープの外を足す想定での触る範囲

| 足す想定（`what-to-build/scope-in-and-out`の外） | 案Aで触る | 案Bで触る |
| --- | --- | --- |
| 新しい型の規則（例: 3か月で失効） | `services` | `rules` |
| 振替の予約を教室のサイトへ代わりに送る | `services`、`jobs`、`web` | 新しいモジュール1つと`web` |
| 月謝の記録 | `services`、`store`、`web` | 新しいモジュール1つと`web` |

## 確かめた方法と限界

テーブル構成の答え（案A）と、材料`core-logic`の一番難しい部分（規則をdataで持つ）を先に読み、全てのモジュールを並べた。実装の言語やフレームワークは決めていない。
