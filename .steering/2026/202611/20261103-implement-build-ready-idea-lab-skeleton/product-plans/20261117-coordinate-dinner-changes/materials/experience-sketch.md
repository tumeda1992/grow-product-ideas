# experience-sketch: 火曜の変更から引受け/結果までを同じ場面で比べる

適用方法: sketch-experience。選定/費用は行わない。

## 依頼と粒度

| 依頼した層と決めるもの | 何のため | 求めた粒度 | この材料で満たしたか |
| --- | --- | --- | --- |
| [how-to-solve R2](../how-to-solve/README.md#材料への依頼) | 各候補の同じ一巡を比較する | 火曜の希望変更/卵不明→買物/料理/水曜の残りの変化まで | 下記で操作/受渡しと不足を返す。全画面の実装仕様ではない |

## 中身

始点: D2は辛い物以外へ変えたい、C2/D2とも帰宅前で卵/玉ねぎは不明。終点: 二人が今回の料理とその根拠を分け、行える人が次の確認/買足し/調理を明示して行い、結果を渡す。これは机上の検査で、実際の返答/引受けを新たに取得した事実ではない。

```text
N1: D2が変更相談を既存メッセージへ
 -> C2/D2が現物を見た時点/不明を確認
 -> 先に帰れる人が確認を申し出る、又は不明のまま代案を相談
 -> 行える人が返答で引受け -> 実行/できない結果を返す
B1: 同じ人の入力 -> メモ上の作った集約処理 -> 同じ返答/行い
B2: 入力道具 -> 相談文生成 -> 人が既存メッセージへ貼付け
 -> 相手が返答 -> N1と同じ判断/引受け/実行
B3: 共有画面へ変更/不明 -> 相手の明示返答 -> 同じ現物/実行
```

相談文ラフ（生成の一例で実際のC2/D2の発言ではない）:

```text
今日: カレーは変更相談中
希望: 辛い物以外
確認済み: まだ無し（誰/いつを付ける）
未確認: 卵、玉ねぎ
次の相談: 帰宅後に確かめられる人はいるか / 不明で別候補にするか
引受け: 未回答（読めた/通知だけでは確定しない）
結果: 未実施
```

N1もB1/B2/B3も人が確認/返答しなければ終点へ届かない。誰も在宅でない時に確認済み欄を埋めない。水曜の残りを昼に消費した時は、D2本人の消費→次の夕食の前提変更を渡す必要があり、既読や生成文があっても消費を自動検出しない。

差のある失敗は、B1の入力先/自動集約停止、B2の道具をスマホで開けない/貼付け忘れ/古い文、B3の同期不明/二人が同時に別の料理へ変える場合。相手の確認/引受けが無い時は『相談中/未回答』で止め、完了欄を自動にしない。

## 確かめた方法と限界

元の場面を各案へ当てた文字ラフによる机上walkthrough。B1の拡張入口、B2を二人のスマホへ届ける経路、B3の共有/同期は未取得で、この先の操作を具体に通せない。道具が有ると仮定した範囲と実際に開ける事実を分けてR1/依頼側へ返す。使いやすさ/初期30分内の導入は未観測。

## 読戻しでの再評価: 生成文と現状の具体の差

原場面でD2は既に変更希望を送っている。B2の『変更相談中/辛い物以外』の生成だけでは新しい価値の根拠にならない。N1なら同じmessageに『卵/玉ねぎは未確認、帰宅後に確かめられる人又は別候補』を本人が加える。B2なら同じ情報を道具へ入力→文を生成→貼付け→相手返答となる。B2は文組立てを支える可能性がある一方、入口を開く/入力/貼付け/現行との照合が増える。

どちらでも現物の不明は残り、本人の確認/代案/引受けが要る。B2で誰の何の迷い/往復を実際に減らすかは未確認。入口が使えると分かっただけで、このラフを有用な部分改善の成立証拠にしない。再開時にN1と同じ内容で操作と残る行いを比べ直す必要を依頼側へ返す。
