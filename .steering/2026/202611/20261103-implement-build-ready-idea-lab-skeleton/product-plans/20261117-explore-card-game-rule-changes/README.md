固定した検査用入力を、価値の探索から順に検討する。実在の利用者の望み又は実利用の結果とはしない。

## 受け入れ時の入力

以下は検査用の利用者役の原文である。全ての出来事・制約と未確認は[初期入力](input.md)に保持する。

### アイデア

> 自分で考えた一人用のカードゲームがある。休むと回復する量を変えた時、選び方がどう変わるのか遊んでみたい。

### 作りたい動機

> 紙でも遊べるけど、計算や並べ直しで、さっき何を迷っていたか忘れる。

### 既にある着想

> 自分のゲームを動かす小さい道具を作るのも楽しそう。遊ぶ代わりに道具の世話だけして終わるのは嫌だ。

## なぜ作るか

<!-- この節を決める層と決めるもの: why-to-build／体験と価値、アウトカム、作ることで得たいもの -->

### 体験と価値

一人で六手の規則を遊ぶ当人が、計算と並べ直しで初手の見込み・比較したい選択を失う。一回の入力は検査用設定であり、実利用の調査ではない。速さだけでなく、自分の選択や規則の差を試して、次の問いを自分で選べる価値を選んだ。他人と共有する価値は否定せず今回は含めない。

### アウトカム

> 当人が六手の遊びの途中又は後に、同じ出発点の自分の別の選択又は規則の違いを、その時の見込みと結果を混同せずに試して比べ、次に何を試すか自分で選んで遊びを続けられる。

| 持つもの | 中身 |
| --- | --- |
| 言い分 | 同じ出発点、変えた物と結果の根拠、当時の見込みと後の評価、次を自分で選べること |
| 大きさ | 当人一人、六手の蓄えのV0／V1と同じ順序からの一回の比較。共有・全ゲーム・最適解の保証は含めない |
| 測り | 比較後に出発点・変えたもの・見込みと差・次に試すことを当人が示せるか。最初の一回で付随作業の時間を分け、3週の試行で自発的な楽しみと世話の負担を見る。全て未観測 |

### 作ることで得たいもの

自分のゲームを動かす道具を作る楽しみ。選んだ体験へは紙でも届き得るので、作る必要性とは分けて手段選定で時間と比べる。

## 解き方

### 解き方の選択肢

<!-- この節を決める層と決めるもの: how-to-solve／解き方の選択肢 -->

基準は規則と12枚を紙で扱う。一回の値は既知でも分岐時に元と理由を保つ行いが不足する。現状維持、元を残す紙P、表計算と紙S、自作C、当日だけのP-dayを比べた。Pも五条件へ届く見込みがあり、Cの採用のために紙を落とさない。

根拠: [候補・一巡と費用](materials/alternatives.md)、[比較の経過](how-to-solve/README.md)

### 解き方の選定

<!-- この節を決める層と決めるもの: how-to-solve／解き方の選定 -->

六手の計算、元を残す分岐・比較を同期の手元道具Cで支える。規則V0/V1と固定順で、理由・次の問いは本人が選ぶ。作る主な理由は自分の規則を動かす楽しみ。節約は未実測。0円、3週の準備計6時間上限、詳細で更新した三点165/310/570分（旧130/250/470分）の超過リスクを引き受ける。6時間で未完成なら強い次点Pで遊び続ける。今回は目標の五条件を支える版を選び、共有・自動最適化・他OS配布は含めない。実利用での達成は未観測。

根拠: [選定の採否](how-to-solve/discussion.md#決定論点1)、[層の閉じ](how-to-solve/discussion.md#決定論点2)。詳細設計で費用が変わり、[再選定](how-to-solve/discussion.md#決定論点3)で継続を受け入れた。追加の差が出れば再び返す。

## どう作るか

<!-- この節を決める層と決めるもの: how-to-build／実装・導入へ渡す設計 -->

### 選んだ版を成立させる設計

Linux/Pythonの同期CLI。V0/V1と固定順をrootとして不変にし、行いを親付きnodeへ追記、結果は再生する。play/restは親nodeを常に指定して元を消さず、V1は新rootの初期から始める。見込みと後の評価・訂正は別で、未記録は未知のまま表示する。比較は規則・順・経過・理由・手札/蓄え/得点と途中/終了を示し、次は本人が選ぶ。

規則を純粋な遷移、入力と表示、一回の調整、記録検証・保存、比較の組立てへ責務を分ける。保存は固定lock取得後に最新を読み、全制約確認後同directoryの一時fileをfsyncして全量切替し、それから成功を表示する。外部API・常駐・共有は無い。

詳細: [全操作のラフ](materials/experience-sketch.md)、[規則とtrace](materials/core-logic.md)、[型・同一性・例](materials/data-model.md)、[責務と受渡し](materials/functional-structure.md)、[構成と復旧](materials/implementation-structure.md)

### 受け入れの根拠と、導入・修正・復旧

保存processの停止・対照・排他の[6検査](materials/technical-feasibility/README.md)は現Linuxで実行済み。本製品は未実装。元の六手、別初手、V1、無効・終了・6手目補充、理由の追記、停止と競合・不正記録・保存失敗の製品受入れは[設計の記録](how-to-build/README.md)に入力と期待を渡した。

当人が保存directoryを選びstartの順を原規則と照合する。誤った手は親から別枝、誤記は追記。停止後はlistで保存済みnodeを確認。破損は上書きせず保存先を退避し、読める控え又は紙の新しい試行へ戻る。失った過去の理由は復元しない。6時間で受入れ未達なら制作を止めPへ。初回と3週目に比較の理解、作業時間、楽しみと世話の負担を測る。実利用の達成は未観測。

### 設計上の裁量と、再判断する境界

関数/class分割、色、表示順序は委ねる。元の履歴、親の明示、規則再生、理由の区別、成功の保存境界を省く判断は戻す。別OS・共有・規則追加・費用増・世話の圧迫も選定へ戻す。電源断/device故障は保証しない。準備165/310/570分の不確かさを保持する。

根拠: [設計の過程と確認](how-to-build/README.md)、[設計の採否](how-to-build/discussion.md#決定論点1)、[閉じ](how-to-build/discussion.md#決定論点2)

## 出口

build-ready。作る版の四層を閉じ、必要な専門材料と保存の限定検証、全場面の仕様・受入れと復旧を揃えた。製品実装・実利用の改善は未完であり出口は設計準備の完了。

directoryの写しを新しいrepositoryへ持っていき、後続の初回構築の入力にする。写し・命名・repository作成は利用者が行う。この試運転では実施しない。

根拠: [出口の採否](discussion.md#決定論点1)。全ての当人役の応答は検査用の自演である。
