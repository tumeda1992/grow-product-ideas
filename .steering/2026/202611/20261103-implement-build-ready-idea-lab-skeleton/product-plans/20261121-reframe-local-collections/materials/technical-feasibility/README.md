## 中身

### 検証する主張と実施前の条件

候補は未採用。公開サイト・資料室・実在のネットワークへ接続しない。PC内で動くPythonとSQLiteの局所構成の性質だけを確かめる。

| 主張 | 入力と方法 | 期待・反例の観測点 |
| --- | --- | --- |
| 別の問いの状態を増やしても既存の片付け番号の意味を保てる | [catalogの写し](existing-site/catalog.json)と[packing_listの写し](existing-site/scripts/packing_list.py)を読み、別DBに問いを保持。前後にpacking_listを実行 | 17/A1・18/B2・19/C1が同じ型・値・対象で一致。原fixtureのhashも不変 |
| 古い管理画面は新しい採否を上書きしない | 二つのSQLite接続が同じrev1を読み、Aが承認後Bがrev1で取下げ、再読後に取下げ | 古いUPDATEは0件、現行は承認rev2。再読後は取下げrev3。0件を成功表示しない |
| 保存直後に応答が失われても同じ受付を増やさない | 同じ受付キーと内容を再送し、別接続で行数を見る。別内容で同じキーも当てる | 同内容は同一行、別内容は衝突。応答不明はキーで照合する |
| 途中停止で半端な状態を残さない | 別processのtransactionで変更し、commit前に終了。commit後終了も別に検査 | 前者は旧状態、後者は確定状態が別接続から読める。応答と確定を混同しない |
| 取下げ・期限終了を新しい読取りと印刷候補から除ける | active/withdrawn/pendingと期限の異なる合成問いを同じ対象へ置く | activeかつ期間内だけを返す。紙の回収・既に見ている画面の消去はこれだけでは証明しない |
| 人の言葉をHTMLとして実行しない | 合成のscript風文字列・引用符・改行を表示用にescapeしHTMLParserで要素を見る | script要素を作らず文字として保持。実browser・実装全体の安全性をこの一例で保証しない |

### 取得した対象

初期fixture三fileをこの材料へ写し、原物を変更しない。catalogのnumberは数値、titleは袋・道具・写真、shelfはA1/B2/C1。問いの識別子と資料番号を別にする。写真画像は取得も複製もしていない。

## 確かめた方法と限界

Python 3.12.14 / SQLite 3.53.1で[probe.py](probe.py)を実行した。処理時間・施設の端末・LAN・本番サイト・実利用の効果は未検証。特に表示済み画面と紙を止める運用の根拠は別に要り、DBの除外だけでC5を保証しない。

### 実行結果と依頼側へ返す差

2026-11-22の局所検査で、二接続のrev1読取り後、Aの承認は1行、Bの旧rev更新は0行で現行active/rev2を保った。再読して取下げるとwithdrawn/rev3、新しいSELECTは空。commit前に子processを終了するとwithdrawn/rev3を保ち、commit後終了ではactive/rev4を別接続から読めた。同じ受付キーを再送しても1行、違う内容は衝突として拒否。期限200に対し199では読め、200では読めなかった。
script風の合成文字列はp要素内の文字として保持され、script要素は作られなかった。packing_listは前後とも17/A1・18/B2・19/C1で数値型も維持。結果・実行環境の実物は[observations.json](observations.json)。
依頼側へ返す不足は、DBから除外しても表示済み画面や紙は消えない点。貸与端末一台と管理した紙だけへ配信を限定し、取下げ時に端末を覆って旧紙を回収・画面を再読してから完了にする等の仕事が要る。自由な来館者端末へのQR公開では同じ回収根拠を使えない。この人の行いと費用を候補比較へ返す。

実施設LAN・貸与端末のbrowser・プリンタ・実装のHTTP処理・時計のずれは未検証。小さなprobeを製品本体の実装済みとはしない。選定後に保持期限と物理的な消去手順を設計し、実装後の受入れへ渡す。

### 追加のHTTP・同時操作・本文消去を確かめる実施前入力

[how-to-solve論点1の実応答](../../how-to-solve/discussion.md)は、局所のアプリの振舞いと同時操作を材料側で確かめ、本番と分けることを求めた。Kはまだ選定の応答待ちだが、比較と後の設計に使う技術の問いとして検査する。
対象はPCのlocalhostにだけ起動する検査用HTTP口と一つのSQLite。実施設のLANや貸与端末には接続しない。ブラウザ操作や物理回収の証明はしない。

| 問い | 実施前の入力と順序 | 観測する結果 |
| --- | --- | --- |
| 二つの同じ受付が競合しても一つとして照合できるか | 同じ受付キー・同じQ17を二つのHTTP接続から同時にPOSTし、別DB接続で行数を読む | 1行。どちらも同じID。違う本文で同じキーは409 |
| 古い画面からの更新をHTTP結果で区別できるか | 二接続がrev1をGET、同じrev1で承認と取下げを競合させる | 一方のみ200、他方409、DBのrevは2。拒否を成功表示にしない |
| 読取り専用口の書込みを拒否し、期間外を返さないか | viewer口へPOST、pending/withdrawn/期限の境界へGET | 書込み拒否。新しいGETにeligibleだけ。Cache-Control no-store。画面の旧表示は別に扱う |
| 本文消去は残すメタデータと分けて行えるか | 終了して本文/照合用payloadを消し、secure_delete=ON・journal=DELETE・VACUUM後にDBを閉じ、生byteも調べる | API/DB論理読取りは本文無し。今回のファイルで合成文字列のbyte列も不在。OSの別backupや写真・過去の印刷まで消した保証にはしない |

これは局所検査の期待であり、結果を得る前に成立としない。本文を消した後の受付再送は元本文との照合を再開せず、閉じた期間として拒否する設計上の境界も確かめる。

### 配分s1の実施前入力

[core-logicのs1と有限例](../core-logic.md)を使い、SQLite上で予約と引受けを同時に確定できるかを確認する。全17が12件、3対象4件ずつ、11:09の集中、11:10ちょうど/1秒後、二接続の最後の同じ枠を検査する。期待は順に4/12/1/1/0件の受理、競合は一枠に一件のみ。方式の採用ではなく、候補の規則と保存の接続の確認である。

### 追加検査の取得結果

[http_probe.py](http_probe.py)をlocalhostで実行し、同じ受付の同時HTTP要求は201/200で同一ID・DB一行、別内容の同じキーは409。二つのrev1画面からの競合更新は200/409でrev2を保った。viewerのPOSTは405、新GETは取下げ/期限後に空、no-storeを返した。本文消去後は論理値がnull、期間の再送は410、今回閉じたSQLiteファイル内に合成本文のUTF-8 byte列は無かった。[実測JSON](http-observations.json)はOSのbackupや印刷の消去までは保証しない。
[allocation_probe.py](allocation_probe.py)でs1を実行した。全17の12入力は4受理、均等は12、11:09に同じ17が3件は1、締切ちょうどは1、1秒後は0。最後の同じ一枠を二接続が争った場合は一方だけが受理し、再送は同じ予約を返した。[入力・途中結果の実物](allocation-observations.json)へ結ぶ。予約の一意性を確認したのであって、物理表示や実来館者の見直しを観測したものではない。

### 情報モデルを同じQ17へ接続する検査と、最初の方法不備

[model_probe.py](model_probe.py)へ、提案schema・Q17/17/左室・土曜10:20枠・紙Q17-P1・旧rev・取下げ・F0の入力とassertによる期待を保存して実行した。最初の実行は `table prompt has 10 columns but 11 values were supplied` で、Q17のINSERT前に停止した。十項目のtupleに十一個のplaceholderを書いた検査codeの不備であり、保存方式や設計の不成立の証拠ではない。この実行では後続の外部キー・表示・消去を確認できていない。
INSERTのcolumnを明示してplaceholderを十個へ直し、同じ入力/期待を再実行する。別対象Q18を17枠へ結ぶ検査は、単なるUNIQUE違反と複合外部キーによる拒否を分けて観測する。

### 情報モデル接続の再実行結果

placeholderの不備を直した[model_probe.py](model_probe.py)を同じ入力で再実行。Q17/17/土曜10:20の予約を読み、別Q18/18を17の枠へ結ぶ更新は複合外部キーで拒否した。coveredの時の新読取りは空。合成の紙/画面確認後はQ17/17/袋/左室/visitor/本文/rev2/epoch2を返し、棚A1を表示場所へ使わなかった。旧rev1の更新は0行。
取下げ準備で新GETは空でも、紙の状態はplacedのまま残り、回収を推測しなかった。合成の回収確認を渡した後にwithdrawn/回収済みへ進めた。日曜F0相当の処理ではprompt/paper_copy/current_displayの個別行が0、aggregateが1行、catalogの17/A1・18/B2・19/C1は不変。閉じたSQLiteで合成本文のbyte列は不在、integrity_check=ok、foreign_key_checkは空だった。[観測結果](model-observations.json)。
この最終モデルのF0は、先のHTTP probeの『本文null・メタデータ残存』より範囲が広い。前の結果だけで集計以外を消したとはせず、個別行を消す根拠はこちらを使う。確認フラグは合成入力であり物理回収の観測ではない。OSの別backupとプリンタ内部の保持はこのDB検査の対象外。
