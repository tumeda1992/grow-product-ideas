## なぜ作るか

### 体験と価値

C1の架空の紙の一回では、初手A3の理由と、初手A2へ戻る時の山札位置を後から戻せなかった。計算時間だけを減らすことより、自分の迷いと別の考えを比較することに価値を置く。演出・配布・最適手の提示は今回の望みとして採らない。

### アウトカム

C1が同じ順序でV0とV1を別々に六手遊び、途中の選択と理由を取り違えずに別分岐から試し直し、違いを自分で振り返れる。

| 持つもの | 中身 |
| --- | --- |
| 言い分 | G1規則と状態を混ぜず遊べる。G2元の試行・別分岐と選択理由を区別して戻れる。G3同じ順序の別版を自分で比較する |
| 大きさ | 一人・12枚・六手・V0/V1。初回の2回と1分岐を比較する。長期の面白さ・他者・他端末を含めない |
| 測り | 初回後に原記録へ戻り、順序/版/初手の理由/分岐点を照合し、選択へ時間を使えたか・世話だけになったかを振り返る。総時間と管理の行いを分け、速度だけで価値にしない。未実施 |

### 作ることで得たいもの

この自分のゲームの小さい道具を作る楽しみは資料にある。遊べなくても制作だけで続ける望みは未提供。制作が遊びを置き換える・6時間超・定期保守が必要なら解き方を再判断する。

## 解き方

### 解き方の選択肢

基準は規則を直接見て12枚を紙で扱い、状態/理由の六行票と別紙分岐を本人が残すこと。正しく行えば条件へ届く見込みがあるが、計算と山札復元の負担を残し、実装部分は無い。

| 補う点 | 選択肢 |
| --- | --- |
| P1状態と山札の管理 + P2元試行/理由/分岐の対応 | 紙票、表計算の計算式+紙、端末対話/自動保存、browser、read-only履歴再生command+本人のfile保持 |
| P3このゲームの小道具を作る楽しみ | 対話道具又は再生commandでゲームの規則処理を実装する。非開発の道へ無関係なscriptは足さない |

### 解き方の選定

B4を採用する。作るのは、本人が保存したJSON入力の検証、V0/V1の規則再生、全prefix状態/合法行動と二入力の比較表示。本人はその場で行いと理由を選び記し、fileを保存し、分岐前に元を保持して別fileへ写し、同じcommandを再実行する。道具は入力を書き換えない。

次点B2の対話/自動保存は入力の利便性を買うが、見積り3.25/6.5/10.75hで6h上限と合いにくい。B4は2/3.75/6hの無補正見立てで、fileの編集/複製を人へ残す。準備は6hを上限とし、完成不能なら止めて保留又は選び直しへ返す。追加契約0円、定期処理/毎週保守を置かない。個人の工数実績は未提供であり、見積りや初回の負担が実測した値ではない。

初回は同順序のV0/V1各六手と初手の1分岐を扱う実験版。条件W1〜W3を目指すが、実装・実利用の達成は未確認。人の理由記入・元file保持が欠けた回はW2達成としない。比較の楽しさ/入力の負担は初回後にwhyの測りで確かめる。

作る理由は、状態と山札の再計算を遊びへ返すことと、この題材の小道具を作る楽しみを分ける。規則不一致、6h超見込み、毎週保守、fileの世話だけになる、原試行を失う、別端末/規則を必要とする時は選び直す。

根拠: [候補/費用と限界](materials/alternatives.md)、[一巡のラフ](materials/experience-sketch.md)、[選定と合成応答](how-to-solve/discussion.md#論点1-履歴再生commandと本人のfile管理を組にして選ぶ)、[層の閉じ](how-to-solve/discussion.md#論点2-層を閉じる)。

## どう作るか

### 選んだ版を成立させる設計

このLinux/Python 3.12.14で、標準libraryだけのread-only commandを一つ作る。本人がUTF-8 JSONへschema1/label/rule/order/actionsと理由を保存し、`python3 replay.py run.json`で一手ずつ再実行する。道具は一度読んだbytesのhash/pathと版を示し、原規則から全prefixの手札/山札位置/捨札/蓄え/点/成立手数と現在の合法行動を返す。入力fileを書き換えない。

情報のD2案を採る。JSONのactionsはkind=play/rest、play時card、本人reasonが必須。新試行で空理由を通さず、旧紙移行の不明理由はlegacy=true/nullとして未記録/W2未達を明示する。labelだけで同一性を決めず、読込snapshotのpath/hashで識別する。状態の二重正本は保存しない。

分岐は本人が元fileを先に保存して別pathへ写し、戻る手までのactionsを残して別の行い/理由を足す。二入力を指定すると、同順序かを検証し、同版なら共通する行動prefixと最初の差を計算してそれぞれの状態/理由を示す。異版は同状態の分岐とせず版比較と表示する。親hashの転記は要求せず、過去の親来歴を証明する製品にはしない。元fileを保つ人の行いはW2へ届くために残る。

受付/再生/比較/表示の責務を分け、一processの中で繋ぐ。不正actionは直前状態を変えず拒否し、その後をskipして完走にしない。schema/parse失敗は状態を作らず、未完は途中結果、六手後は最終点のみとする。exit0は再生成功、exit2は入力/不成立/比較不能、exit1はOSの読取/出力等の失敗。最適手の推薦はしない。

詳細: [全場面とD2差](materials/experience-sketch.md)、[原規則の遷移と訂正済み検査例](materials/core-logic.md)、[型/正本とD2](materials/data-model.md)、[機能の受渡し](materials/functional-structure.md)、[実行/停止/導入](materials/implementation-structure.md)。

### 受け入れの根拠と、導入・修正・復旧

取得済みは、同環境のruntime、日本語JSONの保存/再読と、比較用の置換/lockの限定probe。probeにゲーム本体は含まれず、選んだread-only構成は自動保存の耐久性に依らない。[対象・観測と限界](materials/technical-feasibility/README.md)を参照。

実装後、原文のV0六手の全状態/点7/蓄え2、同列V1の点7/蓄え5、初手A2分岐の手1点2/蓄え1、不正B5拒否、上限/七手目、六手目補充の訂正済列で点8/蓄え1/next7、入力が変わらず再実行できること等を[設計の受入れ表](how-to-build/README.md#4-導入修正復旧と受入れの確かめ方を設計する)で確かめる。全て未実施。

導入は同じ環境にscript/説明/空actions例を置き、本人が原初期値を照合して始める。誤記は本人が位置を確認して入力を直し再実行。途中出力は捨て保存済入力へ戻る。元fileを失った場合は保管copyを本人が確認し、無ければその試行は失われたとして新回又は紙へ戻る。未知schema/新規則は自動推測しない。実利用の初回には、修正を含む操作回数/時間/管理の行いと、理由や迷いへ戻れたか/世話だけにならなかったかを本人が測る。便益と楽しさの実績はまだ無い。

### 設計上の裁量と、再判断する境界

関数名/内部配置、表の横縦、装飾は、情報と責務/不正拒否を保つ範囲で実装担当が選べる。schemaの意味、規則、本人の理由、元保持の分担、read-only、比較/未完/エラーを変えるなら設計へ返す。新規保存/同期/親転記、6h超/毎週保守/追加費用、対象端末や規則を広げる差、世話だけになる負担は解き方へ戻す。残す未知は実装速度の無補正見積りと初回の使いやすさ/面白さで、6h上限と初回振返りで再判断する。

根拠: [選んだ設計と継ぎ目の照合](how-to-build/README.md)、[D2の合成採否](how-to-build/discussion.md#論点1-元の二履歴から比較するd2を採る)、[設計の閉じ](how-to-build/discussion.md#論点2-層を閉じる)。
