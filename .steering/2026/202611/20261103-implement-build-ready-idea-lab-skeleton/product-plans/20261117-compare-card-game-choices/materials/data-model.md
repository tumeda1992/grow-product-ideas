## 中身

### 読取りと情報の出所

本人が保存したJSON一つを一つの試行とする。人がrunを識別するのは表示名だけでなくpathと読込bytesのSHA-256である。ruleは原規則、orderは本人が定める順序、actionsとreasonは本人の行い/語り。状態と最終点は再生結果で、外部在庫等の事実は無い。

### 文書構造案と制約

ここは比較した旧候補Dの記録。現行採用は[分岐注記を省くD2](data-model.md#追加比較d2-分岐元の注記を必須にしない)であり、下表のbranch fieldとその親hash転記/検証は実装へ渡さない。他のschema1のfield/型とread-onlyの意味はD2へ引き継ぐ。

採用候補Dは入力履歴から状態を導出する形。対案Sは全状態を手入力/保存する形だが、得点と行動の二重正本が食い違う時の照合/訂正が増える。Dは再生が必要でも六手であり小さい。専門はDを候補として返し、採用は層へ残す。

| JSON field | 型と必須 | 制約と意味 |
| --- | --- | --- |
| schema | integer、必須 | 1のみ。boolをintegerとして通さない |
| label | string、必須 | 表示用。空白のみ不可。一意性の根拠ではない |
| rule | string、必須 | V0/V1のみ。途中変更不可 |
| order | string配列、必須 | 長さ12、A1〜A6/B1〜B6の集合と一致、重複0 |
| actions | object配列、必須 | 長さ0〜6。配列index+1が成立候補手番号 |
| actions[].kind | string、必須 | play又はrest |
| actions[].card | string、playのみ必須 | 正規ID。rest時はfield自体不可 |
| actions[].reason | string又はnull、必須 | 本人の記入。新しい試行では空白のみ/nullを許さず、既存原紙の不明理由を移す時だけlegacy=trueでnullを許す。nullを推測で補わない |
| legacy | boolean、任意（default false） | 過去記録を移すための申告。trueでも理由が不明ならW2未達と表示 |
| branch | object、任意 | source_label:string、source_sha256:64桁hex、after_turn:integer 0..6。元copyを保った時点の注記であり、このfieldだけで元の保持を保証しない |

未定義fieldは誤記の検出のため拒否する。入力サイズはこの規則に要る短い手動fileに限定し、1 MiB超は拒否、reason/labelの制御文字を拒否して端末への制御列を出さない。日本語はそのまま。これらはschemaと安全な表示の設計上限で、本人の個人データの新事実ではない。

### 読取りと変更の具体

read(path)でbytesを一度だけ読み、size/UTF-8/JSON/schemaを確かめ、SHAとparsed文書を同じsnapshotとして下流へ渡す。logicはその文書のrule/order/actionsだけを読む。出力にpath/hash/labelを添え、現在のfileの最新版を後から再読して同じ結果に結び直さない。

本人が次の行いを足す時は表示を読み、actions末尾へkind/card/reasonを一つ追記して保存、再実行する。実行中のfile更新は、その実行には入らない。次の実行で別hashとなる。file全体の部分保存でJSONが壊れれば受付拒否、本人が保存を完了/修正後に再実行する。

分岐は本人が先に元fileを保存して別pathへコピーし、元hash/labelとafter_turnをbranchへ記す。コピーのactionsをafter_turn件まで残し別の選択を足す。commandは元もコピーも書き換えない。比較時にbranchがあるなら、もう片方がsource_sha256と一致する場合だけ元参照を検証し、そのprefixが一致するか確認する。元copyが渡されない/変わってhash不一致なら『分岐元未照合』を表示し、正式な分岐比較成功へ替えない。比較可能な二回としても順序/版/行動の差を必ず表示する。

反例: labelが同じ二fileでもhash/pathが違えば別試行。途中のscoreを入力へ追記する誤記は未知fieldとして拒否。branchのafter_turn=1なのにprefixの初手が変わるなら、元hashが照合できた時は分岐不整合として拒否。親の最新版へsource_shaを無断で付け替えて成功としない。

旧紙移行では入力の初手理由だけ原文から移せる。他の理由をnullにしlegacy=trueにする。W1の原表照合には使えるがW2全理由保持には不足と表示する。新しい試行の空理由は本人へ入力不足として返す。

### 不足と引継ぎ

schemaの例をH1に統一する必要がある。前の比較用ラフのplay/restキー案とは型が違うので、前の記載を履歴として残し現行はこのkind形式へ繋ぐ。元fileを人が保つ行いは依然必要で、hashを持っただけで失った元を再生できるわけではない。


## 確かめた方法と限界

規則V0/V1と原表、B4の選定と他の専門材料を同じ入力で机上照合した。本製品は実装していない。実際の入力負担や面白さ、実装の正しさは未観測。

## 追加比較D2: 分岐元の注記を必須にしない

上のD案をH4/H5と照合したところ、本人がsource_sha256を手で写す行いが増える。B4は元fileを本人が保持する分担であり、その行いをhash欄だけで保証することもできない。別案D2では、現行のschemaはschema/label/rule/order/actions/legacyだけとし、branch fieldは設けない。上のD案のbranch field/注記照合は比較した不採用候補で、D2の実装仕様ではない。

二つの入力のrule/orderを読み、同版ならactionsのkind/cardを先頭から比較して、最初に異なる位置の手前を共通行動prefixとして導出する。理由文字列は各試行に属したまま別欄に表示し、理由が同じだから同じ試行と統合しない。片方がprefixのまま短い時は『ここまで同じ、片方未完』であり、実際に別行動を選んだ分岐とはまだ言わない。異版ならruleが最初から違うため、共通行動はあっても同状態の分岐とは呼ばず版比較とする。

元試行の同一性は読み込んだpath/hash/labelで残り、元fileの保持は人の仕事として変わらない。分岐元hashの転記/親の参照整合という追加部品を省ける一方、ある入力が過去のどの親から複製されたかの来歴証明は届けない。W2の『元試行を残し指定手前から別試行』は本人の元保持とprefix編集、道具による両履歴の状態再生/共通prefix表示で成立する。実際の保管を確認したことにはしない。

現行案D2の例: 元V0[A3,rest,A2]と別V0[A2]は共通行動0、第一手が相違。元V0[A3,rest,A2]と別V0[A3,rest,B2]は共通行動2、第三手で相違（手2の両状態は同じ）。入力例の理由は本人が書くもの、架空の好反応へ替えない。
