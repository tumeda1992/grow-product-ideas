### 判断: 中核logicの専門を何に使い、何を返せば設計へ繋がるか

#### 判断対象・必要条件・使う根拠

新規design-core-logicの構成と、登録・案内を揃える変更集合を判断する。
必要条件は、与えられた価値・状態・選んだ範囲を保ち、根拠となる事実から結果を出す規則や処理方式を設計し、具体の入出力・境界・不足から採否と後の設計へ使えることである。
計算の難しいalgorithmだけへ狭めず、判断規則や生成が中核になる場合も扱う。同時に、体験の全体設計、保存構造、処理の実装方式、技術の実証を一人で代行しない。
決定表・状態遷移・具体例の検査は必要な所で使い、全ての題材に同じ表と四項目を機械的に埋める方法へしない。

根拠は旧design-core-logic全文、現行sketch-experienceの責務と返し、層のREADME・how-to-build、材料の入口、root READMEと作業designである。
学校の検査用仮説で、15分の作業と最後の可用枠、引受けの19:45/19:46、署名と提出の区別へ当てる。
不足する事実を便利に埋めず、候補とその成立条件・未知を返せるかを見る。
別題材には読書メモから行動案を生成する仮説を使い、一意の正解や決定表が無い処理にも専門の問いが働くかを机上で見る。
実際にコードや生成モデルを動かした証拠にはしない。

新規fileはoutlineのみ、既存fileは完全diffにし、実repositoryへ適用しない。
設計時skill-update-reviewとdocument-reviewを行い、outlineに合意後の本文の作成・実fileのreviewを省略しない。

#### 旧い方法から残すものと、必要な深さ

旧design-core-logicの全文を、現行の依頼・返し方と比較した。
旧版は中核の処理を入出力で定義し、境界・最難部・回避と正面案を見る働きを既に持つ。これらを新しい発見として上書きしない。
ただし四項目を書くことと、何が結果を正当化する規則で、何の事実が無ければ判定できず、どう反例から規則を直すかを実行できることは異なる。
正本の固定の節と旧settle-questionへの依存も、現在の層と材料の依頼へ直す必要がある。

sketch-experienceは、誰が何を見て判断・実施し次へ渡すかを作る。core-logicは、その中の処理が、どの入力・根拠・規則から結果を出すかを設計する。
情報構造はそのために何を保持し識別できる必要があるかを受け、処理の設計は実際の責務と受渡しへ使う。
core-logicが保存tableや外部再送の実装まで抱えると、専門間の境界を失う。必要な状態と外部の性質を返す所に止める。
利用者が受け入れた未達や負担を自分の規則で変えることもせず、条件変更が必要なら依頼側へ返す。

専門の定石は、必要な結果から規則を導くこと、条件が重なるなら決定表や優先関係で矛盾と空白を見ること、状態で結果が変わるなら出来事と遷移で見ること、具体の入力と反例から規則や方式を検査することである。
計算・探索・生成なら、その方式で守れる性質と破れる入力を問う。全てを決定表にしない。
これを個人版では与えられた事実と検査用仮説で机上実行する。実技術・生成モデルの性能や利用者の価値を観測した証拠にはしない。

#### 学校の検査用仮説へ当て、規則と次の設計への要請を取り出す

現在の模型を作る版へ選び直さず、logicが必要な設計を仮に検査する。
固定していた設定から、最後の作業可能枠が水曜19:30〜20:00、残る作業が15分で、実際の引受け後に始められる場面を使う。
この検査での15分は確認・署名・準備に必要な時間で、記録を押す時間や学校の提出が完了する時間へ読み替えない。

入出力の名前だけなら「締切・担当・作業時間を受け、予定を返す」で止められる。
しかしそれでは、引受けが19:46の時にも予定を作って、間に合うと見せる結果を排除できない。
必要な結果から規則を作る案では、作業を実施できる枠、残る作業時間、開始できる根拠が要ると取り出し、候補枠で終わる時刻を計算する。

| 入力の差 | 根拠から辿る結果 | 次の設計へ渡す要請 |
| --- | --- | --- |
| 実際の引受けが19:45、残作業15分 | 最後の枠で20:00に終えられる。条件内の候補がある | 引受けの事実と時刻、現行の残作業、使える枠を区別して取得する |
| 引受けが19:46、残作業15分 | 20:01となり、選んだ条件内に実行枠が無い | 家族の時間や負担を勝手に増やさず、成立しない理由を依頼側へ返す |
| 引受け19:46、残る作業が5分という検査用の変更 | 19:51となり、その枠には入る。19:45という時刻を普遍の締切として固定しない | 作業全体の所要と残作業を混同しない。規則は時刻の定数でなく、残作業と枠の関係を持つ |
| 残る作業時間が未確認 | 成立・不成立の断定に必要な事実が足りない | 推測値を0にして予定を成立させない。不足と、値が分かれば変わる判定を返す |
| 一覧へ署名済みと入るが、提出の根拠が無い | 署名済みから提出済みは導けない | 何の出来事・根拠で完了を判断するかを別に受け取り、必要な情報・操作へ返す |

この例は一件なら直接の規則で足り、複雑な探索や必ず二案のalgorithmを必要にしない。
複数用件が同じ枠を取り合う等、別の方式で差が出る依頼なら、その違いを同じ具体の入力で比べる。
最も難しい部分を避ける案も有効だが、避けて必要な価値・範囲・人の負担が変わるなら、その差を依頼側へ返して選んでもらう。

#### 一意の正解を置けない生成の例で、守備範囲を確かめる

異なる検査用の仮説として、読書メモから、来週一回試す行動の候補を生成する依頼を置いた。
与えるメモは「朝の集中を守るには、割込みのきっかけを減らす」という検査用の文章であり、実在の書籍の引用ではない。
「集中を大切にする」と返すだけなら要約はできても、何をするかを選ぶための候補になっていない。
行うことときっかけ、その案がメモのどこから出たかを返す方式なら、例えば朝に通知を止める案を、根拠のある提案として検査できる。
メモに書かれていない時間や方法を足すなら提案として分け、著者の主張や確認済みの効果へすり替えない。

候補は一意でなく、決定表の正解一つでは採点できない。それでも、入力にない根拠を創作しないこと、行動として選べる具体があること、指定された制約を守ることを問える。
方式の案、品質を判断する具体例と失敗例、実際のモデルへ試していない限界を返す材料は作れる。
この机上検査だけで、生成の成功率や本人にとっての有用性を観測したことにはしない。外部技術の実証や価値・選定の問いは依頼側へ返す。
したがって、専門を決定的な業務判定だけへ狭める案も、どんな入力でも自由生成してよいという案も採らない。

#### 推奨と、構成へ残す代償

design-core-logicを、与えられた状態と範囲に対し、入力から結果を出す中核の規則・処理方式を設計し、具体の入力と反例から案を判断できる材料へする専門として立て直す。
必要な結果から入力と規則を導き、方式を組み、具体で検査して、次の設計へ必要な情報・条件と不足を返す構成を推す。
旧版の入力・境界・最難部を見る仕事を残し、固定の四項目・回避案と正面案の機械的な最低数を方法の中心にしない。
案の比較が要る所で意味のある違いを育て、必要ない難しいalgorithmや形式上の対案は作らない。

正本・保存・module・API検証を全て担当する専門へ膨らませず、それらが満たすべき要請を返す。
代償として、このskillだけで製品の設計は閉じない。特に外部の結果不明や生成性能は、技術の実証が無いまま成立したと扱えない。
この代償は論点71の分担と一致し、残る専門や実際に作る版の検証を案内から消さない。

### 合意の反映と実物の検査: 中核logicの方法から材料を育てられるか

#### claim・合格条件・方法

提案0への合意をdiscussionの対応する欄へ原文とともに一度保存した。本文作成と既存四fileの適用を行う。
新規skillは合意したoutlineを保ち、必要な結果から規則を導く方法、条件の優先・重なり・空白、方式の比較、具体の境界と反例、専門間の受渡しを読者が実行できる本文へする。
同じ材料を粗い依頼から細かい依頼へ育てられ、以前の依頼が読んだ所を変える時に、その影響と理由を返せることも見る。

本文を実際に読んで学校と生成の検査用材料を作り、入力・根拠・規則・結果・未確認を分けて返せるかを確かめる。
学校は19:45/19:46、残作業5分、時間不明、署名と提出の境界を使う。追加の仮説で複数の用件が同じ枠を取り合う時、単独で収まるだけで両方を成立させない規則を問う。
生成は検査用の読書メモから行動候補を作る方式を、根拠・制約・有用な具体と失敗例で比べる。自分が書いた例を実際の生成モデルの成功率や利用者の採否にしない。
材料の試作は一時領域へ置き、意味を辿る結果と限界をこのlogへ残す。模型や実際のproduct directoryは変更しない。

保存済みbeforeとの全文一致を確認して既存四fileをafterへ適用する。
新規本文と全変更をdocument-reviewへ通し、実物のskillの全文へ編集後skill-update-reviewを適用する。
登録と案内の対応、旧settle-questionと固定の正本節への実行依存が無いこと、追加link、書式を検査する。
origin単位のdoc-enricher提案reviewは反映・review後に一回行う。専門の実装や製品全体の完成の代わりにしない。

#### 材料の試作で得た結果

新規skillの本文を書き、既存四fileを承認済みafterの全文へ一致させた。
実物のdesign-core-logicを読み、同じ担当がその方法を適用して、一時領域に学校の材料65行と生成の材料50行を作った。
学校は粗い依頼から詳細へ同じ入口を育て、生成は方式の比較と実証の不足まで返した。第二のagentや生成モデルを実行したものではない。

学校の材料は、結果の役割を「引受け後に、選んだ条件内で作業を実施できる候補を返す」と置いた。
開始=max(枠の開始, 実際に引き受けて開始できる時刻)、終了=開始+現行の残作業、終了<=枠の終わり、という規則を導いた。
実際の引受けの根拠、現行の残作業と枠が必要な入力になる。既読や通知を引受けへ、不明な作業時間を0へ替えない。

| 検査した入力 | 期待と、得た結果 |
| --- | --- |
| 最後の枠19:30〜20:00、引受け19:45、残作業15分 | 20:00に終了して候補あり。机上の計算とPythonの計算が一致 |
| 引受け19:46、残作業15分 | 20:01となり、条件内に候補無し。家族の時間を勝手に足していない |
| 引受け19:46、残作業5分という検査用の変更 | 19:51となり候補あり。時刻19:45を固定の締切にしていない |
| 引受け19:46、残作業時間不明 | 判定の不足として返す。条件内に候補無しとも、0分で候補ありともしていない |
| 引受け19:25、残作業15分という追加の境界 | 枠が始まる19:30から19:45まで。引受け後だからと枠の外を使っていない |
| S1とS2が共に19:45から15分を要し、同じ作業者の枠を使う | 単独なら両方入るが、合わせると30分が要るため全件を置く配置無し。順序の列挙でも一致 |
| 残作業をS1=10分、S2=5分へ変える | S1→S2は19:45〜19:55、19:55〜20:00。逆順は19:45〜19:50、19:50〜20:00。二配置を返し、優先は選んでいない |

一件ずつ判定する案Aと、枠を消費しながら全件の順序を並べる案Bでは、成立させられる依頼の範囲が異なると分かった。
最初の粗い材料の「一件なら入る」という結果と成立条件を保持し、詳細化で同じ枠の競合を加え、前に読んだ依頼へ全件の成立に使えないことを「変えた所」で返せた。
同時に、二件を全て扱う条件で片方だけを選ぶのは優先と未達の採否を変えるため、材料側で決めないと返した。
これで、単独の成功例と名前だけの入出力では検知できなかった、結果同士の矛盾まで見られた。

次の設計へは、体験に実際の引受けと残作業の確認、情報に現行の用件・残作業・担当と引受けの根拠・共有する枠の識別、処理に枠や残作業が変わった時の再判断を要請した。
tableやcolumnの型、外部予定のAPIの実装へ先回りしていない。
署名から実際の提出は導けず、別の完了の根拠が要ると返した。原本を提出した・外部予定を作ったという実績は取得していない。

生成の材料は、検査用の文章「朝の集中を守るには、割込みのきっかけを減らす」から、来週一度試す行動候補を作る依頼である。
案Aは入力から行いときっかけを取り出して既知の型へ写し、案Bは根拠箇所・提案した行動・繋がり・成立条件を含めて生成する方式とした。
Aには型の対象外、Bには未測定の生成品質という成立条件があり、どちらかを未取得の性能・費用の推測で選んでいない。

| 品質を判断するために担当が作った出力例・反例 | 材料での扱い |
| --- | --- |
| 朝の作業前に通知を止めることを一度試す。根拠はメモの割込みの記述。通知を止められる朝の作業がある場合の提案 | 根拠と提案を分け、何を行うか選べる。実際に使える朝や効果は未確認として残す |
| 集中を大切にする | 要約だけで、試す行動を選べる結果ではない |
| 著者が推奨する25分の集中法 | 入力に無い著者の主張を創作している |
| 通知を止めれば必ず改善する | 未観測の効果を保証している |
| 割込みが役立つ相談の窓口も残したい、という別の検査入力 | 全通知を止める型は無条件に当てられない。守る状態と許される行動の違いを返す |

これらは実際の生成モデルの出力ではない。方式と品質の評価例を設計できたことを支持するが、生成の成功率・価値・費用・速度の検証にはならない。
次に必要な技術の実証には、同じ入力群と判断の見方で方式を試すことを返した。本人の行動の採否と有用性も未取得として残した。

#### 支持できる範囲と、実物のreviewへ渡す所
