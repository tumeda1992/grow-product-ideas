# 内部検討記録: 論点60 — whatの条件の試し方と不足の返し先

**discussion:** [implementation_review.md](../implementation_review/implementation_review-56-60.md#論点60-whatの条件を試す時判定の根拠と不足の返し先を明確にする)

**論点:** 論点60

## 開始context

論点59で、手段の自由を残すための抽象化が、粗雑な案を表面上通し、筋のよい案を判定できず遡及させる物差しになっていないかと指摘された。
具体案の比較により、妻の仕分けが必要な一覧は落とし、夫が受け口から担う紙と共有の仕事リストは対象の役割・時間の範囲で通せると判定した。
一方、項目名だけの案は説明不足であり、条件が緩いと断定できない。
模型の候補を既存の方法どおりに十分試さなかった実行不足と、方法の正本の「判定が割れるなら条件が緩い」という一律の帰路を分けている。
この論点は、whatの方法の局所改稿だけを判断し、模型の六条件・具体案の採用やwhyの目標の再確定を一括して行わない。

<a id="iteration-0"></a>

## イテレーション0: 条件の判定を、具体の根拠と不足の場所へ繋ぐ

<a id="iteration-0-record-1"></a>

### 検証: 局所改稿が、粗雑な案・異なるよい案・説明や事実の不足を区別できるか

#### claim・合格条件・方法

what-defines-a-product/what-must-hold.mdの決め方3の、二つの手段を当てる段落と合格条件を改稿対象にする。
既存の誰が・いつ・何が・最低の線・本当の記録との照合、手段の選定をhowで行う境界は維持する。
手段の名前や条件を満たすという説明を合格根拠にせず、共通の入力から行為と根拠を辿って、合否を判断できる案にする。
判定が割れた時に、条件の意味の曖昧さ・案の説明不足・必要事実の未確認を区別して補う先を示す。
条件がwhyの目標や価値へ戻る場合と、単に案の説明を補う場合を混同しない。

論点59のテスト専用の入力とA–Eの比較を根拠として使う。さらに、家族の手続き以外の例として、申請期限までに経費を提出する条件へ、提出欄だけある案・提出先の受領まで辿れる案・締切や所要時間が未確認の案を当てる。
実装を先に完成させたり、全未来の成功の証明を求めたり、全件の詳細ログを追加する重い工程へ変わっていないかも確認する。
具体の時刻や道具を一般条件へ固定せず、判定を支える関係を保てることを合格条件にする。

#### 結果と修正範囲

一時draftでは、決め方3の二つの手段を試す段落と「揃えば満たした」の一箇所だけを置き換えた。
変更は、手段の名を外すことと判定の境界を保つこと、固定した入力と具体案で行為・受け渡しを辿ること、判定不能の原因を分けて不足した先へ返すこと、設計中の見込みと実際の観測を区別することに絞った。
who・when・what・最低の線、本当の記録との照合、迷う条件の扱い、whyへ返す既存の経路は維持した。
条件の数や新しいfile形式、第三者の審査、全件の詳細ログ、実装を先に完了する工程は加えていない。

論点59のA–Eへ、改稿案を机上で当て直した。
Aは条件を満たすという説明や欄の有無でなく、妻の入力が無いと始まらない行為の依存から落とせる。
B・Cは、紙か共有する仕組みかという違いで除かず、原本と利用できる人・時間が次の行いへ繋がる範囲で判定できる。
Dは、案の説明を補う所へ返し、条件の曖昧さや目標の欠陥へ自動遡及させない。
Eは、必要な15分に使える5分しか残らないという関係から落とせる。時刻を一般条件へ固定しなくても、遅すぎる案を落とす根拠は保てる。
これは本文に示したテスト専用の入力の範囲であり、学校全般や実運用の合格ではない。

別の題材として、「会社が認めた方法で金曜17時までに経費の提出が済む」というテスト専用の条件を使った。
ここでは紙とwebの両方で提出を認める会社という入力に固定し、実在する会社の規則とは扱わない。

| 案や不足 | 改稿案での判定と返し先 |
| --- | --- |
| 提出ボタンと提出済みの欄だけがあり、会社の受領が起きるか不明 | 機能名だけを根拠に合格にしない。送信から受領へ至る説明を案の作り手へ求める |
| 担当者が原本を確認し、認められた紙の窓口へ期限内に渡して受領を確認する具体案 | 紙であることを理由に落とさず、示した行為と受領を根拠に判定する |
| 担当者が認められたwebへ送り、受領された結果と元の明細の一致を確かめる具体案 | webであること自体を合格にせず、同じ提出の根拠を問える |
| 実際の会社の締切や受領方法が未確認 | 事実の確認へ返す。案の可否や条件の緩さを推測で確定しない |
| 条件が「早めに提出」としか書かれず、同じ入力・同じ行為への合否が読み手で割れる | 条件のいつ・最低の線を締める。案の説明不足とは区別する |

会社が紙を認めないという別の入力なら、紙の案を通すことは求めない。手段の自由とは、入力の規則や選んだ目標を薄めて全ての案を通すことではない。
この違いから、改稿案が学校の語句だけに依存した判定でなく、条件と具体案を接続する方法として働く範囲を確認した。
数件の机上照合であり、作者以外の実行者が同じ判断へ達することや、あらゆる条件への有効性を実証していない。

#### doc-enricherの提案としての配置と限界

現在の一般化対象は、条件の判定に必要な根拠と、判定できない時の不足の場所である。
この知識はwhatの方法自身に対する変更で、上位READMEへ新規の規則を併記するのでなく、既存のwhat-must-hold.mdの該当箇所を修正するのが役割に合う。
既存文の一律の帰路が反例Dに当てはまらないため、その不正確な記述を残したまま例外だけを足さない。
一時patchは適用可能で、実fileはbeforeのままである。
この提案の採否前に方法や模型を変更しない。採用後は同じ具体例を使って59の六候補へ戻り、名称の整理を条件の判定能力に置き換える。
実行不足の訂正を、方法の改稿だけで済んだことにはしない。

### 適用: 切断前に承認された局所改稿を、復帰後に照合して反映する

#### 入力と方法

承認は会話で受領済みだが、切断により記録と反映が未完になった。
復帰監視がreadyを返し、repository・branch・読み書きを確認した後、提案の応答欄が空で、改稿対象が提示したbeforeのままであることを再読した。
保存したafterを機械適用し、完全一致と対象外の節の保持を確認する。途中で既にafterになっていた場合には二重適用しない。

#### 適用結果とoriginのdoc-enricher review

改稿対象は提示したafterと全文一致した。決め方3の試し方と合格条件以外を変えず、決め方4以降もそのまま保持した。
原本を拾う紙の構成・妻が入力しないと始まらない一覧・説明不足の案・時間の足りない案に、前に保存した判定の違いを当てられる本文になった。
このoriginのdoc-enricher提案reviewは一度だけ行い、一般化した候補「条件を満たす説明ではなく、具体の根拠で判定する」は、この改稿と既存のcontent_densityの実行・自己採点・当たらない例の要求に既出のためGate GでDROPとした。
方法の改稿を理由に模型の候補の検証が済んだことにはせず、六つの内容を判定できる単位へ戻して検討する。

#### content_densityと、追加のescalateの質問への回答

実物のcontent_densityには、具体は検知のためであること、当たらない例まで含めて基準の輪郭を閉じること、読者が実行し自分で採点できる所まで降ろすことが既にある。
document-reviewにも、薄さを一文追加で繕わず書く工程へ戻すことと、標準の正本へ従うことがある。
したがって、今回の主な失敗を防ぐ新しい一般原則が欠けていたとはしない。
前の候補を出した時に未読だったか、読んだが適用しなかったかは、保存された読取・判断の証跡から断定できない。実物へ基準を当てて判定可能性を確かめた根拠が不足していたことは、論点59の訂正で確認できる。
escalateするなら既存標準が素通りした失敗例として、起動漏れ・正本の未読・読んでも形式的に通した経路を調べる材料にする。新規則の追加や外部への送信を、この質問だけから実行済みにはしない。
一方、whatの方法の一律の帰路という反例は別に確認できたため、今回の局所改稿は維持する。
