# 内部検討記録: 論点22 — 問いを扱うskillが、問いに答える以外に何を担うか

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion.md)

**論点:** 論点22

## 開始context

論点21の保留中、assistantは前回steeringの扱いを報告し、論点20がbでよいかと、答えるskillへ要求を足すかを利用者へ問い返した。利用者は、論点20の判断は答えるskillの中身に依存しておりassistantが判断すべきこと、答えるskillへの要求は全体が効果的に進むために必要かを自分で考えること、「問う」のskill化や問うと答えるの統合もゼロベースで考えることを指示した。

前回steeringで確認した事実（論点21の応答欄に出典つきで記録）: 答えるskillは水準の二段目の自己診断を含む。深さは水準、広がりは層の閉じ条件が担保する。深掘りは上限を置く対象。アイデアごとの問いの先鋭化は議論されていない。層ごとのskillへ分けた理由は、層による分岐をskill内に持たないため。

<a id="iteration-0"></a>

## イテレーション0: 一般の問いを、このアイデアの問いに立て直すことの要否と置き場所

<a id="iteration-0-record-1"></a>

### 診断: 問い返した原因

論点20の再判断に要る情報（前回steeringの経緯、答えるskillの中身の選択肢）はassistantの手元にあり、判断の依存関係（20は答えるskillの中身に依存する）も読めた。それでも判断せずに利用者へ戻した。原因は成果物固有であり、think-throughとtask-designの「自分で先に考えてから問う」は既にある。

<a id="iteration-0-record-2"></a>

### 判断: 立て直しの要否

- 一般の問いと一般の満たさない例では、アイデアに特有の浅さを捕まえられない。例: サブスク更新日の痛みで「更新日の前に通知」は一般の例を通るが、更新日が散らばって集めること自体が核心かもしれない点を捕まえない。
- 前回steeringの検査機構の目的（浅い通過の防止）に照らし、立て直しは要る。
- 立て直しの記録は、還元で問いのセットの過不足を判定する根拠になる。

<a id="iteration-0-record-3"></a>

### 判断: 深さの配分

前回steering（過剰な深掘りの排除）と論点4（上限を固定せず機能で判定）の両立として、問いごとに配分する。基準は、答えが変わった時の出口・下位の問いへの影響（問いの選び方と同じ）と、今の材料での確信度。影響が大きく確信度が低い問いだけを詰める。

<a id="iteration-0-record-4"></a>

### 判断: 問うを独立させるか

| 形 | 評価 |
| --- | --- |
| 層の始めに層の全ての問いをまとめて立て直す独立skill | 層内の配分はできるが、後の問いの立て直しが前の答えに依存し、先にまとめると早すぎる |
| 問いごとの独立skill | 結果を使うのは直後の答える手順だけで、受け渡しが増えるだけ |
| 答えるskillの最初の手順 | 前の答えが出た後に問いごとに立て直せる。配分は問い単位の判断で足りる |

三つ目を推す。基準を下げる恐れは、一般の例を外さず足すだけにする、立て直した問いと基準を正本に書き層の閉じで利用者が見る、確認を書かれた基準で行う、で防ぐ。

<a id="iteration-0-record-5"></a>

### 判断: 論点20・21への影響

- 論点20のbは、立て直しが層ごとの分岐を持たないため保たれる。
- 名前は担当の拡大に合わせ、outcomeを名指す`settle-question`にする。
