# 内部検討記録: 論点80 — 最新の方法を新しい一件の入口から出口へ通す

**discussion:** [implementation_review.md](../implementation_review/implementation_review.md)

**論点:** 論点80

## 開始context

共通の層の方法と専門の整備を続けてきたが、最新の一式を新しい入力で入口から出口まで通した観測が不足している。
既存の学校の模型は上流を通し直したもの、論点77は上流を固定入力として受けた下流の試験であり、別の能力の証拠である。
利用者の指示により、未修正の破綻が無い個別PC・APIの追加検証は宿題とし、アーカイブの残数ではなく必要な仕事と具体の不足から次を選ぶ。
論点79で現行の完了判定を同期したため、実際に必要な材料の依頼・返りと採否、差し戻しと出口を一件で確かめる計画へ進む。

## イテレーション0: 一件の入力と試験の射程を揃える

<a id="iteration-0-record-1"></a>

### 判断: どの入力と範囲なら、上流を固定せず必要な仕事を観測できるか

#### 判断対象・必須条件・根拠

最初の一件は、学校の業務や提出の状態と異なる、個人の読書メモを題材にする案を評価する。
必要なのは、着想と動機からwhyを実際に進め、価値の可能性と残す良さを扱い、選んだアウトカムからwhatへ、選定した版から必要な設計へ繋ぐことである。
出口を作るへ誘導せず、声の専門の収集が実際に必要かも、具体の判断から確かめる。
実在の利用者の経験・反応を捏造せず、当人役の全ての設定と応答を検査用と明記する。
対象の実行条件は最初に特定し、後からPC・APIの根拠を都合よく補わない。
元designにある新しいsessionと自演前のresumeの条件を維持し、同じsessionの準備・机上照合をその再現の結果にはしない。

#### 入力と検査の射程の判断

一人用の読書メモを最初の題材にする。学校の提出・担当・回収と異なり、面白さを拾い直すこと、実際に一度試すこと、読書の自由さを保つことが相互に効く。
whyが症状の解消だけに狭まらず、残したい良さと変化の候補を広げ、選んだアウトカムから条件・選定へ畳めるかを観測できる。
過去の専門の小例には読書メモの生成があるが、入口から全層をこの入力で通した例ではない。小例の答えをそのまま正解として流用しない。

固定するのは架空の初期の語り・利用状況・使える記録・時間と支払の制約であり、アウトカム・条件・選定・出口ではない。
AI提案という着想を初期入力へ残すが、生成機能を必須とせず、既存道具・人の見返し・小さく作る案を同じ目標で比較する。
作る楽しみがある場合も、暮らしの改善に不可欠な手段という理由へ混ぜず、独立した動機として選定する。

別のfamilyの複数人の案件も候補になるが、今回は二人の学校の模型で扱った引受け・引継ぎを繰り返すより、体験と価値の違いを保つ一人の題材を先に使う。
外部のaccount・APIやwebの第三者の発言の取得を試験の成立条件へ先に固定しない。必要になった時は性質と権限・根拠を確かめる。
このworkspaceの実行条件を開始時に確認して固定するため、家のPCのOSを後から補って合格にする形を避けられる。

今回の準備と同じsessionで資料が読めることは、新しいsessionの再現の証拠にしない。
現行designの自演前resumeの条件に従い、採用後に開始用の固定入力と記録の入口を準備してから再開を依頼する。
Claude Codeからの読込みの検査は別の未実施として残し、このCodexでの検査へ混ぜない。

#### 提案のreviewと未実施の範囲

提案は既存のcanonical・layer-record・材料の形式を使う一件の入力と検証計画であり、新しい共通の文書構造や専門を採用するものではない。
同じ「読書メモ」という名前でも、入口の動機と着想、本人の一回の体験、価値・条件から設計への判断を実行する範囲と、過去の小さな生成の例を区別した。
当人役を実在の発言とせず、16時間・15分・月額0円も検査の設定と明示した。
生成APIの存在や使えるPCの不明を後付けしないよう、開始時の検査環境の確認を置いた。

提案・背景・保存構造をdocument-reviewに当て、何を入力にしてどの接続を観測し、何を未確認として返すかを読める内容にした。
新規のproduct directory・正本・メモ・各層の本文はまだ作っていない。自演、実利用、新しいsessionでの再現も未実施である。
現行designの自演前の再開条件を維持し、採用後に開始に必要な物を準備してから実際の再開を依頼する。

### 照合: 期待した仕事の受け皿と、詳細へ降りる方法・実証の範囲

#### 起点と確認した資料

利用者は、画面のラフ・ビジネス機能の詳細・全体が実際に回るかを確認し、旧skillを機械的に復元しないことが期待した仕事の欠落に繋がっていないかを問うた。
現在の提案0への採用ではなく、通し検証を始める前の能力のカバー範囲と深さへの確認要求として受ける。
現行のsketch-experience、functional-structure-design、design-core-logic、design-data-model、how-to-buildの該当する方法・水準・境界と、学校の試運転の実際のラフと規則を照合した。
旧archiveのsketch-experience、design-tables、design-modules、design-core-logic、verify-technical-feasibility、gather-target-user-voices、refine-what-defines-a-productと、旧growの出口後の扱いを比較した。
このblockは資料を読んだ後の確認結果を記録するもので、事前に保存した調査入力の履歴は作らない。

#### 仕事ごとの現在の対応と限界

| 期待した仕事 | 現在の担当と要求する深さ | 得た根拠と不足 |
| --- | --- | --- |
| 体験・価値からアウトカムを選ぶ | whyの体験理解・価値発見・目標設定が全体の意味を保って往復する。症状の裏返しだけで閉じない | 方法の本文と学校の架空の模型はある。全く新しい一件への最新一式の適用は未確認 |
| 条件、対案と届ける版を選ぶ | whatとhow、propose-alternativesが、守る条件と今回の改善・未達・費用・運用を繋ぐ | 学校の非開発試行で扱った。全体の目標を部分案の達成に置換しない。最新一式の別件の観測は不足 |
| 画面・操作のラフを作る | sketch-experienceが対象の全場面・全画面で表示情報・入力・操作・中断や失敗後の続きを文字配置図又は画像へする | 学校の実物にU1一覧・U2詳細・U3入力の文字ラフがある。完成した見た目や実利用の操作性を測ったものではない |
| 業務上の各機能の振舞いを詰める | functional-structure-designが前提・対象・入出力・状態・責任と人や他機能への受渡しを、design-core-logicの規則・分岐・例外と繋ぐ | 学校で署名と提出、原本変更、再引受け、二件の同じ時間枠、結果不明を通した。全機能の全仕様が毎回漏れず揃うことは未実証 |
| 情報を実際に読み書きできる構造にする | design-data-modelが同一性・現行・根拠、型・鍵・制約・queryと更新の前提まで育てる | 学校のschemaとSQLを実行したが、最初は家族の選択と未予約の必要時間を保持していなかった。接続の照合で発見・修正した事実がある |
| 実現に必要な性質と導入・復旧を揃える | verify-technical-feasibilityが指定条件の事実と限界を返し、how-to-buildが導入・訂正・復旧・受入れと担い手へ繋ぐ | SQLiteの実測はあるが、実アプリ・UI・対象PC・実APIや実利用の確認ではない。個別PC/APIは宿題として保持 |
| 実装内部の構成と必要な先送りを扱う | 必須の設計判断はhow-to-buildで解消し、機能・logic・情報・実現の検討を必要に応じ往復する。委ねる細かいclass等は裁量と保つ条件を渡す。先送りは理由・影響・見直す条件を持つ | 旧design-modulesのコード分割を機能構成だけで確定する責務は維持していない。必要な内部設計を誰も決めず渡せるという意味ではない。実際の初回構築へ渡す全体の実証は未完 |
| 本人以外の声と文脈を得る | 本人との対話・提供記録はwhy等の方法で扱う。公開の声を専門的に集めるskillは退避中で、提案78は未採用 | whatにはtarget-user-voicesの参照があるが、その必要がある場合まで整備済みとは言えない。条件付きの未整備として保持する |
| 一件の知見をレールへ戻す | 現在の作業ではsteering・議論・reviewで実行できている。root READMEもsteeringへ戻すと記す | 旧growには出口後に還元を促す手順があるが、現行growの出口フローにはその導線が明記されていない。通常利用の誰がいつ何の記録で判定して戻すかの経路を、今回手動で行えたことだけで整備済みにはできない |

旧スキルの名前の復元を止めることと、そこで期待した仕事を捨てることは別である。
現行へ保持・統合・委譲した仕事と、条件付きで必要だが未整備の仕事を分ける必要がある。
特に通常利用の出口後の還元は、専用skillを復元するかとは別に、起点・担当・判定材料・返却先を確認する大枠の残件である。
新たな経路を採用又は共通fileへ反映したものではなく、今回の照合で明らかにした不足である。

#### 大枠の確認と、詳細・実証の確認を分ける

レール自身の大枠は、必要な仕事を誰が引き受け何を返すか、能力の受渡しと不足時の経路が繋がることである。
レール自身の詳細は、その担当の本文に具体の手順・規則・入力・出力・完了の見方があり、その方法で所要の成果を作れることである。
個々の製品でも、業務の全体と画面・規則・状態・情報・失敗の具体を往復し、表示した情報が保存から読め、操作の結果が次の行いへ使えるかを確かめる。
名前や工程の列挙、方法の本文、個別の試験の成功は、これら全ての証拠を代替しない。

提案80の一件が作らないへ着けば、その一件だけでは画面と業務機能の詳細へ降りる接続を確認できない。
したがって提案0を採用済みとせず、期待した仕事の対応と未整備を先に点検する必要がある。
今の照合で大枠の主要な受け皿は確認できたが、全期待の漏れが無いこと、毎回の詳細の完成、全体が回ることを確認済みとはしない。
現行の文書・役割と具体の残件の説明をまず返し、旧skillの自動復元や新たな数・固定工程を追加する判断へ飛ばない。
