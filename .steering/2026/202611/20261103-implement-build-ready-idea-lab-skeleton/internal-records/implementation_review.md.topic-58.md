# 内部検討記録: 論点58 — 新しいwhyを模型へ反映する

**discussion:** [implementation_review.md](../implementation_review/implementation_review-56-60.md#論点58-模型の正本と層の記録を新しいwhyの実演に合わせて更新する)

**論点:** 論点58

## 開始context

論点57で、whyの方法を今回使う版として全体で採用した。その実演は、このsteeringの内部記録にあり、既存の模型にはまだ反映していない。
模型の正本は、三つの教室の振替を使い切る旧アウトカムと旧条件・旧選定を持つ。新しい実演は、学校行事を含め、妻が起点から進捗を一人で管理しない役割の変化を選んでいる。
この二つを混ぜると、古い条件や解き方で新しい目標へ届くことまで確かめたように見える。
今回の対象は、現在の正本・whyの導出と決定過程を更新し、旧結果を履歴として保持し、後続の状態と参照を正確にする一つの変更集合である。whatやhowの新しい中身を、この作業の都合で確定しない。

## イテレーション0: 正本・経緯・履歴・未確定を揃える

<a id="iteration-0-record-1"></a>

### 検証: 新しいwhyへ更新しても、履歴と後続の未確定を保てるか

#### 主張・合格条件・方法

対象はこのsteering内の振替の模型である。正本の雛形と、層の記録の役割・差し戻し・directory内で読み切れる約束を使って、現在のfileと参照を照合する。
現在の正本へは、新しいwhyで決まった内容だけを載せる。旧what・howを新しい目標の確定済みの結果として残さず、必要なら旧正本を履歴へ保存する。
whyの実演では、入力・追加の自演設定・体験の語り・仮説・自演内の選択を区別し、三つの仕事の往復を層の記録と決定過程へ落とす。実在の利用者の合意や観測結果へ変換しない。
whatとhowは、新しい物差しでの再導出・再選定を済ませず、確かめ直し待ちであることを読み分けられるようにする。既存whatの予約完了の条件9と未完は履歴として保つ。
履歴の作り方は、旧正本・旧whyの記録をそのまま退避する案を第一候補とし、移動に伴う相対href以外で旧本文を変えない。過去のdiscussionへの変更も、参照追随だけに限定する。
実在する全hrefを解析して、正本の旧節や旧whyの記録を参照するconsumerを洗い出し、必要な追随範囲を完全にする。模型のdirectory外へ参照を出さず、過去の議論と材料の意味を保持する。
一時draftへ変更集合を作り、適用可能性、参照先とanchor、意図しない本文変更、状態と正本の中身の整合を確認する。新しいarchive fileは、sourceと許可するhref補正・見出し構成を提案へ示し、採否前には本体へ作成しない。

#### 結果と、案を決めた理由

正本は「閉じた層が決めた現在のもの」、層の記録は受け取った物差し・導出・確認・差し戻し、discussionは当時の判断と応答を担う。既存の雛形と模型の役割を照合した。
正本へ警告だけを足して旧条件・旧scriptの選定を残す案では、新しい姿の直後に旧結論が並び、どの条件が現在有効なのかを読者が解き直すことになる。
そこで、現正本と旧whyの層の記録をarchive/3rdへ写し、現在の正本は閉じ直したwhyだけにする。what・howの旧導出と検証は元の層の記録へ残し、現在の入力と確かめ直し待ちを先頭で分ける案を選んだ。
既存のarchive/1st・2ndと同じ履歴の用途であり、新しい責務や管理者を増やさない。

変更集合は12fileになった。新規2fileは旧正本・旧whyの保存、既存6fileは正本・whyの記録・whyのdiscussion・whatの記録とdiscussion・howの記録、残る既存4fileはhrefだけの追随である。
模型内だけでなく、このsteeringの旧正本への実hrefも走査し、implementation_reviewの51–55と論点51の内部記録が、当時の目標・条件・選定を参照するため、保存した旧版へ向ける必要があると確認した。
過去の提案のcode fenceは当時の提示そのものとして変更しない。

一時領域で12fileのbefore/afterと完全patchを作った。正本には論点57で示した姿をそのまま置き、体験・価値、範囲の選択理由、測り、値打ちと期間、作る動機、未確認を記した。
whyの記録は現行の三つの仕事と往復へ組み替え、子どもの具体の体験と夫が長い夜の照合を望まないことも落とさず保持した。
whyのdiscussionへは自演の設定と再構成であることを明示して論点5–7を加え、実在の利用者の新しい合意を捏造しない。whatの論点7は調査中の入口だけにし、新条件を未提示のまま決めない。

機械的検査と本文照合の結果は次の通りである。

| 確かめたこと | 結果 |
| --- | --- |
| 模型内の実hrefのfile・anchor・directory内完結 | 変更前0件、予測した変更後も不整合0件。code fence内の例は対象外 |
| 新規2写しの本文 | 先頭の写しの説明とhrefを除き、source本文が完全一致 |
| why・what・howの過去discussion | 全ての旧本文と生の応答を、href以外はそのまま保持。追加は末尾だけ |
| 41箇所のhref補正 | 模型外のconsumerも含め、予測した保存先のfile・anchorが全て解決する |
| 適用できるか | 一時patchに対するgit apply --check --whitespace=errorが成功 |
| 実fileへの先行適用が無いか | 全対象が記録したbeforeと一致。新規archive2fileは未作成 |
| 状態と現在の決定 | 正本はwhyだけ閉じた検討中、what・howは確かめ直し待ち。旧条件9の未完と旧8条件でのhow選定を、新目標での合格に変えていない |

学校の規則・実際の通知や当日の行いは追加確認が必要であり、今回の写しや文書検査では埋まらない。
既存の子どもの情報の前提は本文を変えず、学校の提出を含める時の効く範囲をwhatで元の採否の文脈へ戻して確認する入口を残した。
新しい条件群、手段の比較、実際の家族の選択や運用の効果は検証していない。
whyの方法本文は論点57の採用版を維持し、この変更集合に再改稿や共有pluginへの移植、commit・pushは含めない。

#### 次の提示への接続

模型を新しいwhyへ反映する一つの採否として、全12対象とbefore→after、新規2写しのsource・見出し・許す補正、既存の完全diffを提案0へ示す。
採否前には模型本体へ適用しない。採用後に適用・参照・状態を再確認し、新しいwhyを受けたwhatの再導出へ進む。

<a id="iteration-0-record-2"></a>

### 適用: 採用した12fileを反映し、完了状態を確かめる

#### 入力と確認方法

提案0への利用者の応答により変更集合を採用した。保存した12fileのbefore/afterを、提案本文の完全diffおよび新規2写しの変換と照合して機械適用する。
適用前には全対象が保存したbeforeと一致することを確認した。
適用後は12fileのafterへの一致、模型内と変更したconsumerのhref・anchor、過去の本文と応答の保持、新規写しのsourceと許可変換、正本と各層の状態を確認する。
この結果を得るまでは反映完了にしない。

#### 適用結果と、作成後のreview

12fileは保存したafterに全て一致した。新規2写しは合意した見出し・本文を持ち、説明と列挙したhref以外はcopy元のbeforeと一致した。
模型内の実href・anchor・directory内完結に不整合は無く、模型外のconsumerも含む41箇所のhref補正が全て解決した。
三つの層の過去discussionの本文と生の応答はhref以外を維持した。新規写しの参照からも、当時の論点と旧条件・旧選定を辿れる。
現在の正本は新しいwhyだけが閉じた検討中で、what・howの旧判定を新しい目標に対する合格へ変えていない。
これにより提案0の適用完了状態に達した。新条件の十分性、手段の選定、実在の人の望みや実運用の効果は未確認のまま維持する。

#### 論点58に対するdoc-enricherの一回の提案review

今回の設計意図は、現在の決定と旧物差しの結果を混ぜず、上流の変化を後続へ渡すことにある。
正本の雛形の「決まっていない節は書かない」、product-plansの記録の役割、層READMEとgrow-product-ideaの差し戻しの規則に、同じ役割・順序が既にあることを実物で確認した。
一般化した候補「上流の物差しが変わった時、旧結論を現在の結果へ読み替えず、影響する下流を確かめ直す」は、既存の契約と重複するためGate GでDROPとした。
このturnでは未知の一般則が無いため、追加READMEの提案も、共有skillの編集も行わない。このoriginのreviewを再帰起動しない。

#### 再評価と次の判断

whyの出口は模型へ到達した。次はwhatへ渡した五つの言い分から、手段を選ぶ前の条件を導く。
旧9条件の数や旧7日前を固定せず、新しい範囲と役割の違い、本人たちの望み、行いの実施完了、望む関わり、継続を照らして再導出する。
未設定を架空の利用者本人への質問待ちにしない。一方、既存の採否や規則は勝手に変更せず、検証用に追加する設定は先に区別して固定する。
