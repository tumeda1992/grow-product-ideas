# 内部検討記録: 論点105 — 参照先を保って記録し、受け渡す区切りでリンクを検査する

**discussion:** [implementation_review.md](../implementation_review/implementation_review.md)

**論点:** 論点105

## 開始context

Cの材料/層の採否/内部記録を生成した実行補助が、公開contextの相対pathを内部記録へそのまま写した。公開README.mdの位置とinternal-recordsの位置が一階層違い、最後のコピー先の読取り検査で25件の不成立を検出して訂正した。現行の記録規約は案件内の相対linkを要求し、sharedのdiscussion検査は論点やlogの対応を持つが、一般の参照全ての検査とは異なる。
現在は104の反例判定を反映・検査し、102の次の一つとしてこの問題を扱う。shared pluginのinstall cacheは編集せず、レール内の記録の受渡しと再利用できる小さい検査補助で対処できるかを検討する。自動修復やネットワーク確認、製品の意味の成立の保証は対象外。

## イテレーション0: 内部記録の参照切れを保存と受領で検出する

<a id="iteration-0-record-1"></a>

### 診断: 相対pathの原の基準と、渡す記録の基準がどこで割れたか

#### 期待との差と原因候補

期待は、原の文書で指していた実file/anchorが内部記録へ写した後も同じ対象へ届くこと。実際はREADME.mdをinternal-records/README.mdとして解決し失敗した。既存のケース内の記録規約、growの材料受領/閉じ/出口の検査、実行補助のbegin/evidenceと既に得た25件の修正証跡を照合する。
原因の切分けは①保存先基準の相対pathという規則自体が無い、②規則はあるが写す時に適用しなかった、③普通のlinkを検出する検査が返りの区切りに無い、の順。今の規則と適用の欠けを分け、全sharedの新しい規範や完全なMarkdown parserを先に要求しない。
同じbasenameの別fileへ偶然届く場合、参照先の存在だけでは意図の保持を証明できないことも扱う。原の基準から意図した対象を決め、保存先から同じ対象へ辿ることと、存在/anchorを検出する機械検査を分ける。

#### 原因を支持・反証する証拠

product-plansの読み切れの規約には、file間のlinkは案件内の相対path、見出しを指す時はfile名を省かないという指定が既にある。原規則の不在ではない。実行補助beginは公開discussionへorigin/contextを記した後、それを内部記録の「判断の入力」へ再利用していた。別directoryへ写した相対pathの基準を変えなかったのが直接原因である。25件の修正証跡にはREADME.md→../README.md、../input.md→../../input.md等があり、全てを一律に同じpathへ置換する問題ではない。

現在のgrowは材料の受領と層の閉じを持ち、案件内読み切れの明示検査をbuild-readyの前に置く。しかし普通の参照が返りで実解決できるかを、受領の区切りで確認する実行補助はrepo内にない。sharedのdiscussion検査をこれと同じものにしてはいけない。

直接原因は今回の適用補助の欠け。次の対処は、原の参照先を保って新しい保存先から相対化する書き方と、受け渡し前の参照検査を組にする。意図しないが実在する別READMEへ向いた誤りは、file存在のcheckerだけでは判別できないため、原文が指した対象との一致はwriterが照合する必要が残る。

<a id="iteration-0-record-2"></a>

### 判断: 参照の保存と受け渡し前の検査を、既存の進行へ繋ぐ

#### 判断対象・必須条件・根拠

受入れ/材料の返り/層の閉じで、その区切りが渡すfileの参照を保存済み実物から検査する。元の文書を直した後、持出し時に初めて発見する形を変える。原の意図と新しい保存基準を保ち、file/anchorが無い時は渡す前に止まること、案件外へのrepository内参照を認めないこと、外部公開URLへネットワークアクセスや自動修復をしないことが必須。

既存の一時的な検査scriptを毎回作り直す案では、次の記録で再利用できる入口が残らない。文書の注意だけを増やす案では、今回も読まれていた相対pathの指示へ同じ失敗を繰り返せる。既存のgrowと記録規約へ区切りの責務を置き、repo内の小さいread-onlyの参照checkerへ繋ぐ案を検討する。これは製品の意味を判定するvalidatorや、完全なMarkdown処理系を新設する要求ではない。

helperは現行案件で使う通常のinline link、reference形式、Markdown見出しと明示anchorを対象とする。未対応の形式は合格へ黙って数えず、未検査として返す。必要ならwriterが具体の保存先/参照先/anchorを手で実解決した根拠を残す。意図した参照先の同一性や説明内容の正しさはcheckerの成功と別に確認する。

<a id="iteration-0-record-3"></a>

### 検証: 現在の正常記録と、誤った基準/見出し/案件外の参照を区別する

#### 主張と確かめ方

新しいcheckerの候補を一時領域で実行する。正しい../README.md#anchorと同じdirectoryの参照を通し、内部記録へREADME.mdをそのまま写した欠け、anchor欠け、案件外への参照を失敗として返すことを確かめる。日本語/重複見出し、percent-encoded path、コード内の例、公開URL、reference形式、未対応形式、同名の別READMEへ届いてしまう場合を含める。
現行C1〜C3の232参照を通し、25件の修正を戻したコピーでは検出できるかを確認する。本番の案件や元の入力は変更せず、scriptもまだrepoへ反映しない。checkerの成功から元の意味の保持や他clientでの実行まで保証しない。

#### 検証結果と、案へ反映した限界

候補のread-only checkerを現在のLinux/Pythonで実行した。C1は29Markdownの136参照、C2は17の50参照、C3は16の46参照が通った。Cの元fileは書き換えず、三件のowned-filesの64件とhashを照合して不変。
別の一時directoryへCをコピーし、保存済みの25件の修正証跡だけを戻した版を実行すると、25件の不成立を検出した。昔の誤りを本番へ戻すことなく、保存場所の違いによる参照切れを拾える根拠となった。

| 構成して実行した境界 | 期待と観測 |
| --- | --- |
| 正しい../README.mdと日本語/重複/inline codeを含む見出し | 成功。見出し/見出し-1/abcへ届いた |
| 内部記録のREADME.mdを原の文字列のまま使う | missing-targetで失敗 |
| fileはあるがanchor無し、案件外への参照 | missing-anchor/outside-planで失敗 |
| 空白のあるfile名のpercent-encodingとangle形式 | 成功 |
| code fence/comment/inline code内の例、外部公開URL | 例は参照に数えず、URLは取得せずに区別 |
| reference形式と定義欠け | 定義ありは成功、欠けはmissing-reference-definition |
| raw HTMLのhref、未符号化の括弧を含むpath | 対応したふりをせずunverified-link-format |
| 閉じていないfence、壊れたURL、空の案件 | 非zeroで不成立/未検査を返した |
| 同名の別READMEが内部記録側にも存在 | 存在/anchorの検査は成功した。原の参照先の意図まで機械判定できない限界を明示 |

最後の対照から、writerが原のfileを基準に意図した対象を保ち、その後で新しい保存基準から検査する分担を残した。checkerの成功を意味の一致と同一視しない。全部で15の構成fixtureを当て、上の限界を含め期待と対応した。本製品の実装、client読込み、ネットワーク上のURLの到達性は検証していない。

### 変更集合とreview

候補は、新しい小さいchecker、記録規約の「保存した参照の検査」、growの受入れ/材料の返り/層の閉じからの接続の3file。codeはPython標準libraryのみ、read-onlyでJSONと終了codeを返す。現行のMarkdownで使う記法に対象を絞り、未対応は未検査として人の実解決へ返す。原の参照先と意味の一致はwriterの仕事に残る。
新しいhelperはgrowの既存の受領/閉じの検査を支える内部処理で、独立した判断や状態/完了を持つ別の仕事を追加しない。skill-update-reviewを設計時として現行grow全体と候補へ適用し、切り出し候補無し。これは検査codeの動作評価の代わりではない。
document-reviewでは、区切りで誰が何を確かめるか、二fileの相互参照の保存途中を作業不能にしないか、未対応の手動確認が参照欠けの抜け道にならないかを照合した。3fileの完全差分を作りgit apply --checkも通った。現物は未反映で、shared pluginとケースの採否/本文を変えていない。

### 採用と反映: 保存先と元の対象を保ち、実物の参照を区切りで検査する

利用者の実応答「ok」を直前の105・提案0への採用として受領した。3fileのbeforeと保存済み完全差分を実物へ照合し、一致を確認した。既存のsteering/task-designで合意した改善単位の連続反映として扱い、別の進行計画や空のtasklistは作らない。
記録規約とgrowの接続、新しいread-onlyの補助を採用afterへ反映する。反映後は3fileの全文一致、Pythonでの実行、Cの232参照、当時の25件の欠けを戻したコピー、対象記法と限界の15fixtureを本線に置いた補助へ当てる。Cの64fileと固定入力を保持する。検査結果を元の参照先の意図・製品設計・別clientの検証へ拡張しない。

#### 反映後の検査と受け渡し

3fileが採用afterと全文一致。本線に保存したcheck-plan-links.pyを実行し、C1の136/C2の50/C3の46参照の合計232件が通った。当時の25件の修正だけを戻した一時コピーでは25件全てを検出し、15fixtureも期待と対応した。同名の別READMEへ届く場合は機械では合格となる限界を、仕様通りに確認した。原のCの64fileとhash、初期入力の固定hashは不変。別directoryへの写しも232参照、13discussionの22論点で問題無し。

編集後のskill-update-reviewをgrowのSKILL.mdと内部の雛形全体へ適用した。参照検査は受領/閉じに付随する確認であり、新しい採否や状態正本・再開条件を持つ工程を抱え込んでいない。記法対応の変更caseでもhelperと記録規約の範囲で直せ、層選択/差し戻し/採否を改める必要はない。切り出し候補無し。この判定は上の動作検査とは別である。
document-reviewでは、保存途中と受渡しの区切りの差、writerとhelperの分担、未対応の有効な記法の具体的な補完と参照欠けを通せない境界、既存の読切り/持出し検査の保持を照合した。読者は記録規約のコマンドで実物を調べ、不成立を元の参照へ戻して訂正できる。新しいscriptの配置とgrowからの導線も採用内容通りである。

このoriginのdoc-enricherを提案modeで一度適用。機械の到達性検査と意図の同一性の分担を残す候補は、反映した記録規約に既出でGate Gにより重複として落とした。root READMEには案件の読み切れ、growには既存の受領/閉じの責任があり、数値や今回だけの診断を恒久のREADMEへ足す案は残さない。追加のdocs提案無し。

105の反映と局所検査は完了。次は102の三つ目の、本人の逐語・設定の地の文・assistantの整理を混ぜない改善へ進む。新しい作る前提の一式実行は、残る個別改善の後に残す。
