### 判断: 項目の対応から、現行の事実と根拠を支える構造へ進めるか

#### 判断対象・必要条件・使う根拠

新規skillの構成と、層の登録・利用可能な専門・rootの案内・作業の残りを揃える変更集合を判断する。
必要条件は、受け取った体験とlogicの入力・結果を必要な情報へ写し、対象の同一性、現行・履歴、状態と根拠、更新で守る関係を設計できることである。
具体の例を入れ、必要な表示・判断にどう読むかと、変更・重複・中断でどう書くかを往復できる材料にする。
画面の項目から保存先を機械的に作らず、全てを出来事履歴にする等の方式も固定しない。値が保存されることと、その値の根拠が取得できることを分ける。
利用者の業務規則を専門側で勝手に足さず、必要な外部の性質の実証と、moduleの責務設計は依頼側へ返す。

既存の根拠は、退避したdesign-tables・design-modules・verify-technical-feasibility、現行のdesign-core-logicとsketch-experience、how-to-buildと層のREADME、材料の入口である。

外部作成後・成功保存前の停止も当て、結果不明を列の追加だけで成功へ替えない方法かを見る。
別題材には生成候補の根拠と本人の選択を使い、学校・紙の原本・関係DBへの固定を避けられるかを机上で問う。

新規skillはoutlineのみとし、既存fileは完全diffを用意する。実repositoryへ先行適用しない。

#### 旧版との対応と、専門の持ち場

旧design-tablesは、画面・logicの必要情報を抽出し、全体の案を並べ、状態を現在値・別のtable・出来事からの導出のどれで持つか、具体の行から表示とlogicを満たすかを問う。
したがって、旧版が状態や具体の行を全く扱わなかったとは診断しない。
残すのは、その全体の対応と具体の読取の仕事である。
組み直すのは、画面から全テーブルを二案以上作る固定の入口と、更新や中断の後に何を根拠に現行と読めるかまでを導く方法である。

新しい専門は、必要な情報の意味・同一性・関係・状態・根拠と、読み書きで守る関係を設計する。
画面に欄が要るからtableとcolumnを足すのではなく、その値がどこから得られ、いつ変わり、どれを同じ対象と扱い、何を現行として使うかを問う。
与えられた業務規則が情報に要求する区別を設計し、その規則の意味を勝手に決め直さない。
保存の更新が依る技術の保証、実行するmoduleの責務は必要な性質として返し、実証や実装を行ったことにしない。

名称はdesign-data-model、材料はdata-modelを推す。
旧名design-tablesを保つ案も、関係DBへ詳しく落とす依頼には合うが、保存方式を先に決めない情報の設計や、文書・既存の道具で持つ版では、仕事をテーブル一覧へ寄せて読ませやすい。
情報の意味と読み書きを主軸にし、選んだ方式へ具体化する仕事を表す名前にする。
旧archiveとそこにあるtablesは保持し、現行の材料を改名・移行する処理は無い。新しい登録先だけをdata-modelに揃える。

#### 期限変更と古い記録へ当てて、必要な区別を取り出す

方法の検査用に、学校の用件を一覧と予定生成で扱う版を仮定する。模型の学校限定の非開発版は変えない。
原本R1の締切は金曜で、引受けと署名の記録、外部予定の作成試行がある。その後、原情報がR2へ変わり締切が木曜になる。
予定の作成試行は、外部作成後・手元への成功保存前に停止したという仮説を置く。

単一の用件行へ「締切=木曜、担当=父、済み=true、外部ID=空」を上書きしただけでは、済みが何を意味し、どの原本に対する記録で、外部には何が起きたかを読み分けられない。
項目が全て存在していても、logicと人の次の行いには使えない。
情報の意味から設計する案では、少なくともこの検査で要る区別を、次のように取り出せる。

| 必要な読取り・変更 | 構造が保持する区別と、次へ返す所 |
| --- | --- |
| 現在の締切を表示し、logicが使う | 同じ用件S1と、現行の原情報R2を辿れ、木曜を読む。別の用件と同じ題名であることだけで統合しない |
| 過去の署名や引受けを読む | 何の原本・内容に対する、誰の何の出来事・根拠かを読める。署名が新しい原本にも有効か、再引受けが要るかは、情報の版を変えただけで一律に決めない |
| 外部の旧予定を訂正・照合する | 試行A1が対象にしたR1と、手元で確認できた結果を保持する。成功記録が無いことを、外でも未作成と断定しない |
| R1を見た古い画面から更新が遅れて届く | 何を前提にした更新かを判別でき、R2を黙ってR1の値へ戻さない。前提付き更新が成立する保存の保証は技術へ返す |
| 署名済みから実際の提出の完了を読む | 別の出来事と根拠が要る。欄を追加してもその事実は生まれず、根拠の取得と採否を返す |

これらは必要な区別を示す一つの構造の枝であり、全製品へ原本の版table・試行tableを必須にするものではない。
現在値と、必要な行いに関する根拠だけを持つ案でも、訂正や照合に必要な情報を失わなければ成立し得る。
版や出来事を保持する案は経緯を辿りやすいが、現行を読む組立てと、増える記録・更新の負担を持つ。
どちらも、保存方式が未確認のまま原子的な更新や重複ゼロを保証したことにはできない。

旧版にあった方式の違いを捨てず、同じ入力と変更を当てて、どの読取り・訂正ができ、どこに追加の規則や技術が要るかを返す専門へする。
全履歴やイベントソーシングを正解として固定しない。必要な範囲を既存の用件票や文書で持つ案も、同じ問いで吟味できる。

#### 別題材で情報の意味と方法の移植性を見る

生成候補の材料で、メモM1から案G1が作られ、本人がG1を試すと選んだ後に、メモが編集される仮説へ当てた。
必要なのは、案がどの記述を根拠にしたか、どの案を本人が選んだか、実際に試したかを読み分ける構造である。
最新のメモへlinkを付け替えるだけでは、古い案が新しい記述から出たかのように見える。
選択の記録だけで試行済みとも扱えない。

必要な根拠箇所を保存した案、対象の版を辿る案等を、その版で何を再表示・修正するかへ照らして比べられる。
全てのメモの編集履歴や生成の全logが必要とは限らない。候補が使った根拠と選択・実施を読み分けるだけで足りる範囲もある。
関係DB・画面・学校の署名に固定しなくても、必要な読取りと変更から情報の構造を問えた。
これは机上で必要な区別を導いた結果であり、実際の保存・query・原子的な更新を実行した結果ではない。

#### 推奨と、構成の粒度

design-data-modelを、体験とlogicに必要な情報を、現行の事実と根拠として読めて変更できる構造へ設計する専門として整備する。
方法は、必要な読取りと変更から意味を取り出し、守る関係と案を組み、具体の情報から読み書きを往復し、案の差と他の設計への条件を返す働きへ分ける。
段数や案数を固定せず、情報の全体と利用の対応を先に並べ、一つずつcolumnを継ぎ足して全体の意味を失うことを避ける。

抽象的な情報の分類だけで終える案では、実装する人が鍵・制約・更新を発明し直すため不十分である。
保存方式が決まった詳細の依頼なら、それに合う鍵・型・制約と具体の読取り・書込みまで材料にする。
方式が未決の粗い比較では、必要な保証と差を返し、選ばれていないDBや全schemaを先行完成させない。
専門が技術の実証まで抱える案も採らず、どの保証が確認できればどの構造が成立するかを返す。

一時領域へ材料と検査を置き、必要な構造・入力・読取りと変更の結果・限界をこのlogへ残す。模型のproduct directoryは変更しない。

反映・review後にorigin単位のdoc-enricher提案reviewを一回行う。実物のschemaの検査を、製品全体や外部の成立の証拠へ広げない。

#### 材料を育てて読み書きした結果

新規skillの本文173行を書き、既存四fileを保存済みafterの全文へ反映した。
実物のdesign-data-modelの方法を適用し、一時領域で学校の材料83行と、生成候補を文書で持つ材料50行を作った。
模型のproduct directoryや選定は変えていない。

学校の粗い比較では、案Aを現在値と必要な行い・外へ渡した内容の根拠を保持する形、案Bを原情報の版と現行への参照・対象の版へ結ぶ根拠の形として並べた。
Aは必要な根拠だけで足りる範囲を持つが、任意の過去へ戻る用途は別に要る。Bは対象の内容を辿れるが、現行を組み立てる読取りと版・関係の管理が要る。
全履歴を正解にせず、実製品の方式も選ばない。検査用の詳細の依頼としてBをSQLiteへ具体化した。

具体の構造はnotice、source_revision、current_notice、action_evidence、external_attemptである。
用件はnotice_id、原情報は(notice_id, revision_id)で識別し、現行と根拠・試行が対象にした内容を分けた。題名は同一性の鍵にしていない。
current_noticeは現行の原情報、現行の残作業時間、書込みの前提を比較するwrite_tokenを持つ。
複合foreign keyで別の用件の原情報を結べないようにし、残作業のNULLを未知として0と区別する。
action_evidenceでは引受け・署名・提出の出来事と対象の原情報、担い手と根拠を保持した。根拠の非空制約だけで真実性を証明したとは扱わない。
external_attemptのA1は対象R1・結果不明・外部ID無しとして読み、手元の未確認を外部での未作成にしていない。

| 検査した入力・変更 | 期待と実際の結果 |
| --- | --- |
| S1の現行がR1 | 現行への参照から締切の金曜をqueryできた |
| 原情報R2を追加し、現行を変更 | 同じ読取りが木曜を返した |
| R1へ署名したE1を読む | 対象R1・金曜を辿れ、現行R2の内容と混ざらなかった。R2への有効性は規則へ返す |
| 署名の根拠だけがある | 提出の根拠は0件。署名を提出済みへ替えていない |
| 外部試行A1の成功保存が無い | 対象R1・金曜・結果不明・外部ID無しを読めた。未作成という値を導いていない |
| R1・比較値1を見た古い更新 | 現行がR2・比較値2なので更新0件。R2をR1へ戻さなかった |
| 同じR2・比較値2を見た二つの更新 | 最初は残作業5分・比較値3へ更新。二つ目の10分への更新は0件で、最初の変更を保持した |
| 新規原情報R3と現行への参照を変える途中で例外 | transactionのrollbackで両方が取り消され、R2と元の比較値のまま残った |
| S1の現行へ、S2の原情報R9を結ぶ | 複合foreign keyが拒否した |
| 同じS1・R2を別の締切で重複して追加 | 識別子の一意性の制約が拒否した |
| 同じ題名のS1・S2を追加 | 別の用件として二件保存できた |
| 根拠が空の提出の記録 | 非空の制約が拒否した。記入された値の真実性を検証するものではない |

12ケースはSQLite 3.53.1のメモリ内DBで実行し、全て期待に一致した。
特に原情報の版がR2で同じでも更新の競合は起き、原本の版だけで全ての古い更新を防ぐ説明では不足すると分かった。
粗い材料の版の意味を保ち、詳細化で書込みの比較値を分けた理由と、前に読んだ依頼へ効く所を「変えた所」に残せた。
実物のskillにも版と競合の印の違いを持たせてあり、材料でその判断を具体化できた。

次の設計へは、体験に現行と過去の根拠・結果不明の区別、logicにどの時点の入力かと署名の有効性の未決、処理に更新の前提とまとまり・拒否後の再読取りを返した。
実際の保存先で同等の比較と更新を保証できるか、外部の試行を何で照合できるかは、技術の実証に必要な性質として返す。
外部APIをtransactionへ含めて戻せることや、実際に署名・提出・予定作成が行われたことは、この検査の結果ではない。

別題材の生成候補は、候補G1に根拠となったメモの箇所と提案、選択C1に対象の提案と選択した事実、試行の根拠に未取得を持つ文書の枝を作った。
メモの最新文が変わってもG1の根拠を付け替えず、候補を直した時にC1を新しい案への合意へ移さないことを辿れた。
選択があっても実施の根拠は無く、試行・効果を成立済みにしなかった。
この範囲なら根拠箇所の保持でも読めるため、全編集履歴や関係DBを必須にしない反例になった。
共同編集や保存失敗を扱う版なら、その方式の保証を別に確認する不足として返した。

#### 支持できる範囲とreviewへの接続

方法から必要な意味・関係を取り出し、粗い比較から、仮の保存方式での鍵・型・制約と具体の読み書きまで同じ材料を育てられた。
SQLiteで試したのは一つの構造の枝と局所transactionの挙動であり、実製品の方式選定、分散した同時実行、外部API、実利用の正しさを保証しない。
文書の例は机上で意味と変更の対応を辿ったもので、実際の文書サービスや利用者を試した結果ではない。
一時領域の試作を唯一の根拠にせず、ここへ構造・入力・queryと更新の結果、次へ返した条件と限界を残した。
別の専門の整備を完了扱いにせず、実物のskillと登録・案内のreviewへ進む。
