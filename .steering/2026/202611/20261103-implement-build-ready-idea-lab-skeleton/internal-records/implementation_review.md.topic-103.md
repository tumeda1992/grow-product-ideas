# 内部検討記録: 論点103 — 作る前提の案件でも、規模と解き方を探索できる入口を設ける

**discussion:** [implementation_review.md](../implementation_review/implementation_review.md)

## 開始context

Cは現在のCloudの同一文脈で、カードゲームは設計のbuild-ready、二人の夕食は非開発の部分案、替芯は具体入力不足で保留まで通った。必要な専門の方法と限定技術検査は実行したが、新規文脈・Claude Codeと実利用は未検査。利用者は結果から直したい点をdiscussionへ列挙し、普段の案件にも作る前提の入口を持てないかと求めた。非開発へ終わる道だけを選定対象から外し、規模・人と既存道具の分担・技術と費用・保留は固定しない入口を具体にする。
共通の方法の改稿は今回の指示だけで細部まで採用済みとせず、具体の契約と現在の案を先に示す。Cの既存の採否と原入力を変更しない。

## イテレーション0: 作る前提の案件でも、規模と解き方を探索できる入口を設ける

<a id="iteration-0-record-1"></a>

### 判断: 入口の指定が閉じる道と、開いたままの判断を分ける

#### 判断対象・必須条件・根拠

判断対象は普段の依頼でbuild_policyの有効値を受け取り、非開発へ閉じる結論だけを禁止して探索を続けられる仕組み。必須は未指定の現在の経路、why/whatの発散と収束、規模と作り方の選定、強い非開発の比較、保留と未知/未達の区別、再開での指定の保持。根拠は利用者の今回の原文と、C2の非開発部分案・C3の実入力不足。正本の配置と層のownerを崩さない具体の変更先を調べ、C2の作る案と異なる使用場面へ机上適用してから提案する。

#### 案の組立てと、比較の結果

`build_policy: open / require-build`を、正本に残す案件の入口の指定とする案を組み立てた。指定無しは現行動作、明確な自然言語の指定も出典付きで受け取る。版全体に働くので、各補う組は非開発を選べる。比較の基準の非開発は残すが採用版が全て非開発なら指定に合わない。必ず大規模に作る、学びが目的だと推測する、成立の不足を消す、という別の意味は足さない。

パラメータを入口だけに書く案では、how-to-solveが非開発へ閉じ、再開で指定が失われる。全専門の分岐に広げる案では選定の責務が分散し、各組に制作を強いる。共通契約を持たせ、growが受入れ/再開/出口で読み、how-to-solveが候補を選ぶ範囲にだけ効かせる案を推す。特殊モード用の別skillを作らず同じ四層を使う代償として、候補の有無と方針に合って採用できるかを区別して記録する必要がある。

変更候補7fileのbefore/afterを現在の本文から作り、まだ正本へ反映していない。rootの使い方、層間の契約、growの任意入力/保存/出口、正本/層記録の雛形、記録の役割、選定の閉じと採用条件が対応する。why/whatの方法と全専門の本文は変えない。C1〜C3の原入力/採否、保留007とshared pluginも変更しない。

<a id="iteration-0-record-2"></a>

### 検証: 入口の指定が探索と停止を壊さず、非開発への終端だけを外せるか

#### 主張と確かめ方

今回の候補afterを机上で照合する。未指定での既存の非開発、明示require-build、最小の作る版、広い作る版、作る/人/既存道具の混合、API不足、上限不足、保存後の再開/途中変更、無関係なscriptによる見せかけ、明示の制作希望を楽しみの発言へ変える失敗を当てる。
合格の線は、指定の有効値が保存→選定の適格性→必要な設計→出口まで一貫し、非開発を選べない以外の実質判断を固定しないこと。必要な根拠が無い時は保留し、費用を0と捏造しないこと。これは文書契約の机上検査であり、新しい案件の一式実行・製品実装・client読込みの検査とはしない。

#### 期待と実際の机上照合

| 当てたcase | 候補afterでの判定と根拠 |
| --- | --- |
| 未指定の旧C2 | 方針行が無い既存案件はopen。従来の非開発Pという決定を勝手に変えない |
| require-buildでC2を別検討 | Pは比較基準にはなるが、そのまま採用して作らないへ閉じない。機能を持つ小さい版から広い版へ育て直す |
| 最小の新規処理と既存連絡 | 相談文の生成だけを作り、送信/了承は既存の連絡と本人に任せても、版全体に意味のある作る部分があれば候補にできる。全条件の達成とはしない |
| より広い共有版 | 変更履歴/現物確認/引受けを繋ぐ版も候補にできる。必ず最小へ絞るという規則は無い |
| 混合の組 | 一組は制作、別の組は人/既存道具でよい。全ての組へ新規制作を課さない |
| C3のAPI/SKU不足 | require-buildでも不足は消えず保留可能。架空のsourceを作ってbuild-readyにしない |
| C2の準備30分不足 | 作る案が30分へ収まる根拠が無ければ保留又は本人への制約変更の判断。作る前提から予算増へ飛ばない |
| 保存後の再開 | 正本の有効値と原文を読み直す。省略をopenへの変更と見なさない |
| 本人が途中でopenへ変更 | 実際の原文を残し、選定/下流を再評価。why/whatは価値/条件の差がある時だけ返す |
| 無関係なscriptを添える | 非開発Pにhello worldを添えても今回の価値/制作上の目的へ働かず、作る部分の条件に不適合 |
| 作る希望から楽しみを推測 | require-buildは採用範囲の指定で、whyの楽しみ/学び/節約の事実を捏造する根拠にならない |

比較の探索と採用可能性を分け、非開発が安いだけで指定撤回を繰り返し求めない文を候補afterへ入れた。候補の有無を入口で固定せず、価値に働く作る版を育て直す。一方、成立の根拠/予算の不足を保留へ返すことは残す。11caseに対するafterの読みは対応したが、これは文書契約を使った机上検査であり、パラメータを持つ新規案件を全層に実行した検証ではない。

#### 構造・内容のreviewと、未確認

skill-update-reviewを設計時として明示適用。growの現行本文全体と変更候補を読み、切り出し候補なし。新しい独立工程をgrowへ抱え込まず、growは入力/保存/再開/出口の照合、版の採用は既存のhow-to-solve、意味の正本は層間の共通READMEというownerを保つ。指定値の違いで別skillを作る根拠は無い。これは機能の動作合格ではない。
document-reviewでは、入口の指定だけで候補選定/再開/出口が変わらない薄い追加、全組への制作強制、旧案件の非開発決定の改変を失敗例として照合した。候補7fileの対応で前二者を防ぎ、旧案件はopenで維持する。正本内に有効値/出典/意味を残すので持出し後にこのレールを読まなくても制約を読める。差分は全162行を保存し、git apply --checkも通った。正本7fileはbeforeのままで未反映。
残るのは利用者の具体案への採否、採用後の反映/編集後review/一式適用である。新規文脈/Claude Codeと実利用の未確認は別に残る。

### 再提示: 保存済み提案0を、その場で採否できる形へ戻す

起点は[discussionの利用者原文と進行指示](../implementation_review/implementation_review-101-105.md#セッションへの再提示とその後の進め方)。前回のchatは一覧・要旨・fileの場所の報告に寄り、判断する内容と応答対象を一つの提案として明瞭に渡せていなかった。指示は再提示と後続の順序であり、7fileの内容への採用ではない。内容に訂正は入っていないので提案0を維持し、架空のfeedbackや新iterationを増やさない。

AGENTSと実際の8.2.5配布のthink-through、facilitate-discussion/iteration、steeringとtask-designの判断・反映・feedbackの境界を再読した。同じ作業/同じ記録ownerの継続で、別作業の準備・handoffを始めない。元作業のtemporary-overridesが無いことを管理の手順に照合してnoneとした。実際の発言と必要な記録以外の適用ルールを作らず、共有pluginの本文を直接変更しない。

今回の提示で、利用者は「require-buildでは価値に働く作る部分を含む版を採用し、規模・解き方と人/既存道具との分担を比較したままにする。技術/入力/予算の不足なら保留する」という一つの採否を判断できるようにする。入口のみのflagでは保存後の再開と選定/出口で失われるため、7fileの保存済み差分が不可分に対応することを説明する。非開発案との比較は払うものを知るために保持する一方、その方が安いだけで制作指定を再度撤回させる手順にはしない。

提案0と162行の差分、7fileのbeforeが現在も一致していることを再確認した。既存の11caseの机上照合は履歴として使い、今回もう一度新規の案件を実行した証拠にはしない。今回の進行指示は103→改善の提案/採否/即時反映/局所検査を一件ずつ→作る前提の新しい一式適用。改善の候補を無条件で全て共通改稿へ変える合意とはしない。

### 採用と反映: 任意の開発方針を本線へ接続する

利用者の実応答は「ok」。直前の103提案0の本線反映への採否に対応する。提案0の完全差分と7fileの現在のbeforeを照合した。対象成果物はレールの文書/skill/雛形で、他の未決改善とは独立し、一つの連続した反映・validationで扱えるためtask-design内の反映へ分類する。実装開始の別承認や空のtasklistは作らない。
採用した契約を既存designの現在の構成へ書き戻し、7fileをafterへ揃える。編集後のskill-update-reviewとdocument-review、指定/未指定/再開/未取得/費用/混合の机上適用と参照を確認する。本製品を実装せず、新しい一式ドライランもこの確認の中で完了扱いにしない。

#### 反映後の検査と、言える範囲

7fileの全文が提案0のafterと一致した。新旧の正本の意味を読み、入口の任意指定、明示の自然言語の受入れ、正本の値/出典、再開、版全体の適格性、必要な設計、出口直前の照合を追った。

| 適用した入力・場面 | 今回の本文から得る判断 |
| --- | --- |
| 未指定で方針行の無い旧C2 | openで、過去の非開発の選定を変更しない |
| require-buildで非開発Pだけを採用しようとする | 比較の材料には残るが採用版の条件に合わず、価値に働く作る版の探索へ戻す |
| 相談文生成を作り、送信/了承は人と既存の連絡へ任せる版 | 制作の効果と範囲を示せれば混合の候補にできる。全組へ新規制作を課さない |
| 指定を保存した案件を、次の依頼では指定を省いて再開 | 正本のrequire-buildを読み、openへ自動変更しない |
| SKU/実source不明、又は準備30分へ作る版が収まる根拠無し | require-buildでも保留可能。未知の根拠や制作時間を作らない |
| 未知の指定値、又は楽しみの発言が無い | 意味を勝手にopenへ直さず必要な意味を確認する。制作指定から楽しみの事実を補わない |

この表は編集後の文書の机上適用であり、新規案件を全層へ通した結果ではない。既存11caseの設計時照合と合わせ、最小/広い制作、既存拡張、人との分担を残す。新しい一式は、Cの個別改善の後に実施する。

skill-update-reviewを編集後のgrow本文全体へ適用。独立した新工程/状態を抱え込まず、意味は共通README、進行はgrow、採用はhow-to-solveへ残るため切り出し候補なし。これは内容の正しさの合格を代替しない。
document-reviewでは入力指定を読んだ利用者が何を頼めるか、再開/保留で同じ意味を保つか、版全体と個々の組を混同する三つの失敗に本文が応えられるかを確認した。7fileの実参照/anchor 20件と末尾空白は問題無し。元の三件64fileと固定入力のhashも不変。

反映直後のdoc-enricherの提案reviewを、このoriginについて一度実施した。rootの使い方、共通READMEの契約、記録規約に有効値・選定の範囲・再開/変更・保留まで既にある。追加で同じ開発方針の規範を別READMEや全専門へ置く候補は重複（Gate G）として落とした。新しい知識追記の提案は無し。Cの別の改善は論点102の受付から扱い、このoriginへ抱き合わせない。
