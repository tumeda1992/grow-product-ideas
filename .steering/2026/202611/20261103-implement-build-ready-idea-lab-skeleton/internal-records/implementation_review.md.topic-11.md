# 内部検討記録: 論点11 — 利用者の譲れない条件の置き場所

**discussion:** [implementation_review.md](../implementation_review/implementation_review.md)

**論点:** 論点11

## 開始context

自演のKindleの件で、「外部のサービスには預けたくない」を作りたい動機として受け取ったが、代案を外す制約として働いた。受け入れ時の入力には、アイデア・作りたい動機・既にある着想しかない。

<a id="iteration-0"></a>

## イテレーション0: 受け取り方と使い方

<a id="iteration-0-record-1"></a>

### 判断

| 案 | 評価 |
| --- | --- |
| 受け入れ時の入力に「譲れない条件」を足す | 動機（なぜ作りたいか）と条件（何を選んではいけないか）を分けて読める。settle-questionが対案を外す根拠として読める |
| 痛みの問いの認識合わせで拾う | 条件が出るのが痛みの問いとは限らず、受け入れ時に分かっている条件を後回しにする |
| 問いのセットに「譲れない条件は何か」を足す | 条件は利用者が持つもので、詰めて決めるものではない。README「載せる・載せない」の基準に反する |

受け入れ時に足し、後から分かった条件は区別して足す。条件そのものの採否は問わないが、条件による影響（費用の膨張、保留）は論点として示す。

<a id="iteration-1"></a>

## イテレーション1: 問答の中で拾う

利用者の応答: 受け入れ時に尋ねられても答えられるか分からない。問答の中で出てくる。

| 案 | 評価 |
| --- | --- |
| 層の閉じの応答の理由から拾い、確かめて正本の条件の節へ足す | 条件が言葉になる場面（対案を退ける時）で拾える。確かめるので一度の言葉を一般化しない |
| 応答をそのまま決定過程に残すだけにする | 以降の問いで条件として読まれる保証が無い。Kindleの摩擦がそのまま残る |
| 定石に「預ける・費用・端末」等の軸を足し、毎回利用者へ問う | 問答の前に尋ねることになり、提案0と同じく答えられない |

条件を足した時に閉じた問いと照らすのは、進行を持つgrow-product-ideaにする。
