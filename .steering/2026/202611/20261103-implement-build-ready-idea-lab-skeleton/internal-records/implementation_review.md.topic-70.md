## イテレーション0: 旧四つの仕事を失わず、独立層を要る形へ整理する

<a id="iteration-0-record-1"></a>

### 判断: 届ける版の選定と、実装へ渡す設計をどう分けるか

#### 判断対象・比較条件・方法

未整備のどこまで作るかを独立層として復元するか、その仕事をhowの選定とどう作るかの設計へ分けて置くかを比較する。
現在のhowの決めるもの、旧how-far-to-buildの四つの問い、退避したhow-to-buildの役割、build-readyの制限を照合する。
最初に推測したarchive直下のfileは存在しなかったため、rgで見つけたarchive/what-defines-a-product/の実fileを読んだ。取得失敗を仕事の不在と扱わない。
比較条件は、今回の価値・範囲・損失を二度選ばず、未達を黙って増やさず、運用と実装上の裁量の仕事を落とさず、作る版の初回構築に必要な設計を残すこと。
学校限定の非開発版、作る所のある一覧＋予定生成の比較候補、別領域のサブスク通知の小さい版へ、仕事の対応と戻り先を当てる。
運用へ任せることを選ぶ判断と、それを実行できる手順・修正・復旧の設計を分ける。実装時の裁量を、現実の操作権限を自動付与する規則へ変えない。
役割を減らすこと自体を目的にせず、独立層でなければ解けない判断が残るかを反例から問う。

#### 結論と、独立層を復元する案との差

今のレールでは、独立したどこまで作るか層を復元せず、仕事をhowの選定とどう作るかの設計へ対応させる案を推す。
howは66以降、技術の道だけでなく「今回届ける改善と受け入れる未達」を費用と合わせて選ぶ。旧い最初の分を後で別に選ぶ層を復元すると、同じ版を二度選ぶか、合意済みの価値を後で狭めるownerが二つになる。
独立層を維持する強い理由は、実装を始める前に投資・範囲・運用・裁量をひとまとまりで確かめられることである。
しかし、その仕事を現在のhowの選定とどう作るかの受渡しへ保てば、別の層でなければ解けない判断は今回の入力には残らない。
逆に、独立層を削除して四つの仕事も消す案は、運用の修正・復旧と実装上の裁量が抜けるため採らない。
これは今の役割分担での判断であり、あらゆる開発工程でMVPや投資の区切りを独立して扱うことが不要だという一般命題ではない。

#### 旧四問の仕事を残す対応

| 旧い問い | 今のownerと、残す仕事 |
| --- | --- |
| 最初に作る分 | 今回届ける版・受け入れる未達・後へ回す条件はhowの選定。技術上の分割や導入順の設計はどう作るか。心臓部だけの技術検証を届ける版の完了にしない |
| 最初の費用と代案 | howがpropose-alternatives等の材料を読んで選ぶ。設計で費用や負担が決め手を変えるならhowへ返す |
| 運用で都度解決するもの | 機能と運用の選択、頻度・負担・未達の採用はhow。具体の訂正・設定変更・例外・復旧の設計はどう作るか |
| AIへ任せる線 | どう作るかの引継ぎとして、設計上の裁量と変えるなら再判断する既決事項を区別。現実の操作権限は後続作業の指示に従い、計画文書が自動で付与しない |

初回構築のtasklistや実装の実行までこのレールへ取り込まない。選んだ版の実装に要る設計と前提を揃え、後続のsteering／task-designへ渡す。
どう作るか層自体はまだ定義していないため、層を減らしただけでbuild-readyにできない線を明示して保つ。

#### 具体のケースと反例へ当てた結果

| 入力・反例 | ownerと判定 |
| --- | --- |
| 68の学校限定の非開発試行 | 今回の範囲・損失・費用と運用はhowで選定済み。独立層で再び最初の分を選ばず、非開発の出口を保つ |
| 一覧＋予定生成を作る候補を仮に選んだ場合 | howが入力・自動生成・人の実施と今回の価値を選ぶ。どう作るかは状態・境界・情報・失敗時の訂正と導入を具体化する。これは未選定候補への照合であり、68の変更ではない |
| 実装を容易にするため通知を後回しにし、計算部分だけを届ける | 合意した版で必要だった通知を欠くなら新しい未達であり、howへ返す。設計側が最初の分の名目で黙って狭めない |
| 心臓部だけを先に試して実現性を確かめる | 技術の検証として扱い、届ける版の価値を達成したことにしない。結果が費用・選定を変えれば影響する判断へ返す |
| 修正・照合が毎日起き、見込んだ運用費用を越える | どう作るかで発見した差をhowへ返し、機能化・別の運用・部分案・保留を費用と損失で選び直す |
| サブスクの小さい通知版で解約実施は人へ残す | 任せる所と未達の採否はhow。通知・状態・外の手続きと根拠の設計はどう作るか。解約済みの欄だけで支払いが止まることにしない |
| 残る三つの定義済み層だけを閉じて、作る版をbuild-readyとする | 未整備のどう作るかを通さず必要な設計が無いので不可。登録済みの層の数だけで出口を決めない |

学校の今回の版はコードを作らず終わるため、どう作るか層を設計済みにしたり実家族の試行を始めたりしない。
作る候補と別領域のケースは責務の判別の机上検査であり、具体の技術設計を決めた証拠ではない。

#### 提案へ含める五fileの境界

層のREADMEで責務を定め、howの受渡し先を一つへ揃え、grow-product-ideaの出口の説明とrootの案内、designの現在の残りを同期する。
旧いhow-far-to-buildや過去の議論は履歴として保持し、既存のhow・why・whatの決定と69のskillは変更しない。
新しいhow-to-build.mdの本文や、退避した専門のskillはまだ作らない。今回決めるのは仕事のownerと未整備の範囲であり、その層の全体を磨く仕事は次の具体の判断で扱う。

### 検証と構造review: 五fileの責務と出口の説明が揃うか

#### claim・合格条件・方法

五fileのbefore/afterを固定し、patch、参照、改稿していない範囲、未承認の現物の不変を確認する。
howの未達・費用・選び直す条件と、作る版のbuild-readyの制限、作らない・保留の出口が保たれるかを机上で追う。
grow-product-ideaは指示の変更を含むため、skill-update-reviewの設計時reviewで全文から独立した工程の抱え込みを検査する。候補の有無を状態遷移や内容の検証に代用しない。
document-reviewでは、初見の読者が、何をhowで選び、何を設計へ渡し、何を後続の初回構築で行うかを読み分けられるかを確認する。
新しい層を定義済みと誤読させず、初期の層の数を所与にせず、旧い仕事の脱落を防ぐ変更集合として完全diffを提示する。

#### 検査と提示前reviewの結果

五fileのpatchは適用検査に通り、全対象の現物はbeforeと一致していた。新しいfile・依存package・外部サービスを加える変更は無い。
howからのどこまで作るか層への四つの受渡しは、どう作るかへの一つのownerへ揃った。費用・未達・選び直す条件の本文は保持している。
grow-product-ideaの分岐では、作る所の無い版は既存どおり出口の判断へ進み、作る版は未整備のどう作るかと必要な設計が残るためbuild-readyにしない。
古い「二つの層が閉じた時」という数の説明は、定義済みの層が閉じても必要な未整備の層が残る、という判断へ揃えた。
設計の履歴・退避資料・保留メモは保持し、designの現在の残りと受け入れ基準との関係だけを今回の責務へ揃えた。

grow-product-ideaの設計時skill-update-reviewは候補なしだった。SKILL.mdの全体を読み、新しい差分は出口の判定の同じ状態の説明を直すもので、別の独立した処理を内包していない。
受け入れ・層の反復・差し戻し・出口は同じアイデアの状態とownerを運ぶ制御であり、層の中身を自分の別workflowとして抱えていない。
「入力の形式を変える」「層側から再判断が返る」という変更caseでも、各層に判断を返して同じ反復へ戻る。今回の設計・実装や操作権限の付与を制御skillへ足すものではない。
切り出し候補なしは本文やstate遷移の正しさの証明にしない。

document-reviewでは、旧四問の仕事を対応表から辿り、初回の範囲・費用をhowで二度選ばず、運用と修正・復旧・裁量を消していないことを見た。
設計の段階で通知を後回しにする例と、技術検証の心臓部だけを先に試す例で、届ける版の変更と技術上の分割を区別できる。
実装の計画・実行は後続のsteering／task-designへ渡すことも明記し、レール内へ初回構築の実行を取り込んでいない。
新しいどう作るか層の本文や材料の再有効化は未実施と分かり、独立層の削減を完成・build-readyと取り違えない。
模型の非開発の選定や69のskillは不変のまま、仕事のownerの変更と五fileの対応を一つの採否で判断できる完全diffにした。

### 検証: 採用した責務の分担を五fileへ反映する

#### claim・合格条件・方法

提案0への実際の応答を同じ欄へ一度保存した。公開した完全diffと一時draft、五fileの現物のbeforeを照合した。
snapshotの一致と各fileの全文を確認してafterを反映し、反映後の全文一致・参照・費用と未達の本文・出口の制限を検査する。
grow-product-ideaの編集後のskill-update-review、document-review、三つの具体の版と反例への再適用を行う。
一回のoriginのdoc-enricher提案review後、次の未整備のどう作るか層へ進む。層の数を減らすだけで設計の完成やbuild-readyを許可しない。
