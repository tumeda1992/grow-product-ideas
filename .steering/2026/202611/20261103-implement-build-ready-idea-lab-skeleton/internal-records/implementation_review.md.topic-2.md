# 内部検討記録: 論点2 — product-plansの決定過程を、どの重さの手順で記録するか

**discussion:** [implementation_review.md](../implementation_review/implementation_review.md)

**論点:** 論点2

## 開始context

自演の3件で、`settle-question`は問いごとに`facilitate-discussion`を使う決まり（design.mdのfile成果物、論点10）だった。`facilitate-discussion`の全手順（入口の解決、snapshotと読取後の照合、論点ごとの内部検討記録、保存後のcheck）を問いごとに回すと重く、自演では論点・提案・検討記録・応答・決定だけの簡略形で書き、内部検討記録を作らなかった。

<a id="iteration-0"></a>

## イテレーション0: 決定過程に何が要り、何が重いか

<a id="iteration-0-record-1"></a>

### 診断: 論点10で何を確かめずに決めたか

論点10は、決定過程の置き場所を`discussion.md`とし、記録を`facilitate-discussion`に任せると決めた。理由は、前回designが再利用を決めていたこと、還元で理由を辿れる必要があること、`facilitate-discussion`の合意モデルが層の閉じのgateと噛み合うことだった。
`facilitate-discussion`の手順の重さが、問いごとに回すレールの使い方に見合うかは確かめていなかった。`facilitate-discussion`は、長く続く設計議論を複数sessionで安全に継ぐための保証（版の照合、内部検討記録、分割、回復）を持ち、その保証は問いごとの「提案→層の閉じでの合意」に必ずしも要らない。

<a id="iteration-0-record-2"></a>

### 調査: 自演3件での決定過程の実際

- 26の論点のうち、提案の後に修正や認識合わせの往復が起きたのは、利用者自身の事実を問うた3件（各アイデアの痛みの問い）だけ。残る23件は提案→合意の一往復だった。
- 決定過程を読む人と使い方: 層の閉じで利用者が論点ごとに応答する。還元skillが、比べた選択肢と理由、利用者の訂正を読む。build-ready後の後続が、答えの理由を読む。どれも論点の本文（立て直した問い、選択肢、理由、材料、応答原文、決定）で足り、内部検討記録や版の照合は使わない。
- `facilitate-discussion`の論点の形（`## 論点N:`、`#### 提案I`、`#### 検討記録`、`#### 提案Iへのフィードバック`、`### 決定`）で書けば、後から`facilitate-discussion`を適用しても同じfileを継続できる（`inspect-discussion.mjs check`は論点の見出しを走査する）。

<a id="iteration-0-record-3"></a>

### 判断

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A: 全手順のまま | 問いごとに`facilitate-discussion`の全手順 | 23件の一往復にも版の照合と内部検討記録が付き、重い。保証は使われない |
| B: 簡略形だけ | 論点の形を`product-plans/README.md`で定め、`settle-question`と`grow-product-idea`が直接書く | 軽い。ただし往復が続く論点（訂正、認識合わせが重なる）で、変遷の保存や中断からの復帰の保証が無い |
| C: 簡略形で始め、議論になったら全手順へ | 既定はBの形で直接書く。層の閉じで修正要求が出た論点、認識合わせが二往復を超えた論点だけ、`facilitate-discussion`を適用して同じfileの同じ論点を継ぐ | 一往復の論点は軽く、議論になった論点だけ保証が付く。形が同じなので同じfileで継げる |

推奨はC。基準は、議論が起きたかどうかである。`facilitate-discussion`自身も、通常の短いやりとりから暗黙に起動せず、議論を記録する時に使うものとしている。

<a id="iteration-1"></a>

## イテレーション1: 決定過程を芯として扱い、全手順で記録する

入口は利用者の訂正である。一往復は出来レースで自明なことを問うたため。速さは目的ではない。目的は細部の合意と、発案者が気づかなかったところまで視野を広げること。一往復でも価値があり、議論が盛んなら必ず残す。今後のプロダクトの雪だるまの芯になる。

<a id="iteration-1-record-1"></a>

### 診断: 提案0の前提

- 自演の一往復の件数を根拠にしたが、自演は利用者役もassistantが演じる出来レースで、根拠にならない。
- 決定過程を手間として扱った。原因は、design.md・`product-plans/README.md`・`settle-question`のどこにも決定過程の目的（細部の合意、視野を広げる）が書かれていなかったこと。design.mdは置き場所と、還元で理由を辿るためとしか書いていない。

<a id="iteration-1-record-2"></a>

### 判断

- 全手順を保つ（論点10のまま）。版の照合と内部検討記録は、変遷と調べた過程を失わないためにあり、芯を残すことに役立つ。
- 目的をレールのfileに書く。提案に、発案者の視野の外にあった点をそれと分かるように書く。サブスクの件で、着想が月払いで機能しないという発見が提案の本文に埋もれていたことが例になる。
- 自演の3件は書き直さず、簡略形であることを冒頭に書く。
