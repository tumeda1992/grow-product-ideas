# 内部検討記録: 論点7 — アイデアを通すworkflow（skill間の起動関係・状態・gate）

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion.md)

**論点:** 論点7

## 開始context

論点2でskill14種をすべて作ると決め、論点3で接合面をこのdesignで先に合意してから各fileの中身を作ると決めた。接合面のうち、各skillの中身を最も多く規定するのは、skill同士がどう起動し合い、どこに状態を持ち、どこでユーザーが判断するかというworkflowである。各`SKILL.md`はこのworkflowの中の自分の担当を書くことになる。

前回designが決めていること:

- 問いに答えるまでの流れ（9手順）: 受け取り → 四層を読む → 未回答の問いのうち下位を最も多く規定するものを選ぶ → 材料を集める → 定石から対案を出して並べて選ぶ → 正本へ書く → 水準を判定し満たさなければ差し戻す → 再評価 → 全問いが閉じたら出口判定
- 出口は三つ（build-ready・作らない・保留）
- ユーザー確認のgateは層の閉じと出口判定時に置く
- skill一覧の「持つもの」: 全体制御は受け入れとディレクトリ準備、次の問いの選択、材料の有無の判定、層skillの起動、層の閉じでのユーザー確認gate、出口判定。層skillは材料を取りに行く順序とその層固有の落とし穴。材料skillはそれぞれの材料を作る手順。還元は出口到達後に問い・水準・定石を判定して戻す
- 材料は層を跨いで再利用され、粒度は要求元の問いが決める
- 載せないもの: 着想、作りたいという動機、体験の質感（寝かせないと出てこないもの）

前回designが決めていないこと:

- 層skillと材料skillのどちらが材料skillを起動するか（全体制御か層skillか）
- 水準の判定（一段目・二段目）を誰が行うか
- 状態（どの問いが閉じたか、出口）をどこに持つか
- 出口判定を、全問いが閉じた時だけでなく途中（なぜ作るか層で「作らない」と分かった時）にも行うか
- 還元を誰がいつ起動するか
- 載せないもの（着想・動機・体験の質感）をいつユーザーから受け取るか

## イテレーション0: 前回designの流れをskill間の起動関係へ落とす

<a id="iteration-0-record-1"></a>

### 判断: 前回designの「持つもの」から、未決の担当を一意に導けるか

#### 判断対象と根拠

上の未決事項を、前回designの「持つもの」と論点4の働きから導けるかを確かめる。導けない箇所だけを判断として提案に含める。

#### 評価

- 材料skillの起動: 前回designは層skillに「材料を取りに行く順序」を持たせている。順序を持つ側が起動するのが自然であり、層skillが起動する。全体制御は「材料の有無の判定」を持つので、起動はしないが有無は見る。
  - 材料が層を跨ぐ場合（なぜ作るか層の問いが、どう作るか層の材料であるラフ画を要求する等）も、要求した問いの層skillが材料skillを直接起動し、粒度を指定する。材料skillは層に属さない。
- 水準の判定: 全体制御が「材料の有無の判定」を持つので一段目は全体制御が行う。二段目（満たさない答えの例との照合）は前回designで担当が未定。答えを書いた層skillが自分で判定すると、甘い判定を通す。全体制御が行えば書き手と判定者が分かれる。これは前回designからは一意に導けないため、判断として提案に含める。
- 状態の置き場: 前回designは正本が「問いごとに答え、水準を満たしたかどうか、根拠となる材料への参照」と「現在の状態」を持つとしている。状態は正本に置く。導ける。
- 途中の出口判定: 前回designは「出口を build-ready だけにしない」とし、「作らない」「保留」の場合はそこで作業が終わるとしている。全問いが閉じるまで待つと、作らないと分かった後も下位層の問いに答え続けることになり、論点4の働き（毎回の紆余曲折を減らす）を妨げる。なぜ作るか層が閉じた時点で出口判定を一度行う。前回designは「全問いが閉じたら出口を判定する」とだけ書いているため、変更として提案に含める。
- 還元の起動: 前回designは「出口到達後」とだけ書いている。出口判定のユーザー確認gateの直後に、全体制御が還元skillの起動をユーザーへ促す形が、出口到達と還元の間を空けない。ただし還元はレール自体（`what-defines-a-product/`とskill）を変えるため、アイデア1件の作業とは別にユーザーが承認してから変更する。
- 載せないものの受け取り: 受け入れ時に、アイデアの文章と一緒に、作りたい動機と既にある着想（ラフな画面イメージ等）を受け取る。その後に問いが着想・動機・体験の質感を必要とした場合は、層skillがユーザーへ問う。これ以外ではユーザーへ問わない（苗床を空けるため）。

#### 推奨

上の導出と判断をまとめて一つのworkflowとして提案する。判断を含む箇所（二段目の判定者、途中の出口判定）は提案内で明示する。

<a id="iteration-1"></a>

## イテレーション1: 水準の二段目を層skillへ戻す

入口はユーザーの指摘である。二段目を全体制御へ置くと全体制御が太る。甘い判定は判定ロジックの問題ではないか。

<a id="iteration-1-record-1"></a>

### 診断: 提案0が二段目を全体制御へ置いた理由

#### 期待との差

提案0は「書き手と判定者を分ければ甘い判定を防げる」として、二段目を全体制御へ置いた。ユーザーは、全体制御の肥大と、甘さの原因は判定ロジックにあることを指摘した。

#### 確認したこと

- 前回designのskill一覧: 全体制御は「受け入れとディレクトリ準備、次の問いの選択、材料の有無の判定、層skillの起動、層の閉じでのユーザー確認gate、出口判定」。層skillは「材料を取りに行く順序、その層固有の落とし穴」。
- 前回designの「水準は二段で判定する」: 二段目は「満たさない答えの例と照合する」。水準は問いごとに`what-defines-a-product/`の層fileが持つ。

#### 原因

二段目は層ごとの中身（問いごとの満たさない答えの例）を要する。全体制御へ置くと、四層分の水準の知識が全体制御へ集まり、前回designの分担（全体制御は進行、層skillは層の中身）が崩れる。

甘い判定の原因は、満たさない答えの例が曖昧で照合しても判定が一つに決まらないことにある。判定者を替えても、例が曖昧なら同じく甘くなる。提案0は原因を判定者に置いていた。

判定ロジックが明確でも残る偏りとして、答えを書いた推論が判定の根拠に混ざることがある。これは判定の入力を限ることで防げ、判定者を替える必要はない。

原因ownerは成果物固有である。分担は前回designに定められており、提案0がそれに照らさなかった。

<a id="iteration-1-record-2"></a>

### 判断: 二段目を層skillに置き、入力を記録だけに限る

#### 結論

- 二段目は層skillが行う。基準は各問いの水準が持つ。
- 甘さは水準の書き方（照合すれば判定が一つに決まる具体性）で防ぐ。これを層fileの中身を合意するときの判定基準にする。
- 判定の入力は正本の答え、材料、水準だけに限る手順を層skillへ持たせる。
- 全体制御は一段目と、判定の記録があることだけを見る。

<a id="iteration-2"></a>

## イテレーション2: 水準を答えを作る時の目標にし、判定は漏れを拾う確認にする

入口はユーザーの訂正である。判定は目的ではなく、同じ目的・基準で作っても漏れるものを拾うためにある。判定前が緩くなる形は言語道断。`document-review`と相似関係。

<a id="iteration-2-record-1"></a>

### 調査: `document-review`の書き手と判定の関係

#### 問いと確認先

`tumeda-dev`の`document-review`が、書く工程と判定の関係をどう置いているかを確かめる。確認先は`plugins/tumeda-dev/skills/document-review/SKILL.md`の冒頭から「当てる観点」まで、およびtask-design `SKILL.md`の2-3節。

#### 結果

- 役割: mdをemitする前に、読者がそのdocで作業できる状態に達しているかを判定し、達していないものを出させない。書き手が自分では見えない薄さを検知させる。
- 観点の正本: 当て方の中身は標準file（`content_density.md`、`expression_notation.md`、`file_naming.md`）が持ち、skill本文へ写さない。
- 書く側: task-designは`documentation.md`を選んだ場合、`document-review`が当てる観点を設計時から見込む。
- 指摘の種類: 記法・命名・言い回しは微細であり、直してレビューを最初から回し直す。骨子・構造・実質の破綻は書く工程へ戻して生成をやり直し、パッチで繕わない。濃さ不足は後者に属する。

#### 解釈

品質は書く時点で観点を見込むことで作り、判定はemit前に漏れを拾うgateである。観点は書く側と判定する側で一つの正本を共有する。漏れの種類で戻り先が分かれる。

<a id="iteration-2-record-2"></a>

### 診断: 提案0・1の前提

提案0・1は、作った後の判定を品質の担保として扱っていた。提案0は判定者を分け、提案1は判定の入力を絞った。どちらも作る段階の品質を前提に置いていない。原因ownerは成果物固有であり、関係は`task-design`と`document-review`に既にある。

<a id="iteration-2-record-3"></a>

### 判断: レールへの写し方

- 水準を一つの正本とし、層skillは作る時の目標と確認の基準の両方に使う
- 確認は正本の読み手（出口判定のユーザー、build-ready後の`steering`／`task-design`）の立場で、書かれたものだけを見る
- 局所的な漏れは直して確認をやり直す。骨子の漏れは材料集めか答えを作る段階へ戻す
- 水準は、作る側が狙え、確認する側が判定を一つに決められる具体性で書く。層fileの中身を合意するときの判定基準にする
