# 内部検討記録: 論点3 — 各要素の中身をこのdesignで決めるか、子designへ分けるか

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion.md)

**論点:** 論点3

## 開始context

論点2で、前回designの構成要素（README、`what-defines-a-product/`の五ファイル、`product-plans/`の構造とテンプレート、skill14種）をすべて作り、中身を1件を通せる程度にとどめると決めた。

残るTBDは大きく二種類に分かれる。

- 接合面: file一覧、配置、名前、各要素の役割、要素間の参照関係（どの問いがどの材料skillを要求するか等）、中身を最小にとどめる基準、受け入れ基準
- 中身: 各層に置く具体的な問い・水準・定石、各`SKILL.md`の本文、テンプレートの本文

この論点では、中身までをこのdesignで合意するか、接合面までをこのdesignで合意し、中身は依存順の子designへ分けるかを決める。
結論によって、このdesignに残すTBDの範囲、execution planの種別（plan無し・tasklist・roadmap）、議論の進め方が変わる。

開始時の既決条件は次のとおり。

- 論点1: 終了状態は「1件を通し始められる最小のレール」
- 論点2: 構成要素はすべて作る
- task-designの完了条件: 実装中に新しい設計判断が生まれないこと。docsやskillの中身を書くことも設計判断を含む
- 前回designの依頼原文: 骨格の後は「fableやastraにちゃんと回していく」

## イテレーション0: 中身までをこのdesignで合意するか

<a id="iteration-0-record-1"></a>

### 判断: 接合面までをこのdesignで決め、中身を子designへ分けるか

#### 判断対象・必須条件・根拠

判断対象は、このdesignが合意する詳細度である。

必須条件は次のとおり。

- 中身を書く作業者が、要素間の整合を設計外の判断で取らずに済むこと
- 一つの合意が過大にならず、ユーザーがreviewできる粒度であること
- 中身のあいだの依存（問いが材料を要求し、材料skillが材料を作る）を壊さないこと

根拠は次のとおり。

- 作る対象の量: `what-defines-a-product/`の五ファイル、テンプレート、skill14種。前回designは、各層の問い・水準・定石を「次段階で確定する」とし、それ自体を一つの設計対象として扱っている
- 中身の依存: 層ファイルの問いが必要な材料を定義し、材料skillがその材料を作り、層skillが材料を取りに行く順序を持ち、全体制御skillが問いの選択と材料の有無判定を行う。問いの中身が先に決まらないと、skillの中身が決まらない
- task-designのroadmap: 二つ以上の区別できる子scopeがあり、各子が親より狭く、子全体で親の完了条件を満たし、依存がDAGになる場合に使う

#### 評価した案

##### 案A: このdesignは接合面までを決め、中身は依存順の子designへ分ける

このdesignでは、file一覧と配置、名前、各要素の役割、要素間の参照関係、中身を最小にとどめる基準、受け入れ基準を決める。
中身（層ごとの問い・水準・定石、各`SKILL.md`本文、テンプレート本文）は、依存順に並べた子designがそれぞれ決めて作る。

- 満たす: 要素間の整合は親designの接合面が固定するため、子designは自分の範囲の中身だけを決めればよい
- 満たす: 子designごとに合意するため、一回の合意の粒度が保てる
- 満たす: 依存順に子designを並べられる（問いの中身 → 問いを使うskill）
- 代償: 子designの数だけsteeringの往復が発生する。親designの段階では各要素の中身が見えない

##### 案B: このdesignで中身まで合意する

このdesign内の議論で、各層の問い・水準・定石と各`SKILL.md`本文の骨子まで合意する。

- 満たす: 一つのdesignで完結し、steeringの往復が一回で済む
- 満たさない: 合意対象が五ファイルとskill14種の中身に及び、一回の合意が過大になる。中身の議論が接合面の議論と同じdesignに混ざり、design.mdがreviewできない分量になる

#### 推奨と決め手

案Aを推す。決め手は、中身同士に依存があり、量も大きいため、接合面を親で固定してから依存順に中身を決める方が、作業者に設計外の判断を残さず、合意の粒度も保てる点である。

この判断が規定する最終案の内容は次のとおり。

- このdesignのTBDのうち、中身に属するもの（各層の問い、各skillの本文）は子designへ送る
- このdesignは、接合面と、子designへの分け方・依存順を決める
- execution planはroadmapになる見込みが高い。最終的な種別はdesign合意後に判定する

前回の依頼原文にある「fableやastraに回していく」は、子designを誰が進めるかに関わるが、この論点の判断（どこで分けるか）は変えないため、判断材料には入れていない。

## イテレーション1: 中身をこのdesignで扱う場合の進め方を前提から見直す

入口はユーザーの提案0へのフィードバックである。

- bへの傾き（前回designがかなり定めているので、形にするだけではないか）
- fable・astraに関する作業は別issueとして既に存在し、このsteeringは存在を知るまでにとどめ、中身を読まないこと

<a id="iteration-1-record-1"></a>

### 診断: 提案0がbを退けた理由の前提

#### 期待との差

提案0は、bを退ける理由を「合意対象が五ファイルとskill14種の中身に及び、design.mdがreviewできない分量になる」とした。ユーザーはbへ傾いている。

#### 確認したこと

- task-design `SKILL.md`の提案準備（facilitate-discussion `iteration.md`の「提案または認識合わせを形にする」）: 新規documentは`document-heading-outline.md`で見出し構成と各見出しの内容へ合意してから実fileを作成し、作成された実file自体をreviewする。本文全文を作成前のdiscussionへ複製しない。
- task-design Step 5: skill、documentation、template等の作成は本番application codingに含まれず、合意済み内容から一意に変更できるならtask-design内で扱う。

#### 原因と影響

提案0は、中身をdesign.mdへ書く前提に立っていた。実際の手順では中身の正本は実fileであり、design.mdは接合面と各fileの役割だけを持つ。したがって「design.mdがreviewできない分量になる」は成立しない。

原因ownerは成果物固有である。task-designの手順には正しい知識が書かれており、提案0の作成時にそれを当てなかった。

<a id="iteration-1-record-2"></a>

### 調査: 前回designが中身をどこまで定めたか

#### 問いと確認先

ユーザーの「前回かなり定めているから形にするだけ」という見方が、各fileで判断が要らないことを意味するかを確かめる。確認先は前回designの「このdesignの対象範囲」「各層の中身は次段階で確定する」「プロダクト1件のディレクトリ」節である。

#### 結果

- 定めているもの: 問いの三属性、四層と閉じ条件、水準の二段判定、調査系と生成系の区別、定石の形（選択肢・判断軸・個人版への翻訳）、skill一覧と各skillが持つもの、リポジトリ構成
- 次段階へ送っているもの: 各層に置く具体的な問い、水準の書き方（満たさない答えの例をどこまで具体的に持つか）、定石の出所と範囲、各`SKILL.md`本文、テンプレート本文、`product-plans/<slug>/`配下のファイル名、skill名

#### 解釈

枠組みは定まっているが、中身の判断は残っている。一つのdesignで扱っても、fileごとの見出し構成の合意として判断が入る。判断の量はa・bで変わらず、変わるのは判断を一つのsteeringで行うか複数のsteeringに分けるかである。

<a id="iteration-1-record-3"></a>

### 判断: 一つのdesignで中身まで扱うか

#### 判断対象・必須条件

提案0と同じ必須条件（作業者が要素間の整合を設計外で取らずに済む、合意の粒度が保てる、中身の依存を壊さない）を使う。

#### 評価

- 整合: 接合面を最初に合意すれば、一つのdesign内でも各fileは接合面に従って作れる。満たす。
- 合意の粒度: fileごとの見出し構成の合意と実fileのreviewで保てる。満たす。
- 依存: 論点の順番として依存順を保てる。満たす。
- aとの差: aは子ごとにsteeringの必須gateとroadmapの状態管理が入る。一つのdesignならそれらは一回で済む。

#### 推奨と代償

一つのdesignで中身まで扱う案を推す。決め手は、提案0でbを退けた理由が成立せず、残る差がsteeringの往復の多さだけになったことである。代償は、一つのsteeringのdesign phaseが長くなることである。

fable・astraの別issueは存在だけを記録し、中身は読まない。
