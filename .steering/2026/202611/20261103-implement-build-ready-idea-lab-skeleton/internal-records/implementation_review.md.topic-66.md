# 内部検討記録: 論点66 — 部分的な改善と、そのために受け入れる未達を選定する

**discussion:** [implementation_review.md](../implementation_review/implementation_review-66-70.md#論点66-howで条件の未達を損失を明示したトレードオフとして扱う)

**論点:** 論点66

## 開始context

65で、whyの余白を守る最低線Gを含むwhatの全体検証版を模型へ採用・反映した。
そのorigin-reviewで、whatの必要条件の定義、上位READMEの物差しを先に閉じる規定、howの条件を手段へ寄せない規定と、howの未充足条件を費用として受け入れる操作指示が食い違うことを確認した。
正本の雛形の選定の欄も、満たさず受け入れることを選択肢として持つ。
このfindingを受けた二fileの修正案を作る。既存の一般原則を新しい発見として増やす仕事ではなく、矛盾する操作と出力の記述を既存の役割へ揃える仕事である。
模型のwhatは開け直しのままであり、実対象の条件を閉じずにhowを選定することにはしない。

## イテレーション0: 比較へ残す案と、上へ返す未充足を取り違えないか

<a id="iteration-0-record-1"></a>

### 判断: how本文と正本の出力で、必須条件の未充足を費用と引き換えにできない形へ揃える

#### 判断対象・使う既存の根拠

既に読んだhow全文、whatの必要条件の定義、READMEの層の順と差し戻し、whyの体験と価値、正本の雛形の選定欄を照合する。
howには足りない点を「満たさずに受け入れる」、費用表の「満たさない条件」、選定に「満たさずに受け入れる」を含める記述があり、本文内部にも同時に条件を緩めない規定がある。
雛形にも同じ扱いがあるため、本文へ注意を足すだけでなく、出力も同じ契約へ変える必要がある。
whyの体験と価値には失う価値と残る負担を読む役割があるので、目標を選び直す判断まで禁止する修正はしない。

#### 必要条件と比較・検査の方法

必須条件に反すると分かる案と、成立が未確認の案を、他の利点で埋めて合格にしない。
必須条件を満たすための補いと、満たしたうえで足す改善を分け、後者を足さない自由を保つ。
満たす案を選べない時の作らない・保留、および必要ならwhy・whatへ返して目標や条件を選び直す道を保つ。
whatで既に受け入れた外部事情を、howで新しく最低線を破る許可へ広げない。
65の望まない長い照合を安さで受け入れる案、必要な条件を満たすが三つを一画面に集める便利さは足さない案、作業量が未確認の案、満たす案が無い場合を同じ記述へ当てる。
別の題材でも、必須の復旧条件に届かないバックアップを安さだけで合格にしないかと、任意の一覧化は足さなくてよいことを確かめる。
費用表から未充足の行を除くなら、八という数を保つための別の軸を追加せず、数を固定した参照を同じ意味へ揃える。
過去の議論や自演の結果は書き換えず、現行の方法本文と雛形の変更だけを一時draftへ作る。

#### 比較で採った修正と、残す役割

howの足りない点の選び方、費用の行、選定の定義と停止条件を、比較する前に必須条件への適合を問う記述へ揃える案を推す。
正本の雛形も同じ選定の意味へ揃え、how本文を読んだ後に古い選択肢を再生成しないようにする。
これは二つの独立した採否ではなく、同じ選定の意味を方法と出力へ反映する一つの変更集合である。

上位READMEとwhatに既にある一般原則をもう一節追加する案は採らない。
howの足りない点・費用・選定が受入れを明記したままなら、追記された注意と実行する操作のどちらに従うかが割れたままになる。
そのため、矛盾する本文そのものを直す。条件を緩めない既存段落と役割は維持する。

一方、最低線を固定して目標や条件を一切選び直せない案も採らない。
実際の費用や成立可能性が分かって目標を変えたい時は、失う価値と負担をwhy・whatへ返し、そのownerで物差しを選び直してからhowへ戻れる必要がある。
満たす案が選べなければ、作らない・保留も残す。満たさない案を同じ目標の合格として閉じることと、取り組むかを選び直すことを分ける。

#### 同じ基準を具体の場面へ当てた結果

| 場面 | 修正前に許される読解 | 修正案での扱い |
| --- | --- | --- |
| whatの最低線に反する夫の毎晩の長い全件照合を、作る時間が短いことと引き換えに採る | 未充足を払う費用として受け入れると書ける | 未充足の案として外す。安さで相殺しない |
| 必須条件は満たすが、三つの教室の一画面への集約だけは足さない | 良くする点を選ばないことは可能 | 同じく可能。任意の改善を足さないことと必須条件の未充足を混ぜない |
| 作業量が未確認でGを満たすか分からない | 払う費用の見込みのまま選定と書く余地がある | 作業の説明・見積り・実測、または事実の両側での条件付き判定へ分ける。未確認を合格にしない |
| 満たす解き方が選べず、利用者が目標や残す時間を変えたい | howの受入れだけで閉じられる | why・whatへ失う価値と負担を返し、物差しを選び直してから比較する。選び直す自由は残す |
| whatで満席や外部中止の受容を既に選んでいる | howでの受入れと区別されない | 既決の物差しの適用範囲として引き継ぐ。新しい未充足の許可に拡張しない |
| 条件を満たす紙の運用を選び、仕組みを作らない | 選べる | 引き続き選べる。作らない解き方を排除しない |

別の題材として、毎日更新する写真の保管で、復旧時に失う更新を1日分以内にする条件を与えた。
週に一度しか写さず、6日目の故障では最大6日分を失う案を、安さだけで同じ条件を満たす選定にしない。
一方、条件を満たしたうえで写真を一つの一覧へ集める便利さは足さなくてよい。
この比較は原則の別題材への机上適用であり、実在の利用者の写真や必要な復旧条件を取得したものではない。

#### 費用の軸と、修正する範囲

「満たさない条件」を費用表から除く。八という数を保つための別の軸は足さず、本文内の固定の数の参照を「比較の軸」へ揃えた。
手間・得たいもの・変化への強さ・作る時間・続ける時間・崩れやすさ・お金は保持する。
崩れやすさには不確かさと対応を残すが、成り立たないと分かる必須条件をリスクの費用へ移して合格にする扱いは止める。
未知の事実に対する条件付きの判定自体は保ち、満たさない枝と満たす枝を分ける。

全体検索では、現行の直接consumerである雛形に同じ「満たさずに受け入れる」指示があったため二fileを対象にした。
whyの体験と価値の記述は、目標を選び直す判断で失う価値を読むという役割を保てるので変更しない。
既存のwhatとREADMEも、今回整合させる元の規定があるため追記しない。
過去の議論・模型の旧how・旧費用表は当時の履歴であり、現在の規則に合わせて遡って書き換えない。

#### 原因ownerとorigin-reviewでの位置づけ

原因は今回の模型固有の設定ではなく、このrepositoryのhowの操作指示と出力の記述の不一致である。
共有skillの一般的な思考プロセスを変更する根拠は無い。
doc-enricherでの新規知識の追記としては、上位READMEとwhatに同等の原則が既にあるためGate Gで落とす。
ただし、既存の相反する操作指示を残したままにする意味ではない。consumerの層の方法の修正として、同じdiscussionの66へ具体の変更集合を出す。
65で実際に反映した模型とその未確認は維持し、今回のhowの規則の修正から模型のwhatやhowを閉じない。

#### 文書の検査と限界

二fileの一時patchは現状へ適用可能である。現物はbeforeのまま保持され、共有pluginのinstall cacheは変更していない。
document-reviewでは、未充足・未確認・任意の改善・既決の外部事情を読者が場面から分けられ、同じ目標の合格と物差しの選び直しを取り違えないかを照合した。
他の比較軸、情報の流れ、候補を作る方法、利用者が重みを決める役割、作る楽しみを独立に比較する役割は保つ。
これは方法本文の内部整合と机上の選定の扱いの検査であり、具体の手段の実運用、全ての価値の競合、余白の実測を検証したものではない。
この具体の二fileの修正を採否へ出し、抽象的な「最低線を守る」という方針だけの合意は求めない。

## イテレーション1: 合意した損失を伴う部分案を、失敗や未確認と分けて選べるか

<a id="iteration-1-record-1"></a>

### 判断: 全体の条件を維持した比較と、部分案を選ぶ合意・記録を両立する

#### 応答から訂正する前提と、判断する範囲

利用者は、完全案が月30万円なら選べない一方、保留だけでなく4%程度でも痛みを部分的に解くv0.0.1を、損失も考慮した合意の上で選べる必要があると指摘した。
原文はdiscussionの提案0への応答に一度保存した。前回案の採用ではなく、同じhowの未達の選定の扱いの修正として受け取る。
前回は「全体目標を満たしたと書かない」を、「未達の案は費用比較の前に外す」という強い制限へ変えていた。この前提を訂正する。
既存howの未達を払うものへ出す仕組みには、損失を見えるようにして利用者が選ぶという機能があり、それ自体を矛盾として除去する診断は撤回する。
ただし、何が届き何が届かないか、誰に痛みや負担が残るかを読めないまま「受け入れた」で閉じる不足は解く。

#### 必要な働きと、比較する場面

全体の条件を先に定め、完全案・部分案・保留を同じ物差しへ当てる。
部分案は、届ける改善と未達・失う価値・残る痛み・負担・費用を併記し、それでも選ぶ理由を利用者が決められる必要がある。
4%は条件の個数の割合へ変換しない。小さい範囲でも、その範囲で実際に価値が生じるかを問う。痛みの改善でなく作る楽しみや学びを選ぶ場合は、その理由を別に明示する既存の役割を保つ。
合意した未達と、選んだ達成範囲に必要な事実・成立が未確認のものを分ける。前者は選んだ損失、後者はまだ判断できない不足である。
全体の目標を満たしたと偽らず、選んだ版で届ける範囲に必要な条件と、後回しにする条件を分けて後工程へ渡せることを要る働きとする。
部分案の採用のためだけにwhy・whatの全体を一律に再議論せず、同じ採用の合意で達成範囲と記録を揃える。新たな価値や優先が未決の場合だけ、その残余をownerへ返す。

#### 調べ比べる対象と方法

現物のhow、whatの条件の定義、READMEの層の順・閉じ・差し戻し、正本の雛形を読み、全体の比較基準と今回の達成範囲をどこへ書けば取り違えないかを比べる。
前回の未適用draftから修正を積まず、現物のbeforeから部分案を扱える改稿を作る。
利用者の完全案月30万円、費用と価値を確認して選ぶ部分案、保留を比べる例、局所の機能は作れても痛みへ効かない案、作る楽しみだけを理由に選ぶ案、未確認を損失の受容へ読み替える案を当てる。
必要なら方法と出力の変更集合として、howだけでなくwhat・README・正本の雛形も、同じ達成範囲の記録へ揃える。
模型の家族の新しい費用・許容・部分版の採否や、実際の改善の効果を創作して反映しない。

#### 推奨と、前回から撤回する扱い

完全案・部分案・作らない／保留を、同じ全体目標の条件へ当てて、実際に届ける改善と受け入れる損失を比べて選ぶ形を推す。
前回の「未充足の案は比較へ残さない」「未充足を費用表から除く」「部分案は先にwhy・whatへ返してから比べる」を撤回する。
65のorigin-reviewと本logのイテレーション0で、howが未充足を払うものに含めること自体を矛盾と判定した部分も訂正する。
未達を満たしたことにしないという区別は維持するが、これは未達を含む案を利用者が選べないという意味ではない。

一つのhowの比較の中で、条件を全て満たすことに月30万円が必要な案と、小さい範囲でも改善を届ける部分案と、保留を並べられる。
部分案の費用と価値が見合い、残る痛みと負担も含めて利用者が選ぶなら、その合意を選定として扱う。
月30万円・4%は利用者の比較例であり、この模型の費用や効果の事実ではない。部分案の費用が示されていない現時点で、その具体案の採否を代わりに決めたことにもしていない。

#### 比較した場面と、選定ができる範囲

| 場面 | 改稿案での判断と残る確認 |
| --- | --- |
| 完全に満たすと月30万円で、利用者は払えない | 満たす案だけへ閉じず、部分案と作らない／保留を比べる。完全案を選べないことだけで議論を止めない |
| v0.0.1で小さくても痛みが軽くなる | どの体験がどこまで良くなり、何が残るかを示す。小さい割合だけを理由に落とさず、費用と損失も踏まえて選べる |
| 条件や機能の4%ができるが、その部分だけでは使えない | その範囲の前後を通して価値へ届くかを調べる。条件の個数から4%の改善を実現したとはしない |
| 家族の一部の失効は減るが、全件の管理の役割は残る部分案 | 失効の減少という得るものと、残る管理負担・関わり・余白への影響を並べる。後者を隠さず、それでも選ぶかを利用者が決める |
| 夫の長い照合が残るが、それを認識して他の改善のために選ぶ | Gに未達があることと誰に負担が残るかを記録し、合意した部分案として選べる。元の余白まで実現したと書かない |
| 改善効果や費用はまだ仮説だが、試して学ぶ価値を選ぶ | 不確かさと何を試して確かめるかを示す。学びや作る楽しみの理由と、確認済みの痛みの改善を区別する |
| 未確認の提出の規則を「受け入れる未達」として閉じる | 未確認の事実と既知の損失は別である。選んだ改善の成立を左右するなら、その不確かさと確認・分岐を残す |
| 部分案の達成範囲と損失が一つの採用で既に合意できた | 同じ合意で正本と層の記録を揃える。部分案であることだけを理由にwhy・whatの全体を一律に再議論しない |

ここでの家族の部分案も、方法を比較する場面であり、実在の家族の採否や効果の観測ではない。
全体の目標と条件を先に持つことは、部分案を排除するためでなく、どの改善を得て何を失うかを読めるようにするために残す。
新しい価値や優先が未決なら、その残る問いをwhy・whatのownerへ返す。合意済みの達成範囲の記録を揃えるだけなら、別の採否を水増ししない。

#### 四fileを同時に揃える理由

howは、足りない点の選び方・費用表・選定と閉じに、部分案の改善と損失の合意を置く。
「満たさない条件」の費用の行は削らず、どの価値が得られず、誰にどの痛み・負担が残るかまで読める行へ深める。
元の八つの軸を数のために保ったのではなく、未達による価値の損失は他の時間やお金の費用では置き換えられず、この比較に要るため残した。

whatには、全体の変化に届く条件と、howで選んだ部分の達成範囲を分ける説明と参照を足す。
READMEには、比較基準を先に閉じる順序を保ちつつ、部分案の同じ合意で記録を揃えられることを足す。
howだけを変えて、whatとREADMEの「先に閉じる」を部分案の排除や全再議論へ読む余地を残さないためである。
正本の雛形には、部分案の時だけ今回の達成範囲・未達・損失・合意理由を置く欄を加え、冒頭の概要にも今回の改善と残る痛みを含める。
そうしないと、後工程が全体の目標を今回全て届けると読み、部分案をまた完全案へ膨らませてしまう。
四fileは、この一つの部分案の選定と受け渡しを成立させる変更集合であり、別の一般原則を四つ採用する提案にはしない。

#### 保ったものと、文書の検査

whyの体験と価値、全体の目標を比較の物差しとして持つ役割、whatの条件を正確に判定する役割、howの費用と損失を利用者が重み付ける役割を保った。
痛みの改善とは別の作る楽しみ・学びを理由として選ぶ道も保ち、部分案で前提条件の変更まで自動的に許可したと扱わない。
全体を実現したとは書かず、選んだ版に必要な条件と未確認の扱いが決まれば、全体の未達だけでその部分版の決着を未完にし続けない。
候補群の列挙からやり直すのではなく、利用者の訂正に依る修正を現物のbeforeから作り、前回の未適用draftの制限は一切引き継いでいない。

四fileの一時patchは現状へ適用可能である。現物はbeforeのままで、共有pluginや模型の条件・家族の採否は変更していない。
document-reviewでは、読者が完全・部分・保留の比較と、今回の達成範囲・受け入れた損失・不確かさを区別して後工程へ渡せるかを見た。
新規の分数や効果を作って部分案を勝たせず、4%を条件数へ換算せず、利用者が実際の価値と損失を選ぶ余地を残した。
この具体の四fileの改稿を提案1へ出す。今回の方法の採用と、模型の家族が実際にどの部分案を選ぶかの採否は混ぜない。

<a id="iteration-1-record-2"></a>

### 検証: 採用した四fileを反映し、部分案の比較と受け渡しが同じ意味で動くか

#### claim・合格条件・方法

利用者は66の提案1を採用した。現物をv1のbeforeへ照合し、四fileのafterだけを反映する。
afterとの完全一致、費用表の未達と失う価値の行、部分案の選定・合意・記録・後工程への達成範囲が四fileで対応しているかを確認する。
参照とanchor、空白不整合、提案0の排除が混入していないことも検査する。
