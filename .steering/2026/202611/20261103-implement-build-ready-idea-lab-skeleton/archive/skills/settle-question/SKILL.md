# settle-question

`what-defines-a-product/`の問い一つに、このアイデアについての決着をつける。

問いは、どのアイデアにも当てる一般の問いである。一般の問いのまま答えると、答えも一般的になり、このアイデアに特有の浅さを捕まえられない。そのため、答える前に、一般の問いをこのアイデアの問いへ立て直し、どこまで詰めるかを決める。

## 持つもの

- 一般の問いを、このアイデアの問いへ立て直すこと
- 詰める深さを決めること
- 材料skillを起動し、必要な材料を揃えること
- 定石の対案と自分の案を並べて選び、答えを書くこと
- 立て直した基準で、書いた後の漏れを確認し、「閉じた」と記録すること
- 問いの決着の記録を書き、答えを正本の反映先の節へ書くこと
- 判断が生じた時に、層の決定過程へ論点を立てること

## 持たないもの

- 次の問いの選択、出口判定（`grow-product-idea`が行う）
- 材料を作ること（材料skillが行う）
- 層ごとの中身。問い、必要な材料、水準、定石は`what-defines-a-product/`の層fileが持つ。このskillは層ごとの分岐を持たない

## 受け取るもの

- `product-plans/<slug>/`の場所
- 決着をつける問いのidentifier
- `grow-product-idea`から戻された時は、足りなかったもの

正本、層の問いの一覧、問いの決着の記録、層の決定過程、材料の入口の場所と、三つの記録の分け方は`product-plans/README.md`で引く。


## 品質は答えを作る段階で担保する

立て直した問いの基準は、答えを作る時の目標であり、書いた後に漏れを確認する基準でもある。
基準を満たす答えを作ろうとして材料を集め、対案を並べ、答えを書く。書いた後の確認は、それでも漏れたものを拾うためにある。確認で直せばよいという前提で、答えを緩く作らない。

## 手順

```text
0. 問いの決着の記録を作る
1. 立て直す
2. 材料を揃える
3. 対案を並べて選ぶ        ← 1〜3の中で判断が生じたら、層の決定過程へ論点を立てる
4. 正本と問いの決着の記録に書く
5. 立て直した基準で漏れを確認する
   ├─ 局所的な漏れ → 直して5をやり直す
   ├─ 骨子の漏れ → 2か3へ戻る
   └─ 漏れなし → 6
6. 「閉じた」と記録して戻る
```

### 0. 問いの決着の記録を作る

[templates/question.md](templates/question.md)から、この問いの決着の記録を、`product-plans/README.md`が定める場所に作る。この問いの層の問いの一覧で、この問いの列を決着の記録へのlinkにし、状態を「回答済み（確認待ち）」にする。

問いの決着の記録は、理由・因果・条件を段落で、規則的に並ぶものを表で書く。一行の箇条書きに丸めない。問いは流れ作業で解くものではなく、一つ一つが、立て直し、深さの判断、下位の問い、確認を持つ仕事である。

### 1. 立て直す

identifierから層file（`what-defines-a-product/`の、identifierの`/`より前の名前のfile）を引き、問いの文面、系統、必要な材料、水準、定石を読む。正本から、受け入れ時の入力、前提にする条件、既に書かれた節を読む。

そのうえで、次の三つを決める。

- 問いを、このアイデアの言葉で言い直す。例: `what-to-build/requirements`「何を満たせば、痛みが解けたと言えるか」を、サブスクの更新日を忘れるアイデアでは「更新日が近いことに、何をすれば気づけ、払い続けを止められたと言えるか」と言い直す。
- 水準の満たさない例に、このアイデアで起きやすい浅い答えの例を足す。層fileの一般の例は外さない。例: 「更新日の前に通知が来ること」。更新日がメールや明細に散らばっていて、集めること自体が痛みの核心かもしれない点を見ていない。
- 詰める深さを決める。この問いの答えが変わった時に、出口や下位の問いがどれだけ変わるかと、今ある材料での確信度を見る。
  - 影響が大きく、確信度が低い: 材料をより細かい粒度で求め、必要ならこのアイデア固有の下位の問いを立てて詰める。
  - それ以外: 水準を満たしたところで止める。

三つの結果と理由を、問いの決着の記録の「一般の問いを、このアイデアの問いへ立て直す」「水準」「どこまで詰めるか」に書く。立てた下位の問いは「立てた下位の問い」に、問うた相手と答えとともに書く。

前提にする条件があれば、問いの言い直しと足す満たさない例に反映する。例: 「外部のサービスには預けたくない」なら、代案の問いに「預ける前提のサービスを、条件と照らさずに代案として数える」を満たさない例として足す。

深さを一律に最大にしない。毎回の紆余曲折を減らすというレールの目的に反する。深さを一律に止めもしない。影響の大きい問いが浅いと、上に積み上がる答えが崩れる。

一般の問いがこのアイデアに合わない時（答える意味が無い、別の問いが要る）は、その旨と理由を立て直しに書く。問いを飛ばすかは、`grow-product-idea`へ返して判断させる。この記録は、還元で問いのセットを見直す根拠になる。

### 2. 材料を揃える

問いが挙げる必要な材料ごとに、材料の入口を確かめる。

- 入口が無い、または立て直しで決めた粒度に足りない時は、その材料の材料skillを起動する。
- 材料skillが、利用者しか持たない事実を問いたいと返した時は、認識合わせの論点として利用者に問い、答えを材料skillへ渡して続けさせる。
- 入口がある時も、`what-defines-a-product/README.md`の「材料の水準」と材料skillの材料ごとの水準に照らして漏れを確かめる。漏れがあれば、何が足りないかを付けて材料skillへ戻す。材料の薄さを、答えの側の推論で補わない。渡すものは`what-defines-a-product/README.md`の「材料」節にある。材料skillの対応は、同じ節の材料の識別子の表で引く。
- 材料が別の層のもの（例: 何を作るか層の問いが、どう作るか層の材料であるラフ画を要する）でも、このskillが直接起動する。下位層の問いを先に答えるのではない。
- 材料skillが「確かめていない（確かめること自体が規約・安全に触れる）」と返した時は、確かめられなかった不確実性を`what-to-build/risks-of-building`の該当する観点（法務・規約、実現性）の材料にする。そのうえで、どう扱うかを利用者の採否が要る論点として立てる。選択肢は、確かめずにリスクとして扱う（避ける・待つ）、確かめる行為が要らない解き方に変える、利用者が自分の判断と手で確かめる、の三つ。利用者が自分で確かめた時は、結果を受け取って材料に書く。
- 他の問いの答えを材料にする時は、その問いが閉じていることを、その層の問いの一覧で確かめる。閉じていなければ、`grow-product-idea`へその旨を返す。

材料は、問いが挙げる順に揃える。層fileが並び順の理由を添えている時は、それに従う。

### 3. 対案を並べて選ぶ

問いの定石から選択肢と判断軸を読み、自分の思いつきと並べる。

- 調査系の問いでは、材料から答えを導き、定石の判断軸で結論を確かめる。
- 生成系の問いでは、材料にある複数案を、定石の判断軸に照らして比べ、一つを選ぶ。
- 前提にする条件に反する選択肢は、どの条件に反するかを書いて外す。外した選択肢も決定過程に残す。条件が変われば候補に戻るためである。

選んだ答えが作らない・保留を示す時（`what-defines-a-product/README.md`の「作らない・保留へ向かう答え」）は、`why-to-build/gains-from-building`の答えと照らし、比較で負けた理由が得たいものに関係するかを答えに書く。照らして続ける時は、続けることを利用者の採否が要る論点として立てる。照らした後も作らない・保留を示すなら、4〜6を終えて問いを閉じ、その旨と理由を付けて`grow-product-idea`へ返す。

利用者へ問うのは、着想・作りたい動機・体験の質感が無いと答えられない時と、利用者しか持たない事実（自分の状況、量、試した経験等）が要る時だけである。それ以外は利用者へ問わず、材料と定石で詰める。

### 判断が生じたら、層の決定過程へ論点を立てる

1〜3の中で、次のどちらかが生じた時に、その判断ごとに論点を立てる。一つの問いから複数立つことも、一つも立たないこともある。問いごとに機械的に立てない。

- 利用者の採否が要る判断（例: 痛みの核心をどれに置くか、受け入れ時の着想を前提にするか、どの案を選ぶか）
- 発案者の視野を広げる点（立て直しで見つけたこと、定石や材料から出てきた、発案者の着想や前提の外の対案・事実）
- 利用者しか持たない事実を問う時は、認識合わせとして論点を立てる

決定過程は、このプロダクトの判断の芯であり、後続のプロダクトへ積み上がる。目的は、細部まで合意すること、さらに、発案者が気づかなかったところまで視野を広げることである（`product-plans/README.md`の「決定過程の役割」）。速く済ませる手間として扱わない。

`tumeda-dev`の`facilitate-discussion`を、この問いの層の決定過程（`product-plans/README.md`が定める場所）を指す`discussion_directory`と`discussion_file_name`を渡して、全手順で使う。

- 論点の題は判断の内容にし、問いの文面にしない
- 検討記録の最初の行に、起点の問い（この問いの決着の記録）へのlinkを書く
- 提案には、合意できるだけの細部と、発案者の視野の外にあった点を、それと分かるように書く。一往復で決まりそうな論点でも省かない
- 論点は起きた順に並ぶ。固定の並びに流し込まない

論点の決定は、層の閉じで利用者が応答した時に行う（`grow-product-idea`の5）。認識合わせは、答えを得るまで先へ進めない。

### 4. 正本と問いの決着の記録に書く

正本の、この問いが決める節を書く・書き足す。どの節かは、正本の各節に残してあるコメント「この節を決める問い」で引く。複数の問いが一つの節を決める時は、既に書かれた内容と一つの筋になるように書き足す。

- 決まった内容を言い切りで書き、表にできるものは表にする
- 節の最後に「根拠」として、その節を決めた論点と材料へlinkする。論点が立たなかった時は「材料から導いた（論点は立っていない）」と書く
- 問いの文面、立て直し、確認結果は正本に書かない

問いの決着の記録には、「答えに至った筋」（どの材料と判断から答えになったか、採らなかった見方、発案者の着想や前提から見方が変わった点）を書き、答えの全文は正本の節へlinkする。「この問いで広がった視野」を書き、層の問いの一覧の「この層で広がった視野」の表へ起きた順で足す。

層の問いの一覧で、この問いの詰める深さと反映先を書く。

`product-plans/README.md`の「directoryの中だけで読み切れるようにする」に従って書く。

### 5. 立て直した基準で漏れを確認する

正本を後で読む人（層の閉じや出口判定で読む利用者、build-ready後に受け取る後続の`steering`／`task-design`）の立場で、正本に書かれた節と材料だけを見て、問いの決着の記録に書いた立て直しの基準（一般の満たさない例と、足した例）に照らして確かめる。
答えを考えた時の推論で補わない。書かれていないことは、無いものとして扱う。

| 漏れ | 戻り先 |
| --- | --- |
| 言い回し、linkの欠け等の局所的な漏れ | その場で直し、5をやり直す |
| 材料が足りない、対案を比べていない、答えが材料から導かれていない、立てた下位の問いに答えていない等、答えの骨子の漏れ | 2か3へ戻って作り直す。一文を足して満たしたことにしない |

### 6. 「閉じた」と記録して戻る

問いの決着の記録の「確認」に、基準ごとに満たしたかとどこで満たしたか、局所的に直した箇所を書く。層の問いの一覧で状態を「閉じた」にして、`grow-product-idea`へ戻る。

## 基準を下げない

立て直す側と答える側が同じため、答えやすいように基準を下げる恐れがある。次を守る。

- 層fileの一般の満たさない例は外さず、このアイデアの例を足すだけにする
- 立て直した問いと基準を問いの決着の記録に書く。層の閉じで利用者が見る
- 確認は、頭の中の基準ではなく、問いの決着の記録に書いた基準で行う
