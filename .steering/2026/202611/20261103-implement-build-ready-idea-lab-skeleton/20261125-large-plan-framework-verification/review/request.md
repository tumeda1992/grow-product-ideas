# 大きな企画を運べる仕組みを、実行結果からゼロベースでレビューする

## 元の依頼と今回のテーマ

同じ作業のapplication.mdに、都度の確認なしで残改善を適用し、少し大きい企画でドライラン・レビューする利用者の原文がある。挙動維持には限定しない。本線が、長い依頼と豊かな未来像から、価値の発散・収束、アウトカムと条件、異なる解き方と部分版の比較、具体の体験・業務・規則・情報・処理・構成・導入運用を繋ぎ、作り始める前の決定を実質として詰められるかを確認する。

このレビューの対象は本線の仕組み。新しい架空案件と通常実行の記録は、その仕組みがどう動いたかの証拠である。架空案件を手で修理して終えるレビューではない。

## 対象と取得元

repositoryは /workspace/grow-product-ideas、現行のREADME.md、product-plans/README.md、what-defines-a-product全層、.agents/skillsの入口と専門・雛形・検査を主対象とする。framework-sha256.jsonで本文を固定する。

同じ作業directoryのrequest.md、future-vision.md、synthetic-user-role.md、fixtures/、runner-results/と、新しいproduct-plans/20261125-repair-workshopがドライラン入力・成果。成果はrunner終了後に親が固定する。実在の利用者の採否・運用とは区別する。

使用するレビューはtumeda-dev10.0.1のexhaustive-review、gpt-6.2-astra・xhigh。SKILL.md、review-findings.md、finding.md、model-profiles.mdを実際の同じ配布元から読み、指摘集合を直しても残る重要な反例を再探索する。最初の走査では旧レビューの結論へ依存せず、必要ならその後に対応を照合する。

## 指摘の出口

具体的な架空例の破綻は一次の証拠として使う。確定指摘の改善案は次まで辿る。

- 本線のどの入力・判断・受領・引渡しの責任が足りず、その症状を通したか。実行担当が既存の明瞭な指示を外した場合と、指示自体の不足・曖昧さを区別する。
- 実際に変える本線のpathと箇所、変更後に何を受けてどう判断し何を返すか。架空の担当名・ID・時刻を置換するだけの案にしない。
- 元の症状を拾う例、別の領域でも同じ原因が効く例、既に成立する例又は合意したトレードオフを不必要に止めない対照。未実施を実測と呼ばない。
- 既存の同じ規則を重ねるだけで解消するのか、別の材料との接続又は実行経路を変える必要があるのか。本人の価値・未取得の同意・外部の事実を代作しない。

指摘そのものを見直し、全件の意図した修正がテーマの重要な不足を覆うか確かめる。細かい表記の指摘を増やして重要な不足を逃さず、主要な反例が残るなら探索へ戻る。確認できない重要な境界は、テーマ全体の成功へ読み替えず具体的な未確認として残す。

## レビュースキルへの評価

新しい重要な不足が出たら、前のレビューの対象・材料・改善案と、今回の実行のどちらから知り得たかを照合する。事前に構成できた反例か、新しい入力・実行で初めて得た事実かを分ける。レビュースキルが不足したのか、テーマ・対象範囲の渡し方や実行・返却が外れたのかを具体的に示す。すべてをレビュースキルの新規則にせず、改善が必要なownerへ戻す。

この段階ではレビュー担当は本線・案件を編集せず、README/coverage/findingsへ結果を保存する。適用は親担当が利用者の全件委任の範囲で行う。
