# 本線の残改善を適用し、新しい大きめの企画で確認する

## 依頼原文と適用範囲

> ok。というか、今もう、ドライラン結果が機能するものって確認するフェーズだから、つどの確認はいらないよ。少し大きい企画でちゃんと回るようになってて、ついでにそのレビュースキルも育ててるってところだから（それにしてはドライランを数回回してるんだから、架空事例べったりの改善案をレビューに書くのやめてほしいけど。指摘の一次情報として架空例の穴から話を進めるのは良いけど、出口も架空例ではいけない）全適用してドライラン回してレビューして。

論点4・提案1の採用と、この確認フェーズの残改善を都度確認なしで適用する委任として受け取った。今回の有効なDRR六件から導いた本線の改善が対象。撤回済み004・005・008、旧13件の再適用、既存の架空案件の採用し直しは含めない。

## 適用と確認の順序

1. 適用済みの受領判断（001・002・003・007）と比較便益（006）の本文・patch・局所確認を照合して保存する。
2. 009から導いた共有資源の時間競合の判断方法をhow-to-solveへ適用し、局所の受領・返却を確認する。原案件は保存した基準版のまま保つ。
3. 三つの本線変更を原因別のcommitで保存しpushする。適用の合意・検証範囲を各変更へ結ぶ。
4. 別の題材、長い原依頼と大きな未来像から、新規案件を通常のgrow-product-ideaと専門スキルで設計の出口まで運ぶ。合成利用者の採否は設定と区別し、外部の同意・実運用を捏造しない。
5. 新しい実行結果を根拠にAstraで本線全体をレビューする。各指摘の出口は、本線の原因・変更先・変更後の判断・別の例でも働く検証方法とする。架空案件の修理案だけを最終的な改善案にしない。

## 返却の判断

本線のどの判断が実際に働き、どこが未確認・不足かを返す。指摘集合を直しても依頼テーマの重要な不足が残らないかをAstraが再検討し、親も結論と根拠の範囲を照合する。新しい重要な不足があれば、既存の委任内で本線へ反映し確認を続ける。費用・価値等の本物の利用者しか決められない事情は、合成設定で勝手に本物の決定を作らない。

共有レビュー手順へ不足が見つかった場合も、症状だけで一般則を足さず、今回のテーマ指定・scope・実際の取得元と実行、指摘集合の再検討・返却のどこに原因があるかを照合する。
