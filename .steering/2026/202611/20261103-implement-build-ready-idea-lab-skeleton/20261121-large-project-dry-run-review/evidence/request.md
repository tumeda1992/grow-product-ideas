# 実際に大きな企画を通した結果のレビュー

## 利用者の原文

> OK。13件も見たけど全部適用していい。したら、コミットプッシュして。そして、大きめの企画でドライランして。レビュースキル回して、指摘点を出して、その指摘が致命的だったら、なぜ前のレビューで洗い出せなかったか内省して

## 対象とテーマ

13件を適用して52476f5までpushした後、新しい1,320字の資料室企画を、旧指摘・正解案を渡さない別文脈の実行担当が、実際のgrow-product-ideaと必要な専門スキル・facilitate-discussion・document-reviewで処理する。
初期入力から価値を育て、解き方と提供範囲を選び、画面・業務・状態・運用・実装先と受入れが繋がった設計を渡せるかを確かめる。
出力の存在・字数・全条件の見かけの充足や、一件の技術検査の成功だけで合格にしない。既知の指摘への答えがあるかに限定せず、利用者が得る結果と実際の判断からゼロベースでレビューする。
実行担当の合成の利用者役との採否、入力・判断の由来、専門への依頼と実際の受領・反映・変更の照合、未確認と実測の区別も対象。
挙動維持だけに限定しない。良い別解を落とす規則、薄い案を通す工程、その場の専門性で書いてある以上の仕事を補っている場合も、現物で裏付けて指摘する。

## 完了する前の問い

各探索後にexhaustive-review 9.1.1のreview-findingsで、指摘の妥当性・責務と、その集合を解消した後に残る重要な不足を検討する。
重要な不足を調べられる限り同じ依頼内で調べる。固定周回数、新規ID0、些末な追加指摘だけで止めない。
依頼の外へ勝手に加えた保証は落とすが、元のテーマを確認例だけに狭めて終えない。
本番の利用価値を実証したことや、実装・公開したことは求めない。実装に渡す核心が未定又は不成立なのにbuild-readyとする、価値を失った薄い版を成功とする、既存業務を破壊するなどは本テーマの致命的な不足として判別する。
未知の事実を要すること自体は欠陥ではない。必要な不足と進められる範囲を誠実に区別できるかを見る。

## 致命的な指摘が出た時の内省

以前の固定対象・依頼・探索と反例・指摘の改善責務・停止判断、実際の13件の差分、ドライランの分岐と得られた事実を突き合わせる。
旧版に存在し同じテーマで見落とした問題、指摘済みだが修正が不十分な問題、適用で初めて導入した問題、新しい入力・契約で初めて生じた問題を区別する。
どの前提・判定・受け手を固定したため何を比較せず終えたかを特定し、単に注意不足・もっとレビューする・モデル名だけを理由にしない。
レビュー方法の規則不足と実行・監督の不足を切り分ける。改善が要るなら同じ見落とし型を別例でも検知できる具体の方法を提案する。

結果を固定したREADME・coverage・個票・必要な再現・内省として保存する。今回の新しい指摘はまだ適用許可を得たことにはしない。
