# レール改訂の再確認

## 判定

**R2〜R6は規則として解消。R1は概ね解消したが対象範囲に小さく重要な残りがある。R7は目的を満たす一方、文言どおりだと再確認を過剰実行し得る。加えて、今回同時に追加された「各有力解釈の外部調査」は無用な先回りを生む可能性がある。**

既存実装へ統合する案件について、認証・所有権・保存形式・整合性・体験を変える未知を止める現行判断は妥当である。物理スキーマや認証を何でも実装者裁量にすべきとは判定しない。

これは現行差分と正本を具体例へ適用した机上確認であり、過去の実行評価は読んでいない。粗い入力による育成実行や次担当の実受取は行っていないため、文書改訂だけを成功の証明にはしない。

## 追加すべき真の差

### F1. 保存前最小化が「資格情報・個人識別値」以外の秘密を落とし得る

- 重要度: **高**
- 根拠: `AGENTS.md` は「秘密情報、個人情報」を対象にするが、工程1とproposalテンプレートの具体命令は「資格情報」「個人識別値」に狭い。具体命令を優先する担当は、識別子を除けば安全化完了と読める。
- 反例: 「社外秘の未発表買収条件を比較する承認支援」を、氏名とAPIキーを除いて入力する。金額・相手企業・契約条件そのものが秘密だが、資格情報でも個人識別値でもないため、安全化した原文としてGitへ残り得る。
- 推奨: 新しい分類一覧は増やさず、工程1の主語をAGENTS.mdと同じ「資格情報を含む秘密情報と個人情報」に合わせる。要求判断に実値が不要な秘密は範囲・属性・仮値へ置換し、実値が必要なら保存せず、ユーザー管理の参照元と必要条件だけを残す。

### F2. 「次に判断へ使う時点」が、変化可能性の低い外部証拠まで工程ごとに再取得させ得る

- 重要度: **中**
- 根拠: `templates/idea/evidence.md` の再確認条件は「次に判断へ使う時点、対象プラン変更等」を例示する。前者を常時トリガーと読むと、比較、設計、最終レビューのたびに同じ公式資料を開くことになる。
- 反例: 公開済みファイル形式の固定仕様を工程2で確認し、翌日に同じ内容を設計とレビューで使う。版も対象も変わっていないのに、各工程で再取得するのは判断を変えず、外部アクセス不能なら無用に停止する。
- 推奨: 再確認条件は「次回利用時」ではなく、証拠ごとの変化イベントまたは妥当な経過条件に限定する。対象版・プラン・地域・利用量・確認後の更新告知・実装開始までの経過などを使い、トリガー非該当なら前回証拠を再利用する。価格のように変わりやすい証拠だけ「最終判断時に再確認」を選べるようにする。

### F3. 本人の一回答で解釈が絞れる前に、各解釈の製品調査を深掘りさせ得る

- 重要度: **中〜高**
- 根拠: `methods.md` と `grow-idea` は、上流が未決でも「各有力解釈で現実に使える手段と適用条件」「有力な代案の公開調査は独立して終える」と要求する。一方、同じmethods.mdは「問題の選択が一つの実例で決まるなら、先にそれを聞く」とする。スクリーニングと正式比較の深さが分かれていない。
- 反例: 「家の食事を楽にしたい」で、献立決定・買物回数・家族予定・調理時間の四解釈がある。本人へ「直近で一番困った一場面」を聞けば一つに絞れるのに、四領域すべてで製品名、地域、端末、プラン、公式条件まで調べ切ると、三領域分が捨て作業になる。
- 推奨: 上位回答前に行うのは、各解釈に実用的な手段が存在するかと、回答による逆転条件を示す軽いスクリーニングまでにする。公式機能・料金・導入負担までの詳細比較は、本人回答なしでも順位が変わらない場合、回答待ち時間に再利用価値がある場合、または選択後の解釈へ限定する。「外部調査をしない」と「全候補を選定可能な深さまで調べる」の二択にしない。

## 新ルールの短い適用

### 反例A: 対象環境でしか読めない独自CADファイル

- 次担当へ渡す: **意思決定用の検証のみ**。匿名化した入力標本、対象OS・ライブラリ版、寸法取得の合否、最大時間、結果保存先、成功時は設計工程へ／失敗時は別ライブラリ比較へ戻る分岐、停止条件。
- 止める: 製品全体のbuild-ready判定と、対象環境での実行権限取得。これはR2の解消を正しく使う例。

### 反例B: 実装先未指定の既存ECへの返品分析追加

- 次担当へ渡す: 返品理由の用語、必要な注文・返品入力、集計出力、データ関係・不変条件、権限エラーの意味、受入例、実装先で最初に照合する契約と不一致時の判断ID。
- 止める: 既存認証が返品データの閲覧主体を表せるか、既存スキーマで履歴・保持責務を満たせるか。これらが不明なら重要な構造未知として確認待ち。物理スキーマや認証を無条件に裁量へ落とさない。

### 反例C: フォームからCRMへ登録するSaaS連携

- 次担当へ渡す: **既製品導入**。確認済み機能・対象プラン、管理者が行う設定、接続試験の入力と期待結果、本番移行、失敗時の切戻し、必要権限。
- 止める: 管理権限や契約プランが必須機能を満たすか不明で、案が覆る場合のみ。接続試験と本番移行が未実施という理由だけでは導入準備完了を止めず、導入済みとも呼ばない。

### 反例D: 匿名投稿をAI要約して公開するサービス

- 次担当へ渡す: 連投・個人情報混入・削除要求を含む受付状態、保留／非公開、従量費上限での遮断、手動停止・回復、公開経路を通した設計と検証結果。
- 止める: 費用遮断や非公開化の責務が決まらず、許容費用・公開契約が変わる状態。閉じた社内入力へ同じ公衆向け管理を強制しない。

### 反例E: 社外秘の買収条件を含む承認支援

- 次担当へ渡す: 実値を除いた項目種別、承認規則、必要な比較結果、実データ参照に必要な権限条件。
- 止める: 現行の具体命令だけでは、資格情報・個人識別値ではない秘密条件を保存前に除ける保証が弱い。F1の修正までは原文の実値を成果物へ保存しない。

## 最終推奨

R2〜R6を再修正する必要はない。R3について重要な構造未知を止める現行線を維持する。追加変更はF1〜F3に限定し、特にF1を優先する。F2・F3は、再確認と調査を「判断が変わり得る最小範囲」に戻す文言調整で足り、状態や文書を増やす必要はない。
