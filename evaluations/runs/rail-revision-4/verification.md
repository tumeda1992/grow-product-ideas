# 大きな手戻りを先に見つける

工程2で有力案が見えた時点と、工程4で今回の到達点が決まった時点に読む。目的は、案を変える可能性の高い問いへ検証を集中すること。全製品に同じ検査を課すことでも、失敗をゼロと保証することでもない。

## 何を確かめるか選ぶ

まず原文・問題の解釈・到達点から、利用者、利用の開始と終了、扱う情報、他者・外部システムとの関係を拾う。下表をその特徴に当て、適用するリスクと、主要な不適用理由を proposal.md の「重点リスク」に記す。機能一覧にないという理由だけで、必要な権限や訂正を不適用にしない。

表にないものでも、外れたときに価値、体験、保存形式、責務・契約、実現可否、費用の許容を変えるなら追加する。似た問いは統合できる。表の全行を独立文書にせず、一つのシナリオで複数のリスクを確かめてよい。

| 案件の特徴 | 見落とすと変わること | 最初に当てる具体例と確認方法 |
| --- | --- | --- |
| 粗い動機・複数の目的・他人への提供 | 解く問題、利用者、乗り換える理由 | 主場面と別解釈を比べる。誰のどの負担を減らし何を増やすか、原文・公開情報・仮説を分ける |
| 繰返し入力・判断・初期設定が価値を左右する | 導入できない、記録が続かない、画面の組み替え | 代表データで初回と普段の一回を通す。必要情報の入手元、操作、訂正、離脱を示し、現状と比べる |
| 共有・複数の役割・他人の情報を持つ | 認証、所有権、データ分割、同時更新 | 別の利用者からの閲覧・更新、招待・脱退、同時編集を具体化。状態と権限の表で結果を確定し、複雑な競合は小さく実行して確かめる |
| データを蓄積・訂正・削除・移行する | 識別子、履歴、復旧、重複、保持方針 | 同一物と同名別物、誤入力、部分失敗、再取込を通す。保存形式と失敗時の前後を決め、互換性や原子性が未知なら実行検証する |
| 外部連携・課金・通知・非同期処理 | 実現可否、状態管理、二重実行、費用 | 認証失効、遅延、失敗後の再実行、取消を適用判定する。公式契約を確認し、未知の成立条件は許可された検証で確かめる |
| 不特定者の入力・利用者生成物の公開・入力に応じた従量費 | 受付制限、公開状態、保持・削除、費用遮断 | 連投、不適切な入力、個人情報の混入、削除要求を通す。保留・非公開、費用上限での受付停止、手動回復の責務を決める。閉じた個人用途に公衆向けの管理機構を追加しない |
| 生成・推薦・最適化など出力の質が価値の中心 | 心臓部ロジック、期待品質、代替手段 | 代表・境界・失敗入力を先に用意し、期待する性質と許せない出力を定めて試す。正解を自分で都合よく選ばず、単純な規則や手動の結果と比べる |
| 実装環境・端末・性能・機密性などに強い制約、他者への配布 | 構成全体、運用、配布、費用上限 | 対象環境と規模を特定し、制約を満たす経路を確認。他者配布なら配布主体・経路・審査や契約等の外部条件・更新と戻し方を通す。未指定なら移送可能な判断と環境依存の判断を分ける |

適用が不明な特徴には、その有無で変わる設計と確認方法を置く。上位の回答が要る間も、共通部分の試作や調査は進める。将来ありうるだけの共有や課金を、今回の設計へ勝手に追加しない。

## どう確かめれば足りるか

問いの性質に合わせて方法を選び、選んだ理由を記す。

- **既知の条件から論理的に決まる**：具体値・状態・例外を表や手計算で追う。例は設計の説明用だけでなく、その設計が破れる入力から選ぶ。
- **外部の仕様で決まる**：対象プラン・版・環境を合わせて公式資料を確認する。未記載の挙動や複数製品の接続を、単一製品の資料だけで成立としない。
- **操作や実行をしないと分からない**：手作業再現、最小モック、技術検証、代表入力でのロジック試行を行う。今回の検討用の成果物として保存し、本番実装とは区別する。
- **本人の価値判断や現実の利用で決まる**：判断できる具体案・比較を完成させ、本人の確認または運用後の観測へ分ける。エージェントの想像を実ユーザーの検証にしない。

単純な CRUD に全環境の試作を課す必要はない。既知の構成で要件を満たす根拠があれば、状態表と具体例で構造を確定できる。逆に生成品質、未知 API の接続、複雑な同時更新のように実測が選択を左右する問いは、文章だけでは通過できない。

## 結果を残して判断へ戻す

リスクは K1 等、確認は V1 等で識別する。proposal.md にリスクと依存、evidence.md に検証の結果を置く。モックやスクリプトなどが必要な場合だけアイデア配下に `validation/` を作る。

各確認は、対象のリスク・仕様版、事前に決めた合格条件、入力と環境、実施方法、実際の結果、結果の限界、設計へ反映した箇所を持つ。未実施・合格・不合格・条件付きのいずれかを明示する。文書の項目を埋めたことや、期待値を書いたことを実行結果にしない。

不合格なら、要求の解釈、解決手段、今回の到達点、構造のうちどこを変えるべきか判断する。下流のパッチで目的を薄めない。重要な不合格が未解決なら build-ready／導入準備完了にしない。

必要なツールや情報がなく実施できない場合は、入力・期待値・手順と独立した設計を完成させて確認待ちへ。影響が許容範囲内であると判断できるものだけを、観測者・見直す条件・対処を付けて運用へ残す。

## 最終版を受け取ってみる

handoff.md を作った後、会話の補足なしに今回の成果物だけを使い、最初の縦の一場面と高リスクの作業を実装するつもりで読む。受取確認では別の設計案を自由に作るのではなく、実装が進むかを確認する。

追加判断を「既に書いてある」「安く変えられる裁量」「重要な未決」に分類する。重要な未決は設計へ戻して解消する。全文へ細部を追加する前に、参照が欠けているだけかを確認する。引き継ぎまで含めた同じ版を最後に review-idea で判定し、レビュー後の仕様変更は関連する検証・受取確認を失効させる。
