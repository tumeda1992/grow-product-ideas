# 受取レビュー

## 対象と方法

- 対象：`shared-final/` の `README.md`、`proposal.md`、`evidence.md`、`decisions.md`、`design.md`、`handoff.md`、`validation/X1-record-template.md`、`review.md`、`versions.md`
- 対象版：`review.md` 記載の SHA-1 と実ファイルを照合し、8件すべて一致した。
- 方法：会話履歴を使わず、許可取得後に handoff の先頭作業と最重要作業 X1 を実施するつもりで、要求、制御、観測、判定、停止条件を追跡した。
- 未実行：checkout、登録、課金、Grocy/PikaPods、Playwright、認証、二browser、backup/restore、一週間利用。製品実装・外部変更も行っていない。

## 判定

現状の「確認待ち」と、未実施項目を成功扱いしない整理は妥当。許可後の価格・認証確認、X1-B、X1後の条件付き導入、停止・相談条件は、重要な追加判断なしに進められる。

ただし X1-A は、現在の手順と記録だけでは「競合更新を検証した」と判定できない。R2 と採用確定を左右する検証なので、この一点を直すまでは X1 実行着手可能とは判定しない。状態は引き続き「確認待ち」でよく、「導入準備完了」にはしない。

## 重要な判断を変える指摘

### RF1：X1-A は競合を制御・観測しておらず、直列実行でも合格する

- 対象：`design.md`「X1-A 競合」、`handoff.md` 手順5、`validation/X1-record-template.md`「X1-A 競合」
- 問題：A/B が同じ表示値2を見た後に「ほぼ同時確定」するだけで、二つの更新要求がサーバ側で重なったこと、または少なくとも一方の処理完了前に他方が送信済みだったことを制御も記録もしていない。現在の期待値 `最終2 + transaction各1件` は、Aの処理が完全に終わってからBを処理する通常の直列実行でも同じになる。
- 影響：競合時だけ起きる lost update や排他処理の欠陥があっても、試験が競合区間を作らなければ合格しうる。したがって、現在の X1-A 合格は K1 の「競合」を解消せず、R2を満たす根拠にも、Grocy採用を確定する出口条件にもならない。
- 必要な対応：二要求が競合区間へ入ったことを再現可能に制御し、その証拠を記録する手順へ置き換える。例えば、二つの mutation を browser 側で捕捉して両方の送信準備完了を barrier で確認してから同時に upstream へ流し、各requestの送信開始・upstream応答完了時刻とresponse、最終count、transactionを保存する。Grocy側の処理を重ねたことまで外部から保証できない場合は、反復回数と限界を事前に定め、「競合安全を保証」ではなく「この負荷条件で取りこぼしなし」と判定範囲を狭める。少なくとも人手の「ほぼ同時」を合格試行の成立条件にしない。

## 今回の範囲で修正できる不整合

なし。RF1以外は、文書間で手順、停止条件、未実施の扱いが整合している。

## 許容できる改善

- `handoff.md` 手順7は restore不能を相談条件に含めているが、手順本文にも「restore不合格なら一週間試用へ進まない」と一文置くと、実施者が相談条件を見落としにくい。現状でも `design.md` と相談条件から判断できるため、主要判断の欠落とはしない。

## 受取追跡の結果

- X1-B：`route.fetch()` の upstream 2xx 完了後に元pageへのresponseだけを abortし、有效試行と到達不明を分離している。overview と user/type/product別transactionを再取得するため、「到達済みの操作を再送せず回復できるか」という問いに答える。到達不明時の `(2,0)` を未反映確定にせず、当該productを変更しない停止規則も妥当。
- 非公開：初期品目投入前のpassword変更、再login、未login・誤・旧password確認まで手順化されている。実instance未確認として正しく残している。
- 費用：公式の開始価格と本人の上限を混同せず、checkout税込円を導入時gateにしている。
- backup/restore・一週間利用：未実施と明記され、X1合格後にのみ進める。失敗時の削除禁止・相談条件もある。
- 状態：公開調査や設計で自律的に進められる仕事は概ね終了し、外部操作を伴う確認を待っているため「確認待ち」は適切。ただし RF1 の修正は外部権限なしに可能なため、厳密にはその修正が終わるまで「自律作業なし」という README/review の記述は成立しない。

## 推奨状態

`確認待ち`を維持する。RF1を文書上で解消した後、許可取得後に X1 を実行する。X1-A/Bの両方が有効な試行として合格するまでは採用確定・実在庫投入・導入準備完了としない。
