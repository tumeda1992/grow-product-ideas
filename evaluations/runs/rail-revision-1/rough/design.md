# 今回の到達点の設計

対象：proposal.md の「到達点」。条件付き部分：U1〜U3、V2。

## 体験と画面・入出力

今回は既製品試用の運用設計であり、新規画面は作らない。

1. 初回に世帯人数、避ける食材、1食の調理上限、使いたい食材、日数を入力する。アレルギー・医療条件は目立つ別欄に置き、AIの保証ではない旨を表示する。
2. 普段は「今夜の候補」最大3件を確認し、所要時間・主材料・不足材料・制約警告を見て1件を採用または全却下する。
3. 採用すると不足材料を買物リストへ追加。利用者が在庫分を削除し、数量を直して確定する。自動購入しない。
4. 条件違反なら却下理由を選ぶ。候補なしなら条件を勝手に緩めず、「時間を延ばす／食材条件を外す／手動で選ぶ」を提示する。
5. 通信・生成失敗時は直前に確定した献立と買物メモを保持し、手動編集へ戻る。

試用記録の1行：`date, current_minutes, trial_minutes, completed, rejected_reason, manual_edits, unsafe_candidate, note`。個人名や健康詳細は記録せず、条件カテゴリのみ残す。

## データと生涯

- 正本：試用中の献立・買物は選定製品、評価記録は利用者管理のCSV。
- `date` はローカル日付で一意。再入力は同日行を更新し、旧値が必要なら別バックアップを取る。
- 7日終了後にCSVを集計し、継続しなければ製品側データを削除/エクスポート可能性を確認して離脱する。エクスポート仕様は製品選定後の確認事項。
- 共有はU1で必要と決まるまで設計対象外。自作へ進む場合も単一所有者を既定とし、共有を暗黙に追加しない。

## 心臓部ロジックとモジュール

条件付き自作へ進む場合の核は `条件 → 候補集合 → 禁止条件で除外 → 最大3件へ順位付け → 人が採用 → 買物差分`。

- 禁止条件は生成指示だけに頼らず候補提示前後に照合。不明食材は「確認要」で採用をブロックする。
- 時間や費用の推定値は根拠と幅を表示し、確定値に見せない。
- 候補0件は正常結果。条件の緩和は人が選ぶ。
- 同じ採用操作の再試行で買物品を二重追加しない（献立日＋候補IDを冪等キーとする）。
- AIが利用不能でも手動登録・編集・CSV評価は継続できる。

## 技術と運用

V2までは既製品＋ローカルCSVで、新規DB/APIは不要。失敗は画面表示とCSVの `note` で検知し、紙/標準メモへ復旧する。外部購入連携、通知、課金処理は非目標。自作時の技術構成は実装先・端末・データ方針が未指定なので確定しない。

## 実装者の裁量と許容する負債

CSVの保存アプリ、見た目、内部関数分割は裁量。禁止条件の扱い、データ所有、二重追加、失敗時保持は裁量にしない。7日試用では詳細な栄養最適化と在庫自動同期を負債として受け入れ、主問題が確認された後だけ再検討する。
