## 実行で見つけた問題への再改訂

初回の失敗から、既製品機能・手動操作・未確認の挙動を分け、公開仕様の確認を本人待ちから分離した。質問を今必要な上位の一問と採用後だけの情報に分け、試用の回数・合否・比較条件の根拠を要求した。

二回目では「本人の問題は公開調査では決まらない」から「外部調査をすべて後へ送ってよい」へ飛躍した。本人の問題選択と、各解釈を解ける現実の手段の調査を別の仕事にし、一般名の代案と試用計画だけで自律作業完了としないよう直した。仮の数値を承認待ちにするだけでは検証設計にならないことも明記した。

別途、[レール自身の静的レビュー](runs/rail-revision-2/rail-final-review.md) を実施した。指摘を一律採用せず、次のように扱った。

- 秘密最小化は既に AGENTS.md にあった。欠落ではなく入口・引用テンプレートの実行順を補強した。
- 条件付き引き継ぎは既に可能だった。検証だけを渡すときの入力・合否・上限・権限・結果別の再開先を具体化した。
- 実装先の未指定を、何でも裁量へ送る根拠にはしない。所有権・保存形式等を変えない接続差だけを裁量とする。
- 導入手順の完成と実接続成功を区別し、未操作でも準備できる部分と、案を覆す事前条件を分けた。
- 不特定入力・従量費・他者配布の特徴にだけ適用する検証を補い、個人ツールへ一律の公開準備を強制しない。
- 外部根拠には再確認条件と影響する判断を付け、全資料への一律の期限は導入しない。

[静的レビューの再確認](runs/rail-revision-3/rail-recheck.md) では、検証専用引き継ぎ、既存実装との境界、導入準備、不特定入力、配布条件は解消と判定された。残った三点も修正した。秘密情報の対象を資格情報・識別値だけへ狭めず、根拠を毎工程で再取得せず、問題選択前の調査は実用手段の存在と大きな条件の絞り込みに留める。後者は無調査と全分岐の詳細調査の両極端を避けるためである。

共有案件の実行では、主場面だけを確認して全操作へ合格を広げる問題が残った。書込操作ごとの共通契約と例外、復元したい値から保存内容への逆向きの確認、実行した範囲だけへの証拠適用を詰め方へ加えた。親レビューで見つけた代案と自作の制約判定の非対称も補正した。共有案は初稿を残し、指摘を渡した修正評価を行った。結果は自作の穴埋めではなく、条件付きの既製品導入案へ変わった。原文要求を削って指摘を回避していないことも受取担当が確認した。

三回目の粗い入力は、二回目の出力を知る同じ sol による反復実行であり、新しい文脈の再現性を実証したとはしない。使用版と入力は [round 3](runs/rail-revision-3/inputs.md)、最終改訂の修正・受取条件は [round 4](runs/rail-revision-4/inputs.md) に保存した。

[正本の最終再確認](runs/rail-revision-4/rail-final-recheck.md) は、前回の五つの反例と追加規則を再適用し、対象範囲で残る具体的破綻なしと判定した。読取専用CLIに書込契約を課さず、復旧を提供しない案件に履歴を要求せず、各代案は同じ構成ではなく同じ制約で評価する線も維持できている。これは机上確認であり、匿名公開やモバイル配布の実装成功を観測したものではない。

最後の共有案では、検証手順を補った後にも競合試験の制御不足が見つかった。新しい文脈の受取担当を利用できた2026-09-15に原稿だけを渡して検出したもので、修正担当の自己確認だけでは見逃した。親担当は、送信前の待合せと開始・完了時刻の観測、到達不明時の停止、再送検出を補い、前版の初期設定・復旧の情報を戻した。費用の仮内訳と日常入力の観測も明記した。

これは既存の「検証が問いに答える」「引き継ぎが単独で使える」という基準の適用不足だった。今回の通信制御手段を全案件の必須規則にはせず、修正例と差し戻しの証拠を残す。品質のためには手順に従うだけでなく、受取時の具体的な反証と修正まで必要である。

最終受取再確認は対象9ファイルのSHA-256一致を確認し、重要な未解消指摘と自律修正可能な不整合をともになしと判定した。実際のGrocy利用成功ではなく、許可後に実施する条件付き案・検証手順を受け取れるという合格である。

### 経路の照合

初版のシナリオ A〜H は以下のように机上照合した。H は欠陥企画レビューでも実行確認した。ほかは実案件の完遂を実証したものではない。

| 経路 | 適用した判断と結果 |
| --- | --- |
| A 個人の貸出 | 8時間は上限。内訳見積と比較が閉じない間は条件付き。市場調査や収益モデルを強制しない |
| B 他人へ売る | 支払意思は未実証とし、公開比較・少数利用の採算・小さく作る投資判断を分ける |
| C 既製カレンダー | 与件の確認済み機能と人の設定操作だけで手順を作る。準備完了と実登録を分ける |
| D 共有が未定 | 共通の要求・代案比較は進める。権限等の詳細は上位回答に依存させ、両案を完全設計しない |
| E 連携が確認不能 | API成功を仮定しない。代案と、環境を持つ担当へ渡す検証作業を完成させる |
| F 完成後に共有へ変更 | 育成中へ戻す。所有権・同時更新・認証等に依存する設計とレビューを失効させ、無関係な根拠は再利用 |
| G 見送り | 理由と再検討条件で閉じ、自作向けの空文書を増やさない |
| H レビューのみ | 問題を発見しても案を改変しない。実行した欠陥例でも原案は保持された |

この評価で市場での成功、日常利用の継続、任意のプロダクトでの手戻りの少なさは実証できない。判断を漏らさず進めることと、現実の人が価値を感じることは別の確認が必要になる。初回実行では実際に失敗しており、修正後の再確認から未知の入力での成功率を推定しない。実ユーザーの思考時間や大手戻りの削減も未計測である。

次の改善は実案件で観測する。公開調査が本人待ちで止まる、推奨案に存在しない機能が混ざる、受取時に主要判断が残る場合は該当工程を再改訂する。逆に単純な案件で不要な調査・試験が増えた場合は、その共通規則の適用条件を狭める。今回の例を全案件の必須手順にしない。
