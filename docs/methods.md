# 調査・判断手法

## 使い方

この文書は、一般的なプロダクトディスカバリーを個人開発で実行できる形へ翻訳する。全手法を毎回行うカタログではない。現在の verdict を変えうる不確実性に対して、必要十分な方法だけを選ぶ。

## 根拠の強さ

| level | 根拠 | 言えること | 言えないこと |
| --- | --- | --- | --- |
| E0 | 発案者の直感、未検証の推論 | 仮説として検討する価値がある | 他者にも問題がある、使われる |
| E1 | Web、公開データ、レビュー、競合資料、検索傾向 | 問題や代替手段が存在する可能性、用語、構造 | 対象者が実際に困り、行動を変える |
| E2 | 対象者の具体的な過去行動の証言、問い合わせ | 問題の文脈と本人が認識する費用 | 実際に導入・支払いする |
| E3 | 観察、行動ログ、プロトタイプ利用 | 特定状況での実行行動と摩擦 | 継続利用や支払いが続く |
| E4 | 予約、支払い、移行、反復利用、既存手段の放棄 | 強いコミットメントと継続価値 | 別セグメントや長期への無条件な一般化 |

根拠は件数だけで格上げしない。競合の宣伝文を20件集めてもE1である。各主張には level、source、観測日、適用範囲、反証材料、再確認する条件を記録する。価格、法令、外部API、競合機能など時間で変わる事実は、再開時にverdictまたは仕様を変えうるものだけを取り直す。

## 問題を理解する

年齢や職業からペルソナ作文を始めない。問題が発生する状況から、次の順に具体化する。

1. 引き金: 何が起きたときに行動を始めるか。
2. 望む進歩: その状況をどのように変えたいか。
3. 現在の経路: 何を、どの順で、どの道具を使って行うか。
4. 摩擦: 時間、金銭、認知負荷、待ち、エラー、諦めがどこで発生するか。
5. 例外: 問題が起きない人・状況は何か。

直接インタビューが難しい場合は、次を代替材料にできる。

- 自分自身の行動記録と操作履歴
- 掲示板、レビュー、Q&A、issue tracker、検索クエリに現れる具体的な過去行動
- 競合のonboarding、価格、制約、解約理由
- 公開統計、業務手順、規制、専門家の一次資料
- 類似タスクの画面録画または公開デモの観察

これらは本人への接触を完全には代替しない。E1をE2/E3として扱わず、build後の最初の学習項目を明示する。

## 競合と代替手段を調べる

競合は同じ製品カテゴリだけではない。利用者が同じ進歩を得るために、現在使っている時間、表計算、メモ、人への依頼、複数サービス、諦めも代替手段である。

各候補を次で比較する。

| 軸 | 確認する問い |
| --- | --- |
| 成果 | 対象状況で望む結果まで到達できるか |
| 初期費 | 購入、設定、学習、データ移行、開発に何が必要か |
| 継続費 | 料金、手作業、監視、保守、外部依存に何が残るか |
| 切替費 | 現在の習慣やデータを捨てる必要があるか |
| 制御性 | 必要な挙動、データ、運用をどこまで制御できるか |
| 失敗費 | 停止、誤作動、ロックイン時に何を失うか |

数字が分からない場合は、架空の金額で埋めず単位を変える。「月2回の手修正」「外部API 3つ」「保守するデータ変換 5本」のように比較可能な代理尺度を使う。

## 広げるか、狭めるか

元のアイデアをそのまま採用せず、少なくとも次の三つの形を具体的な利用シナリオで比較する。

- narrow: 一人、一状況、一成果へ研ぎ澄ます。
- adjacent: 同じデータまたは同じ行動連鎖で自然に解ける隣接問題まで含める。
- broader: プラットフォーム化、複数セグメント、複数ジョブを扱う。

広げる根拠は、共通資産によって追加価値の限界費用が低いこと、または狭い形では価値獲得まで完結しないことである。狭める根拠は、学習を早める、不可逆な設計を減らす、王道体験を完結させることである。市場が大きそう、将来使えそうという言葉だけでは広げない。

## build / buy / assemble を比べる

比較では初期構築費だけでなく、一定期間の総コストを見る。

```text
総コスト = 初期導入 + 移行 + 継続料金 + 手運用 + 保守 + 失敗時損失 + 乗換困難性
```

厳密な通貨換算ができなくても、期間を固定し、各項を低・中・高と根拠で比較できる。個人用ツールでは、開発自体の楽しさを便益として含めてよい。ただし、経済合理性と作りたい動機を同じ主張へ混ぜない。

## 仮説を検証する

「この案が失敗するとしたら、誤っているだけで全体が崩れる前提は何か」を問い、影響が高く根拠が弱い順に扱う。仮説は一つの観測で真偽を判断できる粒度へ分ける。

検証計画には次を含める。

- 仮説
- 現在の根拠level
- 反証可能な成功基準と失敗基準
- 対象と募集・取得方法
- 最小の刺激物またはプロトタイプ
- 観測する行動
- 期間または件数の停止条件
- 成功、曖昧、失敗それぞれの次の判断

意見より行動に近い検証を優先する。ただし、強い証拠を得るために本体をほぼ作るなら順序が逆である。説明ページ、手作業によるconcierge、clickable prototype、予約、既存手段を使った疑似運用などから、仮説に必要な最小の方法を選ぶ。

## アイデア種別ごとの重点

| 種別 | discoveryで重く見るもの | 軽くできるもの |
| --- | --- | --- |
| 自分専用ツール | 自分の行動ログ、現状の時間・ミス、既存手段との総コスト | 架空の市場規模、第三者ペルソナ |
| 他者向けサービス | 実在する状況、切替行動、到達チャネル、支払い・継続仮説 | 発案者だけの好み |
| 開発者向けtool / API | caller workflow、導入・移行、失敗処理、互換性、既存toolchain | consumer UIの画面設計 |
| automation / integration | 手作業baseline、冪等性、監視、再実行、外部停止時の復旧 | 華やかなfront-end |
| content / static product | 情報探索、content schema、更新経路、鮮度、配布 | 永続databaseとbackend module |

表は免除規則ではない。たとえば自分専用ツールを後で公開するなら、他者向けサービスの重点も追加する。

## 参考にした一般的な定石

このラボは、次の考え方を個人開発向けに翻訳している。

- [GOV.UK Service Manual: How the discovery phase works](https://www.gov.uk/service-manual/agile-delivery/how-the-discovery-phase-works) — 解決策を問題として捉え直し、既存サービスや非プロダクト代案を調べ、buildしない結論も成功とする。
- [GOV.UK Service Manual: User research in discovery](https://www.gov.uk/service-manual/user-research/user-research-in-discovery) — 利用者、現在の行動、摩擦、必要な成果を設計前に理解する。
- [Design Council: Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/) — 問題と解決策の双方で、発散してから収束する。
- [Strategyzer: Assumptions Mapping](https://www.strategyzer.com/library/how-assumptions-mapping-can-focus-your-teams-on-running-experiments-that-matter) — 望ましさ、実現可能性、継続可能性の仮説を影響と根拠で優先する。
- [Strategyzer: Start with the most critical hypotheses](https://www.strategyzer.com/library/how-to-test-your-idea-start-with-the-most-critical-hypotheses) — buildを文字どおり始める前に、案を成立させる重要仮説を明確にする。

参照先の手順を丸ごと複製してはいない。チームや多数のインタビューを前提とする方法は、証拠levelを下げて明示する、公開された行動証拠で補う、最初のマイルストーンへ学習を組み込む、のいずれかへ変換している。
