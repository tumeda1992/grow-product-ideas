# 詰め方の手引き

いま決める問いに関係する節を読む。方法を使った事実より、選択や仕様がどう具体化したかを残す。

## 要求を解像する

「欲しい機能」を、きっかけ → 今の行動 → 困る瞬間 → 欲しい結果へほどく。利用者は年齢・職業のラベルより状況で区切る。利用者と支払う人が異なるなら両方の動機を扱う。

粗い入力では、解決手段の比較より先に「何の問題として読むか」を比べる。例えば「家の食事を楽にしたい」なら、献立を決める、買い物を減らす、家族の予定を合わせる、調理を短くする、で改善対象が違う。有力な解釈ごとに、具体場面、今の負担、改善できること、原文の裏付け、反証・必要な情報を書く。機能名を変えただけの案は別解釈として数えない。

比較では頻度・一回の負担・失敗の影響・本人の動機を手掛かりにする。数値や気持ちが不明なら創作せず、条件で順位を示す。「毎晩決めるのが苦痛なら献立、買い忘れで外出が増えるなら買い物」のように、推奨が変わる情報を特定する。初案を広げる価値と、主場面だけへ絞る価値も比較する。

どの解釈を採るか未確定でも、各解釈に使える公開調査、比較、最小の検証案は作れる。本人の情報でしか順位が決まらない場合は、条件付きの主場面を宣言して進む。すべての解釈の詳細設計を作らず、どの回答がどこを変えるかを残す。原文に「購入中の重複回避」とある蔵書案なら、その明示を根拠に限定し、無関係な目的を掘り直さない。

主な負担が不明なことは、外部調査が不要な理由にはならない。例えば献立と買い物で迷う場合、実用的な手段の存在と大きな適用条件を公開情報で確かめ、回答ごとの推奨を具体化できる。回答前はこの絞り込みまでとし、全解釈の料金・設定を詳細化しない。採用または条件付きで引き渡す有力案には、実際に提案する範囲に必要な機能・費用・運用の根拠を揃える。「何に困るかは本人しか分からない」と「何で解けるかも調べられない」を混同しない。調査を省くなら、残る判断に外部事実が不要である理由を示す。一般名の「既存AI」「既製品」で比較を終え、選定と公式条件の確認を丸ごと後続へ渡すのは未完了。

要求には識別子 `R1` 等を付け、望む結果、必須か任意か、根拠、満たせた例を記す。心臓部ロジックの着想があれば保存し、機能の正しさ・例外・代案はラボが詰める。好みや質感そのものは候補を具体化して本人が判断できるようにする。

## リサーチを判断へ接続する

1. 結論を覆す問いを選ぶ。「既製品で必須要求 R1 を満たせるか」「必要なデータを合法的・継続的に取得できるか」など。
2. 公式の製品機能・料金・利用条件・API 資料を優先して読む。利用経験は公開レビューや事例も使えるが、発信者の偏りや一例である限界を残す。
3. `evidence.md` に確認日、URL、対象プランや地域、確認した内容、分からない内容、関係する要求・判断を保存する。検索結果の要約だけで機能や価格を断定しない。
4. 事実が選択へどう効いたかを `proposal.md` に反映する。推奨・棄却・実現可否に使う主張を一つずつ、原文の発言または資料の該当箇所へ逆にたどる。出典にない頻度・失敗・希望を足していないか照合し、裏付けのない部分だけを推論や仮説へ戻して結論を再計算する。

根拠の名前だけを付けても証拠にはならない。「誰に貸したか忘れる」から「紙の転記ミスが発生している」は導けない。「8時間まで使える」は本人の制約であり、8時間で作れるという証拠ではない。複数の主張を一つの証拠 ID にまとめる場合も、各主張の出所を区別する。

公開情報と想定ペルソナは解像度を上げる道具。架空インタビュー、実測していない継続率、購入意向を証拠にしない。ウェブ閲覧不能なら既知情報を未確認と記し、比較軸・計算式・条件付き推奨を完成させる。検索で見つからないことだけで競合不存在と結論しない。

調査の停止条件は「有力案の比較に必要な事実が揃い、追加情報が推奨を変えそうな未調査点が残っていない」。残る未知が現実の利用や有料アクセスでしか確かめられないなら、その検証を設計して調査を切り上げる。資料数のノルマは置かない。

製品の言語・提供地域・対象端末・プランの制約は、本人の好みとは別に公開資料で調べる。対象端末が未指定なら条件別に適合を示し、ある端末の価格を別端末にも適用しない。調べても分からなかった挙動は、調べた範囲と実操作が要る理由を残す。

## 自作・代案・規模を比べる

最初に必須制約を当て、不適合案を費用の安さで復活させない。残った案を要求適合、体験、導入時間、保守、費用、データの可搬性で比べる。重み付き点数が必要なら理由を記し、根拠のない小数点で優劣を作らない。

制約違反と、準備・運用が重いことを区別する。自作に許している準備を代案にも同じ条件で許し、実用的な構成で比較する。例えば「自宅サーバーがない」は外部ホスト利用の禁止ではない。外部ホスト上の自作を採るなら、既製品を外部ホストで動かす案も費用と運用で評価する。調べていない代案を不適合と断定して勝たせない。

拡大案は「隣接する困りごとまで解くことで価値が増えるか」、絞る案は「主場面だけなら安く同じ価値を得られるか」で作る。機能数の多寡だけを対案にしない。組み合わせ案には、ツール名だけでなく、入力から結果までの手動・自動の接続、二重入力、故障箇所を示す。

費用は同じ期間・規模・通貨で比較する。標準は初期と月次を分けた 12 か月の試算だが、短期用途なら期間を合わせる。現金支出と自分の時間は別々に提示し、合算する場合だけ時間単価を明示する。

```text
現金総額 = 初期支出 + 月数 × (月額固定費 + 月間利用量 × 従量単価)
時間総量 = 初期構築・設定時間 + 月数 × 月間保守・手作業時間
換算総額 = 現金総額 + 時間総量 × 仮の時間単価
```

例（すべて架空）：自作は初期40時間、月2時間・1,000円、既製品は初期2時間、月0.5時間・3,000円。12か月なら自作は12,000円と64時間、既製品は36,000円と8時間。差額24,000円で56時間を節約する比較になる。時間単価が約429円を超えると、この仮定での換算総額は既製品が小さい。好みや独自要件の価値はこの式では決まらない。

数字には役割（許容上限／観測値／公式価格／工数見積／感度分析用の仮定）、単位、対象期間、根拠を付ける。役割を暗黙に変えない。既製品も自作も、初期作業・日々の利用・保守を同じ範囲で数える。利用の手間が不明なら比較式の変数として残し、保守時間だけを総運用時間と呼ばない。

工数見積は今回の到達点から作る。主要な作業（体験と入力、核の処理、保存・移行、連携、検証・配布など適用するもの）ごとに幅、前提、類似作業や技術確認などの根拠を置く。根拠がない幅は仮見積とし、精度を上げる次の確認を特定する。希望の予算から各作業へ配分した数字は計画上の配分であり、実現工数の見積とは扱わない。

未知が工数を支配するなら、先に小さく確かめる。低・標準・高の条件で比較を計算し、許容上限に収まるかと、代案より有利かを別々に判断する。上限を超えうる場合は、範囲削減、追加検証、許容上限の確認のどれが有効かを選ぶ。「上限内で頑張る」では確定しない。自作だけ保守無料、既製品だけ導入費ゼロなどの非対称を避ける。

他人へ提供する案では、誰にどう届くか、切替の手間、支払う理由、価格仮説、少数利用時の採算を追加する。個人用途には市場規模や収益モデルを強制しない。学習・楽しさが目的なら非金銭的な価値として比較へ含める。

## 不確実性を小さく確かめる

仮説ごとに、間違うと何を変えるか、最小の確認方法、合格・棄却の観測値、必要時間・費用、実施済みかを記す。どの仮説を必ず確かめるかと検証の粒度は [重点検証](verification.md) で決める。検証計画を、結果の代わりに扱わない。

自分の実例を手作業で再現する、仮データで操作を通す、公式 API の制限を確かめる、権限内の小さな技術検証を行うなど、問いに直接答える方法を選ぶ。インタビューができなければ必須工程にしないが、代替手段で支払意思を証明できたとは扱わない。

検証の負担も比較する。問題の選択が一つの実例で決まるなら、先にそれを聞き、日誌や長期試用は必要になってから提案する。試用期間・合格割合・短縮時間には、その値で今回の判断ができる理由を付ける。仮の目安は本人の合意値や統計的な証明にしない。比較測定なら同じ作業範囲・近い条件を使い、単発の現状値と複数回の試用値の差をそのまま効果と断定しない。

仮の数値に「要承認」と付けるだけでは検証設計の根拠にならない。回数や閾値を導けない段階では、まず一つの代表場面で何を観察すると次の判断ができるかまでに留める。問題を選ぶ確認と、選んだ解決手段の効果を測る試行を分け、共通の長期試行を作ることで未完了の調査・代案比較を置き換えない。

危険な個人データや規制が製品の成立を左右する場合は、その案件で必要な公式情報を調べ、資格・権限が必要な判断を識別する。全案件に法務チェックリストを機械的に追加しない。

## 体験と構造を揃える

既製品・組み合わせを採る場合は、自作向けの画面・モジュール設計の代わりに、実際の導入手順を作る。各重要ステップを「確認済みの製品機能（出典・プラン）」「人が補う操作」「未確認の挙動」に分ける。例えば候補を三件に絞りたいなら、製品の自動絞込みが確認済みなのか、人が三件を選ぶのかを明記する。未確認の安全チェックや失敗時保持を、製品の動作として書かない。確認できない機能には具体的な手動代替を置き、その負担を比較へ戻す。代替できない必須機能だけを導入の阻害事項にする。将来の自作案は別の条件付き案とし、今回の試用合否へ混ぜない。

以下を一つの主場面でつなぎ、そのあと失敗・境界の場面で構造を揺さぶる。数を埋めるための場面を増やさず、作り直しを防ぐ場面を選ぶ。

| 対象 | 決める粒度 | 浅い通過の兆候 |
| --- | --- | --- |
| 体験 | 主体、開始条件、操作、システム応答、完了、失敗時の回復 | 「簡単に管理できる」で止まる |
| 画面・入出力 | 画面一覧と遷移、主情報・操作の配置、初期・空・読込・エラー・完了、入力元 | ページ名だけ、全画面同じテンプレート |
| データ | 実データ相当の例、識別子、型、関係、多重度、制約、所有者、作成・更新・削除、保存場所 | テーブル名と列名だけで操作時の値が不明 |
| 処理・モジュール | 心臓部の入出力例、規則と例外、責務、依存、データの書込主体、境界をまたぐ契約 | 「サービス層で処理」だけ |
| 運用 | 検知する失敗、手動回復、バックアップ・復旧、移行、費用上限など案件に必要な条件 | 「後で運用で対応」で方法がない |

画面の配置はテキストのワイヤーフレームでもよいが、代表データと利用順が読み取れるようにする。体験の価値が入力負担・判断の分かりやすさ・操作順に依存する場合は、見た目の好みと無関係に、初回導入から結果・訂正までを具体的に通す。操作の数、必要な情報をその場で持っているか、途中で止まる条件を、現状の行動と比べる。

遷移や操作をしないと問いに答えられないなら操作可能な最小モックを、文章や静的ワイヤーで答えられるならそれを選ぶ。検証したい問いと無関係な美観の作り込みは行わない。人が使ってみた結果とエージェントによる操作確認は区別する。本人の好みや日常への適合がまだ重要な未知なら確認待ちにし、ツール不足でも配置案・手順・具体データまで完成させる。

API やモジュール境界では入力・出力、失敗、権限、再試行や重複の扱いを必要な範囲で決める。DB のない CLI や外部サービス中心の案では、不必要なテーブルやバックエンドを捏造しない。

代表の更新操作だけを決めて他の操作へ自動的に適用しない。今回の書込操作ごとに、成功で保存するもの、再送で返すもの、競合・応答消失時の挙動を対応付ける。共通契約を使うなら適用する操作と例外を明記する。履歴・訂正・復旧を提供する場合は、復元したい表示や値から保存内容へ逆向きにたどる。例えば改名前の名前を戻すなら、その名前が履歴に残る必要がある。検証結果は試した操作・境界にだけ適用し、未試験の操作まで同じ証拠で合格にしない。

整合確認の例：`R1 重複購入を避ける` → 購入前に識別子を検索 → 検索画面 → 正規化された識別子を持つ所蔵記録 → 検索処理 → 表記ゆれでも登録済みと分かる、まで追う。新規登録の競合も対象なら一意制約と重複時の画面応答まで追う。これで画面だけ・DBだけの最適化を見つけられる。

実装者の裁量には、要求・画面体験・保存形式・公開契約を変えない内部関数の分割等を置ける。「認証をどうするか」「削除時に何を残すか」「エラー時にデータを失うか」は裁量へ押し込まず設計する。
