# 背景と初版の設計判断

## 共有された議論から維持すること

出典は 2026-09-13 にこのリポジトリへの依頼で共有された議論記録。以下はその要約であり、原文全文ではない。

ユーザーは既に個人システムを作り切れている。手が止まることや AI の浅い出力が主な痛みなのではなく、作りながら考えるため毎回土日を使い、経験が次の案件のレールに残らないことが痛み。一般的な手法を個人で実行できる形に取り込み、skill とフローを育てたい。

レールを主、品質検査を従に置く。網羅や完璧さを目標にせず、ユーザーが「そこそこ満足できる」「ここからは運用で直せる」と思える線を目指す。着想や体験の好みを AI の推測で確定させず、情報収集・比較・整合のように詰められる仕事を引き受ける。

体験・画面構成・テーブル構成・バックエンドのモジュール構成は、先に揃えたい重要な対象。ただし、これだけを出口に置いた過去の提案は下流へ偏っていた。最後のフィードバックは、要求定義、そもそも作るべきか、拡大・絞り込み、競合・既製品の組み合わせ、構築と運用の費用比較、ウェブや想定ペルソナによる解像度向上も扱う必要を示している。

過去の提案にある「ラボは四点だけを決め、それ以上を求めない」「着想系はカタログへ載せない」を包括的な合意として採用しない。前者は最後の指摘で範囲不足が判明し、後者も体験案の提示まで禁止する根拠にはならない。

## 今回の自律的な設計判断

ユーザーから、質問せず進められるところを作り切り、決め切れない点だけまとめる指示を受けた。以下はその範囲で作成した初版の運用方針であり、ユーザーが各項目を個別承認したという意味ではない。

1. 要求探索と解決策比較を、下流設計より先に置く。要求を広げる・解決策を広げることを区別し、既製品を買う選択も同じ要求で比較する。
2. 文書は状態、現在案、根拠、判断履歴を基本とし、設計と引き継ぎは必要になったら追加する。初日に空の詳細設計を大量生成しない。
3. 自律判断は根拠を付けて採用できる。好み・支出許容額・実データなどユーザー固有の情報は仮置きし、未回答でも独立した作業を継続する。
4. 初めて通しで動く線と、運用へ移れる線は別々に定義し、同じで足りる案件では統合する。どちらもユーザーの過去の発言から自動確定した値ではない。
5. 主要な構造判断を終える一方、内部関数名など安く変えられる詳細は実装者の裁量にできる。裁量と重要な未決事項を明示的に分ける。
6. skill は育成・レビュー・改善の三つ。調査専用や画面専用へ細分化する案は、初版では受け渡しと読込負荷が増えるため採らない。

## 外部の知見の取り込み方

次は 2026-09-13 に参照した一次資料。手法の有効性をすべての個人開発へ保証するものではなく、採用部分と個人向けの翻訳を区別する。

| 資料 | 取り込む考え | この場所での翻訳 |
| --- | --- | --- |
| [Design Council: Framework for Innovation](https://www.designcouncil.org.uk/resources/framework-for-innovation/) | 問題を探索して定義し、解決策を広げて試しながら絞る | 初案をすぐ仕様化せず、要求と代案の二段階で比較する。全員参加のワークショップは必須にしない |
| [GOV.UK: Learning about users and their needs](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs) | 解決手段とユーザーの必要を区別し、既存の根拠から理解する | 自分の実例と公開情報で始める。想定ペルソナは仮説であり、実際の利用者を調べたことにはしない |
| [Strategyzer: Start With The Most Critical Hypotheses](https://www.strategyzer.com/library/how-to-test-your-idea-start-with-the-most-critical-hypotheses) | 重要な仮説を優先して検証する | 全項目の均等調査をやめ、結論を覆す不確実性へ集中する。個人で行える手作業再現や小さな技術検証を選ぶ |

tumeda-dev の think-through からは原因と提案の接続・異なる具体例での確認、task-design からは完成後の姿と穴埋め完了の区別、steering からは再開可能な状態保存を参考にした。全判断の逐次承認や、実装時の判断を完全にゼロにする条件は持ち込まない。
