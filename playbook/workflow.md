# アイデアを育てる進め方

## 進行の単位

工程は次の問いを見つけるための標準順序。既に決まっていることは根拠をリンクして通過し、結論が変われば影響する工程へ戻る。工程ごとにユーザー確認を挟む必要はない。

判断は次の三種類に分ける。

- **自律確定**：依頼された範囲内で、制約と根拠から選べる。選択と理由を記録して反映する。
- **仮置き**：情報が不足するが、取り消し可能な前提で検討を進められる。前提、違った場合の影響、見直し条件を明記する。
- **ユーザー待ち／外部確認待ち**：本人の好み、費用の許容、アクセス不能な情報、外部への行為など。未決事項へ集約する。

委譲された範囲の判断を再承認へ戻さない。一方、「お任せ」を、未提供の個人情報が分かったことや購入権限を得たことにはしない。

## 1. 入口を保存し、要求を立てる

入力は一文のアイデアでもよい。日付と短い英語の仮称で `ideas/YYYYMMDD-slug/` を作る。命名に議論時間を使わず、改名の希望がなければ安定した識別子として維持する。同名があれば対象を確認し、別件なら連番を付ける。既存ファイルを上書きしない。

[テンプレート](../templates/idea/) から最初に `README.md`、`proposal.md`、`evidence.md`、`decisions.md` を作る。原文は `proposal.md` に保存し、補完した解釈を分離する。

要求では、利用者の属性より「どの状況で何が起き、今どうしのぎ、何が変わると嬉しいか」を書く。自分用か他人にも届けるか、既存資産、予算・使える時間・運用制約を抽出する。粗い入力に複数の解釈がある場合は、[要求の解釈比較](methods.md#要求を解像する) を先に行う。主場面を一つ作ったことだけで問題の選択を終えない。

**進める条件**：有力な問題の解釈を比較し、主場面を選ぶ理由と選択が変わる条件を示せる。本人固有の情報がなければ仮の主場面とし、別解釈でも使える調査を進める。「AI で便利にする」「忙しい会社員向け」だけなら場面を具体化する。原文で問題が限定済みなら、無理に別解釈を増やさず限定の根拠を示す。

## 2. 調査と代案で、作るべきものを決める

[methods.md の要求・調査・比較](methods.md) に従う。まず「この結果なら選択を変える」という問いを立ててから調べる。競合の数を集めることを目的にしない。

現状維持、既製品、既製品の組み合わせ、自作を、同じ要求・利用規模・期間で比較する。候補が存在しない場合も、探索範囲と残る不確実性を記録する。初案を狭くした案と、隣接する要求まで広げた案を検討し、差がないなら無理に別案を作らない。

比較の結論には推奨、改善できる負担と新たに生む負担、最大の弱点、次善案、推奨が逆転する条件を付ける。結論に使った事実を原文または閲覧箇所へ戻って照合する。予算・希望値を見積に転用しない。上流の好みが未決なら有力な案まで絞り、共通部分を先へ進める。分岐の数だけ詳細設計を量産しない。

**進める条件**：問題の解釈と解決手段の両方について選択を説明でき、根拠の出典・数値の意味・見積幅が確かめられている。[重点検証の選び方](verification.md) を読み、失敗すると今回の要求・体験・データ・境界・実現可否を変える未知を選ぶ。ここで分かった問題は到達点を切る前に扱う。資料や実験が必要なら権限内で実施し、できなければ条件付き案と確認方法を残す。

**分岐**：自作が妥当なら工程3へ。既製品・組み合わせなら工程3で導入の到達点を決め、工程4では構成・設定・データ移行・運用を必要なだけ詰める。現状維持・見送りなら理由と再検討の条件を残し工程5へ進む。

## 3. 到達点を切る

「初めて価値を通しで体験できる線」と「以後は運用しながら改善できる線」を具体的な場面で記述する。線が同じならその理由を記す。今回実装へ渡すのがどちらかを一つに定める。

対象機能を列挙する前に、対象利用者、開始条件、達成結果、許せない失敗を決める。そこから必要な機能を導き、非目標、受け入れる負債、成功・中止・再検討の条件を置く。

たとえば「通知機能を完成」ではなく「登録した期限を翌朝確認でき、失敗した通知が分かり、手動で再確認できる」。継続利用や売上は開発完了の合否と混ぜず、公開後に観測する条件へ分ける。

**進める条件**：後続の担当が、今回の範囲を増やす提案と必要な実装を区別できる。本人の満足水準が不明なら推奨到達点を仮置きし、その確認を未決事項へ置く。

## 4. 体験と構造を一緒に詰める

`design.md` を作成し、[methods.md の構造設計](methods.md#体験と構造を揃える) を使う。体験を決めて画面を書き終えてからデータを考える一方通行にせず、具体例を往復させる。

到達点の特徴に [重点検証](verification.md) を当て直し、主場面と、その場面だけでは見つからない失敗・境界を選んで通す。最初の入力・導入から日常利用、訂正・離脱までを見渡して、今回の範囲で高くつく見落としがないか確認する。画面のない製品ならコマンドや通知、DB が不要ならファイルや外部保存先について同じ役割を記述し、不適用理由を明記する。

外部 API 等の重要な成立条件は公式資料や許可された小さな検証で確かめる。未検証なら、その機能だけを条件付きにして独立部分を仕上げる。技術選定では既存資産と制約を優先し、要求を左右しない内部の詳細まで先決めしない。

**進める条件**：要求と選んだ重点リスクから、体験・画面・データ・処理・合格例まで追える。体験や技術の成立を左右する検証は、計画だけでなく結果を残す。未実施の重要検証は出口を止める未決事項へ移し、独立部分は仕上げる。主要な仕様が決まらない箇所を、実装者の裁量という言葉で隠していない。

## 5. 検証して引き渡す

先に `handoff.md` を作り、実装または導入の読み順、順序、合格条件、裁量、相談条件を揃える。次に [review-idea](../skills/review-idea/SKILL.md) で引き継ぎを含む成果物一式をレビューする。途中のレビューは可能だが、最終判定の代わりにはしない。育成依頼の一環なら発見した不整合を直し、最終版を再確認してから状態を確定する。

実装するつもりで最初の作業と最も危険な作業を読み、追加で決めなければ書けない仕様を列挙する。重要な判断なら設計へ戻し、安く変えられる詳細なら裁量に明記する。この受取確認は、別担当が使える場合は会話履歴を渡さず行う。一人で行う場合は受取視点での自己確認と記す。見送りは理由・根拠・再検討条件をレビューし、自作向けの引き継ぎや空の設計書を作らない。

実装先が未指定でも、持ち運べる引き継ぎを完成させる。実装先の確認がアーキテクチャを変えるなら重要な未決事項として扱う。実装先の task-design が必要としても、要求や商品案を白紙から再決定させず、現行コードとの適合と実装単位の具体化へ引き渡す。

## 状態と完了の意味

状態の正本は各アイデアの `README.md`。工程とは別に、次のどれか一つを持つ。

| 状態 | 意味 |
| --- | --- |
| 育成中 | 調査・比較・設計・修正で自律的に進められる仕事が残る |
| 確認待ち | 自律的に進められる範囲を終え、重要な未決事項と条件付き完成案を残した |
| build-ready | 自作の主要判断と今回の合格条件が確定し、レビュー指摘と重要な未決事項が解消した |
| 導入準備完了 | 自作せず実現する構成・導入順・費用・確認・復旧方法が確定した |
| 見送り | 作らない理由と再検討条件が確定した |

build-ready／導入準備完了にするには、次を最終レビューで確かめる。

- 採用した問題の解釈と解決手段に根拠があり、仮説のまま受け入れる範囲が分かる。
- 費用・工数は許容上限と区別され、その幅が到達点の実現判断と矛盾しない。
- 重点リスクの適用判定と必要な検証結果がある。検証を軽くする場合も、問いにその方法で答えられる理由がある。
- 今回の合格条件を、主場面と選んだ境界場面で追える。受取確認で残った主要判断がない。
- 最終レビューが現在の proposal・design・handoff と検証資料を対象にしている。未解消の重要指摘がない。

「重要」とは、外れた場合に今回の価値、対象利用者、体験の流れ、保存形式、公開契約、実現可能性、許容費用を変えるもの。軽微な見た目や内部整理とは区別する。需要の観測のように運用へ残せるものは、失敗しても今回の投資・設計の許容範囲に収まる理由と見直す条件を記す。単に「後で検証」と書いて重要度を下げない。

`build-ready` は市場実証済みや実装済みを意味しない。未実証の需要を受け入れて小さく作る判断は可能だが、その許容が委譲範囲外なら確認待ちにする。未確定の個人予算を事実に見せて完了させない。

## 中断・回答・変更への対応

作業を離れる前に、進めた工程、更新した成果物、未決事項、次に実行できる具体的な一手を `README.md` へ保存する。長い会話だけを再開材料にしない。

未決事項には ID、推奨、選択肢、必要な情報、決める人、依存箇所、回答なしで進めた部分を付ける。ユーザーに返す時は、結論を変える上位の問いからまとめる。

回答が届いたら依存箇所へ反映し、判断履歴を残す。影響を受ける比較・見積・重点リスク・設計・引き継ぎ・検証結果を再確認する。既に完了した案でも前提が変われば `育成中` に戻し、古いレビューを現行案の保証として使わない。依存に変化がなければ検証をやり直さず、その根拠を残す。

同じ論点を新しい根拠なしに往復し始めたら、何が矛盾しているかと逆転条件を明文化する。astra への相談はその資料を用意してから行う。利用できない場合でも、独立した作業は終える。
