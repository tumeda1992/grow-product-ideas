# functional-structure-design

材料`functional-structure`を作る。依頼と返し方は`what-defines-a-product/README.md`の「skillへの頼み方」、配置と入口は`product-plans/README.md`に従う。

## 支える判断と、専門の仕事

選んだ版の一巡に必要な、大きな処理とソフトウェアで表現する機能を構成する。
各機能が何を成立させ、どこまで責任を持ち、誰から何を受け、どんな結果と状態を次へ渡すかを設計する。
体験・logic・情報の材料を使い、人や既存の道具との受渡しまで辿れる材料にする。

機能は、責任範囲と振舞いを説明できる仕事のまとまりである。
それを一つのclass・package・service、DDDのmoduleや境界へ写すと決めたものではない。
同じ機能が複数の実装へ分かれることも、複数の機能が同じ実装に乗ることもある。
ここでの分割・統合の理由は、その機能が果たす仕事と他との関係から示す。

専門の方法は、一巡から必要な仕事を取り出し、同じ目的や責任を持つまとまりを組み、前提・入出力・状態の関係を繋ぎ、具体の出来事から構成を照合することである。
個人版では与えられた体験や規則と、検査用の一件を使って机上で行う。
図が描けたことを、実際のAPI・利用者・技術で成立した証拠にはしない。

設計を進めるworkflowと、この専門が返す材料は別の軸である。
この専門は設計の進行や他の検討の前後を所有しない。他の材料や実現の検討と、必要な入力・不足に応じて往復する。
機能構成の役割から、検討の順序や実装の内部構成まで所与にしない。

## 受け取る入力と、依頼の粒度

| 入力 | 確かめることと、不足の返し方 |
| --- | --- |
| 選んだ版の価値・範囲と分担 | 誰のどの行いをどこまで支え、人・既存道具・作る部分へ何を任せたか。未達と負担を消した構成にしない |
| 体験の一巡、必要な行い・表示・操作 | 何をきっかけに、誰が何を使って続け、どこで完了と判断するか。画面名だけなら必要な行いと結果を問い返す |
| logicの規則・入力と結果 | 機能がどの判断を使い、何を変えてはいけないか。規則の採否を代行せず、欠ける判断は影響を示して返す |
| 情報の意味・状態と根拠 | 何が現行で、何を同じ対象とし、何が確認済みか。保存先の名前だけで状態の意味を補わない |
| 外部・運用の条件と、依頼の目的・粒度 | 成立や構成の差を比べるのか、振舞いと受渡しを詳しくするのか。外部の未確認や人が使える根拠を区別する |

粗い比較では、機能のまとまりと責任範囲、他との関係、構成を変える条件を示す。
詳細の依頼では、対象の一巡の各機能について前提・入出力・状態と、人・他の機能への受渡し、失敗後の続き方を具体にする。
粗い依頼で全実装を先に作らず、詳細の依頼へ機能名だけの図を返さない。

入力が足りなければ、何の機能の何を決められず、答えによってどこが変わるかを返す。
利用者の事実や採否は材料の決定過程へ問いを置き、依頼側から答えを受ける。
他の専門が必要な時も、必要な結果と粒度を依頼側へ返し、利用者や別のskillへ直接頼まない。

## 作る手順

### 一巡に必要な機能と責任範囲を取り出す

受け取った一巡から、始まり、必要な判断・行い、次へ渡る結果、終わりを全体で並べる。
誰にどんな結果を成立させる仕事かを一つずつ取り出し、人や外部で実際に行う部分も境界へ残す。
その仕事を同じ目的・対象・責任でまとめた時、何を一つの機能として説明できるかを考える。
画面・技術・directoryの一覧から機能を逆算しない。

例えば学校の用件なら、原情報を受けて現行の内容を保ち、対応を選び引き受け、次の行いを予定へ渡し、署名・提出等の実際の結果を確かめる一巡がある。
「用件対応」という大きな機能へまとめることも、予定への受渡しと結果確認を別の機能にすることも検討できる。
原本を提出する人の行いが残るのに、ソフトウェアが予定を作った所で一巡を切らない。

各まとまりについて、成立させる結果と、そこでは決めないことを示す。
予定連携の結果は、予定が作成されたか・確認できていないか等であり、学校への提出が済んだことではない。
どの機能が何の結果を判定し、どの根拠を受け取るかを置けば、同じ「済み」を複数の機能が別の意味で決める穴を見つけられる。
独立した判断が無い単純な受渡しまで、名前を増やすためだけに機能へ分けない。

### 機能の境界・入出力・関係を組み、案を育てる

機能のまとまりごとに、誰から何を受けると始められ、どんな情報と規則を使い、どの結果・状態を返すかを繋ぐ。
入力と結果は名前だけでなく、対象と前提、確認済みのこと、相手が次へ使える意味を示す。
どの情報をその機能が現行として扱い、どの変化を他へ知らせる必要があるかも見る。
classやDBの所有を決めるのではなく、機能上の責任と変更の意味を定める。

| 繋ぐ所 | 判断に使える内容 |
| --- | --- |
| 開始のきっかけと前提 | 誰のどの依頼か、対象の内容と時点、何が揃わなければ受けられないか |
| 必要な情報と規則 | どの現行の事実・根拠から判断するか。不明や古い情報を何へ返すか |
| 結果と状態の変化 | 受付と実施、結果確認と業務上の完了を分け、次の担当が何を判断できるか |
| 他との受渡し | 相手が使える対象・根拠・残作業と、その結果をどう受け取るか |
| 未完・失敗・変更 | 何が残り、誰が何を確認して続け、何を再判断するか |

この表を全機能で同じ長さに埋める指定ではない。依頼の粒度で意味と関係を辿れるようにする。
不足する規則や根拠を機能の名前で隠さず、機能が必要とする性質として返す。

機能をまとめる案では、一巡を同じ責任の中で扱いやすい一方、異なる意味の判断が一つの大きな箱へ隠れないかを問う。
分ける案では、変更の理由を分離し他でも使える一方、前提や結果の意味の受渡しが増える。
同じ対象と条件へ当てて違いを示し、機能数や案数を固定しない。分けること自体も、一つへ集めること自体も目的にしない。

調整する機能が必要でも、専門の規則や全ての状態をそこでも決め直す構成にはしない。
各機能が必要な対象・前提・結果と不足を返せれば、調整はその受渡しを繋げる仕事になる。
何を次へ渡すかが無いまま「他が何とかする」と返す案も、全体を成立させる構成になっていない。

### 具体の一件・失敗・変更で、機能構成を照合する

同じ一件の値と出来事を使い、最初の依頼から各機能が何を受け、判断し、返すかを辿る。
元の説明を暗黙に補わず、示した入出力と根拠だけで次の担当が続けられるかを見る。
一件の成功だけで対象の全場面を保証せず、構成を成立させている前提が崩れる境界を選ぶ。

例えば用件S1の原情報R1に対する予定の作成が、外部では済んだが手元の成功保存前に止まったとする。
予定への受渡しを別の機能へ分けた案なら、どの対象の結果が未確認か、用件対応へ何を返し、誰がどの根拠で照合・訂正へ進むかを辿る。
結果が不明なのに未作成と決めて再依頼したり、受付だけで提出完了にしたりする受渡しは成立しない。

原情報R2へ変わった後にR1向けの結果が届く場合も通す。
その結果が何を対象にしたものかを保持し、R2が外部へ反映された成功へ替えず、必要な訂正や再確認へ繋がるかを見る。
原情報や担当・残作業が変わった時、どの機能の何を再判断すべきかも辿る。
そのための技術の性質が未確認なら、機能の図だけで解決したとせず必要な裏づけを返す。

別題材の生成候補でも、メモを元に候補を作る、本人が選ぶ、実際に試す、という結果を分ける。
候補ができたことを本人の選択にせず、選択を実施済みにしない。メモが変わって遅れて返る候補が、どの内容に対するものかを辿る。
全ての題材へ予定連携・同じ状態や機能数を足す必要はない。

構成を変える理由が出た時は、どの機能と関係が変わり、どの判断はそのまま使えるかを示す。
変更で触る箱の数だけを良し悪しにせず、同じ意味を別々に決めて食い違う所や、根拠を失う受渡しを問う。
局所の入力や表記なら直して確かめ直す。責任範囲や完了の意味が繋がらなければ、まとまりと境界へ戻して組み直す。

### 他の設計と実装が使える機能構成と、不足へ返す

機能のまとまりと理由、責任範囲、前提・入出力・状態と関係、一巡と例外の振舞いを材料へ返す。
構成の案の差は、同じ場面で何が変わり、人に何が残るかを比べられるように示す。一案を選ばない。
他の設計で受け取った人が、肝心な機能の意味を発明し直さず使える粒度にする。

体験へは、各機能で必要な入力・表示・操作と人の行いを返す。
logicへは、使う規則と、受け取った規則だけでは結果を決められない所を返す。
情報へは、対象・現行・根拠・状態の区別と、変更で何を保つ必要があるかを返す。
技術の材料へは、機能が約束する振舞いを成立させる性質と、未確認で構成が変わる所を返す。
内部の構成や実現の検討は、これらの材料と必要に応じて往復する。どれを必ず後で行うとも決めない。

追加の人手や遅延が必要になり、選んだ版の価値・範囲・費用・負担を変えるなら、その差を依頼側へ返す。
必要な設計・裏づけが不足する機能構成を、名前が揃ったから完成したと扱わない。
初回構築のtasklist、本実装・運用の実行をこの材料の作成へ取り込まない。

## 返す材料と、止める線

材料の入口の「中身」へ、依頼された範囲と粒度で次を置く。関係は図、入出力・責任の対応は表、理由と不足は本文で示す。

- 受け取った価値・範囲・分担、対象の一巡と既知の事実・検査用の設定・未確認
- 案ごとの機能構成と理由、各機能の責任範囲・前提・入出力・状態と他との関係
- 具体の一件・失敗・変更を通した結果、欠けと直し、案で変わる所と人に残る仕事
- 必要な他の材料や実現上の性質、価値・範囲・負担の差と、答えが変える所

粗い比較なら機能のまとまりと関係の差を判断できた所で止める。
詳細なら、各機能の意味と受渡しを具体の値と出来事で辿れ、対象の一巡と重要な分岐が繋がる所まで育てる。
必要な事実や他の材料が無ければ、不足とその影響を返す。専門の材料が返ったことだけを、版全体の設計やbuild-readyの成立にしない。
机上の照合と実現の裏づけを「確かめた方法と限界」で分ける。

材料は同じ識別子で育て、依頼と粒度を入口へ足す。
以前に読まれた範囲が変わる時は、その姿・理由と影響する依頼を「変えた所」に残して返す。
前の粗い構成を、細かい依頼の結果では成立しない意味のまま保証しているように残さない。

## 水準

| 読み手が出来るべきこと | 満たさない例 |
| --- | --- |
| 一巡から機能を構成した理由と責任範囲を辿れる | 受付・管理・実行という箱だけで、何を成立させるかが無い |
| 前提・対象・結果を使い、機能間と人へ受け渡せる | 予定の受付を提出の完了にする。他の機能に要る根拠を渡さない |
| 失敗・中断後も、残ることと続き方を判断できる | 結果不明を未作成と決める。「適宜人が確認」とだけ書く |
| 変更の影響と、案の意味のある差を比べられる | 古い原情報向けの結果を現行の成功にする。分割数の少なさだけで案を選ぶ |
| 仕事の粒度と実現上の不足を区別できる | 機能をそのままclassやserviceの数にする。専門の役割だけで他の設計との工程順を固定する |
| 全体の役割の中で機能が協調できるかを問える | 全規則を調整役へ集める。個々の成功だけを返して一巡が途切れる |

表記や参照の欠けなら直して見直す。機能の目的・境界・完了の意味・受渡しが欠けるなら、ラベルを足すだけで済ませず一巡と構成へ戻る。

## 持たないもの

- 価値・範囲、人と道具と作る部分の分担、案の採否を代わりに決めること
- 体験・logic・情報の専門の仕事、実技術の性質の実証
- DDD・class・package・serviceの分割を、この機能構成だけから採用すること
- 本実装や運用、利用者への直接の問い、他のskillへの直接の依頼

必要な設計と裏づけの不足は明示し、依頼側へ影響と粒度を返す。
