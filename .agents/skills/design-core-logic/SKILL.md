# design-core-logic

材料`core-logic`を作る。依頼と返し方は`what-defines-a-product/README.md`の「skillへの頼み方」、配置と入口は`product-plans/README.md`に従う。

## 支える判断と、専門の仕事

その案を使う人や次の処理が、受け取った価値・状態へ進むために、何を根拠にどんな結果を得る必要があるかを設計する。
入力から結果を出す中核の規則・処理方式を、具体の値と出来事で辿れる材料にする。
計算、可否の判定、候補の探索・比較、生成等を対象とする。画面・保存の出し入れの名前を並べる仕事ではない。
複雑なalgorithmが要るとは限らず、既知の規則や既存の道具へ任せれば足りる所も、その成立条件とともに示す。

専門の方法として、必要な結果から入力と規則を導き、決定表や状態遷移で条件の重なり・空白を問い、問題に合う計算・探索・生成の方式を組む。
具体の例、境界、反例から規則と方式を吟味し、必要な情報・操作・外部の性質を次の設計へ返す。
個人版では与えられた事実と検査用の入力で机上実行する。計算を小さいcodeで確かめた場合も、検査した規則と範囲を区別する。
生成モデルの性能、実APIの性質、実利用の価値を、設計や自作の例だけで実証したことにしない。

価値・範囲と案の採否は依頼した側が持つ。
こちらの規則を成立させるために、必要な条件や人の負担を黙って変えない。
狭い処理の依頼でも、結果が前後の行いの中で何を果たすかを保つ。全体を新たに設計し直すのでなく、依頼された結果がそこで使えるかを問う。

## 受け取る入力と、依頼の粒度

| 入力 | 確かめることと、不足の返し方 |
| --- | --- |
| 何の判断に使い、どの処理を扱うか | 案の成立や差を比較するのか、作る版の振舞いを決めるのか。保存の仕方や画面名だけが渡れば、何の結果が必要かを依頼側へ返す |
| 届けたい価値・状態、対象の範囲と制約 | 結果が誰の次の行いへ使われるか。今回届ける部分と残す未達、変えてはいけない負担・期限・権限を読み分ける |
| 既知の事実・規則と、既にある着想 | 原情報、利用可能な時間、相手の規則、入力例や思いつき。出典のある事実・仮説・検査用の設定を区別し、着想は案の一つとして扱う |
| 前後の行いと、他の材料 | 入力を何が生み、結果を誰が何に使うか。材料の見立てをこちらで観測した事実に替えず、今の判断に必要な不足を返す |

粗い比較では、成立を左右する規則・難所・方式の違いと、必要な事実を先に示す。
詳細の依頼では、その版に必要な処理を具体の入力から結果まで辿れ、境界や変更の結果も判断できる所へ育てる。
範囲の外の全規則を先回りで定義せず、粗い依頼のまま本質的な未決を実装担当へ渡すこともしない。

不足があれば、何が分かるとどの判定・案が変わるかを示して依頼側へ返す。
利用者の事実や採否は材料の決定過程へ論点として立て、依頼した側が問い、答えを返してから続ける。
別の専門が必要な時も、必要な結果と粒度を依頼側へ返す。利用者や他のskillへ直接頼まない。

## 作る手順

### 結果が果たす仕事から、処理と判断を取り出す

対象の場面で、誰が何を受け取れば次の判断・行いへ進めるかを置き、その結果を出すための処理を取り出す。
結果が予定なら、その予定が何を実施できると示すのかを問う。担当名や日時を返すだけでは、実際に作業できるかは分からない。
必要な結果ごとに、根拠となる入力、適用する規則、使ってはいけない推測、次へ残る判断を導く。

例えば、引受け後に作業できる候補枠を返すなら、枠、残作業時間、始められる根拠が要る。
最後の枠が19:30〜20:00で、引受け後に15分かかるという検査用の設定では、19:45からなら20:00、19:46からなら20:01になる。
この差を支えるのは、開始可能時刻と残作業時間の関係であり、19:45という時刻そのものではない。
通知の既読を引受けの根拠へ替えたり、不明な所要時間を0へ替えたりすれば、入力に無い成立を作ってしまう。
どの出来事を引受けとするかが未決なら、その判断を依頼側へ返す。

処理の対象と、担当する外部・人の行いを分ける。
署名済みを受け取っても、原本を提出した根拠が無ければ提出完了は導けない。
logicが何の状態・根拠を必要とするかを示し、その情報を誰がどう取得するかの体験・保存・接続の設計へ渡す。
単に入力を写して返すだけで足りる処理は、独自の難しいlogicを発明せず、その条件を示す。

### 規則と方式を組み、違いの効く案を育てる

入力の事実と、そこから何を導く規則かを分ける。
外部の締切は事実として受け取るが、その締切を守るために何を優先するかは規則や選択である。
与えられていない優先を、便利な順序や点数として補わない。

条件で結果が変わる所では、決定表等へ条件と結果を置き、同時に当てはまる条件と、どれにも当たらない入力を問う。
複数の規則が同時に効くなら、両立できるか、どれを優先するか、その根拠があるかを確かめる。
優先が未決なら、結果の候補と、その違いを決める問いを返す。行の上から最初に当たったものを黙って正解にしない。
状態や出来事で結果が変わる処理は、前の状態・出来事・必要な根拠・後の状態を辿る。
情報が古くなった時に、前の結果のどこを再判断するかも見る。

| 処理の性質 | 方式を組む時に問うこと |
| --- | --- |
| 計算・可否判定 | 単位、境界を含むか、欠落・範囲外の扱い、入力が変わった時に結果が変わる理由。丸めや仮の既定値で条件を変えない |
| 複数候補の探索・配分 | 何を満たす候補を出し、何を比べるか。同じ資源を重複して使わず、候補無し・複数の同等候補をどう返すか |
| 順位付け・推薦 | 順位の根拠と、誰がその優先を選んだか。点数が高いことだけで、受け取った価値や条件を満たしたことにしない |
| 生成 | 使ってよい根拠、守る制約、出力の役割と品質の見方。根拠のある記述と新しい提案を分け、生成例の見栄えだけで方式を選ばない |

この表を全て埋める指定ではない。対象の処理に合う問いと方式を使う。
案に意味のある違いがあれば、同じ対象と条件で、成立・誤りやすさ・必要な情報・人に残る判断の差を示す。
既知の方式が一つで足りるなら、弱い対案を足さず理由を返す。難所を避ける案が価値・範囲・負担を変えるなら、その差を採否へ返す。
案の数、最初の分け方、回避案と正面案の両方を常に作ることは固定しない。

### 具体の入力と反例から、案の成立と差を確かめる

案ごとに同じ入力を置き、途中の判定と使った規則、結果と残る行いを辿る。
検査に使う例は、何を確かめる例かと、適用する規則の本文/版、開始時の値・状態を結ぶ。途中の前提や可否も順に照合し、初めて成立しない所でその理由と残る状態を示す。その先を成立した結果として使わず、先の境界を試したいなら、そこへ届く別の入力を組んで辿り直す。
不適切な入力を拒否する規則では、入力の不適切さと応答の誤りを分ける。拒否の前後で何を保つべきかを確かめ、正しく断ったことを規則違反にしない。
結果を先に正解として書き、後から規則の説明を合わせない。得た値は、その値を並べ直すだけでなく、元の規則からの別計算、保存される量、前後の関係等、その誤りを見つけられる根拠でも照合する。小さいcodeを使うか手で辿るかは対象に合わせ、同じ式の転記だけを独立した裏づけにはしない。全案件へのscriptや全例の大きな表は必須にしない。
成立の境界、入力の欠落・矛盾・重複・古さ、途中で前提が変わる場面から、その案を破る入力を選ぶ。
全ての組合せの網羅を目指すのでなく、案を成立させている仮定が崩れる所を問う。

作業枠の例では、19:45と19:46へ同じ15分を当て、さらに残作業を5分へ変えれば、時刻を固定していないかが分かる。
所要時間が不明なら候補を確定せず、その不足で変わる結果を返す。
二件の用件が同じ最後の15分を使う時は、各々が単独で収まるだけでは両方を実施できない。
同じ枠を消費する結果同士を合わせて問うことで、一件ずつの成功では見えない矛盾を検知する。
既存の枠が変われば、どの候補や引受けの再判断が必要かを辿る。

一意の正解が無い生成では、固定の正解文へ一致させず、役割と制約を満たす例・満たさない例で見る。
例えば、読書メモから来週試す行動候補を返す依頼へ「集中を大切にする」だけを返しても、何を行うか選べない。
メモにある割込みの話から、朝の作業前に通知を止める行動を提案するなら、根拠と提案した行いを分けて辿れる。
メモに無い時間や効果を、著者の主張や測定済みの事実として足した出力は失敗例になる。

こちらで書いた例は、方式を吟味するための試作である。
モデルが実際にどれだけ根拠を守り、有用な候補を出すかは、そのモデルへ試した結果なしには分からない。
必要なら、同じ入力と評価の見方で実証するために何を試すかを依頼側へ返し、成功率を作らない。
規則や方式が破れたら同じ案を直し、事実や価値の採否が足りなければ影響を分けて返す。
依頼された範囲を狭めたり、残る人の作業を消したりして検査を通さない。

### 次の設計が使える材料と、不足へ返す

各案について、何を受け、どの規則・根拠から何を返し、どの条件では成立しないかを示す。
具体の入力・途中の判断・結果と、検査して直した所を繋げる。
比較が必要な依頼なら、意味のある方式の差と代償を返す。こちらで一案を選ばない。

次の設計への要請は、必要な性質で返す。
例えば、現行の残作業と実際の引受け時刻が要るなら、その情報と意味を示す。table名やcolumnの型まで先に固定しない。
結果不明から再判断するのに外部の完了の根拠が必要なら、その根拠を要請し、取得できるAPIが実在するかは未確認として分ける。
体験へは必要な入力・表示・操作、情報へは保持・識別したい事実と状態、処理へは受け渡す結果や出来事の性質を示す。

不足は「詳細は後で」へまとめず、足りない事実・判断・他の材料と、答えが変える規則・結果を示す。
利用者の事実や採否は材料の決定過程へ、別の専門の仕事は必要な結果と粒度として、依頼側へ返す。
受け取った事実の変更が以前の結果へ効くなら、その影響も添える。

## 返す材料と、止める線

材料の入口の「中身」へ、対象と粒度に応じて次を置く。関係を辿れるよう、規則は表、流れや遷移は図、計算は式や具体の値等を使い分ける。

- 今回の対象と結果の役割、入力・制約・事実の出典と未確認の区別
- 案ごとの規則・方式・成立条件と根拠、重要な違いと代償
- 何を確かめるか、適用規則/開始状態から途中の判断と結果を辿った例、その結果を照合した根拠と、反例から見つけた欠けと修正
- 次の設計へ必要な情報・操作・外部の性質、不足とその答えが変える所

案の粗い比較なら、成立を左右する規則と方式の差を判断できた所で止める。
詳細なら、指定範囲の入力と重要な境界から結果を辿れ、次の設計が肝心な規則を発明し直さず使える所まで育てる。
不可欠な事実や採否が無ければ、その不足を完成した材料へ偽装せず、止まる所を返す。
技術の成立や生成品質が未確認なら、規則の机上照合と区別して「確かめた方法と限界」へ残す。

材料は同じ識別子で育て、依頼と粒度を入口へ足す。
以前に読まれた範囲を変える時は、その姿と理由、影響する依頼を「変えた所」に残して依頼側へ添える。
細かい依頼の結果を使い、粗い比較で保証していた範囲や未確認を無言で置き換えない。

## 水準

| 読み手が出来るべきこと | 満たさない例 |
| --- | --- |
| 必要な結果から、入力と規則が要る理由を辿れる | 「入力は用件、出力は予定」だけで、作業枠や所要時間が無くても成立させる |
| 別の入力にも同じ規則を当て、境界の結果を判断できる | 19:45を固定の締切にして、残作業が5分でも19:46を不成立にする |
| 規則の重なり・空白と、全体での矛盾を見つけられる | 二件が同じ枠を単独で使えるので、両方実施できると返す |
| 例が主張する場面へ届き、入力への応答と結果を規則から判じられる | 拒否すべき入力が有るだけで規則違反とする。途中で不成立になる列の末尾の値を期待値にする |
| 未確認の事実と、条件内での不成立を区別できる | 所要時間が不明なのに0分と扱う。既読を実際の引受けとして使う |
| 与えられた価値・範囲・負担を保って案を比べられる | 時間が足りないと家族の別の時間を使い、成立案として返す |
| 生成の根拠・提案・未測定を読み分けられる | メモに無い主張を引用として足す。自作の良い例一つを成功率の証拠にする |
| 次の設計が材料を使い、不足を適切な判断へ返せる | table名を先に固定する。「技術は後で」とだけ書き、必要な外部の性質を示さない |

表記や参照の欠けなら直して見直す。必要な結果の導出、規則の根拠、反例での成立が欠けるなら、欄を足すだけで済ませず規則と方式の組立てへ戻る。

## 持たないもの

- 価値・目標・条件や今回の範囲、案の採否、利用者の優先を代わりに決めること
- 全体の体験・画面、保存・テーブル、moduleや接続の実装設計
- 候補サービスの探索、費用の見積り、実APIや生成モデルの性能等の技術の実証
- 本実装・運用、利用者への直接の問い、他のskillへの直接の依頼

必要な他の仕事と粒度を返し、この材料で確かめた規則と、他に依る成立条件を読み分けられる形にする。
