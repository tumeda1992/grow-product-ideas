# design-data-model

材料`data-model`を作る。依頼と返し方は`what-defines-a-product/README.md`の「skillへの頼み方」、配置と入口は`product-plans/README.md`に従う。

## 支える判断と、専門の仕事

人の表示・操作とlogicの入力・結果を、根拠を辿って読み、変更できる情報の構造へ設計する。
何を同じ対象と見分け、どれを現行と読み、状態を何の根拠で判断し、変更でどの関係を守るかを明らかにする。
項目を保存できるだけでなく、次の人や処理がそれを使って判断・実施できる材料にする。

専門の方法として、読取りと変更から情報の意味を抽出し、対象・関係・鍵と制約を組み、具体の情報を入れて読取りと書込みを往復する。
同じ事実を複数箇所へ持つ時の更新漏れ、現在値と履歴の混同、状態を変える根拠の不足を検査する。
必要な所で正規化、版や出来事の保持、導出した値と元の事実の分離を使う。全てを別tableや全履歴にする方法にはしない。

個人版では、与えられた体験・logic・規則と検査用の具体例から構造を作る。
仮の保存先で読み書きを確かめた時も、その方式・制約・入力の範囲だけの裏づけとする。
外部の事実が取得できることや、実製品の接続・同時更新・実利用まで確認した証拠にはしない。

価値・範囲、業務規則、案の採否は依頼した側が持つ。
例えば、原本が変われば署名を取り消すかは規則の判断であり、情報に版を持たせたことだけから決めない。
構造が必要とする規則・操作・保存の保証を具体に返し、専門同士で勝手に役割を足さない。

## 受け取る入力と、依頼の粒度

| 入力 | 確かめることと、不足の返し方 |
| --- | --- |
| 判断の目的と対象の範囲 | 案の成立を比べるのか、選んだ版を実装できる構造へ詰めるのか。その情報が誰の何の判断・行いに使われるかを受け取る |
| 必要な表示・入力・操作、logicの入力と結果 | 名前だけでなく、どの時点の何の情報を読み、何を変えるか。画面を持たない処理や外で行う仕事も範囲に含める |
| 情報源と既知の規則・制約 | どこで事実が生まれ、何で同じ対象や完了と判断するか。実在の事実、他の材料の見立て、仮説・検査用の設定を分ける |
| 既にある構造や選んだ保存方式 | あれば案と条件として受け取る。未選定ならDBや全schemaを先に固定せず、構造が要る性質と比較の差を示す |

粗い比較では、必要な対象と関係、何が現行で、読取り・変更をどう成立させるか、方式による差と不足を返す。
詳細の依頼では、その保存方式に合う鍵・型・制約、具体の読取り・書込みと更新の前提まで育てる。
「情報を関連付ける」という図だけで、肝心な保存と更新を実装担当へ発明させない。

利用者しか持たない事実や規則の採否が必要なら、材料の決定過程へ問いと答えで変わる所を記録し、依頼側へ返す。
別の材料が必要な時も、何の情報・判断・技術の性質が必要かと粒度を返す。利用者や他のskillへ直接頼まない。

## 作る手順

### 必要な読取りと変更から、情報の意味を取り出す

対象の全体について、表示・操作、logicの入力と結果、外との受渡しに必要な読取りと変更を並べる。
一画面ずつ保存先を継ぎ足す前に、同じ事実を複数の利用が読んでいないか、利用に必要なのに出所が無い情報が無いかを見る。
各情報に、対象、意味、出所、生まれる出来事、変わる時と、読む側が必要とする時点を対応させる。

例えば学校の用件なら、現在の締切、誰の引受けか、どの原本への署名か、実際の提出の根拠、外部予定へ渡した内容を区別する。
現在の締切は原情報の変更で変わるが、過去に何へ署名したかは、その出来事の事実である。
「済み」という名前へまとめると、署名を終えたことから、学校へ提出したという別の事実を導けてしまう。
必要な表示とlogicが、どの済みと根拠を使うかへ戻す。

同じ題名だから同じ用件、同じ人物名だから同じ担当と決めず、同一性を支える規則と識別の根拠を受け取る。
画面の行番号や表示順が変わっても同じ対象を指す必要があれば、その条件を設計する。
識別の根拠が無いなら、勝手に題名で統合せず、何を確かめれば同じと判断できるかを返す。

元の事実、そこから計算できる値、人が選んだこと、外で確認した結果を分ける。
原情報や外部IDの欄を置いても、その情報が得られるようにはならない。
入手方法や完了の根拠が未決なら不足として返し、空欄を便利な事実へ読み替えない。

### 守る関係を定め、構造の案を組む

抽出した情報から、対象と関係を全体で並べる。
何を鍵に結び、どの値を必須とし、どの重複や組合せを許さず、何を変更しても保つかを受け取った規則から設計する。
情報を分ける時は、独立に変わる事実か、同じ事実を何度も保存していないか、消すと別の根拠まで失うかを問う。
分割自体を目的にせず、読む・直す・根拠を残す仕事から必要な関係へする。

| 設計する関係 | 問うこと |
| --- | --- |
| 同一性と対象 | 同じ物の更新か別の物か。記録や外部の結果が何を対象にするか。別の用件の原情報を誤って現行にしないか |
| 現行と履歴 | 現在何を読むか、過去の何が訂正・照合に要るか。全履歴が必要か、必要な根拠だけで足りるか |
| 状態と根拠 | 何の出来事・判断で状態が成り立つか。状態の欄だけと根拠の内容が食い違わないか |
| 未知・未実施・失敗 | 空欄や単一のfalseが、別の意味を混ぜていないか。手元で未確認を外部でも未実施と断定していないか |
| 更新と整合 | どの前提で何をまとめて変えるか。古い読取りや同じ入力の再実行で、現行や根拠を壊さないか |

現在値を更新し必要な根拠を別に持つ案、版を保つ案、出来事から状態を読む案等を、依頼の読取りと変更へ当てる。
意味のある違いがある所で案を比較し、常に二案や全履歴を要求しない。
版を持つ案でも、原情報の内容の版と、同じ内容の中で競合する更新を見分ける印は役割が異なる。
何の変化を区別する値かを定義し、名前がversionだから全て同じ前提に使えるとは扱わない。

詳細なら、選んだ保存方式に合わせて鍵・型・関係・制約と更新の前提を具体にする。
例えば、用件の現行の原情報が同じ用件に属することや、外部試行が対象にした内容を保持することを、必要な制約として示す。
現在値と現行への参照を一緒に変える必要があるなら、その更新のまとまりを示す。
それを原子的に保存できるか、古い前提を比較して拒めるかは、使う方式の裏づけが必要である。
必要な保証を列挙したことだけを、保存先で保証済みの根拠にしない。

### 具体の情報を入れ、読取りと書込みを往復する

案へ具体の情報を入れ、各表示とlogicの入力をどこからどう組み立てるかを示す。
その後、追加・訂正・状態変更を行い、同じ読取りをもう一度辿る。
項目の対応表だけで止めず、関係を辿ると欠落・重複・誤った現行が生じないかを見る。
詳細ならquery、文書の読取り手順、条件付き更新等、その保存方式で行う具体を示す。

学校の検査例では、原情報R1の締切が金曜から、R2で木曜へ変わる入力を当てる。
現行の表示とlogicは木曜を読めるか、外部へ既に渡した金曜の内容は訂正・照合のため辿れるかを問う。
R1の画面から遅れて届く更新でR2へ戻らないか、同じR2を見た二つの更新でも互いを失わないかを検査する。
どの前提が外れ、再読取りや再判断が要るかを返せる必要がある。

署名の根拠を保持しても、それが新しい原本へ有効かを構造だけで決めない。
受け取った規則へ渡すために、何を対象にした根拠かを読めるようにする。
外部の予定作成が成功保存前に止まった時も、試行が対象にした内容と、手元で確認したことを残す。
外部IDの空欄を未作成と決めてよい根拠にはしない。

重複した入力、別の対象を結ぶ入力、途中で一部だけ保存された状態、古い結果が後から返る場合も、守る関係が崩れる所から選んで当てる。
案が破れたら、必要な情報の意味・関係・更新の制約へ戻して直す。
規則や外部の性質が分からず直せないなら、何が分かると読取り・更新が変わるかを依頼側へ返す。

別題材の生成候補でも、メモを編集した後に、候補が何を根拠に作られたかと、どの候補を本人が選び実際に試したかを読み分ける。
最新のメモへlinkを付け替えるだけで古い案の根拠を変えず、選択を実施済みへ替えない。
必要な引用箇所を保持すれば足りる場合もあり、全てのメモの版や生成の全logを必須にしない。

### 案の差と、次の設計へ必要な条件を返す

各案の構造と理由、読取り・変更の例、守る関係と検査結果を返す。
同じ利用に対して、どの情報を失わず、何を再構成し、どの操作や保証が必要かの差を示す。案を一つに選ばない。
保存する量の少なさだけで、照合・訂正の根拠を失う案を成立したと扱わない。

体験へは、何を取得・確認・表示する必要があるかを返す。
logicへは、どの意味・時点の入力を渡せ、変更によりどの前の結果が再判断を要するかを返す。
処理の設計へは、更新の前提、まとめて守る関係、競合・不足を検知した時に必要な再読取りを示す。
技術の実証へは、成立に必要な比較・更新・外部の根拠等の性質と、未確認で変わる構造を返す。

table名や抽象図だけを返さず、次の担当が同一性・状態・更新の意味を再推論せず使える形にする。
一方で、どのmoduleが処理を所有し、いつ外へ送るかの全体設計まで代行しない。
以前の材料の入力や規則の不足が見つかったら、その差と影響を依頼側へ返す。

## 返す材料と、止める線

材料の入口の「中身」へ、対象の範囲と依頼の粒度に応じて次を置く。
関係は図、情報の意味と読取りの対応は表、具体の読み書きは保存方式に合う記法で示す。

- 必要な表示・判断・変更と、その情報の意味・出所・未確認の区別
- 各案の対象・関係・鍵と制約、現行・履歴・状態と根拠の持ち方と理由
- 具体の情報からの読取りと更新、境界や反例での結果と修正
- 案の差と、必要な規則・操作・技術の保証、不足が変える所

粗い比較なら、成立を左右する構造と読み書きの差を判断できた所で止める。
詳細なら、選んだ方式の具体の鍵・型・制約と読み書きがあり、次の担当が肝心な関係や更新の前提を発明し直さず使える所まで育てる。
必要な情報が取得できない、規則が未決、保存の保証が未確認なら、その不足を完成した構造へ隠さず返す。
仮の保存先で検査した結果は、対象とした条件を「確かめた方法と限界」へ残す。

材料は同じ識別子で育て、依頼と粒度を入口へ足す。
前の依頼が読んだ範囲を変える時は、前の姿・理由・依っていた依頼を「変えた所」に残し、返しへ影響を添える。
前に読んだ抽象図が、具体化後には保証しない読み書きを暗黙に保証した形で残らないようにする。

## 水準

| 読み手が出来るべきこと | 満たさない例 |
| --- | --- |
| 情報の意味・出所と、同じ対象を見分ける根拠を辿れる | 同じ題名の用件を統合する。欄があるだけで提出や外部の完了を得られたことにする |
| 現行を読み、過去の根拠と取り違えず使える | 締切を上書きした時に、旧い外部予定や署名が何を対象にしたか失う |
| 状態の根拠と、未知・未実施の違いを判断できる | 署名済みを提出済みにする。外部IDが無いので外でも未作成と決める |
| 変更・競合の後も、守る関係を読み書きで確かめられる | 古い画面の保存で現行が戻る。同じ原情報の版の中の更新競合を見落とす |
| 依頼の粒度で、構造を次の実装・設計へ使える | 詳細の依頼にも関係図だけを返し、鍵や更新を実装担当に考え直させる |
| 案の差と、規則・取得・技術の不足を読み分けられる | 全履歴を正解にする。仮のDBで通ったので実製品の外部接続も成立したとする |

表記・参照の欠けなら直して見直す。情報の意味・根拠、関係と更新の成立が欠けるなら、columnを足すだけで繕わず必要な読取りと変更へ戻す。

## 持たないもの

- 価値・範囲、業務規則・優先や案の採否を代わりに決めること
- 全体の体験・画面、moduleの責務と接続の全体設計
- 保存技術や外部APIの性質の実証、本実装・移行・運用の実行
- 利用者への直接の問い、他のskillへの直接の依頼

必要な条件と粒度を返し、情報の構造が次の判断と行いの中で機能するように渡す。
