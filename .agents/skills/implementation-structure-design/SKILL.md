# implementation-structure-design

材料`implementation-structure`を作る。依頼と返し方は`what-defines-a-product/README.md`の「skillへの頼み方」、配置と入口は`product-plans/README.md`に従う。

## 支える判断と、専門の仕事

必要な機能・規則・情報を、どこで実行し、どこで結果を確定し、何を経由して人・別の処理・外部へ繋ぐかを設計する。
停止・競合・変更の後にも、誰がどの根拠で続けられるかを含む構成案と、その差・成立条件・不足を返す。
依頼側が案や設計を判断するための材料であり、採用や受容する損失を決めない。

機能は何を成立させる仕事かを表し、実現構成はその仕事をどの実行・保存・接続の責任で成立させるかを表す。
一つの機能を複数の実行単位で支えることも、複数の機能を同じ実行単位にまとめることもある。
機能名からclass・service・processを一つずつ作る方法にはしない。必要な保証と、分ける時に相手へ渡す根拠から境界を組む。

構成案の生成は、結果の保証を読む、確定と継続の境界を組む、前提を動かす、同じ出来事で案を直す、という往復で行う。
検討の順序・候補数・実行単位の数は固定しない。使いたい技術の名前を先に並べて案の差にしない。

## 受け取る問いと、必要な粒度

| 入力 | 読むことと、不足の返し方 |
| --- | --- |
| 比較や設計で決めたいこと、対象と分担 | どの結果を誰へ届け、何を人・既存道具・作る部分へ残すか。依頼の範囲と受容済みの未達・負担を消さない |
| 対象場面、必要な機能・行い・規則 | 何を契機に始まり、何が確認できれば次へ進め、何を業務上の完了とするか。機能名だけなら、構成を左右する結果と前提を返す |
| 情報の意味・現行・履歴と根拠 | 同じ対象・依頼・実施・結果をどう見分け、どの内容に対する結果か。空欄から未実施を推測しない |
| 実行と外部・運用の条件 | 誰がどの場所から使い、何を契機に動き、利用中断・不在・導入・設定変更で何が残るか。未指定の環境や継続作業を仮定で確定しない |
| 既存の案・技術の根拠と、求める粒度 | 確認済みの性質、他の材料の見立て、検査用の仮定を分ける。既に根拠が足りる所を形式のために作り直さない |

比較の依頼では、構成の違い、保つ保証と必要な性質、人の行い・部品と費用を変える差を返す。
詳細の依頼では、各実行単位の入口・開始契機、読む記録、確定する結果、接続する相手、必要な設定、停止・変更後に続ける根拠まで具体にする。
全schemaやコードを先に作ることと、実装する人が必要な境界を補わず使えることを区別する。

全材料の完成を待つ固定の順序にはしない。足りない入力について、何が不明で、答えの違いがどの案を変えるかを返す。
利用者の事実と採否は材料の決定過程に問いを置き、依頼側から答えを受ける。他の専門にも直接依頼しない。

## 構成案を育てる方法

### 必要な保証から、確定・実行・接続と再開の境界を組む

対象の一巡から、誰へ何が成り立ったと返す必要があるかを取り出す。
受付、処理の実施、外部結果の確認、利用者の仕事の完了を分け、各結果を何の事実から言えるかを結ぶ。
重複・古い結果・欠落・遅延のどれが何を壊すかを、受け取った条件と規則から読む。専門の都合で新しい約束を足したり、必要な保証を緩めたりしない。

必要な結果ごとに、次を組む。

- 一緒に成立させる必要がある記録と状態変更、相手の結果を待つ範囲。
- どの実行単位が何を読み、何を確定させ、誰へどの意味の結果を返すか。
- 実行が止まった後にも残る情報と、その情報を使って確認・再実行・訂正できる条件。

例えば、依頼J1の原情報R1を外部の予定へ反映する仕事では、手元の依頼受付と、外部の予定作成、手元の結果保存は別々に起きうる。
手元の保存にtransactionがあっても、外部の予定作成まで一緒に確定する根拠にはしない。
「予定作成済み」と返すなら何を確認するか、結果が不明なら誰が何を調べて続けるかを組む。

依頼・試行・外部の結果の識別と対象の版は、必要な保証に応じて扱う。
再送ごとに新しい識別を作れば同じ仕事を別の新規依頼として重複実施することがあり、同じ識別を別の内容へ使い回せば古い結果を取り違えることがある。
何を同じ依頼とするかの規則が無ければ、識別子の名前で補わず必要な判断を返す。

設定・配置も構成の前提へ含める。実行者、起動の契機、保存先の寿命と共有範囲、必要な接続と権限、設定変更で変わる対象を読む。
端末終了で消える記録を再開の根拠にしたり、起動する者のいない定期処理を置いたりしない。環境の実際の性質は確認済みと未確認を分ける。

### 前提を動かして案を作り、同じ入力・停止・変更で直す

保証に効く境界を動かし、異なる構成を育てる。
その場で終える／依頼を残して別に実行する、同じ場所へまとめる／別の責任へ分ける、手元／共有先のどちらを根拠にするか等から、今回の条件に効く差を選ぶ。
分ければ接続と再開の責任が増え、まとめても外の作用まで同時に確定できるとは限らない。
技術名を替えただけ、あるいは明らかに届かない弱い案を、比較の数を満たすために加えない。

案ごとに、同じ一件の値と出来事を使い、読む情報・実行・保存・外部への作用・返す結果を順に辿る。
構成の前提が崩れる所で、次の三つを具体にする。

| 見る所 | 次の行いを導く根拠 |
| --- | --- |
| 記録や外部作用の前後の停止 | 残る記録と、そこから確認できる事実・まだ不明な結果。誰が何を契機に再開し、何を調べるか |
| 同時実行・再送・遅い結果 | 同じ仕事を誰が実行でき、重複した効果や更新を何で防ぐか。古い結果を何の結果として扱うか |
| 原情報・担当・設定の変更 | 変わる前の入力と現在の内容を見分け、何をやり直し・訂正・再確認するか。既存の結果を使える条件 |

外部で作成された直後、手元へ外部IDを保存する前に止まると、外部IDの空欄だけでは未作成と言えない。
外部への送信前に残る依頼の根拠と、外部で同じ識別の再送・結果の照合をどう扱えるかを組み、次の操作が許されるかを辿る。
workerやqueueを置いたことだけで二重作用が解消したとしない。必要な性質が不明なら、成立を仮定した案と、確認が必要な問いへ分ける。

原情報R1向けの結果がR2への変更後に届く場合、その結果がR1を対象にすることと、現在R2に何が必要かを分ける。
二つの実行者が同じ依頼を読む場合も、開始前に再読するだけでは、その後の競合を防げない。
何を条件に取得・確定し、その条件が外れた時に何を返すかを組み、必要な保存・外部接続の保証を具体にする。
取得権の期限が切れて再取得できても、古い実行者の外部作用まで止まったとは限らない。再取得を許す条件と、外部側で同じ仕事の効果をどう守るかを組む。
手元でR1の結果を現行R2の成功から除いても、外部に起きたR1の作用は消えない。外部の訂正・照合と必要な規則を別に返す。

外部作用の無い一覧の再生成なら、元の確定した入力が再実行の根拠になる構成も比べる。
一時出力から完成した出力へ切り替える必要、処理中に入力が変わるか等、今回壊れる保証を読む。
全てへ耐久的な依頼・worker・全履歴を足さない。不要なものを外した時の差も比較へ返す。

同じ場面で、保証の成立、人が使える時点、実行・停止後の手間、必要な部品と環境がどう違うかを示す。
候補を残す・外す理由は説明するが、依頼側の価値の重みや案の採否を代行しない。

### 他の専門と費用へ返る問いを反映し、案と根拠を育て直す

不足は、構成を変える具体の問いと、必要な結果・粒度として依頼側へ返す。

| 次の設計で必要なもの | 返す問い・材料の例 |
| --- | --- |
| 体験・画面 | 受付後に処理を待つ時、結果不明の時、人は何を知り、何を操作してよいか。操作に要る根拠がどこに残るか |
| 規則・機能 | 何を対象にした結果か、どこが確認・訂正・再開を担うか。技術上の受付を業務完了へ読み替えない責任 |
| 情報 | 依頼と試行・結果の同一性、対象の版、現行と履歴、同時取得・更新の条件。table名だけを追加させない |
| 技術検証 | 対象と版・設定・入力条件を含む主張、期待と反例、成立・不成立で変える構成。通常の成功だけで足りない理由 |
| 費用 | 作る部品と境界、配置・設定・連携・訂正・復旧、継続する人の行い・頻度・きっかけ、共通部分と案ごとの増減 |

例えば技術への問いは「このAPIは使えるか」でなく、同じ依頼識別と同じ内容を再送した時に別の結果を作るか、外部IDを失っても残る情報から対象を照合できるか、になる。
費用へは「復旧対応を作る」でなく、未確認の一覧を読む・照合を依頼する・結果を関連付ける部品と、人が何を契機に何を確認し続けるかを返す。

返った事実や設計を読み、どの案の前提・振舞い・部品・負担が変わるかを直し、同じ出来事へ当て直す。
未取得を成功や受容した損失に替えない。成立に不可欠な性質が不明なら、その条件の両側で変わる案と、判定を止める不足を返す。
前に依頼側が読んだ値や境界を変える時は、共通の材料の変更通知を使い、前の姿・理由・影響する依頼を残す。

## 依頼側へ返す構成と、他の仕事への不足

依頼の粒度に合わせ、次を対応付けた材料を返す。

- 構成案と境界の理由、実行・保存・接続と回復の責任、外の人や道具との関係。
- 同じ入力・正常時と重要な停止・変更で、残る情報から次へ進む具体の経過。
- 案の保証・応答と使える時点・人の行い・部品と環境の差。
- 依る事実と出典・他の材料、仮定、成立しない所、残る不足と答えで変わる構成。
- 他の設計へ渡す必要な結果と粒度、費用を積む部品と継続の行い。

図だけを返さず、各接続で何を読み何を確定できるかを辿れる粒度にする。依頼が比較なら、詳細の完成を偽らず、今回比較できた範囲と条件を示す。
記録の様式は既存の材料の入口を使う。別の採否や進捗の正本を追加しない。

## 確かめ方と、返すべき不足

返す前に、依頼の対象と粒度へ、示した記録・接続・根拠だけで当て直す。

| 使える材料で示せること | 外れている見え方 |
| --- | --- |
| 必要な結果から、実行と確定の境界を導ける | 技術名と箱はあるが、受付と結果確認を何で分けるか不明 |
| 停止後に何が残り、誰が何を根拠に続けるかを辿れる | 外部IDの空欄を未実施にする。workerがあるだけで重複しないとする |
| 同時実行と変更で、対象・版と更新の条件を保てる | version欄だけで古い結果を排除した扱いにする。事前再読で競合が消えたとする |
| 案の差が、保証・行い・部品と費用の比較へ使える | 技術名を替えただけの案や、不要な分散を増やす。箱の数だけで選ぶ |
| 次の設計が必要な意味と条件を補わず受け取れる | 情報へ新しいtable名、技術へ実現可否、費用へ復旧対応という名前だけを返す |

表記や参照の欠けなら直して見直す。保証と確定・再開の根拠が繋がらなければ、境界と案の生成へ戻して直す。
依頼を左右する未指定の規則・環境・外部の性質が残れば、何を決められず、何が分かるとどこが変わるかを返す。
案の比較に応えられたこと、未確認を含む条件付きの構成、実装へ渡せる粒度を区別する。模型の経過を、実API・実runtime・実利用で成立した証拠にしない。

## 持たないもの

- 価値・提供範囲、人と道具と作る部分の分担、案の採否や損失の受容を代わりに決めること。
- 業務規則・情報構造・体験・機能構成を、それぞれの専門に代わって決めること。
- 技術の性質を実測する仕事、見積もりの算出、他のskillや利用者への直接の依頼。
- 本実装、環境の構築、本番の復旧・運用、実装taskの計画と実行。

不足が既定の範囲や受容した負担・費用を変えるなら、その差を依頼側へ返す。構成の都合で受け入れたことにしない。
