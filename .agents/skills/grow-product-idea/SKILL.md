# grow-product-idea

アイデア1件を、`what-defines-a-product/`の問いに順に答えさせ、出口まで運ぶ。

このskillは進行だけを持つ。問いを立て直して答えること、答えが基準を満たすかの確認は`settle-question`が行う。

## 持つもの

- アイデアの受け入れと、`product-plans/<slug>/`の作成
- 次の問いの選択
- `settle-question`の起動
- 水準の一段目と、`settle-question`の確認の記録があることの確認
- 層の閉じと出口判定での、利用者への確認
- 出口判定と、build-readyの時のdirectoryの外への参照の確認
- 出口記録の後に、`refine-what-defines-a-product`の起動を促すこと

## 持たないもの

- 層ごとの中身（各問いの水準、定石）。全体制御が層の中身を持つと、四層分の知識がここへ集まる
- 問いの立て直し、答えを作ること、書いた答えの漏れの確認（`settle-question`が行う）
- 材料を作ること（材料skillが行う）

## 引くもの

| 引くもの | 場所 |
| --- | --- |
| 問いのセット、問いの選び方、水準の一段目 | `what-defines-a-product/README.md` |
| 各層の問い | `what-defines-a-product/`の四層file |
| `product-plans/<slug>/`の配置と名前、三つの記録の分け方、決定過程の役割 | `product-plans/README.md` |
| 正本の雛形 | [templates/canonical.md](templates/canonical.md) |
| 層の問いの一覧の雛形 | [templates/layer.md](templates/layer.md) |

正本、層の問いの一覧、問いの決着の記録、層の決定過程、材料の入口は、file名ではなく役割で扱い、場所は`product-plans/README.md`で引く。

## 流れ

```text
1. 受け入れ（新規）／ 再開
        ↓
2. 次の問いを選ぶ ←──────────────────────────┐
        ↓                                    │
3. settle-questionを起動する                  │
        ↓                                    │
4. 一段目と確認の記録を見る                   │
   ├─ 満たさない → 理由を付けて3へ戻す ──────┤
   └─ 満たす                                 │
        ↓                                    │
5. 層の全問いが閉じたか                       │
   ├─ まだ → 2へ ────────────────────────────┤
   └─ 閉じた → 利用者へ確認 ─────────────────┤
   ※ 3で作らない・保留を示す答えが返ったら6へ │
        ↓                                    │
6. 出口判定 ─ 続ける → 2へ ───────────────────┘
        ↓ build-ready・作らない・保留
7. 出口を記録し、還元を促す
```

### 1. 受け入れ／再開

新しいアイデアの時:

1. 利用者から、アイデア、作りたい動機、既にある着想を受け取る。足りないものだけを利用者へ尋ねる。動機と着想は寝かせないと出てこないものであり、このレールが代わりに作らない。
2. slugを決める。`tumeda-dev`の`name-work-directory`が使える時はそれでアイデアと今日の日付から`YYYYMMDD-slug`を決め、使えない時は同じ形（日付と英小文字のkebab-case）で決める。
3. `product-plans/README.md`に従って`product-plans/<slug>/`を作り、[templates/canonical.md](templates/canonical.md)から正本を作る。受け入れ時は、見出し行・概要・状態（進行中）・受け入れ時の入力だけを書く。受け入れ時の入力は、利用者の言葉を言い換えずに書く。
4. 四つの層ごとに、[templates/layer.md](templates/layer.md)から層の問いの一覧を作り、層fileの全ての問いを並べ順のまま写して、状態を未回答にする。

既にある`product-plans/<slug>/`を再開する時は、正本の状態と、四つの層の問いの一覧の状態を読み、2から続ける。

### 2. 次の問いを選ぶ

`what-defines-a-product/README.md`の問いの選び方に従い、閉じていない問いのうち、下位を最も多く規定するものを一つ選ぶ。

- 規定する量は「この問いの答えが変わったら、答え直しになる問いがいくつあるか」で比べる。
- 上位層の問いが閉じていない間は、下位層の問いを選ばない。上位層の問いが下位層の材料（例: 解き方の案を比べるための粗いラフ画）を要する時は、`settle-question`が材料skillを直接起動して取りに行く。下位層の問いへ答えを先に確定させると、上位層の答えが変わった時に答え直しになる。
- 迷ったら、各層fileに並んだ順（層fileは下位を最も多く規定する順に並べている）に従う。

### 3. settle-questionを起動する

選んだ問いについて`settle-question`を起動し、`product-plans/<slug>/`の場所と問いのidentifierを渡す。
`settle-question`は、問いをこのアイデアの問いへ立て直し、詰める深さを決め、答え、漏れを確認して戻る。

### 4. 一段目と確認の記録を見る

`settle-question`が戻ったら、次を見る。

- 層の問いの一覧でその問いの状態が「閉じた」になり、問いの決着の記録に確認が書かれ、正本の反映先の節が書かれている
- 問いが挙げる必要な材料の入口（`product-plans/README.md`の材料の入口）が全てある。他の問いの答えを材料にする時は、その問いが閉じている
- 生成系の問いでは、材料に複数案があり、各案が対象の全体（全場面、全画面、全テーブル、全モジュール等、問いの水準が挙げる全体）を覆っている

満たさないものがあれば、何が足りないかを付けて`settle-question`へ戻す。
答えの中身が基準を満たすか（二段目）は見ない。`settle-question`が確認済みである。

`settle-question`が、一般の問いがこのアイデアに合わない（答える意味が無い、別の問いが要る）と返した時は、理由を読み、その問いを飛ばすかを決めて、層の問いの一覧の状態を「飛ばした」にし、理由を問いの決着の記録に書く。飛ばした問いは、層の閉じで利用者へ示す。

### 5. 層の閉じを利用者へ確認する

ある層の全ての問いが閉じたら、利用者へ確認する。

- その層で立った未決の論点（層の決定過程）を示す。論点は問いの数ではなく、問いに答える中で生じた判断の数だけある。
- その層の問いの決着の記録（立て直した問いと基準、詰めた深さ）と、正本のその層の節を示す。
- 利用者は論点ごとに応答する。応答の原文を、`facilitate-discussion`の手順で該当の論点へ記録する。合意した論点は決定になる。修正があれば、その論点の起点の問いについて`settle-question`へ戻す。修正や認識合わせが続く論点は、`facilitate-discussion`の手順のまま次の回を重ねる。
- 利用者が対案や答えを退けた時は、退けた理由が、その問いの中だけで閉じず他の選択にも効くもの（例: 「外部のサービスには預けたくない」は、代案、解き方、データの置き場所に効く）かを読む。効くなら、同じ論点の次の回で、その理由を以降の問いでも外せない条件として扱うかを利用者に確かめる。一度の言葉を勝手に一般化しない。利用者が自分から条件を口にした時も同じく確かめる。
- 利用者が条件として扱うと答えたら、正本の「前提にする条件」の節に、条件、出てきた論点へのlink、効く範囲を足す。既に閉じた問いの答え（他の層も含む）がその条件に反していれば、その問いを`settle-question`へ戻す。
- 条件そのものが本当に譲れないかは問わない。利用者が持つものであり、レールが詰めて決めるものではない。条件のせいで作る費用が膨らむ、出口が保留になる等の影響が出た時は、その影響を論点として示す。
- 利用者がその層を受け入れたら、その層の問いの一覧の「層の状態」を閉じたにし、受け入れた応答の論点へlinkして、次へ進む。再開した時は、この欄で層が閉じたかを読む。

### 6. 出口を判定する

出口判定は、次の二つの時に行う。

- `settle-question`が、作らない・保留を示す答えを返した時（`what-defines-a-product/README.md`の「作らない・保留へ向かう答え」）。どの層のどの問いからも返りうる。層の閉じを待たない。
- 全ての問いが閉じた時。build-readyへ進む。

作らない・保留を示す答えが返った時は、答えに、比較や検証の結論と、`why-to-build/gains-from-building`の答えとの照らし合わせが書かれていることを確かめる。無ければ`settle-question`へ戻す。そのうえで、出口判定の論点に、示した問いの答え、照らし合わせ、結論の選択肢（作る・作らない・保留・代案で始め残る痛みだけを作る）を書いて利用者に問う。利用者が続けると答えたら（作る、代案で始め残る痛みだけを作る）、その応答を論点の決定にして2へ戻る。

build-readyにする前に、`product-plans/<slug>/`の中に、directoryの外へのlinkや、外を見ないと分からない参照（問いのidentifierだけで文面が無い、定石の名前だけで中身が無い等）が無いか、directoryの中のlinkとアンカーが全て辿れるかを確認する。見つかったら、その問いについて`settle-question`へ戻して直させる。

出口判定は、判定した時点の層の決定過程に、`facilitate-discussion`の手順で論点として記録する。提案に出口と理由を書き、利用者の応答を得てから確定する。

### 7. 出口を記録し、還元を促す

正本の「状態」と「出口」の節を書く。出口の節の根拠には、出口判定の論点へlinkする。

- 作らない時は作らない理由を、保留の時は復活する条件を書く。
- build-readyの時は、このdirectoryの写しを新しいリポジトリへ持っていき、初回構築の入力にすることを書く。写しを作ること、名前を変えること、リポジトリを作ることは、利用者が行う。

記録したら、利用者へ`refine-what-defines-a-product`の起動を促す。この1件で分かった問い・水準・定石の過不足を、レールへ戻すためである。

## 利用者へ問う場面

利用者へ問うのは、次の時だけである。

- 受け入れ時（アイデア、動機、既にある着想）
- 層の閉じ
- 出口判定
- `settle-question`が、着想・動機・体験の質感を要する問いに当たった時（`settle-question`が問う）
- `settle-question`が、利用者しか持たない事実（自分の状況、量、試した経験等）を要する問いに当たった時（`settle-question`が認識合わせの論点として問う）

それ以外は、レールが詰める。利用者の頭は、寝かせないと出てこないものだけに使う。
