# grow-product-idea

アイデア1件を、`what-defines-a-product/`の問いに順に答えさせ、出口まで運ぶ。

このskillは進行だけを持つ。問いを立て直して答えること、答えが基準を満たすかの確認は`settle-question`が行う。

## 持つもの

- アイデアの受け入れと、`product-plans/<slug>/`の作成
- 次の問いの選択
- `settle-question`の起動
- 水準の一段目と、`settle-question`の確認の記録があることの確認
- 層の閉じと出口判定での、利用者への確認
- 出口判定と、build-readyの時のdirectoryの外への参照の確認
- 出口記録の後に、`refine-what-defines-a-product`の起動を促すこと

## 持たないもの

- 層ごとの中身（各問いの水準、定石）。全体制御が層の中身を持つと、四層分の知識がここへ集まる
- 問いの立て直し、答えを作ること、書いた答えの漏れの確認（`settle-question`が行う）
- 材料を作ること（材料skillが行う）

## 引くもの

| 引くもの | 場所 |
| --- | --- |
| 問いのセット、問いの選び方、水準の一段目 | `what-defines-a-product/README.md` |
| 各層の問い | `what-defines-a-product/`の四層file |
| `product-plans/<slug>/`の配置と名前 | `product-plans/README.md` |
| 正本の雛形 | [templates/canonical.md](templates/canonical.md) |

正本、決定過程、材料の入口は、file名ではなく役割で扱い、場所は`product-plans/README.md`で引く。

## 流れ

```text
1. 受け入れ（新規）／ 再開
        ↓
2. 次の問いを選ぶ ←──────────────────────────┐
        ↓                                    │
3. settle-questionを起動する                  │
        ↓                                    │
4. 一段目と確認の記録を見る                   │
   ├─ 満たさない → 理由を付けて3へ戻す ──────┤
   └─ 満たす                                 │
        ↓                                    │
5. 層の全問いが閉じたか                       │
   ├─ まだ → 2へ ────────────────────────────┤
   └─ 閉じた → 利用者へ確認 ─────────────────┤
              （why-to-build が閉じた時は6も） │
        ↓                                    │
6. 出口判定 ─ 続ける → 2へ ───────────────────┘
        ↓ build-ready・作らない・保留
7. 出口を記録し、還元を促す
```

### 1. 受け入れ／再開

新しいアイデアの時:

1. 利用者から、アイデア、作りたい動機、既にある着想を受け取る。足りないものだけを利用者へ尋ねる。動機と着想は寝かせないと出てこないものであり、このレールが代わりに作らない。
2. slugを決める。`tumeda-dev`の`name-work-directory`が使える時はそれでアイデアと今日の日付から`YYYYMMDD-slug`を決め、使えない時は同じ形（日付と英小文字のkebab-case）で決める。
3. `product-plans/README.md`に従って`product-plans/<slug>/`を作り、[templates/canonical.md](templates/canonical.md)から正本を作る。受け入れ時の入力は、利用者の言葉を言い換えずに書く。
4. 四層fileの全ての問いを、identifierと文面を写して正本の「問いと答え」へ並べ、状態を未回答にする。

既にある`product-plans/<slug>/`を再開する時は、正本の状態と各問いの状態を読み、2から続ける。

### 2. 次の問いを選ぶ

`what-defines-a-product/README.md`の問いの選び方に従い、閉じていない問いのうち、下位を最も多く規定するものを一つ選ぶ。

- 規定する量は「この問いの答えが変わったら、答え直しになる問いがいくつあるか」で比べる。
- 上位層の問いが閉じていない間は、下位層の問いを選ばない。上位層の問いが下位層の材料（例: 費用の見積りに使う粗いラフ画）を要する時は、`settle-question`が材料skillを直接起動して取りに行く。下位層の問いへ答えを先に確定させると、上位層の答えが変わった時に答え直しになる。
- 迷ったら、各層fileに並んだ順（層fileは下位を最も多く規定する順に並べている）に従う。

### 3. settle-questionを起動する

選んだ問いについて`settle-question`を起動し、`product-plans/<slug>/`の場所と問いのidentifierを渡す。
`settle-question`は、問いをこのアイデアの問いへ立て直し、詰める深さを決め、答え、漏れを確認して戻る。

### 4. 一段目と確認の記録を見る

`settle-question`が戻ったら、次を見る。

- 正本でその問いの状態が「閉じた」になり、確認結果が書かれている
- 問いが挙げる必要な材料の入口（`product-plans/README.md`の材料の入口）が全てある。他の問いの答えを材料にする時は、その問いが閉じている
- 生成系の問いでは、材料に複数案があり、各案が対象の全体（全場面、全画面、全テーブル、全モジュール等、問いの水準が挙げる全体）を覆っている

満たさないものがあれば、何が足りないかを付けて`settle-question`へ戻す。
答えの中身が基準を満たすか（二段目）は見ない。`settle-question`が確認済みである。

`settle-question`が、一般の問いがこのアイデアに合わない（答える意味が無い、別の問いが要る）と返した時は、理由を読み、その問いを飛ばすかを決めて正本に書く。飛ばした問いは、層の閉じで利用者へ示す。

### 5. 層の閉じを利用者へ確認する

ある層の全ての問いが閉じたら、利用者へ確認する。

- その層の問いごとに、このアイデアでの問い（立て直した文面と基準）、答えの要点、決定過程の論点を示す。
- 利用者は論点ごとに応答する。合意した論点は決定になる。修正があれば、その問いについて`settle-question`へ戻す。
- 利用者がその層を受け入れたら、正本の「最後に閉じた層」を更新する。

### 6. 出口を判定する

出口判定は、次の二つの時に行う。

- `why-to-build`の層が閉じた時。`why-to-build/reason-to-build-anyway`の答えが作らない・保留なら、ここで出口へ進む。作るなら、続けて2へ戻る。
- 全ての問いが閉じた時。build-readyへ進む。

build-readyにする前に、`product-plans/<slug>/`の中に、directoryの外へのlinkや、外を見ないと分からない参照（問いのidentifierだけで文面が無い、定石の名前だけで中身が無い等）が無いかを確認する。見つかったら、その問いについて`settle-question`へ戻して直させる。

出口は利用者へ確認してから確定する。

### 7. 出口を記録し、還元を促す

正本の「状態」と「出口」を書く。

- 作らない時は作らない理由を、保留の時は復活する条件を書く。
- build-readyの時は、このdirectoryの写しを新しいリポジトリへ持っていき、初回構築の入力にすることを書く。写しを作ること、名前を変えること、リポジトリを作ることは、利用者が行う。

記録したら、利用者へ`refine-what-defines-a-product`の起動を促す。この1件で分かった問い・水準・定石の過不足を、レールへ戻すためである。

## 利用者へ問う場面

利用者へ問うのは、次の時だけである。

- 受け入れ時（アイデア、動機、既にある着想）
- 層の閉じ
- 出口判定
- `settle-question`が、着想・動機・体験の質感を要する問いに当たった時（`settle-question`が問う）

それ以外は、レールが詰める。利用者の頭は、寝かせないと出てこないものだけに使う。
