# grow-product-idea

アイデア1件を、`what-defines-a-product/`の層に沿って決めて閉じ、出口まで運ぶ。

## 持つもの

- アイデアの受け入れと、`product-plans/<slug>/`と正本の作成
- 次の層の選択と、層を始める時の層の記録の作成
- 層fileの決め方に沿って、層の決めるものを決めること（skillに頼むこと、論点を立てることを含む）
- 層の閉じでの、利用者への確認と、正本への書き込み
- 差し戻しを、順に回すこと
- 出口の判定と記録
- 案件で得た原事例と未処理の改善の手がかりを、既存のレール保守へ渡すこと

## 持たないもの

- 層ごとの中身（何を決めるか、決め方、止める時）。層fileが持つ。このskillは層ごとの分岐を持たない
- 層と層、層とskillの間の決まり。`what-defines-a-product/README.md`が持つ
- 記録の置き方と形。`product-plans/README.md`が持つ
- 専門の仕事（候補と事実と費用、ラフ画等）。skillが行う
- 原事例の原因の確定、共通化とレールの改稿。既存の保守のsteering／task-designが行う
- 閉じた層を開け直すかの判断。返された層が、自分の決め方で判じる

## 引くもの

| 引くもの | 場所 |
| --- | --- |
| 層、層の順、層の状態、層の閉じで示すもの、差し戻し、前提にする条件、skillへの頼み方とskillの一覧 | `what-defines-a-product/README.md` |
| 層ごとの決めるもの、決め方、止める時、層の閉じ | `what-defines-a-product/`の層file |
| 記録の置き方、記録の役割、材料の入口の形 | `product-plans/README.md` |
| 案件から保守へ渡す原事例と、受付・吟味の方法 | このリポジトリのroot READMEの「レールを育てる」 |
| 正本の雛形 | [templates/canonical.md](templates/canonical.md) |
| 層の記録の雛形 | [templates/layer-record.md](templates/layer-record.md) |

## 任意の入力

`build_policy`を、対話又は引渡しの依頼文から受け取る。有効値・既定値・再開と変更時の意味は`what-defines-a-product/README.md`の「開発方針」に従う。新しい必須の質問にはしない。

## 流れ

各stepでskillを用いる時は、下の「skillの処理を受け渡す」に従う。決定を反映しただけ、又は必要なskillを読んだだけで、その後続処理を終えたことにしない。

```text
1. 受け入れ（新規）／ 再開
        ↓
2. 次の層を選ぶ ←──────────────────────────────┐
        ↓                                      │
3. 層を決める（層fileの決め方に沿って）         │
   ├─ 今は得られない不足で正式保留を提案 → 5へ│
   ├─ 後の層の側で、前の層に元があると分かった │
   │    → 6. 差し戻しを回す ──────────────────┤
        ↓                                      │
4. 層の閉じを利用者へ確認する                   │
   ├─ 修正 → 3へ ──────────────────────────────┤
   └─ 受け入れ → 正本に書く ───────────────────┘
        ↓ 作らないへ向かう、または全ての層が閉じた
5. 出口を判定し、記録する
        ↓ 未処理の原事例と手がかりがあれば
   既存のレール保守へ渡す（方法はroot README）
```

### 1. 受け入れ／再開

新しいアイデアの時:

1. 利用者から、アイデア、作りたい動機、既にある着想を受け取る。足りないものだけを利用者へ尋ねる。動機と着想は寝かせないと出てこないものであり、このskillが代わりに作らない。
2. slugを決める。`tumeda-dev`の`name-work-directory`が使える時はそれでアイデアと今日の日付から`YYYYMMDD-slug`を決め、使えない時は同じ形（日付と英小文字のkebab-case）で決める。
3. `product-plans/README.md`に従って`product-plans/<slug>/`を作り、[templates/canonical.md](templates/canonical.md)から正本を作る。受け入れ時の入力は、同READMEの「入力・引用・見立ての区別」に従い、原の文面と話者・記述の区別を保って書く。開発方針の有効値と指定の原文・出典又は未指定であることも、共通READMEの規則に従い正本へ記録する。 受け入れの依頼に、今回の検討・試運転の操作制限が併記されている時は、`what-defines-a-product/README.md`の「今回の作業の操作範囲」に従い、制限の原文と作用先を原入力の近くへ区別して残す。製品の前提にする条件へ自動転記せず、層の検討へ渡す時もこの区別を保つ。 受け入れのblockを保存したら、記録規約の「保存した参照の検査」を通して次へ渡す。

既存案件では、まず正本の状態と出口、今回の依頼と新入力を読む。状況を尋ねただけなら現在の結果と不足を返し、未着手の層へ進めない。

- 検討中: 各層の記録・未決の決定過程、依存する材料の「変えた所」を読み、未処理の根拠の変更を6で回す。確かめ直す必要がある所を受領してから2へ続ける。利用者の応答待ちや単なる作業中断は、この経路から保存済みの未完処理へ戻る
- 保留: 出口にある停止判断と不足・復活する条件を、今回の新入力と照合する。変化がなく条件も未達なら、保留を維持し、理由と必要な入力を返す。同じ未提供の事実を得たことにして検討を繰り返さない。新入力があれば、その差を停止した層・材料へ返し、不足と候補・判断の対応から、どの判断を進められるかを判じる。案件全体の不足が全て埋まるまで一律に待たず、識別子から調べられる公開の事実は専門へ渡し、別候補の未提供の事情は残す。進められる未完判断と利用者の再開指示が揃ったら、再開の根拠と位置を残し、案件を検討中へ戻してその判断から続ける。以前の出口と理由は決定過程へ残し、正本の状態と出口表示を再開後の現在値へ揃える。無関係な未確認を解決済みにせず、閉じた層を一律に開け直さない
- 作らない又はbuild-ready: その出口を完了結果として返す。利用者が選び直し・変更を明示した場合だけ、その理由と新入力を、変わる判断を持つ層へ返す。6で変更の影響を回し、再判断が必要な所から検討中として続ける。以前の出口と理由は決定過程へ残し、正本の状態と出口表示を再開後の現在値へ揃える。未着手のhow-to-buildや閉じた全層を自動的に始めない

既存記録を新規の雛形で作り直さない。受入れの原文に作業の操作制限が混在し、製品側の条件との作用先が分からない時も、同じ共通規則へ照らして確かめる。

### 2. 次の層を選ぶ

1で案件が検討中として続行できることを確認してから、`what-defines-a-product/README.md`の「層」の表の順に、閉じていない最初の層を選ぶ。再開位置が保存済みの未完判断なら、その位置から続ける。次の層は、前の層が閉じてから始める（同じREADMEの「層の順」）。

### 3. 層を決める

1. 層の記録が無ければ[templates/layer-record.md](templates/layer-record.md)から作る（`product-plans/README.md`が定める場所）。既にあれば、入力・経過と未決から継続し、再開や差し戻しで履歴を初期化しない。新しく始める層は「決めている」、開け直す層は6の状態を保つ。
2. 層fileの「何を決めるか」「決め方」「止める時」に沿って、決めるものを決める。決め方の段ごとに出したものを、層の記録のその段に書く。
3. 専門の仕事は、`what-defines-a-product/README.md`の「skillへの頼み方」に従ってskillに頼む。頼んだことは層の記録の「材料への依頼」に書き、返ったものは層の決めるものの形へ読み替える。skillが利用者の事実や別のskillの結果を要ると返した時は、その材料の決定過程の論点を利用者に問い、または別のskillに頼み、答えを渡して続けさせる。
4. 利用者の採否が要る判断、利用者しか持たない事実、発案者の視野の外の点が生じた時は、`tumeda-dev`の`facilitate-discussion`で、層の決定過程に論点を立てる（`product-plans/README.md`の「決定過程の役割」）。 依頼側が渡す発言・資料も同READMEの「入力・引用・見立ての区別」に従い、設定やassistantの整理を利用者の返答へ替えない。
5. 止める時に達したら、層の記録の確認に、層fileの「揃えば満たした」を写し、それぞれ満たしたかと、どこで満たしたかを書く。満たさないものがあれば、その段へ戻る。
6. 材料の返りを渡す前に、下の「現在の記述と根拠を揃えて渡す」で関係するblockの実物を読み戻し、`product-plans/README.md`の「保存した参照の検査」に従って検査する。層の閉じでは、4が定める閉じ提案を決定過程へ先に保存し、受け入れたら正本へ載せる内容とその根拠を提案から辿れるようにする。層の記録の「決めるもの」を保存済みの具体的な提案へ、「状態」を「閉じ待ち」とその論点へのlinkへ更新してから、案件全体を読み戻して検査する。参照が不成立なら提示せず直す。成功後に4の提案を利用者へ提示する。

不足で進めない時は、自力で取得できる事実は必要な専門へ依頼し、利用者しか持たない事実や採否は決定過程の論点で問い、通常の応答待ちを正式保留へ替えない。現在は取得できず判断を進められない不足が残るなら、未閉じの層と止まった判断・不足・復活する条件を残して、5で正式保留を提案できる。層の確認を満たしたことにせず、層の状態は現在の未閉じの状態を保つ。

後の層を決める中で、崩れの元が前の層の側にあると分かった時は、層の記録に、何を見つけ、どの層の何に返したかを書き、6へ進む。

### 4. 層の閉じを利用者へ確認する

`what-defines-a-product/README.md`の「層の閉じ」に従い、利用者へ確認する。層の閉じは、層の決定過程に「層を閉じる」論点（種別: 確認）として立てる。3.6で提案を保存・検査し、ここではその提案への応答を扱う。提案に次を書く。

- 層fileの「この層の閉じ」が挙げるもの、層の決定過程の論点、層が頼んだ材料の決定過程の応答待ちの論点を示す
- 利用者は論点ごとに応答する。合意した論点は決定になる。修正があれば、未採用案を正本へ載せず、その段について3へ戻る。旧提案と応答は残し、新しい閉じ提案の保存後に層の参照を更新して再検査する
- 利用者が層を受け入れたら、その応答と対象の提案を「層を閉じる」論点に残す。受け入れた版の内容を正本の該当節へ書き（正本の各節のcomment「この節を決める層と決めるもの」で引く）、層の記録の「決めるもの」をその節へのlinkへ切り替える。層の記録の状態を「閉じた」と採用論点へのlinkにし、正本の閉じた層の表示を揃えて、案件全体を読み戻し参照を再検査してから次の層へ渡す。途中で中断した時は、保存済みの応答・採用版と実fileを照合し、残る反映から再開する
- 前提にする条件が合意されたら、正本の「前提にする条件」に書く。閉じた層があれば、6で差し戻しとして回す

層の受入れや前提の反映を終えた後も、「現在の記述と根拠を揃えて渡す」を通し、採用前の表示を残したまま次の層へ渡さない。

### 5. 出口を判定し、記録する

出口判定の前に、共通READMEの「開発方針」に照らし、既に選んだ版と候補がある時は、その適格性・出口が有効な指定と一致するか確かめる。一致しなければ選定へ戻し、方針が勝手に変わった出口を確定しない。版を未選定のまま正式保留へ向かう時は、未選定とその不足を残す。未選定そのものを方針違反にせず、開発方針を保持したまま保留を確認する。作る版を採用した扱いにはしない。

出口判定は、次の時に行う。

- どの層でも、現在は得られない不足によって判断を続けられず、3から正式保留を提案する時。層の閉じを前提にせず、利用者が保留を採用したら案件だけを保留とする

- 層の閉じで、層fileが作らない・保留へ向かうとした時（例: どう解くか層で、選んだ選択肢に作る所が無い）
- 全ての層が閉じた時。作る版では、選んだ版を実装・導入できる設計と受渡しまで揃っていることが要る。層fileを定義したことだけを、個別の版の設計の完了にしない。設計の成立に必要な専門材料・判断・裏づけの検証が未完、または必要な層をまだ通していないなら、プロダクトの状態を検討中のままにし、その不足を正本に書く

build-readyにする前に、`product-plans/<slug>/`の中に、directory外のrepository内fileへのlinkや、別のレール文書を見ないと分からない参照（層fileの段の番号だけ等）が無いかを確かめる。外部の公開資料の出典URLは、判断に使う要点と対象・時点・限界を内側へ残したうえで辿れるようにする（`product-plans/README.md`の「directoryの中だけで読み切れるようにする」）。

出口は、利用者へ確認してから確定する。正本の「状態」と「出口」を書く。作らない時は作らない理由を、保留の時は、不足、未閉じの層と停止した判断への案件内の参照、何が変わればどの判断を再開できるかを書く。単なる応答待ちや作業中断では出口を変更しない。build-readyの時は、このdirectoryの写しを新しいリポジトリへ持っていき、初回構築の入力にすることを書く。写しを作ること、名前を変えること、リポジトリを作ることは、利用者が行う。

出口を正本へ記録したら、「現在の記述と根拠を揃えて渡す」を通してから返す。

出口又は正式な保留を記録した後は、root READMEの「レールを育てる」に従い、既に得た原事例と未処理の手がかりを、対応する保守作業又はsteeringの通常の入口へ渡す。分析済みの所はその記録を使い、原因の確定や共通化は保守へ委ねる。引渡しと受付の記録は保守側に置き、製品の正本へ外の保守記録を混ぜない。
案件の成立を妨げる欠けは、その層・材料へ先に返す。成立した製品は共通の改稿の完了まで待たせない。途中の中断をこの引渡しのために保留へ替えず、既にある未処理の手がかりが無ければ引渡しを作る必要は無い。

### 6. 差し戻しを回す

`what-defines-a-product/README.md`の「閉じた層への差し戻し」に従って、順に回す。

1. 返された層の記録へ、何がどこから返ったかを渡す。開け直すかは、返された層が自分の決め方で判じる。判じる時は、その層の決め方に沿って3と同じように行い、このskillは判じない
2. 開け直した時は、層の記録の状態を「開け直し」にし、直して、4で閉じ直す。開け直さなかった時は、対象・根拠と「確かめ直した。変わらない」を残し、待ちにする前の状態と採用・未決の参照へ復帰したことを確かめる。同じ採用の再承認を求めない
3. 閉じ直した層を物差しや入力にしている下の層について、待ちにする前の状態と採用・未決の参照を差し戻しの記録へ残してから「確かめ直し待ち」にし、上から順に、1から同じように回す。正本の閉じた層の一覧・不足・出口の現在表示も、共通READMEの復帰の扱いへ揃える

材料の返し又は再開時の確認で、以前に読んだ根拠の変更が分かった時も、閉じた層を含む影響先へ同じように回す。依頼と材料の対応から、変わる判断だけを確かめ直し、無関係な全層を一律に開け直さない。

差し戻しの受領・再判断・反映を区切って返す時も、「現在の記述と根拠を揃えて渡す」を通す。受領だけ終えたものを、再判断と反映まで終わった表示にしない。

### skillの処理を受け渡す

`facilitate-discussion`からdecisionが返り、その内容を層・材料・正本へ反映した時は、反映した内容・影響の再評価・残る不足を、同じ決定過程の記録ownerへ返す。そのownerが所有する後続処理の返りを受け、継続できると返した範囲で次の判断・層へ進む。記録ownerを作り直さず、その実効指示に従って未完の所から継続する。後続処理の起動条件や内部手順をこのskillへ複製しない。
引継ぎは既存の論点/内部記録と層・材料の返りで対象と結果を追えるようにし、別の適用台帳を作らない。読んだskillの一覧やhash、最後の一括reviewを、その時点の処理の返りに替えない。同じ対象/版で既に完了した処理は再利用し、候補無しという有効な返りも受ける。
必要な実物を取得できない又は処理が未完なら、それに依る引継ぎを止め、不足と戻る所を残す。後で適用漏れを見つけた時も、当時実施したことにせず、漏れが影響する判断へ返して今の再評価を行う。独立した仕事まで全てやり直したり、毎回全skillを再読したりしない。

### 現在の記述と根拠を揃えて渡す

`product-plans/README.md`の「記録の役割」と「材料の入口の形」に従い、保存した実物から、今使う決定・状態と根拠の関係を読み戻す。今回変えた内容に依る正本の概要/状態/出口、層の状態や反映予定の記述、材料の依頼表や成果の説明を辿り、現在の判断・実行結果・受領の出典と一致するかを確かめる。無関係な全履歴の再審査は求めない。
例えば選定の合意と反映が終わったのに概要が未選定、取得済みの材料が実行は次回、反映済みの節が閉じた後に反映すると読めるなら、その出典に基づく現在の記述へ揃える。計画だけの検証を実施済みにせず、採否/反映が未完ならその区別を残す。build-readyも実装/実利用の完了へ替えない。
根拠を訂正した材料は、既存の「変えた所」への記録と、前の姿の近くから現行の根拠へ辿る導線を確かめる。過去の提案/応答/採否そのものは書き換えず、履歴の外側の案内で旧い姿であることを示す。末尾に訂正があることやlinkが到達することだけでは、読み手が今使う値を取り違えない根拠にしない。
食い違いが表示だけなら出典に合わせて直し、保存した実物を読み直す。決める内容や根拠が未確定/変更になるなら、その差を持つ層・材料へ返し、表示だけ直して閉じない。参照の検査とこの照合は区別し、checkerに合否の意味判断を代行させない。
このskillが作成・更新したmdは、渡す前に`document-review`を適用し、その実効指示に従うreviewと必要な修正・再読を終えた実物を渡す。現在表示の照合や参照の成功を、そのreviewの代わりにしない。別ownerが作った材料や決定過程の文書は、そのownerの処理の返りと不足を受け、未完ならownerへ返す。このskillが全ての専門のreviewを代行しない。

## 利用者へ問う場面

- 受け入れ時（アイデア、動機、既にある着想）
- 層を決める中で立った論点（採否、認識合わせ、視野の外の点）。材料の決定過程の論点を含む
- 層の閉じ
- 出口判定

それ以外は、層fileの決め方とskillで詰める。利用者の頭は、寝かせないと出てこないものと、利用者しか持たないものと、利用者が選ぶものにだけ使う。
