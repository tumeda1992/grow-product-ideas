# verify-technical-feasibility

材料`technical-feasibility`を作る。依頼と返し方は`what-defines-a-product/README.md`の「skillへの頼み方」、配置と入口は`product-plans/README.md`に従う。

## 支える判断と、専門の仕事

どの性質が分かれば、依頼側が案・設計を判断できるかを受け、その性質を確かめた事実と限界へ変える。
既存の根拠の調査と、必要な最小限の実行を使う。技術や案を選ばず、確認できた条件・反例・未検証と判断への影響を返す。
正常な一件が動いたこと、文書が述べる仕様、実際の観測、まだ確かめていないことを区別する。

専門の方法は、判断を左右する主張を観測できる条件へ写し、比較と反例を含む検査を組み、観測と解釈を分け、結論を根拠のある範囲へ限ることである。
個人版でも、期待どおりの成功だけを集めず、設計を成立させている仮定が破れる所を確かめる。
必要な性質が資料から分かるなら、形式のためにcodeを書かない。実行が要る性質を、資料に書いてあるはずという推測で埋めない。

検査用のcodeは事実を得るためのものであり、本実装へ育てる基盤ではない。
残るのは、何をどの条件で確かめ、どの設計に何が言えるかという材料である。
実製品に残す構築や運用が必要になったら、それを検証の名で始めず、必要な別の仕事として依頼側へ返す。

## 受け取る問いと、検証する範囲

| 入力 | 確かめることと、不足の返し方 |
| --- | --- |
| 何が分かると、どの判断が変わるか | 設計や案が当てにしている性質と、成立・不成立で変わる所。技術を使いたい理由や採否だけを観測の問題へ替えない |
| 対象と条件、欲しい根拠の粒度 | 技術・API・版・設定・環境・入力の範囲。未選定の対象を便利な模擬へ替えて実対象の事実にしない |
| 既存の根拠と未確認 | 資料・他の材料・実測のどこが今回の主張を支えるか。同じ条件で足りる根拠を再取得するだけの仕事にしない |
| 検査に使える環境・データと操作の範囲 | 何を読め、動かし、変更できるか。依頼と既存の権限で足りる所と、不足する条件を分ける |

問いが曖昧なら、観測したい性質と、答えで変わる設計を示して具体化する。
対象が未定、必要な条件を取得できない場合は、その不足と影響を返す。
利用者の事実や採否は材料の決定過程へ問いを置き、依頼側から答えを受ける。利用者や他のskillへ直接頼まない。

## 確かめる手順

### 判断を変える問いと、主張の範囲を定める

依頼が当てにする性質を、何を対象に、どの条件で、何を観測すれば支えられるかへ写す。
「このAPIは使えるか」「保存は安全か」だけで始めず、例えば、外部の作成結果を手元へ保存できなかった後も、残る情報から対象を照合できるかへする。
成立した時だけでなく、何が反例で、何が分からなければ判定できないかも置く。

主張を分ける必要があるかを見る。
外部の既存予定を一意に照合できることと、同じ要求を再送しても予定が増えないことは別の性質である。
前者を確かめて後者まで保証しない。一方、同じ判断のために関係する複数の観測が要るなら、問いの数を一つに固定しない。

既存の資料と実測を、対象・版・設定・入力と照合する。
資料が述べる仕様、実際に観測した性質、そこからの推論を読み分ける。
今回に必要な根拠で足りるなら、その出典と範囲を使う。足りない条件だけを新たに確かめる。
技術の未確認が無いと判断する場合も、何の根拠でどの範囲に十分かを返す。

### 方法と、比較・失敗の条件を組む

問いを支える入力、期待する観測、対照、反例になる入力と観測点を先に定める。
結果だけを見て期待を合わせないよう、実行前に材料へ残す。
必要な主張を最も直接に確かめる方法を選び、関係しない環境構築や機能を作らない。

| 確かめる性質 | 方法を選ぶ時に落とさない条件 |
| --- | --- |
| 結果不明から対象を照合できるか | 実際に手元へ残る情報だけを回復側へ渡す。検査側が知る正解のIDを渡して代用しない |
| 同じ要求の再実行の性質 | 戻り値だけでなく対象に起きた副作用を観測する。正常の一回と、再実行や中断を区別する |
| 保存の競合と更新のまとまり | 接続・transaction・入力を読む順と書く順を指定し、最終の値と拒否の表れ方を観測する |
| 量・時間・上限の性質 | 対象の量・分布・測定区間・環境を定める。一件の計測を全負荷の性能にしない |

これは全項目を毎回検査する指定ではない。今回の判断を支える条件を選ぶ。
正常な条件と、設計が崩れる条件を同じ問いへ当てる。
観測に使う正解の根拠と、検査される処理が使ってよい入力を分ける。

外部への操作は、依頼と既存の許可・規約の範囲へ照らす。
実アカウントやデータ、費用・送信・削除等の作用がある時は、その操作まで許可されているかを確かめる。
未許可の作用や規約に反する手段で確かめず、公式の根拠、検査用の環境・データ等で同じ問いを確かめられる方法を探す。
代替では主張を確かめられない場合は、未実施の理由・探した方法・不足する条件を具体に返す。安全な模擬で動いたことを実対象の成立へ替えない。
既に許可された局所の実行や読取りへ、機械的な追加の許可待ちを作らない。

### 条件を記録して確かめ、観測と解釈を分ける

対象と版・設定、実行する入力、観測する場所と結果を対応させて調査又は実行する。
検査用のcodeや必要な付随fileは、その材料のdirectoryへ置いて入口から結ぶ。
秘密の値はfileや実行logへ書かず、必要な場合は環境変数等で渡す。再現には値自体でなく、必要な設定と取得元の役割を示す。

外部予定の例では、正常に作成し返った外部IDで取得できても、結果保存前の停止から照合できる根拠にはならない。
停止を起こし、回復側には保存が間に合った情報だけを残す。外部に対象があることは別の観測で確認し、その正解を回復側へ混入させない。
似た題名等の別の予定がある場合も、誤って選ばないかを問う。
照合に要る根拠を外部に残せるかも対象であり、存在を確認していないfieldや仕組みを都合よく置かない。

保存の例なら、二つの接続が同じ前提を読んだ後に更新する順を記録する。
前提付き更新があるか、読取りを含むtransactionか等の条件を変えれば、更新件数0、競合・ロックのエラー等、拒否の表れ方が変わり得る。
「二つとも成功しない」と「必ず0件で返る」を同じ主張にせず、実際の結果と、処理側が受け取る必要な意味を返す。

検査の出力が得られない時は、次を区別する。

| 観測したこと | 結論へ使える範囲 |
| --- | --- |
| 前提を満たす入力で期待する性質が破れた | その対象と条件における反例。広い成立の主張は修正する |
| 認証・接続・検査用の環境が足りず対象へ届かない | 取得できていない。技術そのものが不可能とは結論しない |
| 検査用codeが誤り、又は違う分岐へ届いた | 方法の不備。今回の主張の証拠にせず直して確かめる |
| 模擬・仮の対象だけで成功した | その模擬や仮の条件の結果。実対象へどの前提が未確認かを残す |

観測と予想が違えば、その結果を保存して主張・方法・設計への影響を見直す。
都合の悪い結果を捨てて成功例だけを結論にしない。

### 残せる事実と限界を、次の判断へ返す

何の性質を、どの対象と条件で確かめたかを先に示し、観測・根拠・結論・限界を繋ぐ。
確認できた結果、反例、未取得、追加の条件があれば使える所を分ける。
一回の成功を全ての入力や将来の環境へ広げず、調べていない境界を明示する。

結果が案や設計の何に効くかも返す。
例えば、前提付き更新は古い入力を拒否したが、拒否がロックのエラーとして出る条件があるなら、機能側にはその結果をどう識別し再判断へ繋ぐかの検討が要る。
照合できない、実証できない場合は、どの情報や外部の性質が欠け、どの機能・構成が依れなくなるかを返す。
別の方法で確かめられる又は既存の案の別条件なら成立し得る場合も、取得した根拠と未確認を分けて示す。代替案をその場で採用しない。

本実装や運用の完成を返すのではなく、依頼側が判断できる事実の範囲を返す。
費用・範囲・人の負担を変える必要が出たら、その差を示す。技術の結果から利用者の価値や採否を勝手に決めない。

## 返す材料と、止める線

材料の入口の「中身」と「確かめた方法と限界」へ、今回の判断に必要な根拠を繋ぐ。
付随codeや観測の記録がある時は同じ材料へ置き、再現に必要な条件と手順を入口から辿れるようにする。

- 判断に使う問いと主張、対象・条件・既存の根拠と未確認
- 実施前の期待・対照・反例になる条件、使った方法と実際に届いた範囲
- 入力・環境・観測した結果、そこから言える事実と反例・限界
- 残る不足、答えが変える設計、必要な追加の条件と実施できなかった理由

依頼の判断に使える範囲が確かまった所、又は確かめられない条件を具体に返せた所で、今回の返しを終える。
返答できたことと、依頼側が必要とする性質を確認できたことは別である。未確認は材料の入口でも確認済みにしない。
必要な根拠が無いまま、この材料の存在だけで版や機能を成立したとしない。

同じ材料を次の依頼で育て、前に読まれた事実の範囲や結論が変わる時は、前の姿・理由と影響する依頼を「変えた所」に残す。
未確認だった所が確認できたことと、前の証拠が支えないと分かった訂正を分け、返しへ影響を添える。

## 水準

| 読み手が出来るべきこと | 満たさない例 |
| --- | --- |
| 判断と検査の主張・条件・観測を対応させられる | 接続が通ったので、結果不明からの復旧も可能と書く |
| 正解の観測と、回復に使える情報を分けられる | 成功応答のIDが失われる検査で、そのIDを回復側へ渡す |
| 性質の違いと、条件で変わる結果を見分けられる | 照合できたので再送も重複しないとする。更新0件という結果を全transaction条件へ広げる |
| 未取得・方法の不備と、技術の反例を区別できる | 認証できないので技術的に不可能とする。別の分岐の成功を根拠にする |
| 事実と限界から次の設計を判断できる | 模擬APIの結果で実APIを保証する。対象・版・入力・設定が無く確かめ直せない |
| 検証を採否や本実装へ拡張せず返せる | 動いたcodeを基盤として育てる。技術の成功からその案の採用を決める |

表記や参照なら直して見直す。問い・観測の対応や検査の条件が破れている場合は、結果の説明を足して繕わず検査の方法へ戻る。

## 持たないもの

- 価値・範囲、技術やサービス・案の採否、費用の見積りや候補探索
- 本実装、実製品の基盤づくりや運用、検証を口実にした設計や規則の無断変更
- 依頼の権限を超える外部操作、規約に反する手段での実行
- 利用者への直接の問い、他のskillへの直接の依頼

必要な条件と粒度を返し、確かめた事実が他の材料と設計の判断で使えるようにする。
