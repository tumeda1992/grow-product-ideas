# propose-alternatives

材料`alternatives`を作る。頼まれ方と返し方は`what-defines-a-product/README.md`の「skillへの頼み方」に、置き方と入口の形は`product-plans/README.md`に従う。

## この材料の目的

対案を挙げることである。依頼された状態と条件を、どの道でどこまで覆えるかを、行い・根拠・費用と残る不足を持つ比較材料として差し出す。
全体に届く道だけでなく、独立した改善が成立する部分案も育てる。元の目標と条件を物差しに保ち、今回の改善、残る未達と負担、まだ確かめていない所を分ける。
部分案を選ぶために条件を弱めたり、専門が届ける版を先に決めたりしない。

対案から一つを選ぶのは、依頼した側である。この材料は選ばない。費用は対案を比べる軸の一つであり、目的ではない。

## 使う側

依頼した側は、何のための依頼かを、次の「何のため」から名乗る。

| 何のため | 読むもの | 求める粒度 |
| --- | --- | --- |
| 作らずに覆えるかを見る | 非開発の道で、全体のどこまで届くかと残る未達 | 強い非開発の対案と、その成立条件・覆えない所 |
| 覆う点ごとに、作らない道を含む候補と、候補の事実を見る | 覆う点ごとの候補と、その条件での達成範囲・未確認 | 候補×状態の表。各点で非開発の道を検討し、候補又は成立しない理由・不足を含む |
| どの道で覆うかを選ぶために、道ごとの費用を出す | 依頼された候補又は既存の版の、作る・続ける費用と根拠・差 | 同じ対象・比較期間の費用。再見積もりなら変更した部品・行いと前の値との差 |
| 依存するあり物の規約と継続性を見る | 候補の規約・安全と、今も使えるか | 候補ごとの事実と出典 |
| 状態ごとに、作るもので覆うか、外に置くかを決める | 対案ごとの、状態ごとの手段 | 対案ごとの、状態ごとの手段と作る時間 |
| 作る部分を部品ごとに見積もる | 作る部分の部品ごとの三点 | 区切りの案ごとに足し合わせられる程度 |

依頼の目的から、今回行う範囲を選ぶ。候補探索なら3〜5と必要な事実・費用へ進み、既存候補の規約等だけなら4、構成が育った後の再見積もりなら既存の対案と根拠を引き継いで6を行う。
既に足りる材料は再利用し、全段をやり直すための利用者への質問や新しい候補の作成を足さない。選んだ範囲に必要な入力と不足を確かめ、今回返す所へ水準を当てる。

## 入力

| 入力 | 渡すもの | 足りない時 |
| --- | --- | --- |
| 覆う状態と、must・betterの線、状態の条件（例: 期限の何日前に、誰に） | 依頼した側。mustは全体で要る改善、betterは追加で良くする点であり、全候補にmustの充足を課す意味ではない。検討中の条件なら仮の比較条件と出典を受け、採用済みの条件と区別する | 状態が機能の形で書かれている、代案を見た後で寄せられている、条件が曖昧、のどれかなら、分解し直さず、何が足りないかを付けて依頼した側へ返す |
| 今回比べる範囲・制約と、既存の候補・材料 | 依頼した側。未選定なら、全体案と部分案を比べるための対象場面・使える時間や費用等を受ける。異なる目標の候補を比べる依頼は、候補ごとの状態・仮定と共通の比較範囲を受け、全てが同じ目標を採用済みとは扱わない | 分からない所と答えで変わる比較を返す。範囲を自分で採用せず、既存の案や事実で足りる所は育てる |
| 比較の出発点と根拠 | 改善の有無を比べる依頼では、原状の同じ一件と出典、依頼側が構成した基準、そこで加える人の行い。原状と基準が同じならまとめて受ける | 既存の体験/材料から読める所は再利用し、差を変える不足だけを依頼側へ返す。費用だけの更新へ全場面の作成を要求しない |
| 体験と価値（痛みがある場合はその構造も）と、作ることで得たいもの | 依頼した側の正本。未採用の比較では、依頼側の検討記録にある価値候補と原文・根拠、その比較で確かめたい問いを受け、未採用と明示する | 内容が無ければ依頼した側へ返す。未採用という理由だけで既にある比較材料を拒まない |
| 前提にする条件、受け入れ時の着想 | 依頼した側（正本） | 無ければ無いものとして扱う |
| 既に分かっている利用者の事実（出どころが何を見せ、誰が見られるか等） | 依頼した側 | 無ければ、下の「利用者の事実を返す」で問う |
| 他の人の経験・しのぎ方と候補への着想 | 材料`target-user-voices`の経験・着想、出典と文脈・適用限界（ある時だけ。固定の内部節名は要求しない） | 必要な経験が無ければ、何の候補・成立条件を判断できないかを依頼した側へ返す。勧めは着想として残せるが、実際に続いた根拠にはしない |
| 作る部分の形 | 材料`experience-sketch`、`core-logic`、`implementation-structure`、`technical-feasibility`（ある分だけ） | 見積りに要る粒度に足りなければ、何がどの粒度で要るかを付けて依頼した側へ返す。別のskillへ直接頼まない |

## 利用者の事実を返す

今回の判断が利用者しか持たない事実に依る時は、その不足を返す。既存の記録と根拠で足りる事実を再び問わない。このskillは利用者へ直接問わない。問いたいことと、答えで材料のどこが変わるかを、この材料の決定過程（`product-plans/README.md`が定める場所）に論点として立て、依頼した側へ返す。依頼した側が利用者に問い、答えを同じ論点に残す。答えを受け取ってから続ける。

| 事実 | なぜ要るか | いつ返すか |
| --- | --- | --- |
| 利用者が普段使う道具と、その使い方 | 今の行いの中で続けられる候補を探す根拠になる。道具の利用だけで継続を保証しない | 候補探索で不足する時。既存案の費用だけの依頼へ一律に要求しない |
| 今のしのぎ方（紙、家族の決まり、記憶の分け方を含む） | 最小の変更や残る負担を比較する出発点になる | 今回の探索や行いの見積りに必要な所が不足する時 |
| 過去に作ったものの、作る前の見立てと実際にかかった時間 | 作る時間の見積りを補正する根拠になる | 作る時間を見積もる前 |

答えが得られないまま進める時は、得られなかった事実と、それで弱くなった所（例: 補正していない見積りは楽観に寄る）を「確かめた方法と限界」に書く。推測で埋めない。

## 作る手順

次は全体の経路であり、今回実行する段は上の依頼の目的から選ぶ。

```text
1. 入力を確かめる（足りなければ返す）
2. 今回の判断に不足する利用者の事実だけを返し、答えを得る
3. 候補を探す（切り口を選んで使う）
4. 候補の事実を確かめ、候補×状態の表にする
5. 覆い方の対案を組む
6. 対案ごとの費用を出す
7. 水準で漏れを確かめる
```

### 3. 候補を探す

一つの型を毎回当てない。次の切り口を候補として持ち、件ごとに選んで使う。

毎回使う切り口:

| 切り口 | 中身 | 毎回使う理由 |
| --- | --- | --- |
| 今のしのぎ方から少しずつ変える | 今のやり方を出発点に、状態ごとに最小の変更を足す | 最も安い対案が出やすい |
| 毎日の道具の側から | 利用者が毎日開いている道具の、まだ使っていない機能を状態に当てる | 最も続く対案が出やすい |
| 何もしない | 今のまま続けた時に、状態ごとに何が起きるか | 全ての対案を比べる基準になる |

件の手がかりで選ぶ切り口:

| 切り口 | 中身 | 選ぶ手がかり |
| --- | --- | --- |
| 失敗の原因から逆算する | mustの状態ごとに、今なぜ満たせていないかの原因を出し、原因を外す手段を探す | 痛みの原因が一つに絞れる（情報が一人の頭にしかない等） |
| 似た痛みの別の領域から借りる | 同じ構造の痛みを持つ別の領域のやり方を借りる（例: 期限付きの権利の失効なら、図書館の返却期限、ポイントやクーポンの失効、薬の残数） | 痛みの構造が、期限、残数、順番待ち、分担のような、領域を越えてある形をしている |
| 両端から挟む | 何もしない、やり方だけ変える、全部人に任せる、全部自動にする、を先に置き、間を埋める | 候補が一つの方向（全て道具、全て作る等）に寄っている |
| かける時間の段で出す | 5分、1時間、1日、1週末、数週末でできる道を一つずつ出す | 作る道とあり物の道の間の、中くらいの道が欠けている |
| 前提を外す | 要求の状態が置いている前提（規則は変えられない、ある作業は自分たちがする、家の中で閉じる）を一つずつ外す | 痛みが一人に寄る、相手（教室、店、職場）の決まりから来ている |
| 着想の反証から | 受け入れ時の着想が要らないとする、最も強い主張を作る | 着想が道具の形（「通知が来ればいい」等）で強く書かれている |
| 他の人の経験から | `target-user-voices`のしのぎ方、良い体験や別の領域の行いを候補への着想にする。経験の根拠と対象との違いを保つ | 覆う状態や、続く条件を捉え直す経験・着想がある |

経験の材料を使う時は、誰が何を契機に何をしたという報告か、勧め・機能の説明から得た着想かを分け、候補のどこへ使ったかを出所とともに残す。
別の人が使った一回を、本件でも続く保証へ替えない。
例えば「共有calendarがよい」という勧めは候補に残せるが、家族が自ら取り込み・引き受け続けた実績としては使えない。
現在の機能・規則・費用は4で確認し、本人の事情や必要な経験の不足は依頼側へ返す。
別のskillへ直接頼まない。

探す時は、次の手段の種類を手がかりにする。製品の名前から探さない。

- やり方を変える（作業をやめる、減らす、時期をずらす）
- 担う人を変える（家族の担当、相手に頼む）
- 物理的な道具（紙、ホワイトボード、置き場所）
- 既に使っている道具の設定
- 汎用の道具（表計算、ノート、共有カレンダー、フォーム、リマインダー）
- 自動化・小さなscript
- 専用サービス

どの切り口を使い、どれを使わなかったかを、理由とともに一行ずつ材料に残す。読む人が、探していない方向を知れるようにするためである。

全体を覆う道を探す中で、費用・時間・人の行いのどこが負担を増やし、どこを変えると別の改善が成立するかも探る。
対象の場面や期間、担い手、あり物と作る所の分担を動かし、何を今回は変え、どこへ元の負担を残すと、誰の一巡がどう良くなるかを描く。
「狭く・中くらい・広く」や機能数だけで区切らず、その件の具体の場面と成立に必要な前後の行いへ戻す。
例えば学校と教室の両方が対象でも、学校の原本受領から引受け・提出までを変える道は、教室の負担を残す部分案として比較できる。
学校の対応を間に合わせる改善をいうなら、通知を受けた人の判断と対応まで繋ぐ必要がある。
気づくこと自体が今回の改善なら、誰がいつ何に気づけ、それによって残る負担がどう変わるかを示す。
いずれも通知機能の存在だけで改善を数えない。

mustの状態は全ての手段の種類を手がかりに探し、betterは、依頼の比較を変える所を、得るものと払うものの差に結ぶ。
部分案にも必要な行い・根拠・未達を持たせ、全体へ届く案・部分的に届く案・現状維持の間の重要な差を比べられる所まで育てる。
新しい切り口で比較を変える有力な道が出るなら探索へ戻る。取れる事実の答えで候補の成立や比較が変わるなら、4の確認へ進む。
範囲を変えても独立した改善が成り立たないなら、その理由を返し、部分案の数を揃えるために弱い案を作らない。

### 4. 候補の事実を確かめる

組み合わせの対案が崩れるのは、候補が「その機能を持つ」けれど「状態が求める条件では動かない」時である。候補ごとに、次を確かめる。

| 確かめること | 例 |
| --- | --- |
| 状態の条件で覆うか | 表計算の通知は、編集された時やフォームが送られた時に動くもので、日付が近づいたことでは動かないかもしれない。共有カレンダーの通知は、予定を作った人だけでなく共有した相手にも届くか |
| 状態を保つために、誰が、いつ、何をする必要があるか | 共有カレンダーは、欠席のたびに誰かが予定を作る。ホワイトボードは、誰かが書き換え、誰かが毎日見る |
| 規約・安全で当たるもの | アカウントを家族で共有してよいか。子どもや他人の情報を外部のサービスへ送るか。自動操作が禁じられていないか |
| 今も使えるか、費用と上限 | 提供を終えた手段（例: LINE Notifyは2025年3月末で提供を終えた）。無料で送れる数、料金の改定 |

事実は、公式の文書・料金や規約のページ、許可された範囲の実際の結果で確かめ、対象と時点・出典を残す。第三者の記事だけなら、その限界を示す。
動作・停止・再実行等の技術の性質が比較を変えるなら、必要な問い・条件と既存の根拠を依頼側へ返し、技術の専門の結果を受ける。文書の期待だけを実証にしない。
未許可の外部作用や規約に反する手段は行わず、取得できない条件と理由・比較への影響を返す。利用者自身の環境の事実が必要なら材料の決定過程に問いを置き、依頼側から答えを受ける。
不足ごとに、それが必要な候補・判断と取得先を分ける。本人しか持たない識別子を得た後、公開資料から調べられる性質まで本人への未回答の質問として残さない。
一部の入力で進める候補は調べ、別候補だけに要る不足を引き続き返す。対象・時点が分からないまま店舗の在庫等を創作しない。

確かめた事実を、候補×状態の表にまとめる。行は候補、列は要求の状態とし、その条件で覆う／一部／覆わない／未確認と、根拠と理由を書く。
一部なら、どの対象・場面では覆い、どこに既知の未達が残るかを示す。未確認なら、何の事実が足りず、答えでどの判定が変わるかを示す。
一つの状態の中に既知の未達と未確認があれば、その場所を分ける。未知の効果・仕様を、承知して受け入れる損失へ置き換えない。
複数の状態をまとめて覆う候補と、前後の行いが足りず他の候補を組にしないと成立しない所が見えるようにする。

### 5. 覆い方の対案を組む

原文や選んだ価値が重く見る将来・撤収が今の選択で変わる場合、段階の候補を同じ時系列へ当てる。次へ持ち越せる物・根拠、再参加・再許諾・再収集と費用、回復不能な差を示す。最初の体験が同じでも、匿名で破棄する案と任意の再連絡手段を残す案は同じ将来を持たない。後で選べるとする根拠も返し、将来のために現在から最大の機能を作る義務にはしない。

候補を、今回の改善に必要な前後の行いが繋がる対案へ組む。
次の比較対象を吟味し、成立する強い道を残す。同じ道が複数の役割を果たす場合は重複させず、件数を揃えるための案は作らない。

| 比較対象 | 作る材料と、成立しない場合の返し |
| --- | --- |
| 何もしない | 現状を続けた時の行い・負担・失う機会を、比較の基準にする。保留の採否は依頼側へ返す |
| 全体のmustを覆う道 | 作る量と費用を抑える強い道を、非開発・組合せ・作る道から探す。成り立つ根拠が無ければ、その不足又は反例を返し、完全案を捏造しない |
| 作らない道の有力な対案 | やり方・あり物・人の分担を組み、全体又は部分のどこまで届くかを出す。全体へ届かないことだけで除かない |
| 独立した改善を届ける部分案 | 対象の一部又は別の分担で、一巡が成立する改善と、残る未達・負担・費用を示す。機能を削っただけの案を部分改善に数えない |
| 受け入れ時の着想どおりの道 | 比較から外さず、成立の根拠と得失を他の案と同じに調べる。着想が無ければその旨を示す |

組む時は、件の手がかりから次の方法を選ぶ。

| 組み方 | 中身 | 選ぶ手がかり |
| --- | --- | --- |
| 一つの置き場所に寄せる | 一つの道具（カレンダー、表計算、ホワイトボード等）を置き場所にし、その一つでどこまで覆えるかで組む | 置き場所の候補が、利用者の毎日の道具にある。置き場所が二つになると二か所への入力が継ぎ目になり、手間と食い違いが溜まる |
| 触る人の分け方で組む | 状態を保つ操作を、一人だけ／二人とも／誰も触らない（自動）のどれに置くかで組む | 痛みの核心が、誰か一人に寄ること |
| 作る部分の境目から組む | あり物で覆いにくい状態だけを作り、残りをあり物に任せる | あり物で覆いにくい状態が一部にある（日付で知らせる、規則から計算する等） |
| 移る道として組む | 作らない道で始め、足りなくなったら次の道へ移る順番として組む。移る時に記録を持ち越せるか、移る判断の目安を書く | どの道も決め手を欠く |

対案の違いは、同じ入力・状態を当てた時、誰がどの価値・機会を得て、何の損失・負担を引き受けるか、又はそれを決める基準の差から確かめる。置き場所、触る人、作るかは、その差を探す軸の例である。
例えば同じ受付担当・申込書・台帳を使っても、先着順と待機期間を優先する配分は、同じ申込群で利用機会を得る人が変わるため別の対案になる。逆に計算順だけ変えて結果・負担・失敗の性質が変わらないものを、比較の件数を増やすために分けない。
他の対案より全ての点で劣る対案（全ての状態の覆い方も、手間も、費用も劣る）は外し、外した理由を一行残す。どちらも他を全ての点で上回らない対案は、両方残す。

対案ごとに、次を書く。

- 今回、誰のどの場面がどこまで変わるか。全体の条件ごとの達成範囲と、残す未達
- 状態ごとの手段（作る／あり物／やり方を変える／運用／我慢）と、置き場所・継ぎ目
- 受け取るもの、担い手ときっかけ、判断・操作と外の行い、終わったと分かる根拠。その改善に必要な一巡
- 覆えない・弱い所と、誰にどんな痛み・負担が残るか。確かめた根拠、前提と未確認、次に必要な事実

改善を主張する場面は、原状・基準・候補へ同じ入力と出来事を当てる。既にできること、共通して残る仕事、候補で減る/増える行い・負担・失敗等を、依頼側が差を追える形で返す。原状の行いは出典へ結び、基準に新たに足した運用と、候補の処理の効果を分ける。表の形式や全候補×全場面の詳細化は固定せず、比較を変える差を辿る。
例えば、原状で既に変更希望を伝えているなら、同じ希望を文章へする機能だけで「希望が伝わるようになる」とは返さない。整理の迷い/往復が減る仮説を残すなら、必要項目を既存の連絡へ足す基準と、候補へ入力/貼付け/更新する一巡を比べ、差を支える根拠と追加負担を示す。
同じ終点でも、作業量・失敗の違いや明示された制作目的に値打ちはあり得る。差が未確認なら何の場面で何を比べるかを返し、既知の改善へ替えない。未確認というだけで候補を無価値として削らず、実験版として何を確かめるかの採否を依頼側へ渡す。

一巡の途中で人や情報が抜けたら、必要な候補を組み直すか、成立の不足として依頼側へ返す。
分からない所を「運用で対応」や我慢の一語で塞がず、既知の未達と区別する。
原本を一度渡すだけの手間と、全件を仕分け催促し続ける役割を、同じ人の負担という名前へ丸めない。
費用と行いは、同じ対象場面・期間で比較できるよう次の6へ渡す。

### 6. 対案ごとの費用を出す

手持ち資金・前払い・保証金・返金又は精算の時差が候補の可否を変える時は、誰がいついくら払い、いつ何を条件に戻るかと根拠を辿る。期間の純支出と、返金前に必要になる主体別の最大立替額・拘束期間を分けて返す。不確かな返還は戻らない／遅れる枝でも必要額を見る。別主体の支払・分割払いを使うならその合意を根拠にし、予算が期間総額だけの案件に新たな台帳を一律に作らない。

時間を共通の軸にし、時間にできないものを決まった列で並べる。全てを時間に換算しない。換算すると、頭に残る負担や作る楽しみが消えるか、根拠の無い換算になる。

| 列 | 中身 | 出し方 |
| --- | --- | --- |
| 作る時間 | 作る部分の時間。楽観・最も確か・悲観の三点 | 下の「作る時間の見積り方」 |
| 続ける時間 | 比較する期間で状態を保つ操作と保守の時間 | 行いごとの時間と、その期間の回数・頻度の根拠。導入の一回分と反復を分け、未知の頻度を年52回等で埋めない |
| きっかけの無い操作 | 覚えていないとできない操作と、それを誰が担うか | 操作を、きっかけがある（欠席の連絡、通知）か、覚えていないとできない（毎週末に見る、見る習慣）かで分ける。頭に残る負担を、時間に換算せずに観察できる形にする |
| 忘れた時の損失 | 操作を忘れた時に起きることと、起きやすさの見立て | きっかけの無い操作がある道ほど起きやすい、を根拠に書く。数字にする時は前提を書く |
| お金 | 代金、外部サービスの費用 | 候補の事実 |
| 得たいもの | 作ることで得たいもの（作る楽しみ、学び等）のどれを満たすか | なぜ作るか層の答え |

依頼された版・対象場面と同じ比較期間を使う。三週の試行なら三週、継続版を比べるなら根拠のある期間を置く。年への換算は回数・季節差等の根拠がある時だけ行い、未知の量は範囲又は未確認で返す。
回数や時間は、何を一回と数え、どの行い・経路を含めた値かと結ぶ。想定した経路の見積り、実測、根拠のある上限を区別し、対象を同じにしたまま修正・再試行・確認等が一つ増える場合を当て、含まない行いと未確認の量を示す。例えば成立手18件ごとの正常な追記/再実行を18組と見積もっても、不正入力の修正や理由の編集を含む全操作の最大18回とは返さない。
上限を主張するなら、その範囲で追加の行いが増えない又は打ち切られる根拠を示す。三点の悲観値や一度の実測を、そのまま上限にしない。利用者の予算/打切り条件も、完了に必要な量の保証とは分け、打切りで未達になる結果・残る行いを採否へ返す。新しい打切りをこちらで採用しない。
未知の追加量は0にせず、どの行いの何が未知で、その差が比較をどう変えるかを返す。全例外の頻度の確定を候補づくりの条件にはせず、条件付きの見通しと、試して観測する量を区別する。費用の表の近く又は辿れる根拠に示し、新しい台帳や固定列は一律に求めない。
構成の詳細化で増減した部品・配置・設定・連携・訂正・復旧と継続の行いを拾い、前の見積りから何が変わったかを示す。既存の単価や過去補正は使える範囲で再利用し、変えた値と依った依頼は共通の変更通知へ繋ぐ。

作る時間の見積り方:

1. 作る部分を部品に分けて積む。部品は、ラフ画や心臓部ロジックに描かれたものに加えて、描かれにくい部品を必ず見る。描かれにくい部品は、利用者の見分け（認証、合言葉）、置き場所への配置と設定、外部サービスとの連携、定期実行、失敗した時の扱い（届かなかった通知、止まった定期実行）、データの修正の手段、である。
2. 部品ごとに三点（楽観・最も確か・悲観）で出し、合計の幅を書く。
3. 利用者の過去の見立てと実績が得られた時は、それと比べて補正する。個人の計画は楽観に寄りやすいため、見立てより実績がどれだけ延びたかで直す。得られない時は、補正していないことと、その分だけ楽観に寄っていることを書く。

## 水準

今回返す仕事へ、該当する次の水準を当てる。費用だけの更新へ新しい全候補を要求せず、再利用した案と根拠を明示する。依頼全体へ不足する仕事があれば、満たした扱いにせず依頼側へ返す。

- 切り口: 毎回使う三つの切り口を使い、件の手がかりで選んだ切り口と選ばなかった切り口が、理由とともに書かれている。
  - 満たさない例: 「習い事 振替 管理 アプリ」のように、製品の名前だけで探している。
- 候補の事実: 候補ごとに、状態の条件で覆うか、状態を保つ操作、規約・安全、今も使えるかが確かめられ、出典がある。
  - 満たさない例: 「表計算で管理できる」。日付で知らせることができるか（状態の条件）、誰が何を入力し続けるか（状態を保つ操作）が無い。
- 候補×状態の表: 一つの候補がどの状態をまとめて覆うかが見える。
  - 満たさない例: 候補ごとに「痛みのどこが残るか」を一行ずつ書いた表。組み合わせが見えない。
- 対案: 現状維持・全体へ届く道・有力な非開発案・部分案・着想を吟味し、成立する道又は成り立たない理由・必要な不足を示す。 改善を主張する所は、同じ一件の原状/基準/候補の差とその根拠が辿れ、基準に加えた運用の効果と候補の増分を混ぜていない。同じ道の重複を除き、互いの前提と得失の違い、劣る対案を外した理由がある。
  - 満たさない例: 「狭く取る・主要な場面を一通り・周辺まで含める」。どの件にも当てはまる区切りであり、この件の状態をどの手段で覆うかになっていない。
  - 満たさない例: 着想や何もしない基準を検討せず落とす。全体へ届かないという理由だけで、独立した改善のある部分案を除く。
  - 満たさない例: 「通知だけ作る」を部分案と呼ぶが、誰の何が改善するかと、そのために必要な行い・根拠が無い。「条件の4%」という数だけで価値を説明する。
  - 満たさない例: 原状で既に届いていた連絡を比較から落とし、文章生成や通知を加えて初めて届く改善と数える。
  - 満たさない例: 技術や効果が未確認なのに、既知の未達として引き受ければ成立すると書く。
- 費用: 同じ対象・比較期間で時間と時間にできない列を読み分けられ、作る時間は部品ごとの三点と補正の有無、継続は行い・回数と根拠がある。数値の単位と含む行い、想定値/実測/上限の別、含まない追加の行いと未知を読み分けられる。再見積もりは前の値との差と影響する依頼を辿れる。
  - 満たさない例: 「作る時間 約16時間」。内訳も幅も補正の有無も無い。
  - 満たさない例: 正常な18成立手だけを数え、修正や再実行も含む全操作を「最大18回」とする。悲観6時間と予算6時間が同じだから、完了まで必ず収まるとする。
  - 満たさない例: 「妻の負担が大きい」。どの操作が、きっかけ無しに覚えておく必要があるのかが無い。
- 選ばない: 対案から一つを選ぶ結論を書いていない。
  - 満たさない例: 「P4が最もよい」。選ぶのは依頼した側である。比べて見えること（例: ある対案は時間だけで並べると安く見えるが、きっかけの無い操作が残る）は書いてよい。

漏れが局所的（言い回し、出典の欠け）なら直して確かめ直す。骨子の漏れ（切り口が偏っている、対案の前提が同じ、状態の条件を確かめていない）は、その手順へ戻って作り直す。

## 書き方

`product-plans/README.md`の材料の入口の形に従い、「中身」は次の節から今回の依頼で使う所を書き、再利用する案と根拠へ結ぶ。候補の事実だけ又は再見積もりだけなら、その節と関係する差・不足を更新する。未実行の節を空欄で揃えたり、今回全段を完了した形にしたりしない。

```markdown
## 中身

### 入力と前提
（全体の覆う状態とmust・better、状態の条件、今回の比較範囲・制約、利用者の事実と返して得た答え。改善を比べる時は原状の一件と出典、基準で加える行い）

### 候補の事実
#### 使った切り口と使わなかった切り口
#### 候補
（候補ごとの事実と出典。既知の未達と、根拠が不足する未確認を区別する）
#### 候補×状態

### 覆い方の対案
（対案ごとの、今回の改善と達成範囲、成立する一巡と根拠、手段・置き場所と継ぎ目、残る痛み・負担と未達、前提・未確認。外した対案と理由）

### 対案ごとの費用
（列の表。作る部分の部品ごとの三点）
```

同じ材料に別の依頼が来て、覆う状態の切り方が変わった時は、前の切り方の節を消さずに、新しい節を足す。節の名前に、何で切ったかを入れる（例: 候補×状態（S1〜S8）、候補×補う点）。前の依頼が読んだ所を変える時は、入口の「変えた所」に書く（`what-defines-a-product/README.md`の「前の依頼が読んだ所を変える時」）。

## 持たないもの

- 対案から一つを選ぶこと（依頼した側が行う）
- 覆う状態の分解を作り直すこと（依頼した側へ返す）
- 作る部分の設計そのもの（ラフ画は`sketch-experience`、心臓部は`design-core-logic`）
- 利用者へ直接問うこと（材料の決定過程に論点を立て、依頼した側へ返す）
- 別のskillへ直接頼むこと（依頼した側へ返す）
