# propose-alternatives

材料`alternatives`を作る。受け取るもの、粒度、再利用は`what-defines-a-product/README.md`の「材料」節に、置き方と入口の形は`product-plans/README.md`に従う。

## この材料の目的

対案を挙げることである。作りたいものを、要求の満たされた状態（must・better）ごとに、どの道で覆えるかの対案として差し出す。

対案から一つを選ぶのは問い（`settle-question`）である。この材料は選ばない。費用は対案を比べる軸の一つであり、目的ではない。

## 使う側

| 要求する問い | 問いが材料から読むもの | 求める粒度 |
| --- | --- | --- |
| `what-to-build/existing-alternatives-fall-short` | 作らない道（やり方を変える、あり物、組み合わせ）でmustを覆えるか | 作らない道の対案と、その覆えない・弱い所 |
| `what-to-build/solution-shape` | 作る道を含めた対案のうち、どれで覆うか | 一部作る・全部作るを含めた対案と、対案ごとの費用 |
| `what-to-build/risks-of-building` | 選んだ道が依存するあり物の規約・継続性 | 候補の事実の規約・安全と、今も使えるか |
| `what-to-build/scope-in-and-out` | 状態ごとに、作るもので覆うか、外（あり物、運用、我慢）に置くか | 対案ごとの、状態ごとの手段 |
| `how-far-to-build/first-build-cut` | 作るもので覆う状態の、どれを先に作るか | 作る部分の部品ごとの見積り |
| `how-far-to-build/build-cost-pays-off` | 選んだ道の費用が、作らない道に見合うか | 対案ごとの費用を、最初に作る分の粒度で |

この表は今の問いのセットに合わせている。問いのセットは見直し中であり（steeringの論点18・提案7）、変わった時はこの表を直す。

## 入力

| 入力 | どこから | 足りない時 |
| --- | --- | --- |
| 要求の満たされた状態と、must・betterの線、状態の条件（例: 期限の何日前に、誰に） | `what-to-build/requirements`の答え | 状態が機能の形で書かれている、代案を見た後で寄せられている、条件が曖昧、のどれかなら、分解し直さず、何が足りないかを付けて`settle-question`へ返す |
| 痛みと、作ることで得たいもの | なぜ作るか層の答え | `settle-question`へ返す |
| 前提にする条件、受け入れ時の着想 | 正本 | 無ければ無いものとして扱う |
| 他の人のしのぎ方 | 材料`target-user-voices`の「今どうしのいでいるか」 | 親や同じ立場の人のしのぎ方が無ければ、`target-user-voices`の漏れとして`settle-question`へ返す |
| 作る部分の形 | 材料`experience-sketch`、`core-logic`、`technical-feasibility`（ある分だけ） | 見積りに要る粒度に足りなければ`settle-question`へ返す |

## 利用者の事実を返す

この材料は、利用者しか持たない事実が無いと強い対案が出ない。材料skillは利用者へ問わない。問いたいことと、答えで材料のどこが変わるかを付けて`settle-question`へ返し、`settle-question`が認識合わせとして問う。答えを受け取ってから続ける。

| 事実 | なぜ要るか | いつ返すか |
| --- | --- | --- |
| 利用者（と一緒に使う人）が毎日開いている道具と、その使い方 | 一番強い対案は、既に毎日開いている道具の中で済む道である。探す範囲そのものが変わる | 最初。候補を探す前 |
| 今のしのぎ方（紙、家族の決まり、記憶の分け方を含む） | 「今のしのぎ方から少しずつ変える」切り口の出発点になる | 最初 |
| 過去に作ったものの、作る前の見立てと実際にかかった時間 | 作る時間の見積りを補正する根拠になる | 作る時間を見積もる前 |

答えが得られないまま進める時は、得られなかった事実と、それで弱くなった所（例: 補正していない見積りは楽観に寄る）を「確かめた方法と限界」に書く。推測で埋めない。

## 作る手順

```text
1. 入力を確かめる（足りなければ返す）
2. 利用者の事実を返し、答えを得る
3. 候補を探す（切り口を選んで使う）
4. 候補の事実を確かめ、候補×状態の表にする
5. 覆い方の対案を組む
6. 対案ごとの費用を出す
7. 水準で漏れを確かめる
```

### 3. 候補を探す

一つの型を毎回当てない。次の切り口を候補として持ち、件ごとに選んで使う。

毎回使う切り口:

| 切り口 | 中身 | 毎回使う理由 |
| --- | --- | --- |
| 今のしのぎ方から少しずつ変える | 今のやり方を出発点に、状態ごとに最小の変更を足す | 最も安い対案が出やすい |
| 毎日の道具の側から | 利用者が毎日開いている道具の、まだ使っていない機能を状態に当てる | 最も続く対案が出やすい |
| 何もしない | 今のまま続けた時に、状態ごとに何が起きるか | 全ての対案を比べる基準になる |

件の手がかりで選ぶ切り口:

| 切り口 | 中身 | 選ぶ手がかり |
| --- | --- | --- |
| 失敗の原因から逆算する | mustの状態ごとに、今なぜ満たせていないかの原因を出し、原因を外す手段を探す | 痛みの原因が一つに絞れる（情報が一人の頭にしかない等） |
| 似た痛みの別の領域から借りる | 同じ構造の痛みを持つ別の領域のやり方を借りる（例: 期限付きの権利の失効なら、図書館の返却期限、ポイントやクーポンの失効、薬の残数） | 痛みの構造が、期限、残数、順番待ち、分担のような、領域を越えてある形をしている |
| 両端から挟む | 何もしない、やり方だけ変える、全部人に任せる、全部自動にする、を先に置き、間を埋める | 候補が一つの方向（全て道具、全て作る等）に寄っている |
| かける時間の段で出す | 5分、1時間、1日、1週末、数週末でできる道を一つずつ出す | 作る道とあり物の道の間の、中くらいの道が欠けている |
| 前提を外す | 要求の状態が置いている前提（規則は変えられない、ある作業は自分たちがする、家の中で閉じる）を一つずつ外す | 痛みが一人に寄る、相手（教室、店、職場）の決まりから来ている |
| 着想の反証から | 受け入れ時の着想が要らないとする、最も強い主張を作る | 着想が道具の形（「通知が来ればいい」等）で強く書かれている |
| 他の人のしのぎ方から | `target-user-voices`の、同じ痛みを持つ人が実際にやっていることを候補にする | 声に、しのぎ方が集まっている |

探す時は、次の手段の種類を手がかりにする。製品の名前から探さない。

- やり方を変える（作業をやめる、減らす、時期をずらす）
- 担う人を変える（家族の担当、相手に頼む）
- 物理的な道具（紙、ホワイトボード、置き場所）
- 既に使っている道具の設定
- 汎用の道具（表計算、ノート、共有カレンダー、フォーム、リマインダー）
- 自動化・小さなscript
- 専用サービス

どの切り口を使い、どれを使わなかったかを、理由とともに一行ずつ材料に残す。読む人が、探していない方向を知れるようにするためである。

止めるのは、表を埋めた時ではなく、新しい切り口を使っても、mustを覆う新しい候補が出なくなった時である。mustの状態は全ての手段の種類を手がかりに探し、betterの状態は、mustを覆う候補がついでに覆うかを見る程度にとどめる。

### 4. 候補の事実を確かめる

組み合わせの対案が崩れるのは、候補が「その機能を持つ」けれど「状態が求める条件では動かない」時である。候補ごとに、次を確かめる。

| 確かめること | 例 |
| --- | --- |
| 状態の条件で覆うか | 表計算の通知は、編集された時やフォームが送られた時に動くもので、日付が近づいたことでは動かないかもしれない。共有カレンダーの通知は、予定を作った人だけでなく共有した相手にも届くか |
| 状態を保つために、誰が、いつ、何をする必要があるか | 共有カレンダーは、欠席のたびに誰かが予定を作る。ホワイトボードは、誰かが書き換え、誰かが毎日見る |
| 規約・安全で当たるもの | アカウントを家族で共有してよいか。子どもや他人の情報を外部のサービスへ送るか。自動操作が禁じられていないか |
| 今も使えるか、費用と上限 | 提供を終えた手段（例: LINE Notifyは2025年3月末で提供を終えた）。無料で送れる数、料金の改定 |

事実は、公式の文書、料金や規約のページ、実際に触った結果で確かめ、出典を書く。第三者の記事だけの時は、その旨を書く。確かめること自体が規約・安全に触れる時（例: ログインが要るページの自動取得）は動かさず、`verify-technical-feasibility`の「確かめる行為のリスクを見る」と同じ扱いで、確かめていないことを書いて返す。

確かめた事実を、候補×状態の表にまとめる。行は候補、列は要求の状態とし、マスには、その状態の条件で覆うか（覆う／一部／覆わない）と、その理由を書く。一つの候補が複数の状態をまとめて覆うことが、この表で見えるようにする。

### 5. 覆い方の対案を組む

毎回、次の四つを置く。

| 対案 | 置く理由 |
| --- | --- |
| 何もしない | 比べる基準 |
| mustを最も安く覆う道 | 作る量を最も減らせる道を、比べる対象に必ず入れる |
| 作らずにmustとbetterを覆う道（組めれば） | 作らない道の上限を見せる |
| 受け入れ時の着想どおりの道 | 利用者の着想を比べる対象から外さないため。着想を特別扱いするためではない |

その上に、件の手がかりで次の組み方を選んで足す。

| 組み方 | 中身 | 選ぶ手がかり |
| --- | --- | --- |
| 一つの置き場所に寄せる | 一つの道具（カレンダー、表計算、ホワイトボード等）を置き場所にし、その一つでどこまで覆えるかで組む | 置き場所の候補が、利用者の毎日の道具にある。置き場所が二つになると二か所への入力が継ぎ目になり、手間と食い違いが溜まる |
| 触る人の分け方で組む | 状態を保つ操作を、一人だけ／二人とも／誰も触らない（自動）のどれに置くかで組む | 痛みの核心が、誰か一人に寄ること |
| 作る部分の境目から組む | あり物で覆いにくい状態だけを作り、残りをあり物に任せる | あり物で覆いにくい状態が一部にある（日付で知らせる、規則から計算する等） |
| 移る道として組む | 作らない道で始め、足りなくなったら次の道へ移る順番として組む。移る時に記録を持ち越せるか、移る判断の目安を書く | どの道も決め手を欠く |

対案は、互いに少なくとも一つの前提（置き場所、触る人、作るか）が違うものにする。他の対案より全ての点で劣る対案（全ての状態の覆い方も、手間も、費用も劣る）は外し、外した理由を一行残す。どちらも他を全ての点で上回らない対案は、両方残す。

対案ごとに、次を書く。

- 状態ごとの手段（作る／あり物／やり方を変える／運用／我慢）
- 置き場所と、継ぎ目（二か所への入力、手で写す所）
- 触る人と操作
- 覆えない・弱い所

### 6. 対案ごとの費用を出す

時間を共通の軸にし、時間にできないものを決まった列で並べる。全てを時間に換算しない。換算すると、頭に残る負担や作る楽しみが消えるか、根拠の無い換算になる。

| 列 | 中身 | 出し方 |
| --- | --- | --- |
| 作る時間 | 作る部分の時間。楽観・最も確か・悲観の三点 | 下の「作る時間の見積り方」 |
| 続ける時間 | 状態を保つ操作の時間と、保守の時間（年あたり） | 候補の事実の「状態を保つ操作」×年の回数。保守は依存先の変化への追従、不具合、データの手当て |
| きっかけの無い操作 | 覚えていないとできない操作と、それを誰が担うか | 操作を、きっかけがある（欠席の連絡、通知）か、覚えていないとできない（毎週末に見る、見る習慣）かで分ける。頭に残る負担を、時間に換算せずに観察できる形にする |
| 忘れた時の損失 | 操作を忘れた時に起きることと、起きやすさの見立て | きっかけの無い操作がある道ほど起きやすい、を根拠に書く。数字にする時は前提を書く |
| お金 | 代金、外部サービスの費用 | 候補の事実 |
| 得たいもの | 作ることで得たいもの（作る楽しみ、学び等）のどれを満たすか | なぜ作るか層の答え |

作る時間の見積り方:

1. 作る部分を部品に分けて積む。部品は、ラフ画や心臓部ロジックに描かれたものに加えて、描かれにくい部品を必ず見る。描かれにくい部品は、利用者の見分け（認証、合言葉）、置き場所への配置と設定、外部サービスとの連携、定期実行、失敗した時の扱い（届かなかった通知、止まった定期実行）、データの修正の手段、である。
2. 部品ごとに三点（楽観・最も確か・悲観）で出し、合計の幅を書く。
3. 利用者の過去の見立てと実績が得られた時は、それと比べて補正する。個人の計画は楽観に寄りやすいため、見立てより実績がどれだけ延びたかで直す。得られない時は、補正していないことと、その分だけ楽観に寄っていることを書く。

## 水準

この材料は、次を満たす。書いた後に、ここに照らして漏れを確かめる。

- 切り口: 毎回使う三つの切り口を使い、件の手がかりで選んだ切り口と選ばなかった切り口が、理由とともに書かれている。
  - 満たさない例: 「習い事 振替 管理 アプリ」のように、製品の名前だけで探している。
- 候補の事実: 候補ごとに、状態の条件で覆うか、状態を保つ操作、規約・安全、今も使えるかが確かめられ、出典がある。
  - 満たさない例: 「表計算で管理できる」。日付で知らせることができるか（状態の条件）、誰が何を入力し続けるか（状態を保つ操作）が無い。
- 候補×状態の表: 一つの候補がどの状態をまとめて覆うかが見える。
  - 満たさない例: 候補ごとに「痛みのどこが残るか」を一行ずつ書いた表。組み合わせが見えない。
- 対案: 毎回置く四つがあり、互いに前提が違い、劣る対案を外した理由がある。
  - 満たさない例: 「狭く取る・主要な場面を一通り・周辺まで含める」。どの件にも当てはまる区切りであり、この件の状態をどの手段で覆うかになっていない。
  - 満たさない例: 受け入れ時の着想どおりの道、または何もしない道が無い。
- 費用: 時間の軸と、時間にできない列が揃い、作る時間が部品ごとの三点で、補正の有無が書かれている。
  - 満たさない例: 「作る時間 約16時間」。内訳も幅も補正の有無も無い。
  - 満たさない例: 「妻の負担が大きい」。どの操作が、きっかけ無しに覚えておく必要があるのかが無い。
- 選ばない: 対案から一つを選ぶ結論を書いていない。
  - 満たさない例: 「P4が最もよい」。選ぶのは問いである。比べて見えること（例: ある対案は時間だけで並べると安く見えるが、きっかけの無い操作が残る）は書いてよい。

漏れが局所的（言い回し、出典の欠け）なら直して確かめ直す。骨子の漏れ（切り口が偏っている、対案の前提が同じ、状態の条件を確かめていない）は、その手順へ戻って作り直す。

## 書き方

`product-plans/README.md`の材料の入口の形に従い、「中身」を次の見出しで書く。

```markdown
## 中身

### 入力と前提
（要求の状態とmust・better、状態の条件、利用者の事実と、返して得た答え）

### 候補の事実
#### 使った切り口と使わなかった切り口
#### 候補
（候補ごとの事実と出典）
#### 候補×状態

### 覆い方の対案
（対案ごとの、状態ごとの手段、置き場所と継ぎ目、触る人と操作、覆えない・弱い所。外した対案と理由）

### 対案ごとの費用
（列の表。作る部分の部品ごとの三点）
```

## 持たないもの

- 対案から一つを選ぶこと（`settle-question`が行う）
- 要求の分解を作り直すこと（要求の問いへ返す）
- 作る部分の設計そのもの（ラフ画は`sketch-experience`、心臓部は`design-core-logic`）
- 利用者へ直接問うこと（`settle-question`へ返す）
