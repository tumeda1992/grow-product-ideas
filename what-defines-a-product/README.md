# what-defines-a-product

プロダクトのアイデアを、作り始める前に決めるべきことが全部決まった状態（build-ready）まで詰めるための層を持つ。

層は、決めるものと、その決め方を持つ。層fileは、層ごとの中身（何を決めるか、決め方、止める時、限界）を書く。このREADMEは、層と層、層とskillの間の決まりを書く。アイデアごとの記録の置き方と形は、[product-plans/README.md](../product-plans/README.md)に書く。

## 層

| 層の識別と呼び名 | file | 決めるもの |
| --- | --- | --- |
| `why-to-build`：価値・アウトカムの探究 | [why-to-build.md](why-to-build.md) | 体験と価値、アウトカム、作ることで得たいもの |
| `what-must-hold`：達成条件の定義 | [what-must-hold.md](what-must-hold.md) | 満たすべき条件 |
| `how-to-solve`：解決策・提供範囲の探索と選定 | [how-to-solve.md](how-to-solve.md) | 解き方の選択肢、今回届ける版と受け入れる未達・損失・費用・負担を含む選定 |
| `how-to-build`：選んだ版の実現設計 | [how-to-build.md](how-to-build.md) | 実装・導入へ渡す設計 |

独立した「どこまで作るか」層は設けない。今回届ける版と作る境界の選定はhow-to-solveが持ち、その版を実装・導入できる設計へ具体化する仕事を「どう作るか」が持つ。
how-to-buildは、人や既存道具の行いも含む選んだ版、その成立に必要な条件、受け入れた未達・損失・費用・負担と選定理由を受け取る。その版に必要な専門材料を揃え、実装・導入へ渡す設計を決める。
層fileがあることと、個別の版の設計が成立したことを分ける。設計の成立に必要な材料・判断・裏づけの検証が不足する版は、build-readyにしない。

### 選ぶ版と、実装・導入の設計の境界

| 決める仕事 | 持つ所 |
| --- | --- |
| 今回誰にどの改善を届け、何を後へ回すか、何の未達と損失を受け入れるか | how-to-solveの選定。費用と運用の負担も含めて、その版として選ぶ |
| 機能を作るか既存道具・人の運用へ任せるか | how-to-solveの選定。頻度・負担・崩れやすさと残る価値を比べる |
| 選んだ版の体験・情報・処理・外部との接続と、導入・修正・復旧の具体 | どう作るか。選んだ解き方と運用が実行できる設計へ具体化する |
| 実装中に変えてよい設計上の裁量と、変えるなら再判断する既決事項 | どう作るかの引継ぎ。実際の実装作業の権限は、その作業の指示に従う |

実装や検証を技術上の段に分けることと、利用者へ届ける版の範囲を変えることを分ける。
前者はどう作るかで扱えるが、後者で新しい未達や負担を受け入れるならhow-to-solveへ返し、その差だけを再選定する。
独立層を減らしても、旧い「最初の分」「費用」「運用」「AIへ任せる線」にあった仕事を省かない。選んだ版の画面・情報・処理と、導入・修正・復旧、設計の裁量と再判断する境界は、how-to-buildの方法で具体化する。
初回構築の実装計画と実行は、後続のsteering／task-designへ渡す。このレールでは、それが依拠する設計上の境界と前提を揃える。

## 開発方針

`build_policy`は案件を受け入れる時の任意指定であり、採用できる版の範囲を決める。実装の許可や実装済みの状態を表すものではない。

| 有効値 | 選定と出口での扱い |
| --- | --- |
| `open`（未指定の既定値） | 作る版と非開発の道を比較し、作らないという結論も選べる |
| `require-build` | 版全体に実質のある作る部分を含める。作る部分の無い案を採用して「作らない」へ閉じない |

作る前提を明確に指定した自然言語の依頼も`require-build`として受け、原文と有効値を正本に残す。「作れたら嬉しい」等の希望からこの指定を推測しない。未指定は毎回確認せず`open`を使い、未知の指定値や曖昧な指示は勝手に別値へ読み替えない。

`require-build`でも、whyの価値の発散と収束、whatの達成条件の導出、解き方と費用の比較は行う。規模の上限・下限、全部か一部か、新規からか既存の仕組みを拡張するか、人や既存道具に任せる範囲は指定で固定しない。各組に新規制作を強制せず、版全体の分担として選ぶ。
「作る部分」は今回選ぶ価値又は明示された制作上の目的へ働く機能・処理等を実装又は実質的に拡張する部分である。利用者が作りたい対象を指定しているならそれに従う。既存道具の上に処理を作る版もあり得るが、非開発の手順に無関係のscriptを添える、既存道具を使うだけなのに制作と呼ぶ等で指定を満たしたことにはしない。

非開発の基準と強い対案は、どの規模・作り方に何を払うかの比較に残す。作る部分が、選んだ価値又は明示された制作上の目的のどこへ働くかを説明できなければ、価値へ繋がる作り方を育て直す。開発の楽しみや節約の効果を利用者の事実として補わない。指定そのものを、楽しみ・学びの目的が合意された証拠にもしない。

費用・技術・入力の不足はこの指定でも消えない。成立する作る版を選べなければ、不足・既知の不成立・必要な判断と復活条件を示して保留できる。部分案でも、その版に必要な行いと条件を繋ぎ、得られない価値と未確認を区別する。指定を理由に予算を超えたり、未達を全体の達成へ変えたりしない。非開発が安いことだけで指定の撤回を繰り返し求めず、規模や解き方の違う作る版を比べる。方針を緩めるのは利用者が明示的に変更した時だけであり、本人の変更なしに`open`へ戻さない。

再開では正本に残した有効値と出典を使う。方針行の無い既存案件は従来の`open`として扱い、過去の入力や決定を書き換えない。途中で方針が変わったら変更の原文を決定過程へ残し、how-to-solveの選定とそれに依る設計・出口を確かめ直す。価値又は条件自体を変える判断が残る時だけ、その差をwhy又はwhatへ返す。

## 層の進め方

### 層の順

次の層は、前の層が閉じてから始める。

前の層の決めるものは、次の層の物差しや入力になる。目標・条件・解き方の正式な採用は各層が持ち、前の層が未閉じのまま後の層を採用済みとして進めない。
目標の優先が実現方法の負担で変わる時は、その目標を選ぶ層の責任で、選択を変える問いだけを専門材料として先に比較できる。whyでは「目標選択のために、必要な方法と負担を予備比較する」に従う。これは目標候補を残した比較であり、whatの条件やhowの解き方の正式な採用ではない。

whatでも、本番条件の校正に実体験が必要な時は同層の「試して初めて決まる最低線を校正する」で専門材料を依頼できる。既知の限定条件で校正の設計・試行を行うことは、未閉じの本番whatを閉じたり後層の解き方を採用したことにはしない。
比較前に、何を重く見るか、どの差なら選択を変えるか、維持する約束と制約、比較の範囲を記録する。作りたい手段を見つけた後で、それが満たしにくい条件を黙って弱めない。比較によって目標や判定の前提を変える必要が出たら、差と理由を示し、その判断を持つ層で選び直す。

how-to-solveでも、比較を左右する体験・規則・情報・構成・技術の問いがあれば、専門材料を必要な粒度で依頼する。細かいラフや技術の根拠を得ただけでhow-to-buildを始めたことにはしない。層は担当する判断で分け、材料の種類・詳しさで分けない。how-to-buildは、選定時の材料と根拠を引き継ぎ、不足する所を育てる。

how-to-solveで費用や成立可能性が分かり、損失を含めて部分案を選ぶことはできる。
先に定めた全体の目標と条件を比較の物差しとして残し、未達を黙って消さず、今回届ける変化と残る痛み・負担を合意する。
その同じ合意で正本と関係する層の記録へ今回の達成範囲を揃え、全体を満たした扱いにせず後工程へ渡す。
部分案を採用するためだけに、既に合意したwhy・what全体を一律にやり直さない。新しい価値や優先、達成範囲に残る判断がある時だけ、そのownerへ返す。

### 層の状態

| 状態 | 中身 |
| --- | --- |
| 決めている | 決め方を進めている |
| 閉じ待ち | 決め方を終え、利用者の応答を待つ論点がある |
| 閉じた | 利用者が、層を受け入れた |
| 開け直し | 閉じた後に差し戻しを受け、直している |
| 確かめ直し待ち | 物差しや入力にしている上の層が変わり、開け直すかを判じる前 |

層の状態は、層の記録に書く。案件の保留は層の合格とは別であり、層が未閉じのままでも選べる。正式保留した時も層の状態はそのまま保ち、案件の状態と不足・停止判断・復活する条件を正本へ残す。
通常の応答待ちや作業中断は、案件の出口を保留へ変更する理由にしない。出口の採否と再開時の分岐は`grow-product-idea`が持つ。

### 層の閉じ

閉じで、利用者は、層fileの「この層の閉じ」が挙げるものを確かめ、論点ごとに応答する。

採否は、その人が決められる範囲に対して有効である。価値を望むこと、案を選ぶこと、別の人が実施を引き受けること、その人の物や発言等の利用を許すことを、同じ応答の根拠にしない。
採否や版の成立を左右する約束・分担について、希望を述べた人、条件を変更できる人、実施・許諾を担う人と、得た根拠の対象・期間を既存の層記録・論点へ結ぶ。代理権や既存の合意があるなら、その範囲で使い、全ての関係者へ一律に問い直さない。

依頼者は自分の案を仮に育て、条件付きで選べる。その選択だけで他者の引受けや許諾を取得したことにはしない。
未取得なら、何が未確認で、どの答えが版の成立・費用・分担を変え、何を確かめるまでどの判断を確定できないかを残す。独立して進められる比較や、自分の権限だけで成立する版は止めない。
将来の実施前に確認する条件へ残せる場合も、誰が何を契機に確かめ、未取得なら何を実施せず、どの判断へ戻すかを持つ。版に不可欠な未確認を残してよいかは各層の既存の閉じの基準に従い、確認した事実として閉じない。

示すのは、層の決定過程の論点に加えて、層が頼んだ材料の決定過程のうち、応答待ちの論点である（層の記録の「材料への依頼」から辿る）。材料の論点が応答待ちの間は、それに依る所を、確かめた事実として扱わない。確かめた事実が要る所では、その事実の両側で書く。

### 閉じた層への差し戻し

閉じた層は、次の時に差し戻される。

| 起き方 | 返す者 | 返す先 |
| --- | --- | --- |
| 後の層の決め方で、崩れの元が前の層の側にあると分かる | 後の層 | 前の層 |
| 材料が、閉じた層の読んだ所を変える | skillが、今の依頼の返しに添える。依頼した層が受ける | 読んでいた層 |
| 前提にする条件が足される | 足された層 | 閉じた全ての層 |

返す先は、変わる判断で分ける。選んだ版の範囲・未達・損失・費用・人の負担の決め手を変える差はhow-to-solve、条件自体の欠けや緩さはwhat-must-hold、価値・アウトカム・測りの変更はwhy-to-buildへ返す。例えば設計で全件の手動照合が増えるなら、行い・頻度・負担と費用の差をhow-to-solveへ渡す。同じ版の設計の中で吸収でき、既決の選定を変えない差はhow-to-buildで扱う。

- 開け直すかは、返された層が、自分の決め方で判じる。返されたものが自分の決めるものの何に効くかを見て、効かなければ開け直さずに、層の記録へ「確かめ直した。変わらない」と書く
- 返す側は、層の記録に、何を見つけ、どの層の何に返したかを書く
- 返された側は、層の記録の状態を「開け直し」にし、「差し戻し」の節に、何がどこから返り、前の姿と直した後を書く。直したら、閉じで利用者と合意し直す
- 直して閉じ直したら、その層を物差しや入力にしている下の層を「確かめ直し待ち」にする前に、各層の直前の状態、採用済みの内容と閉じの応答、未決の提案への参照を既存の「差し戻し」に残す。下の層も、開け直すかを自分で判じる
- 影響なしなら、「確かめ直した。変わらない」と対象・根拠を残し、待ちにする前の状態へ戻す。「閉じた」なら元の採用と閉じの応答を維持し、同じ採用を二重に求めない。「決めている」「閉じ待ち」なら、それぞれ元の未完判断・提案へ戻る
- 変更ありなら変わる決定だけを開け直し、必要な閉じの応答を得る。元の状態や採否の根拠が不明なら、推測で閉じたことにせず、その記録を確かめる

再評価中は、正本の閉じた層の一覧と現在の不足を層の状態へ合わせ、未確認の版をbuild-readyとして渡さない。影響なしの復帰又は閉じ直しを終えた所から一覧を戻し、関係する全判断の確認が済んでから元の出口を維持できるか再判定する。これを新しい出口の合意の捏造には使わない。

正本には今の決めるものだけを書く。前の姿は、層の記録の「差し戻し」の節に残す。

### 前提にする条件

前提にする条件は、利用者が、どの手段にも課す制約である（例: 子どもの情報を、家族の二人以外に見せない）。満たすべき条件と違い、アウトカムの言い分からは出ない。

- 出た層の決定過程で、論点として立てる。利用者が対案を退けた理由のうち、他の選択にも効くものを、利用者に確かめる
- 合意したら、正本の「前提にする条件」に書き、根拠としてその論点へlinkする
- 閉じた層があれば、差し戻しとして回す
- 後の層は、前提にする条件に反する選択肢を、どの条件に反するかを書いて外す

### 今回の作業の操作範囲

依頼に検討・試運転で行う操作の制限が含まれる時は、原文と、それが誰のどの作業・時点に効くかを、受け入れ時の入力の近くへ区別して残す。新しい台帳や全案件共通の必須欄は作らず、既存の原入力・層の「受け取った物差しと前提」から辿れるようにする。

| 制限の対象 | 判断へ渡す意味 |
| --- | --- |
| 今回のagent/検査の操作 | 購入・外部送信・本番反映を今回は行わない等。その禁止は守るが、製品で届けたい価値や実利用で必要な行いを、対象外にする理由にはしない |
| 製品又は選ぶ版の行い | 自動決済しない、外部送信の機能を持たない等。効く手段や担い手へ反映する。人や既存道具が担う道もあり、これだけで目標の価値を削らない |
| 利用者が選ぶ目標の範囲 | 今回は入手/送達までを目指さず判断/下書きだけの価値を選ぶ等。whyで得失と選択理由を吟味し、今回届ける版の未達の選択ならhow-to-solveで扱う |

「購入はしない」等で対象が曖昧なら、語だけから製品の前提又は検査の制限へ読み替えない。その解釈で目標・候補・実行の可否が変わる時は、原文と両方の意味を示して確認する。既に対象が明確な入力を毎回問い直す必要はない。
検査の禁止により実在庫・送達等の根拠を取得できない所は、検証未実施/未確認として次へ渡す。製品の価値が不要になったことや、その実現が不可能な証拠にはしない。目標・版・設計を変える差がある時は、上の差し戻しのownerへ返す。

## skillへの頼み方

### skillの立ち位置

skillは、層が頼む外部の専門家である。依頼した側の判断とは別の専門の判断を持ち、選ばずに並べ、誰がどの粒度で読むかを自分で知り、同じ結果を粗いものから細かいものへ育てる。

依存は、層からskillへの一方向である。層は、skillに何を頼めるかを知る。skillは、層の名前も決め方も知らない。

### 頼む時に渡すもの

層は、skillの言葉で頼む。層の決めるものを、skillの入力の言葉へ写すのは層である。

- 何の判断に使う依頼か（skill一覧と、そのskillが受け取る入力の言葉で）
- 調べる・描く・設計する対象と条件、今回の範囲・未達・制約、既存の材料と根拠。費用等の比較では対象場面と比較期間も渡す
- 既に分かっている利用者の事実
- 粒度

頼んだことは、層の記録の「材料への依頼」に書く。skillは、受けた依頼を、材料の入口の「依頼と粒度」に書く。

### 返ったものの読み方

層は、返った形を、自分の決めるものの形へ読み替える。skillの出す形を、層の形に合わせさせない。層が持つのは、受け取る時の基準（層fileの決め方の「揃えば満たした」）であり、skillのやり方ではない。基準を満たさない時は、何が足りないかを付けて頼み直す。

層が依った値（決め手の境目の作る時間等）は、層の記録に読み込み、対象・条件・期間と根拠の箇所へ結ぶ。未確認や不足を返せたことと、その性質や条件を満たしたことを分ける。細部は材料の入口の節を指す。

### skillが、利用者の事実や別のskillを要る時

- skillは、利用者へ直接問わない。問いたいことと、答えで材料のどこが変わるかを、その材料の決定過程に論点として立て、依頼した側へ返す。依頼した側が利用者に問い、答えを同じ論点に残して、skillに続けさせる
- skillが別のskillの結果を要る時は、依頼した側へ返す。依頼した側が、別のskillに頼む。skillどうしで直接頼むと、どの層が何のために、どの粒度で作らせたかが、層から見えなくなる

### 前の依頼が読んだ所を変える時

材料を育てる時は、過去の根拠と採否を残して今の返りを明示する。以前の依頼が読んだ所を変える時は、材料の入口の「変えた所」に、前の姿・理由・影響する依頼を残し、今の依頼側へ差を添える。
今の依頼側は、閉じた層を含め、その材料に依った判断へ「閉じた層への差し戻し」を回す。前の層の作業が終わっていることだけを、知らせない理由にしない。
案件が中断中で受け取る側が動いていない時は、影響する依頼と未処理の差を同じ「変えた所」に残し、再開時に受領してから続ける。専門が以前の採否を勝手に変更したり、外部へ連絡したりはしない。
