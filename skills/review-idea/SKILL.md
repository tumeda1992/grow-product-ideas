# アイデアの完成度を確認する

入力はアイデアディレクトリ。基準は [進め方](../../playbook/workflow.md) の完了状態。レビューだけの依頼では設計を書き換えず、指摘を返す。育成中は育成担当が修正と再確認まで行う。

## 確認するもの

`README.md` と現在の `proposal.md` を読み、引用される `evidence.md`、`decisions.md` と照合する。自作または導入の設計がある場合は `design.md` と `handoff.md` も読む。実在しないリンクや古い仕様を根拠にしない。

次を具体的な場面と数値で確認する。すべての案件に同じ文書量を要求しない。

| 確認 | 通過できない例 | 修正の方向 |
| --- | --- | --- |
| 要求が解決手段から独立している | 「AI 機能が必要」だけ | 現状・困る場面・望む結果へ戻す |
| 自作の必然を比較した | 競合名だけ、実用可能な組み合わせが未検討 | 必須要求と同一条件で有力案を比較 |
| 根拠の強さが正直である | 想定ペルソナを需要の証拠とする、未閲覧料金を確定扱い | 事実・仮説を分け、判断への影響を記す |
| コスト比較が対称である | 自作の保守がゼロ、時間と現金を無断合算 | 同じ期間・規模で再計算し逆転条件を確認 |
| 到達点が観測できる | 「いい感じ」「使いやすい」だけ | 主場面と失敗時の合否を例にする |
| 体験と構造がつながる | 画面に出す値の保存元がない、二箇所が同じ値を書き換える | データの生涯と書込責務を通して修正 |
| 引き継ぎが単独で使える | 「詳細はチャット」「バックエンドは適当に」 | 読み順、境界、裁量、相談条件を明示 |
| 状態が正しい | 重要な仮置きを残して build-ready | 依存部分を確認待ちにし共通部分は完成 |

## レビューのやり方

まず推奨案を支持する読み方をやめ、次善案を選ぶとしたらどの前提が崩れるかを考える。その前提が実際に確認されているかを追う。次に主場面と最も構造を揺さぶる失敗場面を、要求 → 入出力 → 保存 → 処理 → 合格例までたどる。自作しない案には不必要な DB や画面設計を要求せず、設定・接続・運用の成立を追う。

レビューする費用計算は再計算する。判断に効く外部情報は参照元と条件を確認し、古い料金や利用条件なら再調査する。文書があることと実際に検証したことを分ける。

指摘は「重要な判断を変える」「今回の範囲で修正できる不整合」「許容できる改善」に分け、対象箇所、問題の具体例、影響、必要な対応を書く。ユーザーしか解決できない指摘は未決事項 ID に結び付ける。件数ゼロを目指して些末な改善を延々増やさない。

## 結果

育成の一環では `review.md` に、対象ファイルと版を特定できる更新日または commit、実行した確認、未実行の確認、指摘と解消状況、推奨状態を記録する。レビューのみなら同じ内容を返答し、保存は依頼されている場合に行う。

重要な未決事項または重要な未解消指摘があれば build-ready／導入準備完了としない。将来の需要検証や許容済み負債は、その失敗時の対処と観測条件があれば分離して残せる。

自己レビューを独立レビューやユーザー確認と呼ばない。実装も動作も検証していない場合は明記する。
