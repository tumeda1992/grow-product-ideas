# アイデアの完成度を確認する

入力はアイデアディレクトリ。基準は [進め方](../../playbook/workflow.md) の完了状態と [重点検証](../../playbook/verification.md)。レビューだけの依頼では設計を書き換えず、指摘を返す。育成中は育成担当が修正と再確認まで行う。

## 確認するもの

`README.md` と現在の `proposal.md` を読み、引用される `evidence.md`、`decisions.md` と照合する。自作または導入の最終判定では `design.md` と `handoff.md`、重点検証の結果と参照成果物も読む。必要なものが未作成なら途中レビューとして扱い、完成判定を出さない。見送りでは設計・引き継ぎの欠落を指摘しない。実在しないリンクや古い仕様を根拠にしない。

次を具体的な場面と数値で確認する。すべての案件に同じ文書量を要求しない。

| 確認 | 通過できない例 | 修正の方向 |
| --- | --- | --- |
| 解く問題を適切に絞った | 最初に思いついた主場面だけを調査 | 有力な別解釈と、選択が変わる条件を比較 |
| 要求が解決手段から独立している | 「AI 機能が必要」だけ | 現状・困る場面・望む結果へ戻す |
| 自作の必然を比較した | 競合名だけ、実用可能な組み合わせが未検討 | 必須要求と同一条件で有力案を比較 |
| 根拠が原文を超えていない | 出典にない失敗や動機を証拠 ID に混ぜる | 推奨・棄却・成立条件の各主張を原文・閲覧箇所へ逆引き |
| コスト比較の入力が正しい | 予算を見積に転用、利用時間を落とす | 数値の役割と作業内訳・幅・出典を確認してから再計算 |
| 到達点が観測できる | 「いい感じ」「使いやすい」だけ | 主場面と失敗時の合否を例にする |
| 体験と構造がつながる | 画面に出す値の保存元がない、二箇所が同じ値を書き換える | データの生涯と書込責務を通して修正 |
| 重要な場面を選べている | 共有なのに脱退・同時更新を検討していない | 原文と案件の特徴からリスクを選び直す |
| 検証が問いに答えている | 操作負担を画面名で評価、核の出力品質を試行なしで確定 | 代表・境界入力の結果と限界を確認 |
| 導入手順が実在する | 既製品に未確認の画面・自動判定を設計している | 製品機能の出典、人の操作、未確認の挙動を分けて通す |
| 引き継ぎが単独で使える | 「詳細はチャット」「バックエンドは適当に」 | 読み順、境界、裁量、相談条件を明示 |
| 状態が正しい | 重要な仮置きを残して build-ready、調査を残して確認待ち | 自律作業が残れば育成中。独立作業を終えて外部の回答・検証だけを待つなら確認待ち |

## レビューのやり方

まず原文から有力な問題の解釈と案件の特徴を取り出し、現在案が捨てた解釈や選び漏れたリスクを探す。次善案を選ぶとしたらどの前提が崩れるかを考え、その前提が実際に確認されているかを追う。現行案に書かれた要求だけを検査対象にしない。次に主場面と重点リスクから選んだ失敗場面を、要求 → 入出力 → 保存 → 処理 → 合格例までたどる。自作しない案には不必要な DB や画面設計を要求せず、設定・接続・運用の成立を追う。

費用計算の前に、入力の役割と根拠を照合する。許容8時間から見積8時間を導いていたら、算術が正しくても差し戻す。工数幅が許容上限を超えうるのに無条件で採用していないか、推奨の逆転条件を確認する。判断に効く外部情報は参照元と条件を確認し、古い料金や利用条件なら再調査する。

必要な検証について、入力・対象版・事前の合格条件・観測結果があるか確認する。未実施を合格と数えない。期間や合否の数値が判断に必要な理由と、もっと軽い確認で足りないかも見る。未決事項を本人にしか答えられないもの、公開調査で解けるもの、上位判断後だけ必要なものに分け直し、自律作業が残るのに確認待ちとしていないか確かめる。受取確認で残る判断と、後回しにしたリスクが重要でないといえる理由も読む。検証後に設計が変わっていれば、結果の適用範囲を再評価する。

指摘は「重要な判断を変える」「今回の範囲で修正できる不整合」「許容できる改善」に分け、対象箇所、問題の具体例、影響、必要な対応を書く。ユーザーしか解決できない指摘は未決事項 ID に結び付ける。件数ゼロを目指して些末な改善を延々増やさない。

## 結果

育成の一環では `review.md` に、対象ファイルと版、実行した確認、未実行の確認、指摘と解消状況、推奨状態を記録する。版は対象ファイルの内容ハッシュまたは対象内容が入った commit で特定する。作業ツリーの変更があるのに基点 commit だけを対象版にしない。review.md 自身と最終状態だけの更新をハッシュ対象へ含めて循環させない。レビューのみなら同じ内容を返答し、保存は依頼されている場合に行う。

重要な未決事項または重要な未解消指摘があれば build-ready／導入準備完了としない。将来の需要検証や許容済み負債は、その失敗時の対処と観測条件があれば分離して残せる。

自己レビューを独立レビューやユーザー確認と呼ばない。実装も動作も検証していない場合は明記する。
