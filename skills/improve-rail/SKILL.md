# レールを育てる

入力は実案件で起きた問題、ユーザーの指摘、または進め方への変更依頼。改善依頼があるなら、合意済みの目的の範囲で原因の確認、修正、検証まで行う。単に個別アイデアを育てている場合は、観測した問題をその案件の `review.md` に残す。

1. [背景](../../playbook/rationale.md) と [進め方](../../playbook/workflow.md) を読み、今回減らす思考コストを一文にする。新設の場合は与えられた背景を起点にする。
2. 問題が個別の前提不足、指示の発見失敗、手順不足、完了判定の不足のどれかを、実際の出力から確かめる。出力がなければ仮説と明示する。
3. 変更後にエージェントがどう違う行動をとるかを記述する。既存の一節の修正で済むなら、その正本を直す。チェックリストの追加だけで解決したことにしない。
4. [検証シナリオ](../../evaluations/scenarios.md) の該当ケースと、性質の異なるケースに適用する。新しい失敗を再現するケースがなければ追加する。元のケースも再確認する。
5. 改善記録を `evaluations/` に残す。観測した問題、変更、確認結果、確認していない範囲、戻す条件を記す。共通規則が変わるときは参照元やテンプレートの矛盾も直す。

検証には可能なら別の実行文脈で実際に skill を使った出力を使う。利用できない場合は机上確認と明記し、独立検証したと主張しない。追加モデルや外部費用が必要なら、現在の利用権限の範囲を超えて呼び出さない。

評価するのは、ユーザーが考え直した回数・時間、構造の手戻り、不要な工程、未決事項が本人の判断に必要な形で返ったか。値は実際に観測できたものだけを使い、文書数や build-ready 件数だけで成功を判定しない。

ユーザー固有の美観・予算などは各案件に置く。同じ好みが複数案件で確認され、ユーザーが標準化を望む場合に共通の既定値へ移す。一件の特殊事情を全案件の必須条件にしない。
