# 引き継ぎ

状態は README.md を参照。この文書があること自体は、実装開始の許可を意味しない。

引き渡す作業：製品実装／既製品導入／意思決定用の検証のみ、から今回の範囲を明記する。検証のみの場合は、入力・環境・合否・時間と費用・結果保存先・結果別の再開工程・停止条件・必要権限を揃え、製品全体の完成判定と分ける。

この文書を作成して受取確認した後に、review.md で成果物一式の最終判定を行う。

## 読む順序

README.md → proposal.md → design.md → review.md。判断の理由を掘るときに decisions.md と evidence.md を読む。
実装先へ渡すときはアイデアディレクトリごと渡し、相対リンクを維持する。存在しないファイルは作成するか、不要な理由と代わりの参照先を示す。

## 実現するもの

今回の到達点・合格条件・非目標の参照先を指定する。仕様を複製しない。条件付き部分があれば未決事項 ID と対応させ、着手可能な部分を区別する。

## 着手順と確認箇所

依存関係に沿って、最初に通す縦の一場面、その後に広げる範囲、各時点で動作・成果物を確認する内容を記す。各作業に入力、期待結果、検証、止まって相談する条件を付ける。

## 実装先との接続

実装先のパス・リポジトリ、既存規約や技術との適合、利用する実行フローを記す。未指定なら「未指定」とし、移送可能な設計として渡す。既存コードに依存する判断は確認待ちとして明示する。

tumeda-dev の steering / task-design を使う場合は、このディレクトリと今回の到達点を入力へ渡す。実装先の現行 skill を読んで呼出契約を確認する。このラボで決めた要求・比較を再実施するのは、新しい根拠で不適合が判明した場合だけにする。

## 裁量・相談・運用後の確認

design.md の裁量範囲、README.md の未決事項、需要等の未実証仮説を参照する。運用後に誰が何を観測し、どの条件で設計や作る判断を見直すかを記す。

## 受取確認

最初の縦の一場面と最も危険な作業を、会話履歴なしで実装するつもりで読む。確認者、対象作業、追加判断と分類（既に記載／裁量／重要な未決）、根拠となる参照先、対応結果を記す。重要な未決が残る間は build-ready としない。別担当がいなければ受取視点での自己確認と明記する。
