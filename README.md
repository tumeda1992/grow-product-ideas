# grow-product-ideas

プロダクトのアイデアを、作り始める前に決めるべきことが全部決まった状態（build-ready、あと作れば終わり）まで詰めるリポジトリ。

詰めれば決まるもの（代案の比較、スコープ、情報構造、機能の構成と受渡し）はこのリポジトリのレールが引き受け、利用者の頭は、寝かせないと出てこないもの（着想、作りたい動機、体験の質感）だけに使う。
決めるべきことは、層ごとの決めるものと決め方として持っていて、全ての層が閉じるまでbuild-readyにしない。

## 使い方

このリポジトリのrootで Claude Code か Codex を開き、アイデアを渡して`grow-product-idea`を使うよう頼む。

```text
grow-product-idea で、このアイデアを詰めたい。
アイデア: 毎月のサブスクの更新日を忘れて、使っていないサービスに払い続けている。
作りたい動機: 自分の家計の無駄を減らしたい。
既にある着想: 更新日の3日前に通知が来れば十分な気がする。
```

途中で止めたアイデアは、`product-plans/<slug>/`を指定して再開できる。

### 利用者に問われる場面

レールが利用者へ問うのは、次の時だけである。

- 受け入れ時: アイデア、作りたい動機、既にある着想
- 層を決める中で立った論点: 利用者の採否が要る判断、利用者しか持たない事実、発案者の視野の外の点
- 層の閉じ: その層で決めたものを受け入れるか
- 出口判定: build-ready・作らない・保留のどれにするか

### 出口

| 出口 | 状態 | 残るもの |
| --- | --- | --- |
| build-ready | 全ての層が閉じた | 正本と、層ごとの記録と決定過程、材料。初回構築の入力になる |
| 作らない | 作らないと判断した | 作らないと決めた理由 |
| 保留 | 今は作らない | 復活する条件 |

出口がどれでも、`product-plans/<slug>/`はこのリポジトリの判断記録として残る。

### build-readyの後

1. `product-plans/<slug>/`の写しを、`initial_product_plan`のような名前で新しいリポジトリへ置く。
2. 新しいリポジトリで、その写しの`README.md`（正本）を入力に`tumeda-dev`の`steering`／`task-design`で初回構築を始める。なぜそう決めたかは、層ごとのdirectoryの記録と決定過程にある。

今回届ける範囲と作る境界は、どう解くか（how-to-solve）層で選ぶ。独立した「どこまで作るか」層は設けない。作る部分のある版は、人・既存道具・作る部分の分担と受け入れた未達・費用・負担を含めて、どう作るか（how-to-build）層へ渡す。how-to-buildは、その版を実装・導入できる設計へ具体化する。
どう作るかの方法や必要な専門skillを備えても、個別の版を実装・導入できる設計へ通したことにはならない。作る版は、必要な材料・判断と裏づけが揃い、層の閉じを受け入れるまでは検討中にとどめる。非開発・保留へ向かう版には、実際の行いと担い手又は保留の理由・復活する条件を残す。

`product-plans/<slug>/`は、作る時からdirectoryの中だけで読み切れるように書かれている。新しいリポジトリに`what-defines-a-product/`やこのリポジトリのskillが無くても読める。
写しの作成、名前の変更、新しいリポジトリの作成は、利用者が行う。

## 構成

```text
grow-product-ideas/
├── README.md                 # このfile
├── AGENTS.md                 # プロジェクト指示の正本
├── CLAUDE.md -> AGENTS.md
├── what-defines-a-product/   # 層。READMEと層file
├── product-plans/            # 1アイデア1directory。レールを通した判断記録。READMEが中の配置を定める
├── .agents/skills/           # レールのskillの正本
├── .claude/skills -> ../.agents/skills
└── .steering/                # このリポジトリ自体を改善する作業の記録
```

| 置き場所 | 役割 |
| --- | --- |
| [`what-defines-a-product/`](what-defines-a-product/README.md) | プロダクトをbuild-readyにするための層。層fileは、層ごとの決めるもの、決め方、止める時を持つ。READMEは、層の順、層の閉じ、差し戻し、skillへの頼み方を持つ |
| [`product-plans/`](product-plans/README.md) | アイデア1件ごとに、正本（プロダクトの説明）、層ごとの記録と決定過程、材料とその決定過程。中の配置と名前、記録の役割は`product-plans/README.md`が定める |
| `.agents/skills/` | レールのskill。Claude Code は`.claude/skills`から、Codex は`.agents/skills`から読む |

### skill

| skill | 役割 |
| --- | --- |
| `grow-product-idea` | アイデアを受け取り、層を順に決めて閉じ、出口まで運ぶ。入口はこれ |
| `propose-alternatives` | 全体の状態と条件を物差しに、非開発・組合せ・作る道と部分改善を探索する。行い・根拠・費用、残る未達と未確認を、依頼の目的と粒度で比較材料へ返す。選ばない |
| `sketch-experience` | 検討中の案の場面・行い・受渡しと表示・操作のラフを、比較から指定範囲の全場面・全画面まで育てる。意味のある案の差と不足を返し、選定・費用の見積りは行わない |
| `design-core-logic` | 与えられた価値・状態と範囲から、中核の規則・処理方式を具体の入力と反例で吟味できる材料にする。案を選ばず、成立条件・差・不足を返す |
| `design-data-model` | 体験とlogicに必要な情報を、現行の事実と根拠を読めて変更できる構造へ設計する。案を選ばず、具体の読み書きと検査、差と不足を返す |
| `functional-structure-design` | 機能構成設計。大きな処理と、ソフトウェアで表現する機能のまとまり・責任範囲・入出力と関係を設計する。具体の一巡・失敗・変更を照合し、案を選ばず構成と差・不足を返す |
| `implementation-structure-design` | 実装構成設計。必要な機能・規則・情報を実行・保存・接続と回復の責任配置へ組み、同じ入力・停止・競合・変更で構成案の差・根拠・不足と費用の部品を返す。案は選ばない |
| `verify-technical-feasibility` | 技術検証。判断を左右する性質を確かめ、対象と条件、観測・反例・未検証を分けて事実と限界を返す。技術や案を選ばず、本実装は行わない |
| `gather-target-user-voices` | 他者の体験の探索・整理。問題意識と止まる判断から必要な経験と違いを調べ、根拠・着想・不足を返す。価値・条件・案の採否は依頼側が持つ |

旧skillは比較用の履歴として`.steering/2026/202611/20261103-implement-build-ready-idea-lab-skeleton/archive/`に保存している。
案件からレールへの還元は、以下の「レールを育てる」の方法で既存の保守へ渡す。

## 前提

- `tumeda-dev` plugin: `facilitate-discussion`（決定過程の記録）、`name-work-directory`（slugの決定）、`steering`／`task-design`（レールの改善、build-ready後の初回構築）を使う。

## レールを育てる

案件で得た原事例を既存のレール保守へ渡し、方法をどう使って何が起きたかから直し方を吟味する。grow-product-ideaは原事例の引渡し、steeringは保守の入口と進行、task-designは原因・具体の直し・共通化の設計を持つ。repo固有の引渡しと吟味の方法は、この節を使う。
層の決め方は網羅を目指さない。毎回悩むところを先回りして、答えの出し方ごと用意するために置く。

### 案件から、原事例と未処理の手がかりを渡す

案件の成立を妨げる欠けは、先に該当する層や材料へ返す。共通の改善へ預けただけで案件を閉じない。
出口又は正式な保留を記録した後、grow-product-ideaは、既に得た摩擦、方法に無い判断を補った所、想定外に成立した条件のうち、まだ保守で扱っていない手がかりを渡す。途中の中断を還元のために保留へ替えず、手がかりが無い時に新しい問題を作ることも求めない。

渡すのは、入力と前提、何をしようとし何を期待したか、実際の出力・出来事と差、案件の該当記録・材料、その時に使った方法の箇所と分かる版、途中で補った判断と残る不足である。原因や一般則を完成させてから渡す必要は無い。既に分析・対処した所は、その記録と未処理の差を渡し、同じ検討を最初から繰り返さない。
対応する保守作業があればそこへ渡す。新しい作業が必要ならsteeringの通常の入口で受け付け、task-designへ繋ぐ。受付した作業と原事例の対応、残る処理は保守側の`.steering/`の既存の作業記録に残す。製品の正本へ保守の台帳や外部参照を足さず、`product-plans/<slug>/`内だけで製品を読み切れる形を保つ。

### 当時の適用から、具体の直しと共通化を吟味する

task-designは原事例の入力・使った方法・実際の進め方・出力を対応付ける。指示へ辿れなかったのか、従っても必要な関係が欠けるのか、薄い結果が条件を通るのか、適用を落としたのか、入力の事実が足りないのかを、確認できる根拠から絞る。複数が重なる場合もある。版や過程が不明なら、その不足を残し、現在の本文に指示があるだけで当時の原因を断定しない。
まず元の具体の入力に対し、何をどう直せば次の担当が使えるかを描く。同じ原因を解く別の直し方があれば、得失を比べる。出力の修正や参照の導線を直せば足りる場合も、方法の改稿と比べる。共通化を先に決めて規則を足さない。
共通の方法へ戻す案は、元の失敗を防ぐ関係と適用する条件を取り出し、条件の異なる場面・既存の良い案・当てる必要の無い依頼へ試す。元の失敗を防いでも別の成功を壊すなら、範囲又は案を直す。

例えば、画面と規則が使う選択・残時間を保存から読めないなら、必要な読取りをどう渡し、どの情報が落ちたかを辿る。具体の直しは選択や時間を読める意味と保存の対応を作ることであり、全製品に同じcolumnを足すことではない。方法を直す場合も、粗い候補の比較に全物理schemaを要求する改稿では、別の正しい依頼を壊してしまう。

### 判断できる返りから、反映と案件への差し戻しへ繋ぐ

保守が返すのは、直す先と具体案・根拠、どの失敗をどう防ぎ何を保つか、元の場面と異なる場面での確かめ方、残る未確認である。変更箇所の名前や「注意する」の列挙だけでは、直った時の仕事を判断できない。共通を変えない場合も、その理由と、原事例のどこで対処した又は何が残るかを返す。
採否はfacilitate-discussion、設計と必要な反映・実行計画はtask-design、進行はsteeringの既存の責務で扱う。文書とskill本文はdocument-review、skillの構造は設計時と編集後のskill-update-reviewを通す。専用の第二の採否や状態の台帳を作らない。
共通の方法を直しても、元の案件の欠けが自動で直るわけではない。必要な変更を案件の層・材料へ差し戻し、当時の提案・採否・限界を保持して追う。一方、成立した製品の出口は共通の改稿の完了まで待たせず、残る改善は保守側で追う。

専用skillが無いことで呼出しや知識の再利用が繰り返し破綻するなら、役割の切出しを再検討する。現在はこの方法を既存の保守で使う。

- 実体化の設計: `.steering/2026/202611/20261103-implement-build-ready-idea-lab-skeleton/design.md`
