# grow-product-ideas

粗いプロダクトアイデアを、作る価値と作る範囲を確かめたうえで、実装中にプロダクト判断が発生しない状態まで育てるラボです。

このリポジトリが引き受けるのは、頭の中で寝かせなくても調査・比較・設計で決められる「詰将棋」です。着想や作りたいという動機を型へ押し込めるのではなく、次を毎回ゼロから考え直すコストを減らします。

- 誰の、どの状況の、何が問題なのか
- そもそも作るべきか。既存製品、設定、運用変更、複数サービスの組み合わせで足りないか
- 元のアイデアを広げるか、狭く研ぎ澄ますか
- どの仮説を、実装前にどこまで確かめるか
- 最初のマイルストーンまでの体験、接点、データ、モジュールをどう構成するか

## 使い方

Codex などのエージェントへ、次のように依頼します。

```text
このアイデアを build-ready まで育てて:
「毎日の料理を、家にある食材から提案してくれるアプリ」
```

エージェントは [refine-product-idea skill](./.agents/skills/refine-product-idea/SKILL.md) に従い、必要なら [`scripts/new-idea.sh`](./scripts/new-idea.sh) で `ideas/<slug>/` を作り、調査・比較・定義・監査を自走します。ユーザーにしか決められない高影響の事項は、独立して進められる作業を終えた後にまとめて返します。

手動でアイデアを作る場合:

```bash
./scripts/new-idea.sh pantry-meal-planner \
  "家にある食材から献立を提案する" \
  "毎日の料理を、家にある食材から提案してくれるアプリ"
```

作成後は `ideas/pantry-meal-planner/source.md` の `Raw idea` へ元の発言をそのまま保存します。元の発言は後から整形せず、解釈や追加情報は別の節へ書きます。

## 出口

このラボの出口は常に「作る」ではありません。

| verdict | 意味 | 次の行動 |
| --- | --- | --- |
| `build` | 最初のマイルストーンを作る根拠と仕様が揃った | 実装設計・実装へ渡す |
| `validate-first` | 作る前に潰すべき高影響・低根拠の仮説がある | 最小の検証を実行する |
| `use-existing` | 既存手段の方が総コストで優れる | 採用する手段と運用を確定する |
| `park` | 今は条件が揃わないが再評価条件が明確 | 条件が成立するまで保留する |
| `stop` | 解く価値または実現可能性が不足する | 理由を残して終了する |

`build-ready` は `build` のうち、体験、画面やその他の接点、データ、バックエンドモジュール、受入条件の間に追跡可能性があり、重大な未決事項がない状態だけを指します。資料を埋めただけでは到達しません。

## リポジトリの地図

```text
.
├── AGENTS.md                         エージェントが常に守る運用契約
├── docs/
│   ├── operating-model.md            進行、状態、成果物、改善ループの正本
│   └── methods.md                    調査・比較・検証手法の選び方
├── .agents/skills/refine-product-idea/
│   ├── SKILL.md                      アイデアを育てる実行 skill
│   └── references/                   フェーズ別の詳細手順
├── ideas/
│   ├── README.md                     アイデアディレクトリの運用方法
│   └── _template/                    各アイデアが持つ正本の雛形
```

進行の考え方と品質ゲートは [運用モデル](./docs/operating-model.md)、個人開発向けに翻訳した一般的なディスカバリー手法は [調査・判断手法](./docs/methods.md) を参照してください。

## ラボ自体を育てる

各アイデアの `retrospective.md` には、進行中に起きた迷い、後戻り、役に立った手順、過剰だった手順を残します。同じ問題が複数アイデアで起きた場合、または一度でも重大な手戻りを生んだ場合は、共有 skill・雛形・品質ゲートへの変更候補です。

共有の型を変えるときは、変更理由となった実例に加え、性質の異なる既存アイデアでも悪化しないことを確認します。1件の特殊事情を全アイデアの必須工程へ昇格させません。

## build-ready の後

`build-ready` は実装コードが確定した状態ではなく、プロダクト判断が確定し、技術設計へ安全に渡せる状態です。`handoff.md` のImplementation handoffを入口に `steering` / `task-design` などの実装設計へ渡します。

後続工程は `source.md`、`product.md`、`specification.md`、`handoff.md` を上位制約として扱います。技術調査で前提矛盾が見つかった場合は、実装中の独断で仕様を変えず、該当するラボの正本へ戻します。
